### 3.3.1 启动交互式 REPL（Starting an Interactive REPL）

### 英文原文

> By most measures, the simplest way to run Python code is to type it at Python's interactive command line, sometimes called the **interactive prompt**, and often more concisely labeled the **REPL** (which stands for read–eval–print loop). There are a variety of ways to start this command line—in a coding GUI or app, in a web notebook, from a system console, and so on.
>
> Assuming Python is installed locally as an executable program on your device, the most platform-neutral way to start an interactive interpreter session is to simply type a **Python command** at your device's console prompt, without any arguments. Since this is most common, nearly universal, and arguably simplest, let's start here.
>
> Despite this scheme's generality, **both the Python command you'll type and where you'll type it vary per platform**. On **Windows**, **macOS**, and **Android**, for example, **py**, **python3**, and **python**, respectively, do the job as follows:

> ```
> $ py
> Python 3.12.3 (…etc…, Apr 9 2024, 14:05:25) [MSC v.1938 64 bit (AMD64)] on win32 Type "help", "copyright", "credits" or "license" for more information.

> >>> ^Z
> $ python3
> Python 3.12.2 (…etc…, Feb 6 2024, 17:02:06) [Clang 13.0.0…)] on darwin Type "help", "copyright", "credits" or "license" for more information.

> >>> ^D
> $ python
> Python 3.11.4 (…etc…, Jul 2 2023, 11:17:00) [Clang 14.0.7…)] on linux Type "help", "copyright", "credits" or "license" for more information.

> >>> ^D
> ```
> A **python3** works on Android and Linux, too, if you want to narrow this to one exception—for Windows' **py**. This book uses **python3** in platform-neutral examples just because it works almost everywhere. If you're working on Windows, instead use **py** (or **py -3** to ensure Python 3.X); **python3** works on Windows, too, but is reserved for a lesser Store install today per **Appendix A**.
>
> Also per that appendix, all these commands must be on your system search path (generally known as **PATH**) and require a full pathname if they're not, but most installs set this up automatically. Typing a Python command at your system prompt like this begins an interactive Python session (i.e., REPL).
>
> The **$** character at the start of listings here stands for a generic system prompt on all platforms throughout this book—it will likely vary on your device and is not input that you type yourself. On **Windows**, a Ctrl+Z key combo (followed by Enter) ends this session as shown; on **Unix** (which includes macOS, Linux, and Android), it's Ctrl+D instead.
>
> You'll notice that the interactive prompt opens with a message that identifies the Python being used (e.g., "3.12.3" is Python 3.12) and the platform it's running on (e.g., "win32" for Windows, "darwin" for macOS, and "linux" for both Linux and Android in Python 3.12), followed by a line with tips for more info. We're going to omit these opening lines in this book, except where they're helpful.
>
> The notion of a system prompt (a.k.a. **shell** or **console**) where you type the Python command is generic, but exactly how you access it varies by platform. It might be **Command Prompt** or **PowerShell** on **Windows**; **Terminal** on macOS and Linux; the **Termux** app on Android; or a dedicated terminal screen in some apps like **Pydroid 3**.
>
> On most platforms, you can also start an interactive session in ways that don't require typing a command at all, but they vary even more widely. On **Windows**, for example, a Start-menu option opens a similar REPL, as do the IDLE GUI on all PCs, dedicated screens in apps on Android and iOS, and some web-browser interfaces.
>
> We'll cover some of these options ahead, but see **Appendix A** for more platform tips, and the web for more help with other options. Anywhere you see the **>>>** prompt, though, you're in an interactive Python session and REPL—you can type any Python statement or expression here and run it immediately by simply pressing the Enter key (or similar button).
>
> We will do so in a moment, but first we need to get a few admin details sorted out to make sure all readers are set to go.

### 中文翻译

> 从多数标准衡量，运行 Python 代码最简单的方式，就是在 Python 的交互式命令行里输入代码。它有时被称为**交互式提示符（interactive prompt）**，常常更简洁地称作 **REPL**（即 read–eval–print loop，"读取—求值—打印"循环）。
>
> 启动这个命令行有多种途径——在编码 GUI 或 App 里、在网页笔记本里、在系统控制台里，等等。假设 Python 已经作为可执行程序安装在你设备上，那么启动交互式解释器会话最具平台无关性的方式，就是直接在设备控制台提示符下、不带任何参数地输入一个 **Python 命令**。由于这种方式最常见、几乎通用、也最简单，我们就从这里开始。
>
> 尽管这个方案具有通用性，**你要输入的 Python 命令以及在哪里输入，都是随平台而异的**。例如在 **Windows**、**macOS** 和 **Android** 上，分别用 **py**、**python3** 和 **python** 就能做到，如下所示：
>
> ```
> $ py
> Python 3.12.3 (…等等…, 2024 年 4 月 9 日 14:05:25) [MSC v.1938 64 位 (AMD64)] on win32
> 输入 "help"、"copyright"、"credits" 或 "license" 获取更多信息。
> >>> ^Z
>
> $ python3
> Python 3.12.2 (…等等…, 2024 年 2 月 6 日 17:02:06) [Clang 13.0.0…)] on darwin
> 输入 "help"、"copyright"、"credits" 或 "license" 获取更多信息。
> >>> ^D
>
> $ python
> Python 3.11.4 (…等等…, 2023 年 7 月 2 日 11:17:00) [Clang 14.0.7…)] on linux
> 输入 "help"、"copyright"、"credits" 或 "license" 获取更多信息。
> >>> ^D
> ```
>
> 如果你想把这个差异收窄到唯一一个例外（即 Windows 的 **py**），那么 **python3** 在 Android 和 Linux 上也都能用。本书在平台无关的示例中使用 **python3**，仅仅因为它几乎到处都能用。如果你在 Windows 上工作，请改用 **py**（或用 **py -3** 来确保是 Python 3.X）；**python3** 在 Windows 上也能用，但按**附录 A**，如今它被保留给功能较弱的 Store 安装。
>
> 同样依据该附录，所有这些命令都必须位于系统搜索路径（通常称为 **PATH**）中；若不在，就需要给出完整的路径名，不过大多数安装都会自动设置好。
>
> 像这样在系统提示符下输入一个 Python 命令，就开启了一个交互式 Python 会话（即 REPL）。本书列出的每条命令开头的 **$** 字符，在所有平台上都表示通用的系统提示符——它在你的设备上可能不同，而且它不是需要你自己输入的。在 **Windows** 上，按 Ctrl+Z（之后回车）如所示那样结束会话；在 **Unix**（包括 macOS、Linux 和 Android）上则是 Ctrl+D。
>
> 你会注意到交互式提示符打开时会先打印一段信息，用来标明所用的 Python 版本（如 "3.12.3" 即 Python 3.12）和运行平台（如 Windows 是 "win32"、macOS 是 "darwin"、"linux" 对应 Linux 和 Android 的 Python 3.12），随后是一行获取更多信息的提示。本书除了必要时会省略这些开头几行。
>
> 系统提示符（又名 **shell** 或 **console**）的概念是通用的——你在那里输入 Python 命令，但具体如何访问它则因平台而异。在 **Windows** 上可能是 **命令提示符（Command Prompt）** 或 **PowerShell**；macOS 和 Linux 上是 **Terminal**；Android 上是 **Termux** 应用；或者像 **Pydroid 3** 这类应用中专门的终端屏幕。
>
> 在大多数平台上，你还可以用完全不需输入命令的方式启动交互式会话，但那些方式差异更大。例如在 **Windows** 上，开始菜单里有一个选项会打开类似的 REPL；所有 PC 上的 IDLE GUI、Android 和 iOS 应用中的专用屏幕、以及某些网页浏览器接口也都能做到。我们稍后会覆盖其中一些选项，但更多平台技巧请看**附录 A**，其它选项可上网查找更详细的帮助。
>
> 不过，任何你看到 **>>>** 提示符的地方，你就正处于交互式 Python 会话（REPL）中——你可以在那里输入任意 Python 语句或表达式，只要按下回车键（或类似的按键）就能立即运行。我们马上就会这样做，但首先还需要处理几个"管理细节"，确保所有读者都准备就绪。

### 深度理解

- **核心概念**：REPL = **Read（读取）– Eval（求值）– Print（打印）– Loop（循环）**。这个名字精确描述了交互式会话的工作循环：读一行输入 → 编译并执行 → 打印结果 → 等待下一行。
- **命令名差异的来龙去脉**：
  - `py`：Windows 的 **launcher（启动器）**，专为 Windows 设计，可以让你在同一机器上选择不同 Python 版本（`py -3`）。微软商店（Store）安装的 `python3` 是个入口别名，能力受限，所以本书主推 `py`。
  - `python3`：Un\*x 世界的标准命名，明确区分 Python 3。
  - `python`：部分发行版把 Python 2 和 3 分别叫 `python`/`python3`，但如今（Python 2 已 EOL）多数系统 `python` 也指向 3。
- **`PATH` 是什么**：系统"搜索路径"。当你输入 `py`，系统按 `PATH` 中列出的目录逐个查找名为 `py.exe` 的程序。若 Python 安装目录不在 `PATH` 里，就要输完整路径（如 `C:\Python312\python.exe`）。
- **退出方法**：`Ctrl+D`（Unix，发送 EOF）vs `Ctrl+Z`（Windows，传统 EOF）。这是历史遗留——Windows 的 EOF 用 `^Z`。
- **启动横幅信息**：第一行告诉你三件事——版本号、编译环境（如 MSC = 微软编译器）、平台（win32/darwin/linux）。这些是排错时的重要线索。
- **生活类比**：REPL 就像**计算器加记事本**——你按一个数字计算器立刻给结果，但算完就忘。存盘要靠"脚本文件"（后面讲）。
- **初学者误区**：①把 `$`、`>>>` 也敲进去了（下一节专门讲）；②以为 REPL 里写的代码能被保存——不能；③分不清"系统提示符"和"Python 提示符"——`$` 或 `PS>` 是操作系统，`>>>` 是 Python，它们是两套不同的环境。

### 代码分析

```python
# 三个平台的启动对比（注意这只是"启动"REPL，本身不是 Python 代码）
py          # Windows：启动 Python 3.x（launcher）
python3     # macOS/Linux/Android：启动 Python 3
python      # 部分系统（尤其 Linux）也支持

# 会话结束方式
# Windows：先按 Ctrl+Z 再回车，退出
# Unix/macOS/Linux/Android：按 Ctrl+D，退出
```

处理流程：
- 当你在系统控制台输入 `py` 并回车，**操作系统**根据 `PATH` 找到解释器可执行文件，把它作为一个新进程启动。
- Python 进程启动后进入 REPL：打印版本横幅 → 打印 `>>>` 提示符 → **read** 等待你的输入。
- 你在 `>>>` 后输入任意语句，Python 内部会做：源码→词法分析→编译为**字节码（bytecode）**→交给 **PVM（Python 虚拟机）**执行 → 若有结果则 **print** 到屏幕。这正是第 2 章讲过的执行模型，在这里第一次有了直观体验。
- 你按 `Ctrl+D`/`Ctrl+Z` 时，进程收到 EOF 信号，主循环结束，解释器退出，控制权还给系统 shell。

### 3.3.3 不要输入什么：提示符与注释（What Not to Type: Prompts and Comments）

### 英文原文

> Speaking of commands, remember not to **type the $ character** used at the start of this book's command lines to denote a system console prompt; type just the text **after** these prompts. This may sound simple to experienced programmers, but it's a very common first error for beginners, and we're not excluding anyone here.
>
> Similarly, do not type the **>>>** and **...** prompt characters shown at the start of lines in interpreter interaction listings and used by this book to denote code run in a REPL; type just the text **after** these prompts. These are prompts that Python's standard REPL displays automatically as visual guides for interactive code entry and may or may not appear in your interface.
>
> For instance, the **...** prompt is used for **continuation lines** in some REPLs, but is just a label in IDLE, and is omitted by some of this book's listings for easier copy/paste; either way, don't type it yourself.
>
> To help you remember this, user inputs you must type are shown in **bold** in this book, and prompts are not. Also keep in mind that commands typed after these system and Python prompts are meant to be run immediately and are not generally intended to be saved in the source files we will be creating; you'll see why this distinction matters ahead.
>
> In the same vein, you normally don't need to type text that starts with a **#** character in this book's code listings—as you'll learn later, these are **comments**, not executable code. Except when **#** is used to introduce a **#!** directive at the top of a script, you can safely omit it and the rest of the line that follows it (there's more about **#!** in **Appendix A**).

### 中文翻译

> 说到命令，请记住**不要输入 $ 字符**——它被用在本书命令行开头，表示系统控制台提示符；只输入这些提示符**之后**的文本即可。对有经验的程序员来说这听起来很简单，但这是初学者非常常见的第一个错误，我们这里可没有排除任何人。

### 深度理解

- **核心概念**：区分三类"你看到的符号"——**系统提示符**（`$`、`PS>`）、**Python 提示符**（`>>>`、`...`）、**注释标记**（`#`）。三者都不是你要输入的执行内容。
- **两个不同的解释器层级**：`$` 后的命令交给**系统 shell**（command.com/bash），`>>>` 后的命令交给 **Python REPL**。把 `python3 script1.py` 输进 Python 的 `>>>` 会报语法错误——因为 `python3` 是 shell 的命令、不是 Python 语句。同理，把 `>>>` 输进文件会语法错误。
- **`#` 注释**：从 `#` 到行尾的任何文本，Python 一律**忽略**。它为人类而存在，不参与执行。
- **`#!`（shebang）**是个例外：脚本第一行的 `#!/usr/bin/env python3` 是给操作系统看的——当你在 Unix 上直接 `./script.py` 运行时，系统靠它决定用哪个解释器。
- **生活类比**：教科书上的选择题答案写在括号里，你做题时不该把括号抄进去。`$`/`>>>`/`#` 就是那些"括号"。
- **初学者误区**：把整段带提示符的代码直接复制进文件 → 语法错误！这是新手最容易、也最典型的翻车现场。

## 3.4 交互式运行代码（Running Code Interactively）

### 英文原文

> With those preliminaries out of the way, let's move on to typing some actual code. However it's started, the Python interactive session begins by printing some informational text (again, mostly omitted hereafter), then prompts for input with **>>>** (or similar) when it's waiting for you to type a new Python statement or expression.
>
> When working interactively, the results of your code are displayed below the **>>>** input lines after you press the Enter key (or similar). For instance, here are the results of two Python **print** statements:

> ```
> $ python3
> >>> print('Hello world!')
> Hello world!

> >>> print(2 ** 8)
> 256

> ```
> There it is—we've just run some Python code (it's not much, but it proves the point). We're still skipping most code details for now, but in brief, **print** is a built-in tool that sends a line displaying whatever you pass to it, to wherever you're working; because it's a **function call** in Python, the parentheses in this code are required.
>
> We've used it here to display a Python string and an integer, as shown by the output lines that appear after each **>>>** input line. When coding interactively like this, you can type as many Python commands as you like; each is run immediately after it's entered.
>
> Moreover, because the interactive session automatically prints the results of expressions you type, you don't usually need to say "print" explicitly at this prompt; the format of the following automatic displays can differ slightly from **print**, but it's not yet important to know how:

> ```
> >>> language = 'Python'
> >>> language
> 'Python'

> >>> 2 ** 8
> 256

> >>> ^Z
> # Use Ctrl-D (on Unix) or Ctrl-Z (on Windows) to exit
> $

> ```
> Here, the first line saves a value by **assigning it to a variable** (**language**), which is created by the **=** assignment; and the last two lines typed are **expressions** (**language** and **2 ** 8**), whose results are displayed automatically. Again, to exit an interactive session like this and return to your system prompt, type Ctrl+D on Unix-like machines, and Ctrl+Z on Windows.
>
> In the IDLE GUI discussed later, either type Ctrl+D everywhere, or simply close the window. Notice the **italicized note** about this on the **right side of this listing**—starting with **#** here. This book uses these throughout to add remarks about what is being illustrated, but you don't need to type this text yourself; if you do, they're ignored by Python as **comments**.
>
> In fact, much like system **$** and Python **>>>** prompts, you shouldn't type this when it's on a system command line; the **#...** part is ignored by Python but may be an error in system shells. Now, we didn't do much in this session's code—just typed some Python **print** and assignment statements, along with a few expressions, all of which we'll study in detail later.
>
> The main thing to notice is that the Python REPL executes the code entered on each line **immediately**, when the Enter key (or similar) is pressed. For example, when we typed the first **print** statement at the **>>>** prompt, the output (a Python string) was echoed back right away.
>
> There was no need to create a source code file, and no need to run the code through a compiler and linker first, as you'd normally do when using a language such as C or C++. Strictly speaking, interactive code is compiled to bytecode in memory and run by the PVM in CPython (see **Chapter 2**), but you don't need to care.
>
> As you'll see in later chapters, you can also run **multiline statements** (e.g., **for** loops) at the interactive prompt; such a statement may prompt for continuation lines with **...** as noted earlier and runs immediately after you've entered all of its lines and pressed Enter **twice** to add a blank line.
>
> Blank lines aren't required (and are ignored) in code files, but are needed to let some REPLs know your statements are complete. Also, bear in mind that the current and standard REPL runs just **one** statement at a time—don't paste large code **blocks** at its prompt!

### 中文翻译

> 排除了那些预备事项，让我们继续输入一些真正的代码。无论以何种方式启动，Python 交互式会话都会先打印一些信息文本（以后大多省略），然后在等待你输入新的 Python 语句或表达式时，用 **>>>**（或类似符号）提示你输入。
>
> 在交互式工作时，按下回车键（或类似按键）后，你的代码结果会显示在 **>>>** 输入行的下方。例如，下面是两条 Python **print** 语句的结果：
>
> ```
> $ python3
> >>> print('Hello world!')
> Hello world!
> >>> print(2 ** 8)
> 256
> ```
>
> 就是这样——我们刚刚运行了一些 Python 代码（虽然不多，但证明了这一点）。目前我们仍略过大部分代码细节，但简要地说，**print** 是一个内建工具，它把你传给它的任何内容以一行文本的形式发送到你正在工作的任何地方；因为它是 Python 中的**函数调用（function call）**，这段代码里的括号是必须的。我们在这里用它显示了一个 Python 字符串和一个整数，正如每条 **>>>** 输入行下方出现的输出行所示。
>
> 像这样交互式编码时，你想输入多少条 Python 命令都行；每条命令在输入后立即运行。此外，因为交互式会话会自动打印你输入的**表达式**的结果，所以你通常不必在这个提示符下显式地说 "print"；下面的自动显示格式可能与 **print** 略有不同，但现在不必关心：
>
> ```
> >>> language = 'Python'
> >>> language
> 'Python'
> >>> 2 ** 8
> 256
> >>> ^Z
> # 在 Unix 上用 Ctrl-D、在 Windows 上用 Ctrl-Z 退出
> $
> ```
>
> 这里，第一行通过把值**赋值给一个变量（variable）**（**language**）来保存它，这个变量由 **=** 赋值创建；最后输入的两行是**表达式（expressions）**（**language** 和 **2 ** 8**），其结果被自动显示出来。同样，要退出这样的交互式会话回到系统提示符，在类 Unix 机器上按 Ctrl+D，在 Windows 上按 Ctrl+Z。在后面讲到的 IDLE GUI 中，要么任何地方都按 Ctrl+D，要么直接关闭窗口。
>
> 请注意这个列表**右侧的斜体注释**——从这里以 **#** 开头。本书全篇都用它们来补充说明这段列举在演示什么，但你不必自己输入这段文字；就算你输入了，它们也会被 Python 当作**注释（comments）**忽略。事实上，和系统 **$**、Python **>>>** 提示符很类似，当它出现在系统命令行上时你也不该输入它；**#…** 部分会被 Python 忽略，但在系统 shell 里可能是错误。
>
> 好吧，本次会话的代码没做多少事——只是输入了一些 Python **print** 和赋值语句，外加几个表达式，这些我们以后都会详细学习。最主要观察点是：Python REPL 在按下回车键（或类似按键）时，会**立即（immediately）**执行每行输入的代码。
>
> 例如，当我们在 **>>>** 提示符下输入第一个 **print** 语句时，输出（一个 Python 字符串）立刻被回显出来。无需创建源代码文件，也无需像使用 C 或 C++ 这类语言那样，先让代码过一遍编译器和链接器。
>
> 严格来说，交互式代码是在内存中被编译成字节码、再由 CPython 中的 PVM 运行的（见**第 2 章**），但你不需要关心这些。
>
> 正如你在后面的章节会看到的，你也可以在交互式提示符下运行**多行语句**（例如 **for** 循环）；这样的语句可能像前面提到的那样，用 **...** 提示你输入续行，并且在你输完所有行、连续按**两次**回车补充一个空行后立即运行。在代码文件里空行不是必需的（并且会被忽略），但在某些 REPL 里，要让它们知道你的语句已经完整，空行是必要的。另外请记住：目前的标准 REPL 一次只运行**一条**语句——不要往它的提示符里粘贴大段代码**块**！

### 深度理解

- **核心概念**：交互模式的"立即执行"特性，源自它**没有"编译-链接"阶段**。你每按一次回车，这一行的源码就被实时编译执行。这让 Python 成为"所见即所得"的语言——而 C/C++ 需要先编译整个程序再运行。
- **底层细节（回应第 2 章）**：严格说，交互式代码也要先编译成字节码——只是**在内存里**进行，不落盘为 `.pyc` 文件。所以它依然是"编译为字节码 → PVM 执行"，只是省掉了文件往返。
- **表达式自动回显 vs print 的区别**：在 REPL 里，`language` 和 `2 ** 8` 这种**表达式**的值会被 REPL 自动"打印"，无需 `print`。而 `print(...)` 是**语句调用**，把值送往标准输出流。两者的输出格式略有差异（表达式回显常带 `repr()` 的效果，字符串会带引号）。**这是 REPL 特有的行为——脚本文件里没有自动回显**，文件里必须显式 `print`。
- **"按两次回车"的机制**：多行语句（如 `for`）需要用户连按两次回车——第一次结束复合语句的某个子句、第二次的空行表示整个语句块结束。空行是 REPL 判断"语句输入完毕"的信号。这是解释型语言的交互特性。
- **一次一条语句**：标准 REPL 一次只执行一条逻辑语句，粘贴大块代码会造成麻烦——这是它在交互模式下的天然限制。
- **生活类比**：表达式自动回显就像自动回复的语音助手——你说一句它答一句；而 `print` 是你明确要求它记在便签上，去向明确。
- **初学者误区**：①以为自己敲的 `language = 'Python'` 会"保存"成文件——不会，交互会话结束一切归零；②在脚本文件里期望表达式自动输出——文件里没有自动回显，不 `print` 就什么都看不见。

### 代码分析

```python
print('Hello world!')   # 打印一个字符串字面量
print(2 ** 8)           # 打印 2 的 8 次方，结果是 256
language = 'Python'     # 把字符串对象赋给变量 language
language                # 表达式，REPL 自动显示其值，得到 'Python'
2 ** 8                  # 表达式，REPL 自动显示 256
```

解释器如何处理：
- `print('Hello world!')` 是**函数调用**。Python 先在当前命名空间查找名字 `print`（它是个内建函数 builtin），然后把字符串对象 `'Hello world!'` 作为参数传入，函数把该字符串写到标准输出（stdout），随后换行。这里的括号是**必需的**——`print` 在 Python 3 中是函数（不是像 Python 2 那样的语句）。
- `print(2 ** 8)`：先对 `2 ** 8` 求值。`**` 是幂运算符，CPython 把它编译为 `BINARY_OP`（幂）字节码，在整数对象上调用乘幂算法，得到整数对象 `256`，再传给 `print` 输出。
- `language = 'Python'`：赋值语句。右侧的字符串字面量在内存中创建**字符串对象**，左侧的 `language` 只是指向该对象的**名字**（name binding，名字绑定）。
- 单独一行 `language`：这是一个表达式。REPL 会对它求值得到字符串对象，然后自动调用其显示表示（repr）并打印——所以能看到带单引号的 `'Python'`。**在脚本文件中这行不会有任何输出。**
- `2 ** 8`：同理会话自动显示 `256`，但注意和 `print(2 ** 8)` 显示的 `256` 在本文末尾其实相同，只是层次不同：一个是表达式自动回显，一个是函数显式输出。

## 3.5 为什么用交互式提示符？（Why the Interactive Prompt?）

### 英文原文

> The interactive prompt runs code and echoes results as you go, but it doesn't save your code in a file. Although this means you won't do the bulk of your real-world coding in interactive sessions, the interactive prompt turns out to be a great place to both learn the language and test program files on the fly. Here's a quick rundown of these roles.

### 中文翻译

> 交互式提示符一边运行代码一边回显结果，但它不会把你的代码保存到文件里。尽管这意味着你不会在交互式会话中完成大部分实际编码工作，但交互式提示符实际上是**学习语言**和**即时测试程序文件**的绝佳场所。下面快速盘点这些角色。

### 深度理解

- **核心概念**：交互模式的定位是**学习 + 测试的临时沙盒**，不是生产环境。作者给出全书第一条"经验法则"——**对代码有疑问就开 REPL 试**。
- **为什么"不会崩"**：你不小心敲错代码，Python 只会抛出异常并打印 Traceback（回溯信息），解释器进程本身不会崩溃。这在 C 里意味着段错误可能直接让进程崩溃。
- **生活类比**：教练在泳池边先让你在浅水区（REPL）扑腾熟悉水性，再让你下水道（脚本文件）正式游。

### 代码分析

```python
>>> 'Hack!' * 8        # 学习利器：试着运行，立刻得到答案
'Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!'
>>> 2 ** 500           # 大整数测试：Python 的整数不限制位数
>>> 1 / 0              # 练习错误：数学错误，会抛 ZeroDivisionError
```

- `'Hack!' * 8`：字符串与整数相乘 = **字符串重复拼接**。`*` 运算符在数字上是乘法、在字符串（和列表等序列）上是重复。字节码层面，CPython 会为 `str * int` 走序列重复实现，直接分配拼接后的新字符串。
- **"实验破坏不了任何东西"的保证**：纯 Python 表达式的求值是"沙盒式"的——它只会操作内存中的对象，不碰文件系统、不碰操作系统。真正危险的操作（删文件、执行 shell 命令）只能通过显式 `import os` / `import shutil` 后调用其函数才能做到。

### 3.5.1 学习（Learning）

### 英文原文

> Because it executes code immediately, the interactive prompt is ideal for experimenting with code and learning the language, and we'll be using it throughout this book to demonstrate smaller examples and amplify concepts. In fact, this is the first rule of thumb to remember: if you're ever in doubt about how a piece of Python code works, fire up the interactive command line and try the code out to see what happens.
>
> For instance, suppose you're reading a Python program's code and you come across an expression like **'Hack!' * 8** whose meaning you don't understand. At this point, you can spend 10 minutes wading through manuals, books, and the web to try to figure out what the code does, or you can simply run it interactively:

> ```
> $ python3
> >>> 'Hack!' * 8    # Learning by trying
> 'Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!'

> ```
> This immediate feedback you receive at the interactive prompt is often the quickest way to deduce what a piece of code does. Here, it's clear that it does string repetition: in Python, **\*** means multiply for numbers, but repeat for strings—it's like concatenating a string to itself repeatedly (there's more on strings in **Chapter 4**).
>
> Chances are good that you won't break anything by experimenting this way—at least, not yet. To do real damage, like deleting files and running shell commands, you must really try by **importing modules explicitly** (we'll sample tools that can make you that dangerous later in this chapter). Straight Python code, though, is almost always safe to run.
>
> For instance, watch what happens when you **make a mistake** at the interactive prompt:

> ```
> >>> X     # Making mistakes is OK
> Traceback (most recent call last): File "<stdin>", line 1, in <module> NameError: name 'X' is not defined

> ```
> In Python, using a variable before it has been assigned a value is always an error—otherwise, if names were filled in with defaults, some errors might go undetected until it's too late. This means you must **initialize counters to zero** before you can add to them, must **initialize lists to empty** before extending them, and so on.
>
> You don't need to declare variables in Python, but they must be assigned before you can fetch their values. Other error messages try to be more helpful in Python today with "Did you…?" tips—as when looking for the **sys.ps1** prompt hook mentioned earlier.
>
> You must import modules like **sys** before using them (though you probably won't need the reminder fairly soon, and we'll be truncating some error messages in this book for brevity):

> ```
> >>> sys.ps1     # Requires "import sys"
> Traceback (most recent call last): File "<stdin>", line 1, in <module> NameError: name 'sys' is not defined. Did you forget to import 'sys'?

> ```
> You'll learn more about all that later. The important point here is that you won't **crash** Python or your computer when you make a mistake this way. Instead, you get a meaningful error message pointing out the mistake and the line of code that made it, and you can continue on in your session or script.
>
> In fact, once you get comfortable with Python, its error messages may often provide as much debugging support as you'll need (watch for more about debugging options in the sidebar **"Debugging Python Code"**).

### 中文翻译

> 因为它能立即执行代码，交互式提示符非常适合实验代码和学习语言，本书全篇都会用它演示较小的示例、放大概念。事实上，这是要记住的第一条经验法则：**如果你对某段 Python 代码如何工作有任何疑问，就启动交互式命令行，把代码实际跑一遍看看会发生什么。**
>
> 例如，假设你在读一个 Python 程序，遇到一个你不理解含义的表达式，比如 **'Hack!' * 8**。此时，你可以花 10 分钟翻手册、查书、上网搞清这段代码做什么，或者干脆交互式地运行它：
>
> ```
> $ python3
> >>> 'Hack!' * 8      # 通过尝试来学习
> 'Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!'
> ```
>
> 你在交互式提示符下获得的即时反馈，常常是推断一段代码做什么的最快捷方式。这里很清楚：它在做**字符串重复**。在 Python 中，**\*** 对数字是乘法、对字符串是重复——就像把字符串反复拼接到自己身上（第 4 章会详谈字符串）。
>
> 以这种方式实验，你很可能不会破坏任何东西——至少现在不会。要造成真正的破坏，比如删除文件、执行 shell 命令，你必须认认真真地通过**显式导入模块（importing modules explicitly）**才行（本章稍后会示范那些能让你"变危险"的工具）。但纯粹的 Python 代码几乎总是可以安全运行的。
>
> 例如，看看你在交互式提示符**犯错**时会发生什么：
>
> ```
> >>> X     # 犯错也没关系
> Traceback (most recent call last):
>   File "<stdin>", line 1, in <module>
> NameError: name 'X' is not defined
> ```
>
> 在 Python 中，在变量被赋值前就使用它永远是一个错误——否则，如果名字自动填了默认值，某些错误可能会在发现之前就为时已晚。这意味着在给计数器累加之前必须先**把它初始化为零**，在扩展列表之前必须先**把列表初始化为空**，诸如此类。Python 中你不需要声明（declare）变量，但必须先把它们赋值，之后才能取它们的值。
>
> 如今 Python 的其它错误消息会尽量提供更多帮助，比如 "Did you…?"（你是不是想…？）式的提示——就像前面提到找 **sys.ps1** 这个提示符钩子时那样。使用 **sys** 这类模块之前必须先导入它（不过很快你可能就不再需要这个提醒了，而且为了简洁，本书会截断一些错误消息）：
>
> ```
> >>> sys.ps1     # 需要先 "import sys"
> Traceback (most recent call last):
>   File "<stdin>", line 1, in <module>
>   NameError: name 'sys' is not defined. Did you forget to import 'sys'?
> ```
>
> 所有这些你以后都会了解更多。这里的重点是：用这种方式犯错，你**不会让** Python 或你的电脑**崩溃**。相反，你会得到一条有意义的错误消息，指出错误之处和产生错误的那行代码，然后你可以继续你的会话或脚本。事实上，一旦你熟悉了 Python，它的错误消息常常就能提供你需要的几乎全部调试支持（更多调试选项请看侧边栏**"调试 Python 代码"（Debugging Python Code）**）。

### 深度理解

- **核心概念——"先用后声明"原则（Assignment before Use）**：Python 的变量不需要声明（declaration），但**必须先赋值才能取值**。访问未定义的名字会抛 `NameError`。这一设计杜绝了"隐式初始化为 0/空"带来的隐藏 bug。
- **为什么这样设计**：C 语言里使用未初始化变量是未定义行为（垃圾值）。Python 选择"一刀切报错"——宁可严格报错，也不允许静默地给你一个假默认值，因为"隐式默认值"会让 bug 潜伏到无法定位。这是显式优于隐式（explicit is better than implicit）哲学的又一次体现。
- **Traceback 的结构**：错误消息从上到下是——错误类型（如 `NameError`）、出错的代码位置（哪个文件哪一行哪个作用域）、以及具体描述。`<stdin>` 表示代码来自标准输入（即交互式键盘输入）。读到 Traceback 的顺序是"从下往上看主线索、从上往下看调用链"。
- **`NameError ... Did you forget to import 'sys'?`**：Python 3.10+ 会给常见错误加"温馨提示"——这是解释器在尝试猜测你的意图（名字拼写错、忘了 import 等）。它是编译器级别的启发式功能，来自 CPython 的 "did you mean" 逻辑（也用于属性名拼写建议）。
- **生活类比**："变量必须先用后赋"就像"先开一盏灯再问它的亮度"——你不能问一个从未开过的灯有多亮，Python 干脆说"这灯我根本不认识"。
- **初学者误区**：①写 `total = total + 1` 却忘了初始化 `total` → `NameError`；②以为报错会"搞崩"程序 —— 不会，当前这条语句失败，会话/脚本仍可继续；③把"未定义"误以为是"默认是 0"。

### 代码分析

```python
>>> X          # 尝试使用一个从未赋值的名字
# 输出：
# Traceback (most recent call last):
#   File "<stdin>", line 1, in <module>
# NameError: name 'X' is not defined

>>> sys.ps1    # 尝试访问 unimport 的模块属性
# 输出：
# Traceback (most recent call last):
#   File "<stdin>", line 1, in <module>
# NameError: name 'sys' is not defined. Did you forget to import 'sys'?
```

解释器如何处理：
1. 你在 REPL 中输入 `X`，Python 把它作为一个**名字表达式**编译。
2. 求值时，PVM 在当前作用域的**命名空间**（这里是最外层/全局命名空间）中查找名字 `X`。
3. 找不到 → 触发 `NameError` 异常。由于没有 `try` 捕-获它，**默认异常处理器（default exception handler）**接管，打印 Traceback 到 stderr，然后**会话不中断地继续**。
4. `sys.ps1` 同理，但 Python 3.10+ 还附带了提示：它会检查是不是存在"类似名字的模块/内置"来给你 `Did you forget to import 'sys'?` 的建议。
5. 教训：用 `sys` 之前必须先 `import sys` —— `import` 会把模块对象的名字绑定到当前命名空间。

> 更一般地说，交互式提示符是测试程序组件的地方，无论它们的**来源**是哪种——你可以导入并测试 Python 文件里的函数和类、输入对链接进来的 C 函数的调用、在 Jython 之下驱动 Java 类，等等。部分由于它的交互特性，Python 支持一种实验性、探索性的编程风格，你会发现它很方便。
>
> 虽然 Python 程序员也会用文件内代码做测试（本书稍后会教你一些让它变简单的方法），但对许多人来说，交互式提示符仍然是他们测试的第一道防线（first line of testing defense）。

### 深度理解

- **核心概念**：交互模式是"测试工作台"——`import` 把模块加载进来，然后你手动调用其函数、检查返回值。
- **为什么这个测试流程高效**：Python 模块运行后，其顶层的绑定（函数、类、变量）会保留在模块对象中。你在 REPL 里 `import` 后，就获得了对模块 `__dict__`（命名空间）访问的入口，于是可以反复尝试各种参数组合。这正是"脚本语言快速迭代"的优势。
- **底层细节**：`import os` 会先搜索 `os.py`（标准库），把它编译成字节码、存入 `__pycache__`，然后执行其中全部顶层代码，最后把 `os` 名字绑定到模块对象。
- **初学者误区**：①`os.getcwd()` 必须带括号——它是函数调用，不带括号得到的是函数对象本身；②忘了 `import os` 直接用 `os` → `NameError`（3.5.1 刚演示过）；③以为交互式测试能代替正式测试——它能验证"函数能跑"，但自动化回归测试仍需文件内测试工具（如 `unittest`/`pytest`）。

### 代码分析

```python
import os            # 加载标准库模块 os
os.getcwd()          # 调用 os 模块里的 getcwd 函数，返回当前工作目录字符串
```

解释器如何处理：
1. `import os` 是语句。CPython 按模块搜索路径（`sys.path`：当前目录 → `PYTHONPATH` → 标准库目录 → site-packages）找到 `os.py`，首次导入时编译为字节码，把生成的 `.pyc` 缓存进 `__pycache__/`，然后执行模块顶层代码（`os` 是平台相关模块，内部还会再 import `nt` 或 `posix` 等具体实现模块）。
2. `os.getcwd()`：先对 `os.getcwd` 做属性解析（attribute lookup）——在 `os` 模块对象的命名空间里找到 `getcwd` 这个函数对象，然后以零个参数调用它。该函数在底层调用操作系统的 `getcwd` 系统调用，返回当前工作目录的字符串。
3. REPL 自动显示函数返回值 `'/Users/me/code'`。**测试方法论**：以后你写的每个模块，都可以这样 import 后逐个调用函数验证——这是 Python 程序员"第一道测试防线"。

## 3.6 程序文件（Program Files）

### 英文原文

> Although the interactive prompt is great for experimenting and testing, it has one big disadvantage: programs you type there go away as soon as the Python interpreter executes them. Because the code you type interactively is never stored in a file, you can't run it again without retyping it from scratch. Cut-and-paste and command recall can help some here, but not much, especially when you start writing larger programs.
>
> To cut and paste code from an interactive session, you would have to edit out Python prompts, program outputs, and so on—which is too tedious to try.
>
> To save programs permanently, you need to write your code in **files**, which are usually known as **modules**. Modules are simply text files containing Python statements. Once they are coded, you can ask the Python interpreter to execute the statements in such a file any number of times, and in a variety of ways—by system command lines, by file icon clicks, by options in the IDLE user interface, and more.
>
> Regardless of how it is run, Python executes all the code in a module file **from top to bottom** each time you run the file.
>
> Terminology in this domain can vary by role. For instance, module files are often referred to as **programs** in Python—that is, a program is considered to be a series of precoded statements stored in a file for repeated execution. Module files that are run directly are also sometimes called **scripts**—an informal term usually meaning a top-level program file.
>
> Some reserve the term **module** for a file imported from another file, and **script** for the main file of a program; we generally will here too (stay tuned for more on the meaning of top-level, imports, and main files later in this chapter).
>
> Whatever you call them, the next few sections explore ways to run code typed into files. In this section, you'll learn how to run files in the most basic and portable way: by listing their names in a Python **command line** entered at your computer's system prompt.
>
> Though this might seem primitive to some—and can often be avoided altogether by using alternatives discussed later—for many programmers, a system console window for command lines, together with a text editor window, constitutes as much of an integrated development environment as they will ever need and provides more direct control over programs.

### 中文翻译

> 虽然交互式提示符很适合实验和测试，但它有一个大缺点：你在那里输入的程序，一旦被 Python 解释器执行就消失了。因为你交互式输入的代码从未存进文件，你想再运行它，就必须从头重新输入一遍。复制粘贴和命令召回（command recall）能帮上一点忙，但帮助不大，尤其是当你开始编写更大的程序时。要把代码从交互式会话中剪切粘贴出来，你必须编辑掉 Python 提示符、程序输出等等——这太繁琐了，不值得试。
>
> 要永久保存程序，你需要把代码写进**文件（files）**，它们通常被称为**模块（modules）**。模块就是包含 Python 语句的文本文件。一旦写好，你就可以让 Python 解释器以任意次数、多种方式执行文件中的语句——通过系统命令行、点击文件图标、IDLE 用户界面中的选项，等等。无论以何种方式运行，每次运行文件时，Python 都会**从头到尾（from top to bottom）**执行模块文件里的全部代码。
>
> 这一领域的术语可能因角色而异。例如，模块文件在 Python 中常被称为**程序（programs）**——即程序被看作存储在文件里、供重复执行的一系列预编码语句。直接运行的模块文件有时也被称为**脚本（scripts）**——一个非正式术语，通常指顶层程序文件。有些人把术语 **module** 保留给"从另一个文件导入的文件"，把 **script** 留给"程序的主文件"；本书通常也这么用（稍后本章会继续讲顶层、导入和主文件的含义，敬请期待）。
>
> 无论你叫它什么，接下来的几节会探索运行"输入到文件里的代码"的各种方式。在本节中，你将学到最基础、最可移植的运行方式：在计算机的系统提示符下输入一条 Python **命令行**，在命令中列出它们的文件名。虽然对某些人来说这看起来原始——而且常常可以用后面讨论的替代方案完全避开——但对许多程序员而言，一个用于命令行的系统控制台窗口，加上一个文本编辑器窗口，就已经构成了他们永远需要的全部集成开发环境，并且提供了对程序更直接的控制。

### 深度理解

- **核心概念——module 与 script 的精确区分**：
  - **module（模块）**＝任何以 `.py` 结尾的源文件，可以被其它文件 import。
  - **script（脚本）**＝作为**主文件/顶层文件**直接运行的程序文件。
  - 同一个文件，被 import 时是"模块"，被直接运行时是"脚本"。**角色由运行方式决定，不是文件本身的性质。**
- **"文件内没有自动回显"**：前面强调过——REPL 会自动打印表达式结果，**模块文件不会**。文件里必须显式 `print`，否则输出为零。这是初学者第一个"脚本怎么没输出"的根源。
- **"从头到尾执行"意味着什么**：每次运行文件，解释器从上到下依次执行每条语句。这意味着：函数必须先定义后调用（运行时查找）；文件顶层的副作用（如 print）每次运行都会执行。
- **为什么命令行+编辑器是老手的最爱**：因为**直接**（explicit）——没有 GUI 的"糖衣"，你能精确控制运行目录、参数、环境变量。Lutz 坦言对很多人来说这就是"永远需要的 IDE"。
- **生活类比**：REPL 是黑板——粉笔字擦了就没了；模块文件是笔记本——记下来才能反复用、分发给别人（import）。
- **初学者误区**：①把 `>>>` 提示符连同代码一起存进 `.py` 文件 → 语法错误；②以为 import 的文件"应该"像主脚本一样重复执行——不是，默认只执行一次（3.11.2 会讲 reload）。

### 深度理解

- **核心概念**：`.py` 后缀是 Python 世界的"身份证"——它决定了：①文件能否被 `import` 找到（import 只认 `.py`）；②编辑器是否启用 Python 语法高亮；③文件系统是否把文件关联给 Python 解释器。**文件后缀在 Python 里不是摆设，是语言规范的一部分。**
- **为什么 import 必须认 `.py`**：import 语句要按名字（如 `sys`）搜索文件，它会把名字和 `.py` 拼接去找 `sys.py`。没有后缀，搜索系统就没法工作。这是"命名即协议"（convention over configuration）的体现。
- **脚本的三个功能块**：本脚本其实展示了 Python 程序的三个基本构件——①`import` 加载库；②变量绑定（`x = 'Hack!'`）；③函数调用与表达式（`print(...)`、`2 ** 100`、`x * 8`）。第 4 章起逐个展开。
- **`sys.platform` 是什么**：`sys` 模块在解释器启动时由 C 代码初始化，`platform` 是其中记录宿主平台的字符串（`win32`/`darwin`/`linux`）。它是程序判断运行环境的惯用手法。
- **生活类比**：`.py` 后缀就像信封上的"邮政编码"——没有它，信件（import 搜索）就投递不到，编辑器也"看不出"这是 Python 代码。
- **初学者误区**：①文件名用 `script.py` 之外却存成 `script.txt`，导致 import 失败；②把文件命名为 `sys.py` 或 `os.py`——这会遮蔽（shadow）标准库同名模块，引发神秘错误！**不要用标准库名字给你的文件命名。**

### 代码分析

```python
# 第一个 Python 脚本
import sys                 # 加载一个库模块
print(sys.platform)        # 打印平台标识，如 win32 / darwin / linux
print(2 ** 100)            # 计算 2 的 100 次方（Python 整数无精度上限）
x = 'Hack!'                # 把字符串对象绑定到名字 x
print(x * 8)               # 字符串重复拼接 8 次
```

解释器如何处理：
1. **逐行编译执行**：解释器把整个文件编译为字节码（首次运行时存入 `__pycache__/script1.cpython-312.pyc`），然后由 PVM 从上到下逐条执行——先执行 `import sys`，再执行三条 `print` 与赋值。
2. `import sys`：执行 import 机制（搜索 → 编译 → 执行 → 绑定名字 `sys` 到当前模块的全局命名空间）。
3. `print(sys.platform)`：属性访问（attribute access）——从 `sys` 模块对象中取出 `platform` 字符串，作为 `print` 的参数输出。
4. `2 ** 100`：整数幂运算。Python 3 的 `int` 是**任意精度**的（基于 30 位小数的分段表示），所以 `2 ** 100` 能精确算出 31 位十进制数 `1267650600228229401496703205376`——无需担心 C 语言里的溢出。
5. `x = 'Hack!'`：赋值创建变量。`x` 指向内存中的一个 str 对象（对象在堆上分配，引用计数管理生命周期）。
6. `print(x * 8)`：`str.__mul__` 执行重复拼接，产生新字符串后传给 print。
7. **与 REPL 的关键区别**：文件中第 4 行 `x = 'Hack!'` 不会有任何输出；第 3 行若没有 `print` 也什么都看不到——**文件模式无自动回显**。

> 请务必在与**脚本文件**保存位置相同的**工作目录**里运行你的 Python 命令（必要时先 **cd** 过去），并在系统提示符下运行，而不是在 Python 的 **>>>** 提示符下。和启动 REPL 一样，如果 Python 不在你的 **PATH** 设置里，你可能得把命令的第一个词替换成完整目录路径；但大多数安装会自动确保它在（更多关于 Python 安装和 **PATH** 的内容见**附录 A**）。
>
> 如果一切按计划进行，这条 shell 命令（或类似命令）会让 Python 一行一行地运行文件里的代码，你将看到脚本三条 **print** 语句的输出——Python 所知的底层平台名、2 的 100 次方、以及我们之前见过的那条字符串重复表达式的结果（后两者的含义在**第二部分**还有更多内容）。
>
> 如果一切**没有**按计划进行，你会得到一条错误消息——请确保文件中的代码与你所见的完全一致，然后重试。我们会在侧边栏**"调试 Python 代码"（Debugging Python Code）**里讨论调试选项，但在这个阶段，你最好的策略大概是机械模仿（rote imitation）。如果一切都不奏效，你也可以试试在后面的 IDLE GUI 下运行——那是一个把某些启动细节"裹上糖衣"的工具，不过有时要以牺牲使用命令行时的更显式控制为代价。
>
> 如果复制代码变得越来越繁琐或容易出错，你也可以从网上获取本书的示例；不过再说一次，初期亲手打字能帮你学会避免语法错误。获取示例的信息见**前言（Preface）**。

### 深度理解

- **核心概念——"解释器 + 文件名"模式**：`python3 script1.py` 的意思是"用 Python 3 解释器执行 `script1.py` 这个文件"。解释器读完整个文件后逐行执行。这是脚本语言最经典的运行方式。
- **第一个参数（first argument）**：`python3` 是程序名，`script1.py` 是它的第一个命令行参数。解释器看到参数就以"脚本模式"启动——不再进入 REPL，而是打开文件、按文件内容执行。
- **工作目录的重要性**：命令必须在"脚本所在目录"运行（或给完整路径）。因为解释器要找文件、脚本内部要读写文件，都相对**当前工作目录**进行。`cd` 是 shell 命令，不是 Python 命令。
- **为什么不能在 `>>>` 里输入**：`python3` 是 shell 的程序名，不是 Python 语句；在 `>>>` 里输入它会导致 `SyntaxError`。两个世界（shell 与 Python）的命令不能混用。
- **`2 ** 100` 的输出在第二部分才讲解**：作者在这里埋点——整数、字符串是后面 Part II 的主角，现在只需"看得懂输出"。
- **生活类比**：`python3 script1.py` 就像"请大厨（python3）按菜谱（script1.py）做菜"——菜谱要放在灶台（工作目录）上，大厨才能找到。
- **初学者误区**：①在 `>>>` 里输入 `python3 script1.py`；②双击 `.py` 文件一闪而过看不到输出（3.10.1 会讲原因）；③文件名拼写错误（`script1.py` vs `script1.py `）导致 `can't open file` 报错。

### 代码分析

```python
# shell 命令（不是 Python 代码）：
python3 script1.py   # Windows 上写作：py script1.py
```

解释器如何处理：
1. shell 解析命令：程序名 `python3`、参数 `script1.py`。
2. 操作系统按 `PATH` 找到 `python3` 可执行文件，启动新进程，并把 `script1.py` 作为 `argv[1]` 传给进程。
3. CPython 启动后检查 `argv`：没有参数 → REPL 模式；有参数 → 把它当作脚本文件路径，进入**脚本模式（script mode）**。
4. 脚本模式下，解释器读取整个文件、编译为字节码（若有 `__pycache__` 则直接加载缓存以省去编译）、然后从上到下执行全部语句。
5. 三行输出对应脚本里的三个 `print`——这就是"运行文件的命令行"的全部秘密：**换一个入口，执行逻辑完全相同。**

## 3.9 命令行用法变体（Command-Line Usage Variations）

### 英文原文

> When you type a command to run a Python code file, the command you type is run by a system **shell** program (e.g., **Bash** on Unix). Because of this, all of the shell's syntax is available for more custom runs. For instance, you can route the printed output of a Python script to a file to save it for later use or inspection, by using special shell syntax:

> ```
> $ python3 script1.py > saveit.txt
> ```
> In this case, the three output lines shown in the prior run are stored in the file **saveit.txt** instead of being printed. This is generally known as **stream redirection**; it works for both output (**>**) and input (**<**) text and is available on Windows and Unix-like systems. This is useful for testing, as you can write programs that watch for changes in other programs' outputs.
>
> It also has little to do with Python, though (Python simply supports it), so we will skip further details on shell redirection syntax here. Redirection is for command lines only, though, because it's a function of the system shell. On **Windows**, you can also type just the **name** of your script and omit the name of Python itself.
>
> Because Windows uses filename associations to find a program with which to run a file, the file's name is enough to run a **.py** file. The following command, for example, will automatically be run by Python on Windows (technically, by Python's **py** Windows launcher described in **Appendix A**):

> ```
> $ script1.py
> ```
> This works just as though you had clicked on the file's icon in File Explorer (a launch mode covered later). One fine point here: Command Prompt runs programs this way in its own window, but PowerShell may not; use **py** to view unredirected output in the latter if needed (or use the icon-click **input()** trick also coming up).
>
> Finally, remember to give the full path to your script file if it lives in a different directory than the one in which you are working. For example, the **py** Python command in the following, run in PowerShell on Windows, assumes Python is in your system path but runs a file located elsewhere:

> ```
> PS C:\Users\me\code> cd D:\temp\savecode # Go to a different folder PS D:\temp\savecode> py C:\Users\me\code\script1.py # Run a script elsewhere win32 1267650600228229401496703205376 Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!

> ```
> If your **PATH** doesn't include Python's directory, and neither Python nor your script file is in the directory you're working in, use full paths for **both**—like the following on macOS, which for good measure throws in output stream redirection to a file located outside the **current working directory** (where you are when this command is run):

> ```
> $ /usr/local/bin/python3 /Users/me/code/script1.py > /Users/me/data/saveit.py
> ```
> This is a lot to type, but also pathological and atypical. To keep your commands simpler than this, make sure Python is on your **PATH**, and **cd** to script or data folders first. Again, most installs set up **PATH** automatically, so you need only focus on script and data folders when running commands.

### 中文翻译

> 当你输入命令运行一个 Python 代码文件时，你输入的命令是由系统的 **shell** 程序（例如 Unix 上的 **Bash**）执行的。正因如此，shell 的全部语法都可用来做更定制的运行。例如，你可以用特殊的 shell 语法，把 Python 脚本打印的输出**路由到一个文件**，保存起来供以后使用或检查：
>
> ```
> $ python3 script1.py > saveit.txt
> ```
>
> 这种情况下，前一次运行中显示的三行输出会被存进 **saveit.txt** 文件，而不是打印出来。这通常被称为**流重定向（stream redirection）**；它对输出（**>**）和输入（**<**）文本都有效，在 Windows 和类 Unix 系统上都可用。这对测试很有用，因为你可以编写程序来监视其它程序输出的变化。不过它与 Python 本身关系不大（Python 只是支持它），所以我们这里跳过 shell 重定向语法的更多细节。不过重定向只适用于命令行，因为它是系统 shell 的功能。
>
> 在 **Windows** 上，你还可以只输入脚本的**名字**，而省略 Python 本身的名字。因为 Windows 使用文件关联（filename associations）来寻找运行某个文件的程序，所以对于 **.py** 文件，光有文件名就足以运行它。例如，下面的命令在 Windows 上会自动由 Python 运行（严格说，是由**附录 A** 中描述的 Python **py** Windows 启动器运行）：
>
> ```
> $ script1.py
> ```
>
> 这就像你在文件资源管理器中点击了文件图标一样（后面会讲这种启动模式）。这里有一个细节：命令提示符（Command Prompt）会在自己的窗口里用这种方式运行程序，但 PowerShell 可能不会；在后者中，如果需要查看未重定向的输出，就用 **py**（或者用后面要讲的图标点击 **input()** 技巧）。
>
> 最后，如果你的脚本文件所在的目录与你当前工作的目录不同，请记得给出脚本文件的完整路径。例如，下面在 Windows 的 PowerShell 中运行的 **py** 命令，假定 Python 在你的系统路径中，但运行的是位于别处的文件：
>
> ```
> PS C:\Users\me\code> cd D:\temp\savecode     # 转到另一个文件夹
> PS D:\temp\savecode> py C:\Users\me\code\script1.py     # 运行别处的脚本
> win32
> 1267650600228229401496703205376
> Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!
> ```
>
> 如果你的 **PATH** 里没有 Python 的目录，而且 Python 和你的脚本文件都不在你工作的目录里，那就给**两者**都用完整路径——就像下面在 macOS 上那样，它顺手还把输出流重定向到了**当前工作目录**（你运行命令时所在的位置）之外的一个文件：
>
> ```
> $ /usr/local/bin/python3 /Users/me/code/script1.py > /Users/me/data/saveit.py
> ```
>
> 这样要输入很多东西，但也算病态和非典型的用法。要让命令比这更简单，请确保 Python 在 **PATH** 里，并先 **cd** 到脚本或数据文件夹。再说一次，大多数安装会自动配置好 **PATH**，所以运行命令时你只需要关心脚本和数据文件夹。

### 深度理解

- **核心概念**：命令行由 shell 解释执行，因此你可以白赚 shell 的能力——**重定向（`>`/`<`）、管道（`|`）**等，都是"零成本"的额外功能。Python 只是被当作一个普通的命令行程序。
- **重定向的底层**：`>` 是 shell 层的文件描述符操作——把进程的标准输出（stdout，fd 1）指向文件，而不是终端。**这是操作系统功能，与 Python 无关**。Python 的 `print` 写 stdout，所以被重定向走。
- **Windows 文件关联（filename association）**：Windows 注册表把 `.py` 扩展名关联到 Python。输 `script1.py` 时，cmd 调用关联程序（py launcher）运行它。这和双击图标是同一机制。
- **PowerShell 的怪癖**：PowerShell 对"直接输入文件名"的处理与 cmd 不同（可能把输出当作对象管道化而不显示），所以作者建议用 `py` 保持确定性。
- **完整路径的两种使用场景**：①Python 不在 PATH——给解释器全路径；②脚本不在当前目录——给脚本全路径。两者都缺才需要都写全。
- **生活类比**：shell 重定向就像"开会时有人做会议纪要"——原本打在屏幕上的字（输出）被转写进文档（文件），发言人（Python）根本不知道换了记录方式。
- **初学者误区**：①把 `>` 当 Python 语法用（在 REPL 里输入 `print(...) > file`）——那是 shell 的事；②忘记 Windows 的 `script1.py` 直跑依赖文件关联，在 PowerShell 里行为不同；③路径含空格不引号导致找不到文件。

### 3.10.1 点击/轻点文件图标（Clicking and Tapping File Icons）

### 英文原文

> On most PC platforms, Python program files can be run by simply clicking or tapping their filename or icon in the local file explorer. For example, this works automatically on **Windows** in File Explorer, thanks to filename associations set up during Python's install. Clicks also run code files on **macOS** in Finder, if made to Open With the Python Launcher included in the macOS install; drags to the Python Launcher app when available work the same as clicks.
>
> The file-clicks story is more involved on **Linux**, where files likely need executable permission and a **#!** first line to name Python. On smartphones, tapping a filename in a file explorer on **Android** (or Files on **iOS**) may open the file in an associated Python app, but this may work only for some explorer/app combos, and may not give access to all of a program's files in some contexts.
>
> For more insight, consult your platform and app docs, or experiment on your device.
>
> Also see **Appendix A** for more info. As noted there, Windows and Linux clicks don't keep the window open for viewing output and error messages after programs end: if a script just prints and exits, it, well, just prints and exits—the console window appears, and text is printed there, but the console window closes and disappears on program exit.

> Per **Appendix A**, coding a closing call to Python's **input()** forces a pause before exit so you can see output, but this doesn't help for error messages. Use other run techniques when this matters.

### 中文翻译

> 在大多数 PC 平台上，只需在本地文件资源管理器中点击或轻点文件名或图标，就能运行 Python 程序文件。例如，在 **Windows** 的文件资源管理器（File Explorer）里，这能自动生效——多亏了 Python 安装时建立的**文件关联（filename associations）**。在 **macOS** 的 Finder 里，如果把文件"用打开方式（Open With）"选择为 macOS 安装自带的 Python Launcher，点击也能运行代码文件；在可用时把文件拖到 Python Launcher 应用上，效果与点击相同。

>
> 更多信息也请看**附录 A**。正如那里所述，在 Windows 和 Linux 上点击运行，程序结束后**不会让窗口保持打开**以查看输出和错误消息：如果一个脚本只是打印然后退出，那么它——呃——就是打印然后退出；控制台窗口出现、文本被打印到那里，但程序退出时控制台窗口就关闭消失了。按**附录 A** 的说法，在代码末尾调用一次 Python 的 **input()** 会强制在退出前暂停，让你看到输出；但这帮不上错误消息的忙（错误发生在到达 input() 之前）。当这一点很重要时，请使用其它运行技术。

### 深度理解

- **核心概念**：点击图标＝隐式调用"关联程序"（Windows）或"Python Launcher"（macOS）。这套机制方便，但**隐藏了运行细节**，还带来窗口一闪而过的老问题。
- **为什么窗口会闪退**：双击运行脚本时，系统为脚本开一个控制台窗口；脚本执行完、进程退出，窗口随之关闭。如果脚本只是 print 完就退出，你根本来不及看输出。**这不是 Python 的 bug，是控制台窗口生命周期决定的。**
- **两个经典解决方案**：
  - 脚本末尾加 `input()`——让程序等待用户输入，窗口停住直到按回车。**但只对正常运行有效**：若中途报错，异常已使进程退出，到不了 `input()`。
  - 更可靠：改用命令行或 IDE 运行——输出和错误留在终端/IDE 面板里。
- **Linux 的 `#!` + chmod**：在 Unix 系，直接运行文件需要两个条件——文件有可执行位（`chmod +x`），且首行 `#!/usr/bin/env python3` 告诉内核用哪个解释器。这是 Unix 的"可执行文本文件"协议。
- **生活类比**：双击图标就像按了"自动洗车"按钮——方便，但你想中途看泡沫怎么冲的（看输出），洗完了车（窗口）已经开走了。
- **初学者误区**：①双击 `.py` 报错闪退就以为"程序坏了"——先在命令行跑看错误信息；②把 `#!` 当作 Python 语法（它是给操作系统看的注释）；③以为所有平台双击行为一致。

### 深度理解

- **核心概念**：IDLE 的定位是**"零门槛 IDE"**——编辑、运行、调试三合一，随 Python 免费分发。它由 tkinter 编写，本身就是 Python 程序（所谓"吃自己的狗粮"）。
- **IDLE 的架构**：两个核心窗口——**Shell 窗口**（REPL，即交互式解释器界面）和**编辑窗口**（多文件文本编辑器）。`Run → Run Module` 相当于把编辑窗口的文件作为顶层脚本交给解释器执行，输出回到 Shell 窗口。
- **`python3 -m idlelib.idle` 的深层含义**：`-m` 让 Python 用 **import 搜索机制**找模块并**当作脚本运行**。`idlelib` 是包（package），`idle` 是包里的模块，`.` 是包层级语法。这预示了 Part V 的模块系统——**运行模块和导入模块共用同一套文件搜索逻辑**。
- **为什么要看深色主题截图**：图 3-1 同时示范了"编辑窗口 + Shell 窗口"的双窗口布局——理解这个布局就理解了 IDLE 的一切操作。
- **IDLE 的取舍**：对新手，GUI 隐藏了路径、参数等细节，降低入门门槛；对老手，这些"被隐藏的细节"正是需要显式控制的东西。作者态度中立："vet for yourself"（自己验证）。
- **生活类比**：IDLE 就像"一体式豆浆机"——泡豆、研磨、煮浆一步到位，但不灵活（你不能单独调节研磨细度）；命令行像"分开的豆浆机+锅"，麻烦但每一步都可控。
- **初学者误区**：①以为 IDLE 是"Python 的一部分必须用"——它只是可选工具；②在 Shell 窗口输 `python3 xxx.py`——Shell 里不需要也不接受这个，直接用 `Run → Run Module`；③不知道 `Run → Run Module` 是运行"当前编辑窗口"的文件，运行错文件还一脸茫然。

### 代码分析

```python
# 在系统控制台输入（不是 Python 语句）：
python3 -m idlelib.idle   # 用模块方式启动 IDLE
```

解释器如何处理：
1. `-m` 告诉解释器："接下来的参数是模块名，不要当文件名，去 `sys.path` 里搜索它。"
2. 搜索找到 `idlelib` 包（标准库目录下的一个文件夹），再找到包内的 `idle` 模块（`idlelib/idle.py`）。
3. 解释器像运行顶层脚本一样执行该模块，并设置 `__name__ == '__main__'`，于是 IDLE 的 GUI 主循环启动。
4. **意义**：这证明了"模块"与"脚本"的同一性——同一份文件，被 `import` 时是模块，被 `-m` 运行时是脚本。这是本书 Part V 的核心思想，在这里首次露出端倪。

### 3.10.5 浏览器里的 WebAssembly（WebAssembly for Browsers）

### 英文原文

> Although still an emerging technology, it's also possible to run Python code in web browsers. This is enabled today by **WebAssembly** (a.k.a. **Wasm**), which defines a portable bytecode format that is run by web browsers, much as the Python PVM runs its own bytecode (see **Chapter 2**). By compiling the Python interpreter's source code to this format with tools like the **Emscripten** LLVM-based compiler, web browsers are able to run Python, and hence, your Python programs.
>
> While other Python-in-the-browser initiatives of the past have largely fizzled, WebAssembly is standardized by the World Wide Web Consortium (W3C) and already supported by all major desktop and mobile web browsers.

> Compiling Python itself to Wasm is not trivial, and much too much to ask of Python beginners, but the **Pyodide** system has already done much of the work for you. It's a port of CPython to the WebAssembly/Emscripten platform, compiled and ready to run, with JavaScript integration for access to the browser **DOM** and web APIs.
>
> To use Pyodide in a web page, you'll load it from a server and initialize it in a browser, with an HTML document that uses supplied JavaScript code and API tools.
>
> The end result can run many Python programs in web browsers, with no local installs required.

> The chief downsides of this model seem to be **speed** and **utility**. Downloading a Python interpreter to run a Python script isn't fast, and the speed of Python scripts can be slow relative to natives. Moreover, Pyodide comes with a fixed set of Python tools, and Python scripts run by browsers live in a sandbox with limited access to tools and resources on the host device.
>
> Persistent storage, for example, may support POSIX file calls and paths, but is virtual and ultimately supported by browsers. Hence, while this option may avoid some Python installs, it opens the possibility of Python on the web, but with limitations for general software development, and futures options are impossible to predict.
>
> Watch the web for more on this evolving story—including the alternative **MicroPython** for Wasm, which is smaller than CPython but implements a constrained subset of the language, and the **py2wasm** Python-to-Wasm compiler, announced just as this book was being written.

### 中文翻译

> 虽然仍是一项新兴技术，但现在也**可以在网页浏览器里运行 Python 代码**。今天这由 **WebAssembly**（又名 **Wasm**）实现——它定义了一种可移植的字节码（bytecode）格式，由网页浏览器运行，正如第 2 章里 Python 虚拟机（PVM）运行自己的字节码一样。通过用 **Emscripten** 这类基于 LLVM 的编译器把 Python 解释器的源码编译成这种格式，网页浏览器就能运行 Python，也就运行了你的 Python 程序。过去"把 Python 跑在浏览器里"的其它倡议大多不了了之，但 WebAssembly 由万维网联盟（World Wide Web Consortium，W3C）标准化，并且已得到所有主流桌面和移动浏览器的支持。

> 把 Python 本身编译成 Wasm 并不简单（让 Python 初学者去做更是强人所难），但 **Pyodide** 系统已经替你完成了大部分工作：它是 CPython 到 WebAssembly/Emscripten 平台的一个移植，编译好即可运行，并带 JavaScript 集成，可访问浏览器的文档对象模型（**DOM**，Document Object Model）和 Web API。要在网页里使用 Pyodide，你要从一个服务器加载它，并在浏览器里用一个使用现成 JavaScript 代码和 API 工具的 HTML 文档来初始化它。最终结果是：无需任何本地安装，就能在浏览器里运行许多 Python 程序。

> 这个模式的主要缺点似乎是**速度（speed）**和**实用性（utility）**。下载一个编译好的 CPython 解释器到浏览器里运行一个 Python 脚本并不快，而在此环境中 Python 脚本的速度也可能不如人意。此外，Pyodide 自带固定的一套 Python 工具，而浏览器运行的 Python 脚本又活在一个**沙盒（sandbox）**里，对宿主设备上的工具和资源访问受限。例如，持久化存储（persistent storage）可能支持 POSIX 文件调用和路径，但它是虚拟的，最终只支持浏览器所支持的选项。所以，虽然这个选项能省去一些 Python 安装、为 Web 上的 Python 打开新的可能，但它对通用软件开发并没有其它方式那么有用，其未来也无法预测。请在网络上关注这个仍在演进的故事——包括另一种针对 Wasm 的 **MicroPython**（比 CPython 小，但实现的是第 2 章所述的受限 Python 子集），以及一个在本书写作时刚刚宣布的 **py2wasm** Python 到 Wasm 编译器。

### 深度理解

- **核心概念**：浏览器里也能跑 Python，靠的是 **WebAssembly（Wasm）**——一种浏览器原生支持的"可移植字节码"。这把 Python 的"字节码→解释器"模型又套了一层：**Python 字节码 → 解释器 → Wasm 字节码 → 浏览器**。
- **底层如何实现**：Wasm 是浏览器这门"虚拟机"的执行格式。用编译器（如 Emscripten）把 CPython 解释器（本身是 C 写的）编译成 Wasm，浏览器就能当"解释器的宿主"运行，从而解释 Python 源码。Pyodide 就是"预编译好的 CPython for Wasm + JS 胶水"。这就是设备无需安装 Python 的原因——解释器跟着网页下载。
- **为什么是"沙盒"**：浏览器有严格的安全模型（browser security model）——沙盒限制对资源（文件、网络等）的访问。所以 Pyodide 里"打开文件"其实是浏览器虚拟出来的。**浏览器的安全模型决定了 Python 在这里只能是"受限"**：能计算、能画图、能交互，但不能随心所欲地操作主机系统。
- **实际用处**：这类方案适合"无需安装环境就能演示 Python""把 Python 代码放进网页给用户玩"，不适合做真正的后台服务或本地大型项目。对真正的软件工程来说，命令行/IDE 仍然不可替代。
- **生活类比**：Wasm 里的 Python 像"来你家帮忙的钟点工"——能干不少活（算数、画图表），但你不能把"装修布线"（控制系统资源）这种粗活交给它。
- **初学者误区**：①以为 Wasm 的 Python 就是"普通 Python"——它跑在浏览器沙盒里，能用的模块有限；②把它当作"免安装好方案"——它的启动速度其实很慢；③读到"浏览器能跑 Python"就想到"以后不用装环境了"——错了，这种模式的适用范围很窄。

> 这个我们之前在谈 REPL 时已经遇见的选项。**Jupyter** 是一组让 Python 代码能在网页浏览器中运行的工具，重点支持科学编程（scientific-programming）任务。它的经典工具需要一个**单独安装**并启动的**服务器（server）**来运行你在网页里输入的代码；不过它还有一种形式，是使用上一节描述的 **WebAssembly** 和 **Pyodide** 系统在浏览器本地直接运行代码。无论哪种形式，Jupyter 页面都遵循灵活的**笔记本（notebook）**范式——用我们前面也见过的 **IPython** REPL 交互式编码、一点按钮就运行的代码单元格（code cells）、用 Python 数值工具做可视化，等等。

- **实际场景**：数据分析（统计、画图）、机器学习实验记录、教学演示、报表生成。它不是通用"程序运行环境"，而是"叙述性计算文档"。

### 3.10.7 把代码编译成机器码：AOT 编译器（Ahead-of-Time Compilers for Speed）

### 英文原文

> Also per **Chapter 2**, a number of **ahead-of-time** (AOT) compiler systems—including **Nuitka** and **Shed Skin**—compile Python programs all the way to machine code, like C and C++ compilers compile C and C++ programs. Once you install such a system, you'll run its compiler against your file of Python code, and it will produce an executable program. You run that executable like any other program.
>
> AOT compilers can speed up your program, but at the cost of additional steps that slow the development process and negate some of the advantages of using Python. They're probably best saved for later in your career, when speed truly matters.

### 中文翻译

> 按照**第 2 章**的说法，一些**提前编译（ahead-of-time，AOT）**的编译器系统——包括 **Nuitka** 和 **Shed Skin**——可以把 Python 程序一直编译成**机器码（machine code）**，就像 C 和 C++ 编译器把 C/C++ 程序编译成机器码一样。你一旦安装这类系统，先要把你的 Python 代码文件交给它的编译器，然后像运行其它可执行程序那样运行编译结果。AOT 编译器可以提升程序速度，但代价是增加了额外的开发步骤、明显拖慢编程流程，并抵消了使用 Python 的一些优势。对 Python 新手来说，最好在通过常规 REPL、IDE、命令行这类更易上手的途径学完 Python，之后再探索这些系统。

### 深度理解

- **核心概念**：之前讲的都是"解释型运行"（每次运行都解释字节码）；AOT 走的是**一次性编译成机器码**的 C/C++ 路线，编译产物是"可执行文件"，以后直接运行。**用"编译时间"换"运行速度"**。
- **底层原理**：Nuitka 把 Python 源码翻译成 C 代码再调用编译器编译成原生可执行文件；Shed Skin 则在推断类型后把代码编译成 C 再到机器码。但有一个现实的困难：Python 的**动态类型 + 反射**特性使其"编译成高效机器码"远比 C/C++ 艰难——这也是为什么即便 AOT 后的 Python 仍难达到 C 的性能。
- **为什么牺牲开发速度也要用**：当你的 Python 脚本是"每天处理海量数据的批任务"时，运行速度直接决定成本和可行性，巨大的收益压倒编译成本；但若程序需要频繁迭代，编译时间反而会拖垮开发效率。
- **与解释执行的 Python 的关系**：这不是"更好"，而是"另一类工具"。**开发期用解释器（快速获得反馈），需要极致性能的发布期才考虑 AOT**——两者在 Python 生态中长期并存。
- **初学者误区**：①以为"把 Python 编译成独立可执行文件"就等于"更快"——编译优化的是性能，语义仍然不变；②指望靠 AOT 轻易拿到 C 的速度；③以为第 2 章讲的"解释器"和 AOT"编译"互斥——其实 Python 生态里编译器和解释器并存，组合使用才是常态。
- **生活类比**：AOT 像"预制菜"——备料（编译）一次，开饭（运行）很快；解释型像"现炒现卖"——每顿都从切菜（解释）开始，灵活但慢。两者做的是同一道菜（同样的 Python 语义），只是"备料时机"不同。

### 3.11.1 导入模块（Importing Modules）

### 英文原文

> In simple terms, every file of Python source code whose name ends in a **.py** extension is a **module**. No special code or syntax is required to make a file a module: any such file will do. Other files can access the items a module defines by **importing** it—which essentially loads another file and gives you access to that file's contents.
>
> The contents of a module are made available to the outside world through its **attributes**—a term defined informally in the next section.

> This module paradigm turns out to be the core idea behind **program architecture** in Python. Larger programs usually take the form of multiple module files, which import tools from other module files. One of the modules is designated as the main or **top-level** file, also often called the **script**—the file launched to start the entire program, which runs line by line as usual. Below this level, it's all modules importing modules.

> We'll delve into such architectural issues in more detail later in this book. This chapter is mostly interested in the fact that import operations **run** the code in a file being loaded as a final step. Because of this, importing a file is yet another way to launch it.
>
> For instance, if you start an interactive session (from a system command line or otherwise), you can run the **script1.py** file we wrote earlier in **Example 3-1** with a simple **import** statement—which is really Python code running other Python code:

> ```
> $ python3
> >>> import script1
> darwin
> 1267650600228229401496703205376
> Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!
> ```

> > **NOTE.** Where to run imports: Be sure to run this Python command in the directory (i.e., folder) containing **script1.py**. Per this chapter's earlier coverage of code folders, this is easiest if you save module files and run imports in a per-chapter folder. Later in this book, you'll learn that imports in a REPL search for a module in the **current directory**, plus those listed on environment variable **PYTHONPATH** or specified otherwise.
>
> The current directory part of this will suffice for most imports you're likely to try until then—as long as all your code files reside there.

### 中文翻译

> 简单地说，每个文件名以 **.py** 扩展名结尾的 Python 源代码文件都是一个**模块（module）**。不需要任何特殊的代码或语法来让一个文件成为模块：任何这样的文件都可以。其它文件可以通过**导入（importing）**来访问模块定义的内容——导入本质上就是加载另一个文件，并让你访问该文件的内容。模块的内容通过它的**属性（attributes）**向外界开放——这个术语下一节会有非正式的定义。

> 这种模块范式最终被证明是 Python **程序架构（program architecture）**背后的核心思想。较大的程序通常表现为多个模块文件，彼此互相导入工具。其中一个模块被指定为主文件或**顶层（top-level）**文件，也常被称为**脚本（script）**——即被启动以开启整个程序的文件，它照常一行一行地运行。在它之下，全部是"模块导入模块"。

> 我们稍后会在本书中更详细地钻研这些架构问题。本章主要关心的事实是：**导入操作会把被加载文件中的代码作为最后一步运行**。正因如此，导入一个文件是启动它的又一种方式。例如，如果你启动一个交互式会话（从系统命令行或其它方式），你可以用一条简单的 **import** 语句运行我们之前在**示例 3-1** 里写的 **script1.py** 文件——这其实就是"Python 代码在运行其它 Python 代码"：

> ```
> $ python3
> >>> import script1
> darwin
> 1267650600228229401496703205376
> Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!
> ```

> > **注意。在哪儿运行导入**：请务必在包含 **script1.py** 的目录（即文件夹）里运行这条 Python 命令。按照本章前面关于代码文件夹的讲解，最省事的方式是：把你正在学习的章节的模块文件和导入操作都放在一个按章节划分的文件夹里。本书后面你会学到：REPL 中的导入会按 **当前目录（current directory）**、环境变量 **PYTHONPATH** 中列出的目录、或以其它方式指定的目录来搜索模块。在那之前，只要你把所有代码文件都放在当前目录下，仅靠"当前目录"就足以应对你很可能尝试的大部分导入。

### 深度理解

- **核心概念**：**.py 文件 = 模块，import = 执行文件内容并暴露其属性**。这里第一次正式定义"模块"：不需要任何特殊声明，凡是 `.py` 文件都是模块。
- **"导入运行文件"的双重身份**：`import script1` 干了两件事——①搜索并**执行** `script1.py` 的全部顶层代码（所以三个 print 都输出了）；②把模块对象以名字 `script1` 绑定到当前命名空间。**这是"运行程序"的又一种官方姿势**。
- **为什么 import 要在当前目录运行**：import 的搜索路径（`sys.path`）第一项通常是当前工作目录。你在别的目录 `import script1` 会报 `ModuleNotFoundError`——这就是本章前面强调"代码文件夹"的回报。
- **程序架构蓝图**：Python 大型程序的形态 = 一个顶层脚本 + 一堆被它导入的模块。这是 Part V 的主线，这里只是"剧透"。
- **生活类比**：import 像"借邻居家的工具"——打开人家的工具箱（执行文件）、把工具摆出来（属性暴露），你就能借来用；而"直接运行脚本"像"把邻居请到你家现场表演一遍"——同样的事做一次，但不会有"工具借出"关系。
- **初学者误区**：①在错误目录 import 报错就以为代码坏了；②以为 `import` 只是"加载定义"而不会执行代码——不，**导入时会执行文件的顶层语句**（顶层 print 会打印！），这是初学者最意外的行为。

### 代码分析

```python
# 在 REPL 中（不是 Python 文件里）：
import script1   # 导入 = 搜索并执行 script1.py 的全部顶层代码
```

解释器如何处理：
1. `import script1` 时，CPython 先按 `sys.path` 搜索 `script1.py`（当前目录排第一，所以能命中）。
2. 首次导入：把源码编译成字节码，缓存进 `__pycache__/script1.cpython-312.pyc`，然后**执行**整个文件的顶层代码——三个 `print` 依次输出，这就是你看到的 `darwin`、`2**100`、字符串重复三行。
3. 执行完毕后，把模块对象绑定到当前命名空间的名字 `script1`。
4. **关键**：这里没有出现任何"错误"，因为导入成功地把文件"运行"了一遍。程序员的直觉是"import = 读文件"，但 Python 的真相是"import = 执行文件 + 绑定模块对象"。

### 3.11.2 重新加载模块（Reloading Modules）

### 英文原文

> Imports work to run a file, but only **once per session** (really, **process**—a program run) by default. After the first import, later imports do nothing, even if you change and save the module's source file again in another window:

> ```
> >>> import script1
> >>> import script1
> ```
> This is by design; imports are too expensive an operation to repeat more than once per file in a given program run. As you'll learn in **Chapter 22**, imports must find files, compile them to bytecode, and run the code line by line, and importers usually care only that the module's lines have defined its exports.

> If you really want to force Python to run the file again in the same session without stopping and restarting the REPL, you need to instead call the **reload** function available in the **importlib** standard-library module (and previously in the now-defunct **imp** module, and a built-in function before that: that's three incarnations, for anyone counting!):

> ```
> >>> from importlib import reload
> >>> reload(script1)
> darwin 1267650600228229401496703205376 Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack! <module 'script1' from '/Users/me/Code/script1.py'>

> ```
> The **from** statement here simply copies a name out of a module (more on this in the next section). The **reload** function itself loads and runs the current version of your file's source code, picking up the file's changes if you've modified and saved it in another window. This allows you to edit and use new code on the fly in the current Python interactive session.

> The **reload** function expects the name of an already-loaded module object, so you have to have successfully imported a module before you can reload it (and if the import failed with an error, you can't yet reload, and must import again).

> Notice that **reload** also expects parentheses around the module object name, whereas **import** does **not**—**reload** is a function that is **called** with an argument, and **import** is a statement. That's also why you get back an extra output line when reloading—the odd last line is just the display representation of the **reload** call's return value, a Python module object.
>
> You'll learn more about using functions in general in **Chapter 16**; for now, when you hear "function," remember that parentheses are required to run a call, even if there's nothing to send.

### 中文翻译

> 导入可以用来运行文件，但默认情况下**每个会话（session）只做一次**（准确地说，是每个**进程 process**——一次程序运行）。第一次导入之后，再导入就什么都不做了——即使你在另一个窗口修改并保存了模块的源文件：

> ```
> >>> import script1
> >>> import script1
> ```

> 这是有意设计：在给定的一次程序运行中，对每个文件重复导入是过于昂贵的操作。正如你在**第 22 章**会学到的，导入必须查找文件、把它们编译成字节码、逐行运行代码——而导入者通常只关心模块的代码行是否已经定义了它导出的内容。

> 如果你真的想在同一会话里强制 Python 再次运行该文件，而又不停止并重启 REPL，你需要改而调用 **importlib** 标准库模块中的 **reload** 函数（它之前存在于现已废弃的 **imp** 模块中，再之前则是个内建函数——整整三个化身，数一数！）：

> ```
> >>> from importlib import reload
> >>> reload(script1)
> darwin
> 1267650600228229401496703205376
> Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!
> <module 'script1' from '/Users/me/Code/script1.py'>
> ```

> 这里的 **from** 语句只是把一个名字从模块中复制出来（下一节有更多内容）。**reload** 函数本身会加载并运行你文件的源代码的**当前**版本——如果你在另一个窗口修改并保存过文件，它会拾取这些改动。这让你能在当前 Python 交互式会话中**即时**编辑并使用新代码。

> **reload** 函数期望的是**已经加载**的模块对象的名称，所以你必须先成功导入一个模块，之后才能 reload 它（如果导入因错误而失败，你还不能 reload，必须重新 import）。

> 注意 **reload** 还要求模块对象名字**两边带括号**，而 **import** **不用**——**reload** 是一个需要用参数**调用（call）**的**函数**，而 **import** 是一条**语句**。这也解释了为什么 reload 时会多一行输出——那最后一行奇怪的输出，只是 **reload** 调用返回值的显示表示（display representation），它是一个 Python 模块对象。你会在**第 16 章**更全面地学习函数的使用；现在，听到"函数"时请记住：即使没什么可传，调用也必须带括号。

### 深度理解

- **核心概念**：**import 默认每个进程只执行一次**（这是"导入缓存"机制）；想在同一进程里强制重跑，用 `importlib.reload()`。
- **为什么 import 只跑一次**：因为 import 是"昂贵操作"——查找文件 → 编译字节码 → 执行。而且导入者的语义是"让我能用到这个模块的导出"，不是"每 import 一次就重跑一遍"。重复导入会浪费 CPU，还可能在重跑时重置模块内部状态。
- **reload 的底层行为**：reload 会重新执行模块的**顶层代码**，并**就地更新**已存在的模块对象（`sys.modules` 里的那个），而不是新建模块对象。**注意**：reload 只更新 `import` 绑定的名字，**不会**更新 `from ... import name` 已经复制出去的名字——这是著名"坑"。
- **import 是语句、reload 是函数**：语句和函数的调用语法不同——`import a`（无括号）vs `reload(a)`（带括号）。reload 的最后一行输出就是函数返回值的 REPL 自动回显（模块对象的 repr）。
- **历史彩蛋**：reload 的"三个化身"——内置函数 → `imp` 模块 → `importlib` 模块，反映了 Python 标准库重构史（imp 在 3.12 中被移除）。
- **生活类比**：import 像"安装好的家用电器"——装一次就一直在那儿，按开关（reload）才重新工作；再"安装"一遍什么也不会发生。
- **初学者误区**：①改了文件后继续 `import`，以为会自动生效——不会！必须 reload 或重启进程；②用 `from x import f` 后又 reload——拿到的还是旧函数；③给 reload 不存在的模块名——必须先 import 成功。

### 代码分析

```python
import script1                    # 首次导入：执行文件（输出三行结果）
import script1                    # 第二次导入：什么都不做（已缓存）
from importlib import reload      # 从 importlib 模块复制出 reload 函数
reload(script1)                   # 重新执行 script1 的代码，返回模块对象
```

解释器如何处理：
1. 第一次 `import script1`：`sys.modules` 里没有 `script1` → 走完整导入流程（查找→编译→执行→绑定）。
2. 第二次 `import script1`：`sys.modules` 里**已经有** `script1` → 直接把缓存对象绑定，**不执行文件**。
3. `from importlib import reload`：导入 `importlib` 模块，把其 `reload` 属性**复制**为当前作用域的名字 `reload`。
4. `reload(script1)`：函数调用。`reload` 从 `sys.modules` 取出 `script1` 模块对象，重新编译并执行它的源码，用新命名空间**覆盖更新**模块对象内部的名字；返回该模块对象，REPL 于是自动回显 `<module 'script1' from '...'>`。
5. **设计思想**：函数调用必须带括号（`reload(x)`），语句不用（`import x`）——这种语法差异是有意为之，帮助区分"执行动作"与"绑定关系"。

### 3.11.3 模块属性初探（Module Attributes: A First Look）

### 英文原文

> Imports and reloads provide a natural program launch option because import operations **execute files** as a last step. In the broader scheme of things, though, modules serve the role of **libraries** of tools, as you'll learn in **Part V**.
>
> The basic idea is straightforward, though: a module is mostly just a package of variable names, known as a **namespace**, and the names within that package are called **attributes**—variable names that are attached to a specific object (like a module). In more concrete terms, all the names assigned at the top level of a module's file become its attributes, and a module's importers gain access to all of them.
>
> These names are usually assigned to tools exported by the module—functions, classes, variables, and so on—that are intended to be used in other files and other programs. Externally, a module file's names can be fetched with two Python statements, **import** and **from**, and may be reset with the **reload** call.

> To illustrate, use a text editor to create a one-line Python module file called **myfile.py** in your working directory, with the contents in **Example 3-2**.

> **Example 3-2. myfile.py**

> ```python
> title = 'Learning Python, 6th Edition'
> ```
> This may be one of the world's simplest Python modules (it contains a single assignment statement), but it's enough to illustrate the point. When this file is imported, its code is run to generate the module's attribute. That is, the assignment statement creates a variable and module attribute named **title**.

> You can access this module's **title** attribute in other components in two different ways. First, you can load the module as a whole with an **import** statement, and then **qualify** the module name with the attribute name to fetch it (note that we're letting the interpreter print automatically here):

> ```

> >>> import myfile    # Run file, load module as a whole
> >>> myfile.title     # Use its attribute names: '.' to qualify
> 'Learning Python, 6th Edition'

> ```

> Alternatively, you can fetch (really, copy) names out of a module with **from** statements:

> ```
> $ python3    # Restart Python REPL
> >>> from myfile import title    # Run file, copy its names
> >>> title    # Use name directly: no need to qualify
> 'Learning Python, 6th Edition'

> ```

Technically, **from** copies a module's attributes, such that they become simple **variables** in the recipient. So, you can refer to the imported string this time as **title** (a variable) instead of **myfile.title** (an attribute).

> Naturally, modules usually define more than one name to be used both in and outside their files. **Example 3-3**, for instance, defines three.

> **Example 3-3. threenames.py**

> ```python
> a = 'PC'       # Define three attributes
> b = 'Phone'    # Exported to other files
> c = 'Tablet'
> print(a, b, c) # Also used as variables in this file
> ```
> This code file, **threenames.py**, assigns three variables, and so generates three attributes for the outside world. It also uses its own three variables in a **print** statement, as you see when this is run as a top-level file from a system prompt:

> ```
> $ python3 threenames.py
> PC Phone Tablet

> ```
> All of this file's code also runs as usual the first time it is imported elsewhere, by either an **import** or **from**:

> ```
> $ python3
> >>> import threenames    # Grab the whole module: it runs here
> PC Phone Tablet

> >>> threenames.b, threenames.c    # Access its attributes: qualify to use
> ('Phone', 'Tablet')

> >>> from threenames import b, c   # Copy multiple names out: use directly
> >>> b, c

> ```
> The results here are printed in parentheses because they are really **tuples**—a kind of object created by the comma in the inputs (and covered in the next part of this book)—that you can safely accept on faith for now.

> From a grander perspective, modules form the highest layer of Python program architecture: as self-contained namespaces, they naturally support code organization and reuse, and they automatically minimize name collisions in your code. We'll deal with their loftier goals later in this book.

> For this chapter, it's enough to know that imports and reloads are another way to run your code files, though probably a **secondary option**: due to complicated quirks that we'll skip here (e.g., **reload** updates importers using **import** but not **from**), tools like command lines and IDEs are generally **better bets** for running Python code.

- **核心概念**：**模块 = 命名空间（namespace）＝顶层名字的集合；属性 = 模块里的变量名**。这是 Python 程序架构的第一课：`.py` 文件顶层赋的每一个名字，都自动成为该模块的属性。
- **两种取用方式的本质差异**：
  - `import myfile` → 用 `myfile.title` 点号限定访问。模块仍是一个独立命名空间，名字不泄漏。
  - `from myfile import title` → **复制**一份名字进当前作用域，`title` 成为本地变量。省事，但**切断**了与模块的同步（reload 也不更新它）。
- **为什么 `from` 是"复制"而不是"引用"**：`from` 本质是"先 import，再把属性赋给本地名字"。之后你改 `title` 不影响 `myfile.title`；reload 模块也不会更新已复制的 `title`。这是后续 Part V 的重要知识点。
- **顶层代码执行的后果**：`threenames.py` 里的 `print(a, b, c)` 在**导入时也会执行**——所以 `import threenames` 输出了 `PC Phone Tablet`。模块顶层代码"每次被导入只执行一次"（本进程内）。
- **程序架构的最高层**：大型程序 = 顶层脚本 + 相互导入的模块；模块的命名空间隔离**自动**消除了名字冲突——两个模块都定义 `a` 互不干扰。这是 Python 天然的设计优势。
- **生活类比**：模块像"工具房的货架"——每个货架（模块）有自己的格子（命名空间）；`import` 是"站在货架前取用工具"（要报货架名）；`from` 是"把工具搬到自己家"（直接用，但搬走了就与货架无关了）。
- **初学者误区**：①以为 `from ... import` 会"保持同步"——不会，它只是复制；②在模块里写顶层代码（如 print）时没意识到 import 时会执行；③两个文件互相 import 造成循环导入——Part V 会讲。

解释器如何处理：

2. `myfile.title`：点号表达式——先解析 `myfile` 找到模块对象，再在其命名空间（`__dict__`）里查 `title`。**属性访问是 Python 中最常用的字节码操作之一**（`LOAD_ATTR`）。
3. `from myfile import title`：等价于"import myfile，然后 `title = myfile.title`"——把模块对象的 `title` 属性**复制**到当前命名空间成为普通变量。
4. **设计思想**：用命名空间隔离代码 = "显式优于隐式"的工程化体现——谁导入谁负责声明，冲突自消。

### 3.11.4 exec 内建函数（The exec Built-In）

### 英文原文

> Python also provides a way to launch files with code that does not rely on the module concepts of the preceding section. The **exec** built-in function compiles and runs whatever Python source code statements are in the string you pass to it. Along with its **eval** expression cousin, this supports many dynamic roles you'll meet in upcoming chapters.

> By passing a code file's loaded contents to **exec**, though, this yields another way to launch code files from a REPL or other file—without having to import and later reload. Each such **exec** runs the **current** version of the code read from a file, without requiring imports or reloads. For instance, using **Example 3-1**'s **script1.py** again:

> ```
> $ python3
> >>> exec(open('script1.py').read())
> darwin 1267650600228229401496703205376 Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!

> ```
> To understand this code, you must first know that the **open** and **read** nested inside it run first, and left to right, and load the file's entire contents as a string. We'll study files in the next part of this book, so take this as a preview for now. (This was also a forward knowledge dependency, but that's what this book presents.)

> Once the file is loaded, though, the **exec** call has an effect similar to an import, but it doesn't actually import the module. Instead, each time you run an **exec**/**open** combo this way it runs the file's code anew and unconditionally—as though you had pasted the file's code at the place where **exec** is called. As one consequence, this **exec**/**open** scheme does not require module reloads after file changes.

> On the downside, because it works as if you've pasted code into the place where it is called, **exec** has the potential to silently overwrite variables you may currently be using. For example, our **script1.py** assigns to a variable named **x**. If that name is also being used in the place where **exec** is called, the name's value is replaced—sans warning:

> ```
> >>> x = 999
> >>> exec(open('script1.py').read())    # Code run in this namespace by default
> …same output…

> >>> x    # Its assignments can overwrite names here
> 'Hack!'

> ```
> This potential for name collisions is a downside shared by the last section's **from** statement. By contrast, the basic **import** statement makes the file a separate module namespace, so that its assignments will not change variables in the importer's scope. The price you pay for its namespace partitioning of modules is the need to reload and qualify.

### 中文翻译

> Python 还提供了一种不依赖上一节模块概念、用代码启动文件的方式。**exec** 内建函数会编译并运行你传给它的字符串里的任何 Python 源代码语句。连同它的表兄弟——表达式求值的 **eval**——一起，支撑着你在后续章节会遇到的许多动态（dynamic）角色。

> 不过，把代码文件加载后的内容传给 **exec**，就得到了从 REPL 或其它文件启动代码文件的又一种方式——无需 import、之后也无需 reload。每一次这样的 **exec** 都会运行从文件读到的**当前**版本的代码，不需要导入或重载。例如，再用 **示例 3-1** 的 **script1.py**：

> ```
> $ python3
> >>> exec(open('script1.py').read())
> darwin
> 1267650600228229401496703205376
> Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!
> ```

> 要理解这段代码，你得先知道：嵌套在里面的 **open** 和 **read** 先执行，从左到右，把文件的全部内容加载成一个字符串。我们会在本书下一部分学习文件，这里就先当作一次预览吧。

> 一旦文件被加载，**exec** 调用的效果就与 import 类似，但它并不真正导入模块。相反，你每运行一次这样的 **exec**/**open** 组合，它都会**重新、无条件地**运行文件的代码——就好像你把文件的代码**粘贴**在调用 **exec** 的位置一样。一个直接后果是：这种 **exec**/**open** 方案在文件修改后**不需要**重载模块。

> 缺点在于：因为它的行为如同把代码粘贴在调用处，**exec** 有可能静默覆盖你当前正在使用的变量。例如，我们的 **script1.py** 给名为 **x** 的变量赋值。如果这个名字在调用 **exec** 的地方也正被使用，这个名字的值就会被替换——没有任何警告：

> ```
> >>> x = 999
> >>> exec(open('script1.py').read())    # 代码默认在这个命名空间里运行
> …同样的输出…
> >>> x    # 它的赋值可以覆盖这里的名字
> 'Hack!'
> ```

> 这种名字冲突的可能性，是上一节的 **from** 语句同样存在的缺点。与之相反，基础的 **import** 语句会把文件变成独立的模块命名空间，使它的赋值不会改变导入者作用域里的变量。模块命名空间隔离的代价，就是你必须 reload 和点号限定。

### 深度理解

- **核心概念**：`exec` = **在调用处直接执行一段代码字符串**。`exec(open('file.py').read())` = "把文件内容当成粘贴过来的代码运行"，是 import 之外的另一种"运行文件"手段。
- **底层机制**：`open('script1.py')` 返回文件对象 → `.read()` 读出整个文件内容字符串 → `exec` 接收字符串，**现场编译**成字节码并在**当前命名空间**执行。与 import 的关键区别：exec 不查 sys.modules、不做缓存、不产生模块对象——每次都是"全新执行"。
- **为什么能免 reload**：因为 exec 每次都是"读最新文件内容再执行"，天然拿到的就是当前版本。import 的缓存机制反而成了需要 reload 的根源。
- **为什么危险**：exec 的代码在**调用者的命名空间**里运行——文件里赋值 `x = 'Hack!'` 会把调用处已有的 `x = 999` **静默覆盖**。这正是 Python 哲学里的"显式优于隐式"的反面教材：隐式注入名字 = 隐患。
- **对比三兄弟**：`import`（隔离命名空间，安全但需 reload+限定）、`from`（复制名字，省事但不同步）、`exec`（粘贴代码，最灵活但**最危险**）。三者是"隔离性 → 便利性"的光谱。
- **现实用途**：exec 常被用于配置文件加载（读一段 Python 语法配置）、插件系统、DSL 执行。生产代码里要谨慎——`exec` 任意字符串等于运行任意代码（安全风险）。
- **初学者误区**：①以为 exec 之后还能 `reload`——exec 与模块系统无关；②以为 exec 不会改当前变量——恰恰相反，它默认就在当前命名空间执行；③把 exec 与 eval 混用——exec 运行语句、eval 求值表达式。

### 代码分析

```python
exec(open('script1.py').read())   # 读文件内容 → 在当前位置执行
x = 999                           # 先定义一个变量
exec(open('script1.py').read())   # script1.py 里赋值 x='Hack!' → 覆盖了上面的 999
x                                 # 结果是 'Hack!'（静默覆盖，无警告）
```

解释器如何处理：
1. `open('script1.py')`：打开文件，返回文件对象（Python 的文件操作，Part II 讲）。
2. `.read()`：一次性读出全部文本，返回 str 对象。
3. `exec(字符串)`：CPython 对这个字符串调用编译管线（tokenize → parse → 字节码），然后在**当前帧的命名空间**逐条执行——相当于"文本粘贴执行"。
4. 副作用：文件里的 `x = 'Hack!'` 直接改写调用处命名空间的 `x`，覆盖掉原来的 `999`。
5. **设计思想**：exec 是 Python "一切皆可动态"哲学的极致体现——连"程序文本"本身都可以是运行时输入。能力越大责任越大：生产环境慎用。

### 3.11.5 命令行启动器（Command-Line Launchers）

### 英文原文

> Finally, Python code can also be run by Python code that uses standard-library tools to spawn command lines in parallel processes. The **os** module's **system** call, for instance, runs a command as if you typed it at a system console (its **0** return value echoed at the end here means all worked well):

> ```
> $ python3
> >>> import os
> >>> os.system('python3 script1.py')
> darwin 1267650600228229401496703205376 Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack! 0

> ```
> This **os** module's **popen** call does similar but returns a file object from which you can read the spawned command's printed output as a string for use in the spawning code; and Python's **subprocess.run** call can be used to launch programs by command lines with much more control over the fine points. We'll deploy **popen** in **Chapter 21**.

> Though related to running code, all these tools are well beyond the scope of this getting-started chapter, so consult Python's library manuals for the full story if and when such utilities become useful in your future work. And a caution: these tools, along with **exec**, will happily run any command line you throw at them—including one to erase all your files!—so they're best limited to running Python commands unless and until you're sure that other commands are safe.

### 中文翻译

> 最后，Python 代码还可以由使用标准库工具、在并行进程中生成命令行的 Python 代码来运行。例如，**os** 模块的 **system** 调用会像你在系统控制台输入一样运行一条命令（这里结尾回显的 **0** 是返回值，表示一切正常）：

> ```
> $ python3
> >>> import os
> >>> os.system('python3 script1.py')
> darwin
> 1267650600228229401496703205376
> Hack!Hack!Hack!Hack!Hack!Hack!Hack!Hack!
> 0
> ```

> **os** 模块的 **popen** 调用与此类似，但会返回一个文件对象，你可以从中把所启动命令打印的输出读成字符串，供启动它的代码使用；而 Python 的 **subprocess.run** 调用则能用命令行启动程序，并对细节有更多控制。我们会在**第 21 章**用到 **popen**。

> 虽然都与运行代码相关，但这些工具都远远超出本章这个入门章的范畴；如果这类工具在你将来的工作中变得有用，请查阅 Python 的库手册了解全貌。还有一条告诫：这些工具连同 **exec**，会乐此不疲地运行你丢给它们的任何命令行——包括一条能**删光你所有文件**的命令！——所以在你确信其它命令是安全的之前，最好只让它们运行 Python 命令。

### 深度理解

- **核心概念**：Python 程序可以**自己启动外部进程**——`os.system`（扔给 shell 执行）、`os.popen`（可读输出）、`subprocess.run`（现代推荐，精细控制）。这是"程序内的命令行"。
- **底层机制**：`os.system('python3 script1.py')` 调用操作系统 API 启动一个新的**子进程**，由系统的 shell 解析并执行命令字符串；子进程的 stdout 直接连到当前进程的 stdout（所以输出照常显示）；返回值 0 表示退出码为 0（成功）。
- **为什么现代推荐 subprocess**：`os.system` 把命令交给 shell 解析——一旦命令字符串含空格/特殊字符/用户输入，就有**注入与转义**风险；`subprocess.run` 支持参数列表传递（不经 shell）、超时、捕获输出、错误检查，是 `os.system` 的现代替代。
- **安全告诫的分量**：`os.system('rm -rf /')`（Unix 删文件）这类命令一旦执行就不可挽回。**永远不要**用这些工具执行未经检查的字符串——尤其是来自用户输入或网络的内容。
- **生活类比**：`os.system` 像"按下遥控器让机器人替你去敲键盘"——方便，但机器人**不挑命令**，你说删库它真删。
- **初学者误区**：①把 `os.system` 当"运行 Python 代码"的常规手段——它运行的是**系统命令**，不是 Python 语句；②以为返回值是输出内容——它是退出码；③在 Windows 上把 Unix 命令（如 `ls`）传给它。

### 代码分析

```python
import os                     # 导入 os 模块
os.system('python3 script1.py')  # 让系统 shell 执行这条命令，返回退出码 0
os.popen('python3 script1.py')   # 类似 system，但返回文件对象，可读输出
import subprocess
subprocess.run(['python3', 'script1.py'], capture_output=True, text=True)  # 现代方式
```

解释器如何处理：
1. `os.system(...)`：CPython 调用 C 库的 `system()` → 操作系统 fork 一个子进程，用 `sh -c "python3 script1.py"` 执行 → 子进程运行完，父进程拿到退出状态码（0 = 成功）。
2. `os.popen(...)`：也是启动子进程，但把子进程的 stdout 接回一个管道，包装成 Python 文件对象——你可以 `.read()` 读出全部输出。
3. `subprocess.run([...])`：直接 exec 程序（不经过 shell 解析，所以参数用列表，避免转义问题）；`capture_output=True` 捕获输出；返回 CompletedProcess 对象。
4. **安全设计思想**：任何"运行外部命令"的 API 都是潜在后门——Python 文档反复强调这一点，开发者必须自己守好"什么命令可以跑"的边界。

### 3.15.1 答案（Answers）

### 英文原文

> 1. A Python interactive session can be started by typing a Python command line in your system's console window. Type **py** on Windows and **python3** everywhere else, and type it into a **Command Prompt** or **PowerShell** window on Windows, **Terminal** on macOS and Linux, and the **Termux** app on Android. Another alternative is to launch **IDLE**, as its main Shell window is an interactive session.
>
> Other IDEs, smartphone apps, and browser-based systems may offer REPLs in more unique ways.

> 2. You type system command lines in the same interface used to launch an interactive session by command line. This is whatever your platform provides as a system console: again, **Command Prompt** or **PowerShell** on Windows, **Terminal** on macOS and Linux, **Termux** on Android, or other.
>
> You type this at the system's prompt shown as **$** in this book, not at the Python interactive interpreter's **>>>** prompt used to enter Python code—be careful not to confuse these prompts, because Python and the system shell are different systems.

> 3. Code in a script (really, module) file can be run with system command lines, file icon clicks, imports and reloads, the **exec** built-in function, **os** module tools, and IDE GUI devices such as IDLE's **Run → Run Module** menu option. Some platforms support more specialized launching techniques, like drag and drop on macOS, app UIs on smartphones, and web notebooks.
>
> In addition, some text editors have unique ways to run Python code, some Python programs are provided and run as standalone executables, and some systems use Python code in embedded mode. Though in its early days, code may also be run in web browsers with a Python port to WebAssembly like Pyodide.

> 4. Scripts that print and then exit cause the output window to disappear almost immediately, before you can view the output. **input()** can pause before exit so the output window stays open, but error messages generated by your script's code also appear in that window and can blank it before you can examine it. Hence, system command lines and IDEs are your best bet for most development.

> 5. Python imports (i.e., loads) a module **only once** per process, by default. If you've changed your module's source code and want to run the new version in the same process, you'll need to reload it. You must import a module at least once before you can reload it. Reloading is far less common than importing in practice—a more typical solution to "new code" needs is to restart the process or use an IDE/command line.

> 6. Within the text edit window that holds the script you wish to run, select the window's **Run → Run Module** menu option. This runs the window's source code as a top-level script file in IDLE, and displays its output back in the interactive Python "Shell" window.

> 7. Each module file is automatically a **namespace**—that is, a package of variables reflecting the assignments made at the top level of the file. Each of the module's variables is an **attribute** of the module, accessed by "**.**" qualification or **from** name copies. The namespace concept is what makes module code reusable and keeps program code organized.

### 中文翻译

> 1. 可以通过在系统控制台窗口里输入一条 Python 命令行来启动 Python 交互式会话：Windows 上输 **py**，其它地方输 **python3**，并把命令输入到 Windows 的**命令提示符**或 **PowerShell** 窗口、macOS 和 Linux 的**终端（Terminal）**、Android 的 **Termux** 应用里。另一个替代方案是启动 **IDLE**，因为它的主 Shell 窗口本身就是一个交互式会话。其它 IDE、智能手机应用和基于浏览器的系统可能以更独特的方式提供 REPL。

> 2. 系统命令行输入的地方与"用命令行启动交互式会话"的界面相同——即你的平台提供的系统控制台：Windows 的**命令提示符**或 **PowerShell**、macOS 和 Linux 的**终端**、Android 的 **Termux**，等等。你要在本书中以 **$** 表示的系统提示符处输入，而不是在 Python 交互式解释器输入 Python 代码所用的 **>>>** 提示符处——务必小心不要把这两种提示符搞混，因为 Python 和系统 shell 是两个不同的系统。

> 3. 脚本（准确说是模块）文件里的代码可以通过系统命令行、点击文件图标、import 与 reload、**exec** 内建函数、**os** 模块工具、以及 IDLE 的 **运行 → 运行模块**（Run → Run Module）等 IDE GUI 选项来运行。更多例子还包括 macOS 的拖放、智能手机的 App UI、网页笔记本等。此外，一些编辑器能一键运行当前文件，有些 Python 程序以独立的可执行文件形式分发运行，还有些系统以嵌入（embedded）方式运行 Python。另外，用 Pyodide 这类把 Python 移植到 WebAssembly 的方案，代码目前也能在浏览器里运行。

> 4. 只打印然后退出的脚本，会让控制台窗口在你能查看输出之前就几乎立刻消失。**input()** 可以让窗口在退出前暂停、保持可见，但脚本生成的**错误消息**也会出现在那个窗口里，而且这些错误信息可能还没等你看到就消失了。因此对大多数开发来说，系统命令行、IDE 才是更稳妥的选择。

> 5. 默认情况下，Python 在每个进程里**只**导入（即加载）一个模块**一次**。如果你改了模块源码，又想在同一个进程里运行新版本，就必须 reload 它。至少成功 import（或 from）一次后你才能 reload。实践中 reload 远不如 import 常用——更常见的"换新代码"做法是重启进程，或直接使用 IDLE/命令行重新运行。

> 6. 在保存了你想要运行的文件的文本编辑窗口里，选择窗口菜单的**运行 → 运行模块（Run → Run Module）**。这个命令会把窗口里的源代码作为顶层脚本文件在 IDLE 中运行，并把输出显示在同一个交互式 Python "Shell" 窗口里。

> 7. 每个模块文件自动就是一个**命名空间（namespace）**——即反映文件顶层赋值的一个变量包。模块的每个变量都是模块的一个**属性（attribute）**，可通过"**.**" 点号限定或 **from** 名字复制来访问。命名空间这个概念保证模块组织有序且程序各部分能协调一致。

### 深度理解

- **答案 1**：核心信息是"命令因平台而异"——`py`（Windows launcher）／`python3`（其它平台）；同样重要的还有"控制台也要对应平台"（Command Prompt/Terminal/Termux）。
- **答案 2**：重新强调**两套提示符不能混**：`$` 是系统 shell，`>>>` 是 Python——这是新手事故第一高发地。
- **答案 3**：这道题的考点是"启动方式多态"——命令行、图标、导入、exec、os 工具、IDE、浏览器全能跑，答案只要求 4 种以上，背不全也不要紧，掌握"导入=执行"这一主线即可。
- **答案 4**：呼应 3.10.1——闪退的本质是"输出窗口生命周期"问题，`input()` 只能救输出、救不了闪退的错误消息。

- **答案 6**：IDLE 的标准流程 = 编辑窗口里 `Run → Run Module`，对应 3.10.2 的讲解。
- **答案 7**：三词缝合——**模块=命名空间，命名空间里的名字=属性**；访问方式两种（`.点号` 或 `from` 复制）。这是 Part V 的地基。

## 3.17 侧边栏：调试 Python 代码（Debugging Python Code）

### 英文原文

> Naturally, none of this book's readers ever have bugs in their code (insert smiley here), but for those less fortunate friends of yours who may, here's a quick review of the strategies commonly used by real-world Python programmers to debug errors in their code.
>
> The first two may be all you'll need early in the learning process, but others may grow important when you start writing larger scripts, and all are useful to review now before you start coding in earnest in the next chapter—and making the mistakes that are inevitable in programming:

> **Do nothing.** This might read as odd, but when you make a mistake in Python, you get a useful and readable error message. The message pinpoints the location of the error in your code by file and line numbers and often offers suggestions about how to fix it. And if Python is new to you, that may be all you need—read the error and fix it.

> **Insert print statements.** The most common debugging method in Python is to add temporary print statements at strategic places in your code and run it again, printing out the values of variables and other state at the points you're curious about. Because Python code runs immediately after changes, this is usually the fastest way to get a read on what's happening.

> **Use pdb.** Python also ships with a debugger on a module named `pdb`, the Python debugger. Like the debuggers in IDEs, pdb lets you step through your code line by line, examine variable values, and so forth. You can launch it with `python3 -m pdb script.py`, or set `breakpoint()` in your code to open it right at that spot.

> **Insert calls to the logging module.** If you also need permanent records of your program's progress, the `logging` module can route informational messages to files, syslog, and other places, with levels of severity including `DEBUG`, `INFO`, `WARNING`, and `ERROR`.

> **Use GUI debuggers.** IDE GUIs such as IDLE include debuggers that let you step through code visually, set breakpoints with a click, and watch variable values, all without the command line. This can be easier for beginners than pdb.

> **Use the `–i` command-line flag.** Short of adding prints or running a debugger, you can still get more info on errors: pass the **-i** flag to the interpreter when running a script, e.g., `python -i title.py`, to drop into the interactive prompt after the script completes, where you can inspect final variable values and continue exploring.

> **Record to the `logging` facility.** This is not just print statements, but Python's library-managed logging with tools for message routing, level filtering, formatting, and more that can be very useful in larger programs.

> Perhaps the most important thing to know about debugging in Python is that errors are detected and reported, not ignored. When you make a mistake, Python runs an **error handler** that prints a useful error message. This differs from some other languages, where you might only get a stack trace or nothing at all. Use this to your advantage—the error is your friend.

### 中文翻译

> 当然，本书的读者都从不在代码里出 Bug（此处插入笑脸表情）。但考虑你那些没那么走运的朋友，下面快速盘点一下真实世界 Python 程序员常用的调试策略。学习初期，前两个可能就够你用了；等你开始写较大脚本时其它策略会变得重要。它们现在都值得过一遍——免得你下一章开始认真写代码时，做出编程中难免会犯的错误：

> **什么都不做。**这听起来奇怪，但：当你在 Python 里犯错时，得到的是一个既有用又可读的错误消息，它通过文件名和行号精准定位代码里的错误位置，有时还会给出建议。如果错误足够明白，这可能就是你需要的一切——读错误，修代码。

> **插 print 语句。** Python 程序员最常用的调试方法就是插入 print 语句：在关注的代码处纷纷打印出变量值，然后再跑一次。因为 Python 改了代码后立刻就能运行，这通常是最快获得"现场情报"的方法。

> **用 pdb。** Python 自带一个命令行调试器，模块叫 `pdb`。它和 IDE 里的调试器原理类似：你可以单步执行代码、查看变量值等等。启动方式是 `python -m pdb 文件.py`，或在代码里写了 `breakpoint()` 的地方恰好在那一行进入调试器。

> **用 logging 模块。** 如果你还需要程序运行过程的持久记录，`logging` 模块能把信息类消息路由到文件、syslog 等处，并有轻重级别（`DEBUG`、`INFO`、`WARNING`、`ERROR`）。

> **用 GUI 调试器。** IDLE 这样的 IDE GUI 带有调试器，可以可视化地单步通过代码、单击设置断点、观察变量值——对初学者比 pdb 容易上手。

> **用 `-i` 命令行开关。** 不加 print 也不跑调试器，你仍能窥探错误后的状态：运行脚本时加 `-i` 参数（如 `python -i title.py`），脚本运行结束或报错后，Python 会交互式地停在 `>>>` 提示符处——在那里你可以查看最后的变量值、继续探索。

> **把一切都记录进日志（相关于 logging）。** 我们要鉴别一下：print 调试是即时的手工侦察，logging 是"制度化"的运行时记录——logging 库提供的分级（级别）、路由、格式和数据完整性让它在生产级、大数据程序里更越好。

> **关于 Python 调试最重要的一句话**：错误是被**报告**出来，而不是被悄悄吞掉。犯错时，Python 会运行一个异常处理器，打印有用的错误信息。这和某些会在错误时沉默的语言对比鲜明——善用它：**错误消息是你的朋友**。

### 深度理解

- **核心概念**：调试第一公理——**Python 报错是"报告式"的，是对你友好**。错误消息带文件名、行号、异常类型和描述，还能给出修正建议。把它当朋友而不是敌人。
- **策略排序（学习曲线从低到高）**：do nothing（读错）→ print（快而糙）→ logging（正式化）→ pdb（命令行单步）→ IDE GUI 调试器（可视化）→ `-i`（事后现场）→ try/except（主动捕获，Part VII）。初学用前两个就够，生产环境用 logging + 调试器。
- **pdb 与 breakpoint() 的底层**：`python -m pdb script.py` 相当于"把调试器接在解释器上"；代码里的 `breakpoint()` 则在你指定的位置召唤调试器。Python 3.7+ 的 `breakpoint()` 是 `pdb.set_trace()` 的现代语法。
- **logging 为什么比 print 高级**：print 只能输出到 console，项目发布后你没法"人肉盯屏"；logging 支持级（DEBUG/INFO/WARNING/ERROR）、路由、格式化、持久化——是"管理输出"的工程方案。
- **`-i` 的现实意义**：`python -i script.py` 跑完脚本不退出，直接进入 REPL——你可以打印最终变量值、甚至继续执行代码。这是"事后现场勘查"的利器，比一次次加 print 快。
- **生活类比**：报错如山上的"烟雾报警器"——它会告诉你位置（哪一行）、火的类型（异常类型），还可能提示你"是不是忘了关灶台"（did-you-mean 建议）。你要做的是读懂，然后灭火。
- **初学者误区**：①以为报错说明"我写的东西没救"——恰恰相反，Python 的错误消息是给你设计最贴心的地方；②只盯着最后一行看——要**自下向上**读 traceback，最顶层才是异常真正源头；③遇到错误就慌着删代码——先读错误、再打印、再断点，一步一步来。

# 本章总结

## 技术拓展（Technical Expansion）

### 实际应用

- **开发环境矩阵**：本章的全部内容就是一份"环境排障手册"——现实中 90% 的 Python 新手卡在的不是语法，而是：`python` 不在 PATH、在 `>>>` 里输 shell 命令、脚本双击后窗口闪退、import 找不到同目录文件。把这些启动技术练熟，等于修好了"环境-代码"之间的所有接口。
- **Python 的"通用启动协议"**：无论 IDE、Jupyter、Pyodide 还是嵌入式 C 程序，底层都是同一件事——**把源码交给解释器执行**。因此你只需要掌握命令行（显式、可移植、可脚本化），任何新出现的 UI 都能秒懂。
- **工程实践要点**：
  - 用 `py -m script.py` 或 IDE 运行脚本，避免双击闪退。
  - 项目用"按章节/按模块"的目录组织，`import` 零配置可用。
  - 程序内启动子进程优先用 `subprocess.run`，而不是 `os.system`。
  - 生产环境调试用 `logging`，临时排查用 print + `-i`，深入定位用 `pdb`/IDE 断点。

### 与 Java/C++ 的对比

| 维度 | Python | Java | C/C++ |
|---|---|---|---|
| 启动方式 | REPL、命令行、IDE、图标、import、exec、App、Web……百花齐放 | 需先 `javac` 编译出 `.class`，再 `java` 启动 JVM | 需先 `gcc` 编译链接出二进制，再执行 |
| 交互式运行 | 原生支持（REPL 即语言的一部分） | 需 JShell（Java 9+）等附属工具 | 无原生 REPL（可用 CINT/ROOT 等第三方） |
| 编译步骤 | 通常无（字节码在内存/`__pycache__` 中） | 必选（编译+打包+JVM） | 必选（编译+链接） |
| 模块/导入 | `.py` 文件天然是模块，import 即运行 | package/import 需类路径（classpath）配置 | 头文件+链接器，模块化较繁琐 |
| 学习曲线 | 低（入门章就能跑起来） | 中（环境+语法都要学） | 高（内存、指针、编译链） |
| 程序内运行代码 | `exec`/`eval`/`importlib` 原生支持 | 反射（Reflection）较繁琐 | 几乎没有动态执行能力 |

### Python 发展历史背景

- **`py` 启动器**：Windows 上的 `py.exe` 是 2011 年（PEP 397）随 Python 3.3 引入的，目的是解决多版本共存问题——同一台机器可以装 2.x 和 3.x，`py -3` 选择版本。
- **reload 的三次变身**：内置函数（早期）→ `imp` 模块（Python 2.x/3.0）→ `importlib.reload`（3.4，PEP 451 后）——`imp` 在 3.12 中被正式移除。
- **IDLE 的历史**：由 Guido van Rossum 本人早期参与设计，随 CPython 分发的"官方入门 IDE"，用 tkinter 写成——它证明了"Python 写 GUI"这件事本身可行。
- **WebAssembly 时代**：2022 年 CPython 官方仓库开始支持 Wasm 构建；Pyodide 从 2019 年起持续演进——"浏览器里跑 Python"从实验变成了可用的现实。
- **AOT 编译的尝试**：Nuitka（2015 年起）和 Shed Skin 走的是"Python 到 C 再到机器码"路线，说明 Python 社区从未停止对性能的追求。

### 高级开发者知识

- **sys.path 与模块搜索机制**：`import` 的搜索顺序 = 当前目录（脚本目录）→ `PYTHONPATH` → 标准库 → site-packages。理解它，才能诊断"import 不到"的所有问题。
- **`__pycache__` 与字节码缓存**：`.pyc` 文件的命名含 Python 版本和哈希（如 `script1.cpython-312.pyc`），解释器靠它判断缓存是否失效。
- **命名空间与作用域**：模块 = 命名空间 = `__dict__`；`from ... import` 是复制、`import ...` 是绑定——这个区别在大型项目里决定"改一处是否生效"。
- **子进程与 shell 注入**：`os.system` 把字符串交给 shell 解析，存在注入风险；`subprocess.run([...])` 传参列表则无此问题——安全编程的分水岭。
- **`-i`、`breakpoint()`、PYTHONBREAKPOINT**：现代 Python 调试三件套，配合 `PYTHONBREAKPOINT` 环境变量可以把 `breakpoint()` 重定向到任何调试器（如 `pudb`、`debugpy`）。
