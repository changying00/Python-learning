- **核心概念**：异常处理的四大语句——`try`（捕捉）、`raise`（主动引发）、`assert`（条件引发）、`with`（自动化进入/退出动作）。前 33 章里你可能已经零散见过它们，本章把它们全部拼成完整拼图。

## 34.2 The try Statement（try 语句）

### 英文原文

> First up, the `try` statement is how your code catches exceptions. In short, if an exception occurs while running this statement's main block, the program jumps back to run one of the statement's handlers and continues from there. Its handlers may be specified by `except`, `else`, `finally`, and `except*` clauses nested in the `try`, and separate rules apply to these clauses' syntax, and their valid combinations.
>
> This is a simple model on the surface, but the `try` statement's handler clauses have disjoint purposes, and its rules for valid combinations mean that it comes in distinct flavors. Because of this, we'll approach this subject by exploring the `try`'s common roles in isolation first and putting their pieces together later as a combined statement. This parallels the fact that `try` really *was* separate statements in Python's dim past, but our focus here is on its unified present.
>
> Although technically part of the `try`, we'll also defer the `except*` clause until the next chapter, partly because it encroaches on that chapter's exception-object topic, but mostly because this is a tool that complicates the `try` story substantially for an extension that's rarely useful in practice. Our priority here is learning the fundamentals.

### 中文翻译

> 首先，`try` 语句就是你的代码**捕捉异常**的方式。简而言之，如果在运行该语句的主代码块（main block）时发生异常，程序会跳回来运行该语句的某个处理器（handler），然后从那里继续。它的处理器可以由嵌套在 `try` 里的 `except`、`else`、`finally` 和 `except*` 子句（clause）指定，而这些子句的语法及其有效组合各自有不同的规则。
>
> 这个模型表面上很简单，但 `try` 语句的各处理器子句目的各不相同，而"哪些组合合法"的规则意味着它有几种不同的形态（flavor）。因此，我们将分而治之：先单独探索 `try` 的各种常见角色，之后再把它们拼装成一个组合语句。这也与历史吻合——在 Python 遥远的过去，`try` 确实是**彼此独立**的语句，不过我们这里关注的是它今天统一的形态。
>
> 虽然 `except*` 子句技术上讲属于 `try` 的一部分，但我们还是把它推迟到下一章再讲：部分原因是它侵占了那一章"异常对象"的主题，但主要原因在于，这是一个会显著复杂化 `try` 故事的扩展，而它在实践中很少派上用场。我们的优先任务是学好基础。

### 深度理解

- **核心概念**：`try` 是"异常的中转站"——主块（main block）是你要守护的代码，各子句是守护方案：`except` 拦截、`else` 兜底无异常情形、`finally` 保证清理、`except*` 处理异常组。
- **底层实现**：解释器执行 `try` 时，会记录当前的程序上下文（帧信息、异常处理入口），一旦块内抛出异常，就沿"最近的异常处理器"链查找匹配项；这本质上是解释器内置的一张"跳转表"。
- **设计原因**：把异常处理写成语句而非函数调用，是因为异常发生时**栈上所有中间帧都要展开（unwind）**，语句式语法让编译器可以精确地在每个栈帧上挂接清理和匹配逻辑。
- **实际问题**：一套统一的 `try` 语法取代了历史上"`try/finally` 与 `try/except` 是两条独立语句"的旧格局，让代码更简洁——这也是本书反复强调"统一现形"（unified present）的原因。
- **初学者误区**：误以为 `else`、`finally` 只能二选一或顺序随意——实际上它们有严格的组合规则（`try -> except -> else -> finally`），违反会在运行前被语法检查（syntax error）拦下。

## 34.3 try Statement Clauses（try 语句的子句）

### 英文原文

> When you write a `try` statement, a variety of clauses can appear after and below the `try` header. Table 34-1 summarizes all the possible forms as both reference and preview. We've already seen that `except` clauses catch exceptions and `finally` clauses run on the way out. New here, `else` clauses run if no exceptions are encountered, and `except*` clauses process exception groups and support all `except` forms except the empty.
>
> Formally, a `try` must use at least one of the clauses in Table 34-1. There may be any number of `except` clauses, but you can code `else` only if there is at least one `except`, and there can be only one `else` and one `finally`. A `finally` can appear in the same statement as `except` and `else`, with ordering rules given later in this chapter.
>
> **Table 34-1. `try` statement clauses and forms**
>
> | Clause form | Interpretation |
> |---|---|
> | `except:` | Catch all (or all other) exception types |
> | `except name:` | Catch a specific exception only |
> | `except name as var:` | Catch the listed exception and assign its instance |
> | `except (name1, name2):` | Catch any of the exceptions listed in a tuple |
> | `except (name1, name2) as var:` | Catch any listed exception and assign its instance |
> | `else:` | Run if no exceptions are raised in the `try` block |
> | `finally:` | Always perform this block on exit, exception or not |
> | `except* …`（非空 except 形式）| Catch multiple exceptions in a group（Chapter 35）|
>
> We'll explore the `as var` part available in some of Table 34-1's clauses in more detail when we meet the `raise` statement later in this chapter because it provides access to the object raised as an exception via `var`. Before all that, let's get started by examining the more common clauses of Table 34-1 more closely.

### 中文翻译

> 当你编写 `try` 语句时，各种子句可以出现在 `try` 头部之后、下方。表 34-1 汇总了所有可能的形式，既作参考也作预览。我们已经见过 `except` 子句捕捉异常、`finally` 子句在退出时执行。这里的新内容是：`else` 子句在没有遇到异常时执行，`except*` 子句则处理**异常组（exception groups）**，支持除空 `except` 之外的所有 `except` 形式。
>
> 形式上，一个 `try` 必须至少使用表 34-1 中的一个子句。`except` 子句可以有任意多个，但只有**至少有一个 `except`** 时你才能编写 `else`，而且 `else` 和 `finally` 各只能有一个。`finally` 可以与 `except`、`else` 出现在同一条语句中，其顺序规则将在本章后面给出。
>
> **表 34-1. `try` 语句的子句与形式**
>
> | 子句形式 | 含义 |
> |---|---|
> | `except:` | 捕捉所有（或所有其他）异常类型 |
> | `except name:` | 只捕捉特定异常 |
> | `except name as var:` | 捕捉列出的异常，并把其实例赋给 `var` |
> | `except (name1, name2):` | 捕捉元组中列出的任一异常 |
> | `except (name1, name2) as var:` | 捕捉任一列出的异常，并把其实例赋给 `var` |
> | `else:` | 当 `try` 块中没有引发异常时运行 |
> | `finally:` | 退出时总是执行此块，无论有无异常 |
> | `except* …`（非空 except 形式）| 在组中捕捉多个异常（第 35 章）|
>
> 表 34-1 中某些子句里的 `as var` 部分，我们将在本章后面遇到 `raise` 语句时再深入探讨，因为它通过 `var` 提供了对"作为异常被引发的对象"的访问。在那之前，让我们先更仔细地考察表 34-1 中更常见的子句。

### 深度理解

- **核心概念**：一张表看懂 `try` 的"菜单"——空 `except`（全能）、具名 `except`（点菜）、元组 `except`（多选）、`as var`（拿到异常实例）、`else`（无事发生）、`finally`（必然执行）、`except*`（异常组，下章讲）。
- **底层实现**：`except (A, B) as var` 在字节码层面编译为"逐一比较异常类型（isinstance 检查），命中即绑定局部变量"；空 `except` 则是无条件命中，对应一个不检查就跳转的处理器。
- **设计原因**：允许"元组多选 + 同一处理器"是为了消除重复代码——多个异常共享同一个处理逻辑时，不必写多遍相同代码块。
- **实际问题**：形式规则（至少一个子句、`else` 依赖 `except`、只有一个 `else`/`finally`）保证了语句含义无歧义：如果没有 `except`，`else` 就没有"参照系"可言。
- **初学者误区**：把 `except:` 当作"万能药"到处用，或者记不住"`else` 必须搭配 `except`"。另注意 `except*` 是 Python 3.11 才引入的新语法，老项目里看不到它——本书特意把它推迟到下一章，就是为了不让它干扰基础学习。

## 34.4 The except and else Clauses（except 与 else 子句）

### 英文原文

> Syntactically, the `try` is a compound, multipart statement. It starts with a `try` header line, followed by a block of (usually) indented statements, which is followed by clauses that each identify a condition to be handled and give a block of statements to handle it. In its most common form, `try` is coded with one or more `except` clauses and an optional `else` clause at the end. You associate the words `try`, `except`, and `else` by indenting them to the same level (i.e., lining them up vertically), like this:
>
> ```python
> try:
>     statements                          # 先运行这个主动作
> except name1:
>     statements                          # 若 try 块中引发 name1 则运行
> except (name2, name3):
>     statements                          # 若 try 中发生 name2 或 name3 则运行
> except name4 as var:
>     statements                          # 若引发 name4 则运行，并将其赋给 var
> except:
>     statements                          # 为所有其他引发的异常运行
> else:
>     statements                          # 若 try 块中未引发异常则运行
> ```
>
> Semantically, the block under the `try` header in this statement represents the *main action* of the statement—the code you're trying to run, and wrapping in exception handlers. The rest of the statement defines the handlers themselves: `except` clauses give handlers for exceptions raised during the `try` block, and the optional `else` clause gives a handler run if *no* exceptions occur in the `try` block.
>
> Within a `try`, each `except` names exceptions to catch: a *single* exception catches just that exception, a tuple catches *any* exception in the tuple, and an `except` that omits the exception altogether matches *all* (or all *other*) exceptions. Each nonempty `except` can also give a variable name after `as` to be assigned the exception object raised by Python or `raise` statements; again, we'll explore this option ahead.

### 中文翻译

> 从语法上看，`try` 是一个复合的、多部分语句（compound, multipart statement）。它以 `try` 头部行开头，后面跟着一个（通常缩进的）语句块，再后面跟着若干子句——每个子句标识一种需要处理的条件，并给出处理它的语句块。在它最常见的形式中，`try` 编码一个或多个 `except` 子句，以及末尾一个可选的 `else` 子句。你要通过把 `try`、`except`、`else` 这些词缩进到同一层级（也就是在垂直方向上对齐它们）来把它们关联起来，就像这样：
>
> ```python
> try:
>     statements                          # 先运行这个主动作
> except name1:
>     statements                          # 若 try 块中引发 name1 则运行
> except (name2, name3):
>     statements                          # 若 try 中发生 name2 或 name3 则运行
> except name4 as var:
>     statements                          # 若引发 name4 则运行，并将其赋给 var
> except:
>     statements                          # 为所有其他引发的异常运行
> else:
>     statements                          # 若 try 块中未引发异常则运行
> ```
>
> 从语义上讲，本语句中 `try` 头部之下的代码块代表语句的**主动作（main action）**——也就是你试图运行、并用异常处理器包裹起来的代码。语句的其余部分定义处理器本身：`except` 子句为 `try` 块运行期间引发的异常提供处理器，而可选的 `else` 子句则提供一个"如果 `try` 块中**没有**异常发生"时运行的处理器。
>
> 在一个 `try` 中，每个 `except` 指明要捕捉的异常：一个**单个**异常只捕捉那一个异常；元组捕捉元组中的**任一**异常；而完全省略异常的 `except` 匹配**所有**（或所有**其他**）异常。每个非空 `except` 还可以在 `as` 后面给一个变量名，用于接收 Python 或 `raise` 语句引发的异常对象；再说一次，这个选项我们稍后再深入。

### 深度理解

- **核心概念**：`try` 的主块 = "被守护的代码"；`except` = 处理清单（自上而下匹配）；`else` = "平安无事"时的成功处理分支。缩进不是装饰，而是**归属关系的语法**。
- **底层实现**：CPython 在编译含 `try` 的代码块时，会在字节码里插入 `SETUP_EXCEPT`/`SETUP_FINALLY` 等栈帧指令，异常发生时解释器调用 `PyErr_ExceptionMatches` 逐条做子类匹配；命中后执行处理器代码块。
- **设计原因**：用"从上到下、逐一匹配"的线性规则，而不是像 C++/Java 那样只按类型精确匹配，是因为 Python 的异常是**类层次结构**——一个 `except Exception` 要能接住所有子类，线性扫描 + isinstance 语义最自然。
- **实际问题**：如果你需要"任何失败都要记录日志、但只有特定错误才恢复"，这一节的结构就是模板：特定 `except` 放前面，通用兜底放最后，`else` 放成功分支。
- **初学者误区**：以为 `except` 匹配是"精确类型相等"——其实是"isinstance 关系"（子类也能匹配父类）；还容易忘记 `except` 一旦命中就不再继续往下试，所以**顺序很重要**：具体异常必须写在通用异常前面。

### 代码分析

```python
try:
    statements                          # 先运行这个主动作
except name1:
    statements                          # 若 try 块中引发 name1 则运行
except (name2, name3):
    statements                          # 若 try 中发生 name2 或 name3 则运行
except name4 as var:
    statements                          # 若引发 name4 则运行，并将其赋给 var
except:
    statements                          # 为所有其他引发的异常运行
else:
    statements                          # 若 try 块中未引发异常则运行
```

- **解释器如何处理**：解释器先完整执行 `try` 块；若中途抛出异常，它**立即**中断当前执行，取出异常的类对象，与第一个 `except` 后面的名字做 isinstance 匹配——不匹配就试下一个，匹配就执行对应处理器（有 `as var` 则先绑定异常实例）。`else` 块只在 `try` 块**正常跑完**（没有异常）后才执行。注意：`else` 不会因为"异常被捕捉过"而执行——"捕捉过"意味着有异常，属于 `except` 的功劳。
- **设计思想**：这个骨架展示了"具体 → 通用"的匹配次序：越精确的处理器越靠前，`except:` 兜底永远在最后。`as var` 让处理器能"拿到证据"（异常实例），这是后续调试与重抛（reraise）的入口。

## 34.4.1 How try Statements Work（try 语句如何运行）

### 英文原文

> Operationally, here's how `try` statements are run. When a `try` statement is entered, Python records the current program context so it can return to it if an exception occurs. The statements nested under the `try` header are run first. What happens next depends on whether an exception is raised while the `try` block's statements are running, and whether a raised exception matches any of those that the `try` is watching for:
>
> **Exception and match** — If an exception occurs while the `try` block's statements are running, and the exception *matches* one that the statement names, Python jumps back to the `try` and runs the statements under its topmost `except` clause that matches the raised exception, after assigning the raised exception object to the variable named by `as` in the clause (if present). After the `except` block runs, control resumes below the entire `try` statement. If the `except` block itself raises another exception, the propagation process is started anew from this point in the code.
>
> **Exception and no match** — If an exception occurs while the `try` block's statements are running, but the exception *does not* match one that the statement names, the exception is propagated up to the next most recently entered `try` statement that matches the exception; if no such matching `try` statement can be found and the search reaches the top level of the program, Python prints a default error message and terminates the program (unless it's the REPL).
>
> **No exception** — If an exception does *not* occur while the `try` block's statements are running, Python runs the statements under the `else` clause (if present), and control then resumes below the entire `try` statement. If the `else` block itself raises another exception, it kicks off the propagation process again.
>
> In sum, `except` clauses catch any matching exceptions that happen while the `try` block is running, and the `else` clause runs only if no exceptions happen while the `try` block runs. Exceptions raised are *matched* to exceptions named in `except` clauses by *class* relationships we'll explore both ahead and in the next chapter (brief: a subclass matches its superclass), and the *empty* `except` clause with no exception name matches any exception.
>
> In effect, `except` clauses are *focused* exception handlers—they catch exceptions that occur only within the statements in the associated `try` block. However, as the `try` block's statements can call functions coded elsewhere in a program, the source of an exception may very well be outside the code of the `try` statement itself.
>
> In fact, a `try` block might invoke arbitrarily large amounts of program code—including code that may have `try` statements of its own, which will be searched first when exceptions occur. In other words, because `try` statements can nest at runtime, where an exception goes depends on the code run before it, a phenomenon we'll explore in Chapter 36.
>
> If a `finally` clause is added to a `try`, its code block is run for all three of the cases listed previously, as you'll see ahead. First, though, let's take a look at some common variations of exception-catching clauses.

### 中文翻译

> 从运行机制上讲，`try` 语句是这样运行的。当进入一条 `try` 语句时，Python 会记录当前的程序上下文（context），以便在发生异常时能返回此处。`try` 头部下面嵌套的语句先运行。接下来发生什么，取决于 `try` 块的语句运行期间是否引发了异常，以及引发的异常是否与 `try` 正在监视的某个异常匹配：
>
> **异常且匹配** —— 如果 `try` 块的语句运行期间发生异常，且异常**匹配**语句点名的某个异常，Python 会跳回 `try`，先按 `as`（若有）把引发的异常对象赋给子句中的变量，然后运行与引发的异常匹配的**最靠上**（topmost）那个 `except` 子句下的语句。`except` 块运行完毕后，控制流在整条 `try` 语句**下方**继续。如果 `except` 块自己又引发了另一个异常，传播过程将从代码中的这一点重新开始。
>
> **异常但不匹配** —— 如果 `try` 块的语句运行期间发生异常，但异常**不匹配**语句点名的任何一个，该异常就被传播（propagate）到下一个"最近进入的、且匹配该异常"的 `try` 语句；如果找不到这样的 `try` 语句、搜索到达程序顶层，Python 会打印一条默认错误信息并终止程序（除非是在 REPL 里）。
>
> **无异常** —— 如果 `try` 块的语句运行期间**没有**发生异常，Python 会运行 `else` 子句（若有）下的语句，然后控制流在整条 `try` 语句下方继续。如果 `else` 块自己引发了另一个异常，它会再次启动传播过程。
>
> 总而言之：`except` 子句捕捉 `try` 块运行期间发生的任何匹配异常；`else` 子句只在 `try` 块运行期间没有异常时运行。被引发的异常是**按类关系**与 `except` 子句点名的异常进行**匹配**的——我们稍后和下一章都会深入（简短版：子类匹配它的超类）；而没有任何异常名的**空** `except` 子句匹配任何异常。
>
> 实际上，`except` 子句是**聚焦的**（focused）异常处理器——它们只捕捉关联 `try` 块中语句内部发生的异常。不过，由于 `try` 块的语句可以调用程序中别处编写的函数，异常的来源很可能在 `try` 语句自身的代码之外。
>
> 事实上，一个 `try` 块可能调用任意大量的程序代码——包括那些自身带有 `try` 语句的代码，这些代码里的 `try` 会在异常发生时**优先被搜索**。换句话说，由于 `try` 语句可以在运行时嵌套，异常去哪里取决于它之前运行的代码——这一现象我们将在第 36 章探索。
>
> 如果给 `try` 加上 `finally` 子句，它的代码块对前面列出的三种情况都会运行，你稍后会看到。不过首先，让我们看看捕捉异常的子句的一些常见变体。

### 深度理解

- **核心概念**：三条运行规则——匹配则跳回执行 `except` 并从 `try` 之后继续；不匹配则向上传播（交给外层 `try` 或顶层默认处理）；无异常则执行 `else`。加上"处理器自己出错会重启传播"，这就是异常的全部动力学。
- **底层实现**：CPython 解释器维护一条"异常处理器链"。每个 `try` 块进入时把处理器信息压栈，异常发生时从链顶（最近进入的 `try`）开始搜索；找不到匹配就一直弹栈，直到顶层由 `sys.excepthook` 打印 traceback 并退出。
- **设计原因**："传播 + 最近优先"的设计让异常能自动穿过任意深的调用栈——`crashware.py` 里三层函数调用，异常却能一路冒到顶层，这正是"异常隔离业务代码"价值的体现。
- **实际问题**：理解这条规则，你就明白为什么"顶层脚本"不需要处理异常（报错即退出往往是对的），而"长期运行的服务器"必须在每次请求边界设 `try`（否则一个请求的异常会杀死整个进程）。
- **初学者误区**：误以为"`try` 块内函数的异常不会冒出来"——恰恰相反，异常**会**穿透所有中间函数，除非沿途某处有匹配的 `except`。还有人不明白"异常被捕捉后就是"死的"（dead）"：一旦 `except` 处理完，异常就消失了，控制流绝不会回到出错点。

## 34.4.2 Catching Many Exceptions with a Tuple（用元组捕捉多个异常）

### 英文原文

> Per the fourth and fifth entries in Table 34-1, `except` clauses that list *many* exceptions in a parenthesized tuple catch *any* of the listed exceptions. Because Python looks for a match within a given `try` by inspecting the `except` clauses from *top to bottom*, the tuple version has the same effect as listing each exception in its own `except` clause, but you have to code the common statement body associated with each only once.
>
> Here's a partial example of multiple `except` clauses at work, which demos just how specific your handlers can be:
>
> ```python
> try:
>     ...
> except NameError:
>     ...
> except IndexError:
>     ...
> except (AttributeError, TypeError, SyntaxError):
>     ...
> ```
>
> If an exception is raised while this `try` block is running, Python returns to the `try` and searches for the first `except` that names the exception raised. It inspects clauses from top to bottom—and left to right along the way—and runs the statements under the first clause that matches. If none match, the exception is propagated past this `try`.
>
> Note that *parentheses* are required around the tuple in the "any" form, and using an `as` in this form lets you check which exception occurred when you listed many:
>
> ```python
> try:
>     ...
> except (AttributeError, TypeError, SyntaxError) as What:
>     ...
>     # 然后检查 What
> ```
>
> To learn more about both `as`, as well as what happens when no `except` matches, we must move on.

### 中文翻译

> 按表 34-1 的第四、第五项，`except` 子句在带括号的元组（parenthesized tuple）中列出**多个**异常时，会捕捉所列异常中的**任意一个**。由于 Python 在一个 `try` 内查找匹配时是**自上而下**逐个检查 `except` 子句的，元组版本与"把每个异常各写一个 `except` 子句"效果相同，只是你只需把公共的语句体编写一次。
>
> 这里是一个多个 `except` 子句发挥作用的局部示例，它演示了你的处理器可以多么具体：
>
> ```python
> try:
>     ...
> except NameError:
>     ...
> except IndexError:
>     ...
> except (AttributeError, TypeError, SyntaxError):
>     ...
> ```
>
> 如果这个 `try` 块运行期间引发了异常，Python 会回到 `try` 并搜索第一个点名该异常类型的 `except`。它自上而下（沿途还从左到右）检查子句，运行第一个匹配子句下的语句。如果都不匹配，异常就被传播越过这个 `try`。
>
> 注意，"任意一个"形式中元组周围的**圆括号是必需的**；在这种列出多个异常的形式里使用 `as`，可以让你检查究竟是哪一个异常发生了：
>
> ```python
> try:
>     ...
> except (AttributeError, TypeError, SyntaxError) as What:
>     ...
>     # 然后检查 What
> ```
>
> 要了解更多关于 `as` 的细节，以及"没有 `except` 匹配时会发生什么"，我们必须继续往下读。

### 深度理解

- **核心概念**：元组 `except (A, B, C)` 是"一份多买"——三种异常共享同一处理器，等价于三个各自成段的 `except`，但代码只写一份。
- **底层实现**：匹配时解释器从左到右遍历元组中的每个类型做 isinstance 检查——这就是"从左到右"的来源；一旦命中，后面不再检查。
- **设计原因**：同一个错误处理逻辑常常适用于一组相关异常（比如 `(ValueError, TypeError)` 都是"输入不合规"），元组语法避免了复制粘贴处理器体。
- **实际问题**：真实代码里最常见的写法是 `except (ValueError, TypeError) as e:` 处理解析错误；注意元组必须加括号，写成 `except ValueError, TypeError:` 是旧版 Python 2 语法，Python 3 里会变成语法错误。
- **初学者误区**：有人以为元组里的异常会"按顺序逐个尝试处理"——不会，元组只选**一个**命中者，整个处理器只运行一次。另一个坑：圆括号不能省。

### 代码分析

```python
try:
    ...                                        # 可能引发多种异常的代码
except NameError:
    ...                                        # 只处理名字未定义
except IndexError:
    ...                                        # 只处理下标越界
except (AttributeError, TypeError, SyntaxError) as What:
    ...                                        # 三者共享处理器；What 记录实际异常
```

- **解释器如何处理**：异常抛出后，解释器把异常类依次与 `NameError`、`IndexError` 比较；都失败后，再与元组内的 `AttributeError`、`TypeError`、`SyntaxError` **逐个**比较，命中即绑定 `What` 并执行处理器。若三类都不匹配，异常继续向上传播。
- **设计思想**：这个示例刻意展示"具体在前、聚合在后"的层次感。`as What` 相当于给处理器一个"现场证人"——你可以用 `isinstance(What, TypeError)` 之类的判断走更细的分支，而不必拆开写多条 `except`。

## 34.4.3 Catching All Exceptions with Empties and Exception（用空 except 与 Exception 捕捉所有异常）

### 英文原文

> Per the first entry in Table 34-1, `except` clauses that list *no* exception name catch *all* exceptions not previously listed in the `try` statement. That is, if you want to code a general "catchall" handler to be run when no other `except` clause matches the exception raised, an empty `except` does the trick:
>
> ```python
> try:
>     ...
> except NameError:
>     ...                     # 处理 NameError
> except IndexError:
>     ...                     # 处理 IndexError
> except:
>     ...                     # 处理所有其他异常
> else:
>     ...                     # 处理无异常的情况（预览）
> ```
>
> The empty `except` clause is a sort of *wildcard* feature—because it catches everything, adding it to the mix allows your handlers to be as general or specific as you like. In some scenarios, this form may be more convenient than listing all possible exceptions in a `try`—especially when working interactively in a REPL, or writing code that must recover no matter what occurs. For example, the following catches *everything* by not listing anything:
>
> ```python
> try:
>     ...
> except:
>     ...                     # 捕捉所有可能的异常
> ```
>
> That being shown, the empty `except` can also cause problems. It may catch *unexpected* exceptions, and *intercept* events unrelated to your code and required by another handler. For example, even *system exit* calls and Ctrl+C key-combination interrupts in Python work by triggering exceptions, and you usually want these to pass.
>
> Perhaps worse, the empty `except` may also catch genuine *programming mistakes* for which you probably want to see an error message. Otherwise, you may not even know that a bug exists until it's too late to avoid a user's report. We'll revisit this as a gotcha at the end of this part of the book. For now, the standard "use with care" applies.
>
> Python provides an alternative that solves at least one of these problems—catching the built-in `Exception` has almost the same effect as an empty `except`, but won't catch exceptions related to system exits and Ctrl+C:
>
> ```python
> try:
>     ...
> except Exception:
>     ...                     # 捕捉所有可能的异常——但除了退出类
> ```
>
> We'll explore how this form does its magic formally in the next chapter when we study exception classes. In short, it works because exceptions match if they are a *subclass* of one named in an `except` clause, and `Exception` is a superclass of all the exceptions you should generally catch this way. This form has most of the same convenience of the empty `except` without the risk of catching exit events and also allows you to check the exception raised via `as`. While better, though, it also has some of the same risks—it may still mask and silently ignore programming errors.
>
> The opening snippet of this section deliberately listed an `else` clause, to call out that it is *not* a catchall like the empty `except`—an understandable source of confusion for `try` newcomers. The next section dissects the difference.

### 中文翻译

> 按表 34-1 的第一项，**没有**列出任何异常名的 `except` 子句，会捕捉 `try` 语句中此前未列出的**所有**异常。也就是说，如果你想编写一个通用的"捕获一切"（catchall）处理器，在没有任何其他 `except` 子句匹配到所引发异常时运行它，一个空 `except` 就能搞定：
>
> ```python
> try:
>     ...
> except NameError:
>     ...                     # 处理 NameError
> except IndexError:
>     ...                     # 处理 IndexError
> except:
>     ...                     # 处理所有其他异常
> else:
>     ...                     # 处理无异常的情况（预览）
> ```
>
> 空 `except` 子句是一种**通配符（wildcard）**特性——因为它捕捉一切，把它加入组合后，你的处理器想要多通用或多具体都可以。在某些场景下，这种形式比在 `try` 中列出所有可能的异常更方便——尤其在 REPL 中交互式工作时，或者编写"无论发生什么都必须恢复"的代码时。例如，下面这段通过什么都不列来捕捉**一切**：
>
> ```python
> try:
>     ...
> except:
>     ...                     # 捕捉所有可能的异常
> ```
>
> 话虽如此，空 `except` 也可能引发问题。它可能捕捉到**意料之外**的异常，并且**拦截**那些与你的代码无关、却被另一个处理器需要的系统事件。例如，在 Python 中就连**系统退出**（system exit）调用和 Ctrl+C 组合键中断也是靠触发异常来工作的，而你通常希望它们放行通过。
>
> 也许更糟的是，空 `except` 还可能捕捉到真正的**编程错误**——对这种错误你大概是想看到报错信息的。否则，你可能直到"已经来不及避免用户报 bug"时才意识到存在缺陷。我们会在本书这一部分的结尾把这一点作为"陷阱"（gotcha）重新审视。眼下，标准的"慎用"忠告适用。
>
> Python 提供了一个至少能解决其中一个问题的替代方案——捕捉内置的 `Exception` 与空 `except` 效果几乎相同，但**不会**捕捉与系统退出和 Ctrl+C 相关的异常：
>
> ```python
> try:
>     ...
> except Exception:
>     ...                     # 捕捉所有可能的异常——但除了退出类
> ```
>
> 我们将在下一章学习异常类时正式探讨这种形式是如何"施魔法"的。简而言之，它之所以有效，是因为：只要异常是 `except` 子句所点名的某个异常的**子类**，就视为匹配；而 `Exception` 是"你应该用这种方式捕捉"的所有异常的超类。这种形式拥有空 `except` 的大部分便利，却没有捕捉退出事件的风险，而且还能通过 `as` 检查被引发的异常。不过，虽然它更好，它也有一些同样的风险——它仍可能掩盖并静默忽略编程错误。
>
> 本节开头的代码片段故意列出了一个 `else` 子句，是为了指出：它**不是**像空 `except` 那样的全能捕捉器——这是 `try` 新手一个可以理解的困惑来源。下一节将剖析这个区别。

### 深度理解

- **核心概念**：三种"全能"级别——空 `except:`（连 `SystemExit`、`KeyboardInterrupt` 都抓）、`except Exception:`（不抓退出类）、`except (X, Y):`（只抓指定）。通用性越强，风险越大。
- **底层实现**：`BaseException` 是异常体系的总根；`SystemExit`、`KeyboardInterrupt`、`GeneratorExit` 直接继承它，而普通错误（`ZeroDivisionError` 等）都继承 `Exception`。所以 `except Exception` 通过"子类即匹配"的规则天然放过了退出类。
- **设计原因**：把退出与中断设计成异常、但又**不**挂在 `Exception` 名下，是刻意的分层——普通代码的"捕捉一切"不应误吞用户的 Ctrl+C（`KeyboardInterrupt`）或 `sys.exit()`（`SystemExit`），否则程序将无法被用户正常终止。
- **实际问题**：空 `except` 的典型危害是**吞 bug**：代码里有个拼写错误，却被兜底处理器默默吞掉，线上毫无日志，直到用户投诉。这也是为什么 Python 社区流传"空 except 是代码坏味道"的说法。
- **初学者误区**：写 `try: ... except: pass` 试图"压制错误"，结果连 `KeyboardInterrupt` 都被吞，程序按 Ctrl+C 都没反应；或者把 `except Exception` 当成"绝对安全"——它照样会掩盖逻辑 bug。生活类比：空 `except` 像"不管屋里什么声音都关掉警报"——小偷（真 bug）也一起被放过了。

### 代码分析

```python
try:
    ...                                 # 危险区域
except NameError:
    ...                                 # 处理 NameError
except IndexError:
    ...                                 # 处理 IndexError
except:                                 # 兜底：所有其他异常
    ...                                 # 包括 SystemExit / KeyboardInterrupt！
else:
    ...                                 # 无异常分支
```

- **解释器如何处理**：匹配按顺序进行：`NameError` → `IndexError` → 空 `except`（无条件命中）。注意空 `except` 在字节码里对应一个不比较任何类型的处理槽，`SystemExit`（`sys.exit()` 引发）和 `KeyboardInterrupt`（Ctrl+C 引发）也会被它接住——这正是它"危险"的原因。
- **设计思想**：本书这里埋伏了一个教学伏笔：`else` 与空 `except` 外观相似（都以 `:` 结尾），但职责天差地别——`else` 只管"没异常"的分支，绝不拦截任何异常。把两者放在一起展示，就是要你一眼分清"拦截"与"成功"。

## 34.4.4 Catching the No-Exception Case with else（用 else 捕捉"无异常"的情况）

### 英文原文

> All told, `else` can be used in *three* places in Python: in `if` selections, `for` and `while` loops, and `try` exception handlers. In the latter, `else` is run when *no* exception occurs—not for *unmatched* exceptions (that's what the prior section's empty `except` is for). This `else` role may seem different than in `if` and loops, but this context differs.
>
> The need for an `else` clause in `try` is not always obvious to Python beginners. Without it, though, there is no direct way to tell whether the flow of control has proceeded past a `try` statement because no exception was raised, or because an exception occurred and was handled. Either way, we wind up after the `try`:
>
> ```python
> try:
>     ...                     # 运行代码
> except IndexError:
>     ...                     # 处理异常
> # 我们到这里，是因为 try 失败了还是没失败？
> ```
>
> Of course, we could initialize, set, and check a Boolean flag to know what happened, which adds lines of admin code. Much like the way `else` clauses in loops make the exit cause more apparent (for exits sans `break`), the `else` clause provides syntax in `try` that makes the outcome unambiguous with minimal extra code:
>
> ```python
> try:
>     ...                     # 运行代码
> except IndexError:
>     ...                     # 处理异常
> else:
>     ...                     # 没有异常发生
> ```
>
> You can *almost* emulate an `else` clause by moving its code into the `try` block:
>
> ```python
> try:
>     ...                     # 运行代码
>     ...                     # 没有异常发生
> except IndexError:
>     ...                     # 处理异常
> ```
>
> This can lead to incorrect exception classifications, though. If the "no exception occurred" action itself causes an `IndexError`, it will register as a failure of the `try` block and erroneously trigger the exception handler below the `try` (unlikely perhaps, but true). By using an explicit `else` clause instead, you make the logic more obvious and guarantee that `except` handlers will run only for real failures in the code you're wrapping in a `try`, not for failures in the `else` no-exception case's action.

### 中文翻译

> 总而言之，`else` 在 Python 中可以用在**三个**地方：`if` 选择中、`for` 和 `while` 循环中，以及 `try` 异常处理器中。在后一种情况下，`else` 在**没有**异常发生时运行——而不是为**未匹配**的异常运行（那是上一节空 `except` 的职责）。这个 `else` 角色看起来可能与 `if` 和循环中的不同，但这里的环境本来就不同。
>
> 对 Python 初学者来说，`try` 中 `else` 子句的必要性并不总是显而易见。但没有它，就无法直接判断控制流越过 `try` 语句，是因为**没有异常被引发**，还是因为**发生了异常且被处理了**。两种情况我们都会来到 `try` 之后：
>
> ```python
> try:
>     ...                     # 运行代码
> except IndexError:
>     ...                     # 处理异常
> # 我们到这里，是因为 try 失败了还是没失败？
> ```
>
> 当然，我们可以初始化、设置并检查一个布尔标志来知道发生了什么——这就要多写几行管理性代码。正如循环中的 `else` 子句让退出原因更明显（针对**没有** `break` 的退出），`try` 中的 `else` 子句提供了用最少额外代码就让结果毫无歧义的语法：
>
> ```python
> try:
>     ...                     # 运行代码
> except IndexError:
>     ...                     # 处理异常
> else:
>     ...                     # 没有异常发生
> ```
>
> 你**几乎**可以通过把 `else` 的代码挪进 `try` 块来模拟它：
>
> ```python
> try:
>     ...                     # 运行代码
>     ...                     # 没有异常发生
> except IndexError:
>     ...                     # 处理异常
> ```
>
> 但这可能导致**错误的异常归类**。如果"没有异常发生"的动作本身引发了 `IndexError`，它会被登记为 `try` 块的失败，从而错误地触发 `try` 下方的异常处理器（也许不太可能，但确实如此）。改用显式的 `else` 子句，你就让逻辑更清晰，并保证 `except` 处理器只为 `try` 所包裹代码中的**真正失败**运行，而不会为 `else`"无异常"分支的动作里的失败运行。

### 深度理解

- **核心概念**：`else` 的使命是消除歧义——"走到 `try` 之后"这件事本身说明不了任何事，`else` 明确告诉你"成功路径在此"。
- **底层实现**：字节码层面，`else` 块与 `except` 块的跳转目标不同：异常处理器只在异常发生时进入；`else` 在 `try` 块正常结束（`END_FINALLY` 正常路径）时进入，两者互斥且不可能同时执行。
- **设计原因**：不用标志变量的原因是"管理性代码"（admin code）会增加出错面——每多一行状态代码就多一个出 bug 的机会。语法本身表达意图，比程序员自己维护标志更可靠。
- **实际问题**：经典场景是"读文件 → 处理数据"：`except` 处理"读不到"的错误，`else` 里做只有"读到数据"才该做的事（如写日志"解析成功"）。如果把成功逻辑塞进 `try`，处理逻辑自身抛错会误导你以为是读取失败。
- **初学者误区**：以为 `else` 会"在异常被处理之后"执行——恰恰相反，只要发生过异常，`else` 就**绝不**执行。另一个误区：把 `else` 当 `except` 用，以为它能捕捉异常——它连一个异常都不抓。

### 代码分析

```python
try:
    ...                                     # 运行代码
    ...                                     # 错误写法：把成功动作塞进 try
except IndexError:
    ...                                     # 处理异常
# 若"成功动作"本身越界，会被误当成 try 的失败 → 错误触发上面的处理器
```

- **解释器如何处理**：把成功动作放进 `try` 后，解释器无法区分异常来自"主体代码"还是"成功动作"——对解释器而言它们都在同一个受保护区域内。而 `else` 是独立于受保护区域的代码块，它的异常不会被下面的 `except` 拦截。
- **设计思想**：这正是"职责分离"（separation of concerns）在语法层面的体现——`try` 块只放"可能失败的原始操作"，成功后的衍生操作放 `else`，让错误的归属一目了然。

### 代码分析

```python

    return x / y                          # 除零发生在这里（第 2 行）
```

## 34.4.6 Example: Catching Built-in Exceptions（示例：捕捉内置异常）

### 英文原文

> Python's error checking and default exception handling is often exactly what you want: especially for code in a top-level script file, an error often *should* terminate your program immediately. For many programs, there is no need to be more specific about errors in your code.
>
> Sometimes, though, you'll want to catch errors and recover from them instead. If you don't want your program terminated when Python raises an exception, simply catch it by wrapping the program logic in a `try`. This is an important capability for programs such as network servers, which must keep running persistently. For example, the code in Example 34-2, file `kaboom.py`, catches and recovers from the `TypeError` Python raises immediately when you try to concatenate a list and a string (remember, the `+` operator expects the same sequence type on both sides).
>
> **Example 34-2. `kaboom.py`**
>
> ```python
> def kaboom(x, y):
>     print(x + y)                        # 触发 TypeError
>
> def serve(n=2):                         # 模拟长时间运行的任务
>     for i in range(n):
>         try:
>             kaboom([1, 2], 'hack')
>         except TypeError:                # 在这里捕捉并恢复
>             print('Hello world!')
>         print('Resuming here...')        # 无论有无异常都继续到这里
>
> if __name__ == '__main__': serve()
> ```
>
> When the exception occurs in the function `kaboom`, control jumps to the `try` statement's `except` clause, which prints a message. Since an exception is "dead" after it's been caught like this, the program continues executing below the `try` rather than being terminated by Python. In effect, the code processes and clears the error, and your script recovers:
>
> ```text
> $ python3 kaboom.py
> Hello world!
> Resuming here...
> Hello world!
> Resuming here...
> ```
>
> Keep in mind that once you've caught an error, control resumes at the place where you caught it (i.e., after the `try`); there is no direct way to go back to the place where the exception occurred (here, in the function `kaboom`). This makes exceptions more *like simple jumps* than function calls—there is no way to "return" to the scene of the crime.

### 中文翻译

> Python 的错误检查和默认异常处理常常正是你想要的：尤其对顶层脚本文件中的代码来说，错误**应该**立即终止你的程序。对许多程序而言，没有必要对代码中的错误做更精细的处理。
>
> 不过，有些时候你会想**捕捉错误并从错误中恢复**。如果你不想让程序在 Python 引发异常时被终止，只需把程序逻辑包进 `try` 来捕捉它。这对网络服务器这类**必须持续运行**的程序来说是一项重要能力。例如，示例 34-2 中文件 `kaboom.py` 的代码，捕捉并恢复了当你尝试拼接列表（list）和字符串（string）时 Python 立即引发的 `TypeError`（记住，`+` 运算符期望两侧是**相同的序列类型**）。
>
> **示例 34-2. `kaboom.py`**
>
> ```python
> def kaboom(x, y):
>     print(x + y)                        # 触发 TypeError
>
> def serve(n=2):                         # 模拟长时间运行的任务
>     for i in range(n):
>         try:
>             kaboom([1, 2], 'hack')
>         except TypeError:                # 在这里捕捉并恢复
>             print('Hello world!')
>         print('Resuming here...')        # 无论有无异常都继续到这里
>
> if __name__ == '__main__': serve()
> ```
>
> 当异常发生在函数 `kaboom` 中时，控制流跳到 `try` 语句的 `except` 子句，它打印一条消息。由于异常被这样捕捉后就是"死的"（dead）了，程序会在 `try` 下方继续执行，而不会被 Python 终止。实际上，代码处理并清除了错误，你的脚本得以恢复：
>
> ```text
> $ python3 kaboom.py
> Hello world!
> Resuming here...
> Hello world!
> Resuming here...
> ```
>
> 请记住：一旦你捕捉了错误，控制流就在**捕捉点**（也就是 `try` 之后）恢复；没有任何直接方法回到异常发生的地方（这里是函数 `kaboom` 内部）。这使得异常更像**简单的跳转（jump）**而非函数调用——没有办法"返回到犯罪现场"。

### 深度理解

- **核心概念**：捕捉异常 = 把"致命错误"降级为"可处理事件"。`kaboom` 展示了错误恢复（recovery）的核心模式：异常被 `except` 处理后，程序继续跑。
- **底层实现**：`except TypeError` 匹配成功后，解释器清除异常状态（`PyErr_Clear`），从 `try` 语句之后的字节码继续执行——这就是"异常已死"的字面含义：它不再存在，无法继续传播。
- **设计原因**：**异常 ≠ 返回**。作者强调"不能回到犯罪现场"，是因为异常只携带"向上跳"的信息，不携带"向下回"的路径——这种单向性让错误处理不可能陷入"重放错误现场"的死循环。
- **实际问题**：服务器模型：`serve()` 的循环每次迭代都包 `try`，单个请求的 `TypeError` 只打一句"Hello world!"（这里用打印模拟容错处理），循环继续处理下一个请求——这正是 Web 框架里每个请求都被 `try` 包裹的原理。
- **初学者误区**：以为捕捉异常后能"从出错的那一行继续执行"——不能！执行点只能从 `try` 之后继续。还有初学者把 `try` 块内的代码写得巨大，指望"哪里出错都行"——捕捉范围越大，恢复策略就越难精准。

### 代码分析

```python
def kaboom(x, y):
    print(x + y)                        # 触发 TypeError：列表+字符串不合法

def serve(n=2):                         # 模拟长时间运行的任务
    for i in range(n):
        try:
            kaboom([1, 2], 'hack')      # 异常从这里抛出
        except TypeError:                # 在这里捕捉并恢复
            print('Hello world!')
        print('Resuming here...')        # 无论有无异常都继续到这里

if __name__ == '__main__': serve()
```

- **解释器如何处理**：第一次循环：`kaboom([1, 2], 'hack')` 执行 `[1, 2] + 'hack'`，PyObject 层发现 list 与 str 不能相加，抛出 `TypeError`。该异常在 `kaboom` 帧内无匹配处理器，上抛到 `serve` 帧——这里 `try` 匹配 `TypeError`，命中！执行 `print('Hello world!')`，异常清除，继续执行 `print('Resuming here...')`。第二次循环重复同一剧本。`+` 运算符的"同类型序列"约束在 C 层的 `sequence_concat` 中检查。
- **设计思想**：注意 `print('Resuming here...')` 在 `try/except` **外面**、循环**里面**——这正是"每轮迭代独立容错、整体持续运行"的服务器模式雏形：错误被拦截在单次请求内，服务本身不中断。

## 34.5 The finally Clause（finally 子句）

### 英文原文

> The other main flavor of the `try` statement is for coding *finalization* (a.k.a. termination) actions and is really related to exceptions only incidentally. If a `finally` clause is included in a `try`, Python will always run its block of statements "on the way out" of the `try` statement—whether an exception occurred while the `try` block was running or not. That is, this clause doesn't *catch* exceptions, it works around them.
>
> When used in isolation, this flavor's general form is this:
>
> ```python
> try:
>     statements                      # 先运行这个动作
> finally:
>     statements                      # 退出时总是运行这段代码
> ```
>
> When a `finally` appears in `try`, Python begins by running the statement block associated with the `try` header line as usual. What happens next depends on whether an exception occurs during the `try` block, and what other clauses are present:
>
> **Exception and match** — If an exception occurs during the `try` block's run and is matched by an `except` clause, Python first runs the matching `except` block and then runs the `finally` block. After both finish, the program then resumes below the entire `try` statement. The `finally` is also run if the `except` raises a new exception.
>
> **Exception and no match** — If an exception occurs during the `try` block's run but is *not* caught by an `except`, Python still comes back and runs the `finally` block, but it then propagates the exception up to a previously entered `try` or the top-level default handler. That is, `finally` is run even if an exception is raised and uncaught, but unlike an `except`, the `finally` does not terminate the exception—it continues being raised after the `finally` block runs.
>
> **No exception** — If an exception does *not* occur while the `try` block is running, Python first runs the `else` block (if present) and then runs the `finally` block. After both finish, the program then resumes below the entire `try` statement. The `finally` is also run if the `else` raises a new exception.
>
> The `try`/`finally` form is useful when you want to be completely sure that an action will happen after some code runs, regardless of the exception behavior of the code. In practice, it allows you to specify cleanup actions that always must occur, such as file closes and server disconnects where required.
>
> Technically speaking, `finally` can appear in the same statement as `except` and `else`, so there is really a single `try` statement with many optional clauses. Because of its distinct role, though, as well as its ordering rules we will meet in a moment, the `finally` clause may be best thought of as a distinct tool. Whether mixed or not, `finally` serves the same purpose—to specify cleanup actions that must always be run, regardless of any exceptions.
>
> As you'll also see later in this chapter, the `with` statement and its context managers provide an object-based way to do similar work for exit actions. Unlike `finally`, this statement also supports entry actions, but it is limited in scope to objects that implement the context-manager protocol it employs.

### 中文翻译

> `try` 语句的另一主要形态是用于编写**终结化（finalization，又名终止 termination）**动作，它与异常的关系其实只是顺带相关。如果 `try` 中包含 `finally` 子句，Python 在"离开" `try` 语句时**总是**运行它的语句块——无论 `try` 块运行期间是否发生异常。也就是说，这个子句**不捕捉**异常，而是绕开它们工作。
>
> 单独使用时，这一形态的通用形式如下：
>
> ```python
> try:
>     statements                      # 先运行这个动作
> finally:
>     statements                      # 退出时总是运行这段代码
> ```
>
> 当 `finally` 出现在 `try` 中时，Python 照常先运行与 `try` 头部行关联的语句块。接下来发生什么，取决于 `try` 块期间是否发生异常，以及还有哪些其他子句在场：
>
> **异常且匹配** —— 如果 `try` 块运行期间发生异常，并被某个 `except` 子句匹配，Python 先运行匹配的 `except` 块，再运行 `finally` 块。两者都完成后，程序在整条 `try` 语句下方继续。即使 `except` 引发了新异常，`finally` 也照样运行。
>
> **异常但不匹配** —— 如果 `try` 块运行期间发生异常，但**没有**被任何 `except` 捕捉，Python 仍然会回来运行 `finally` 块，但之后会把异常传播到此前进入的某个 `try` 或顶层默认处理器。也就是说：即使异常被引发且未被捕捉，`finally` 也会运行；但与 `except` 不同，`finally` **不会终结异常**——异常在 `finally` 块运行后继续被引发。
>
> **无异常** —— 如果 `try` 块运行期间**没有**发生异常，Python 先运行 `else` 块（若有），再运行 `finally` 块。两者都完成后，程序在整条 `try` 语句下方继续。即使 `else` 引发了新异常，`finally` 也照样运行。
>
> 当你想要**完全确定**某个动作会在某段代码运行之后发生——无论这段代码的异常行为如何——`try`/`finally` 形式就很有用。在实践中，它让你指定必须始终发生的清理动作（cleanup action），比如按需关闭文件和断开服务器连接。
>
> 严格来说，`finally` 可以与 `except` 和 `else` 出现在同一条语句中，所以实际上只有**一条**带多个可选子句的 `try` 语句。不过，鉴于它独特的作用，以及我们马上要讲到的顺序规则，把 `finally` 子句当作一件独立的工具来思考也许最好。无论混用与否，`finally` 服务于同一个目的——指定无论任何异常都必须运行的清理动作。
>
> 你还将在本章后面看到，`with` 语句及其上下文管理器（context manager）为退出动作提供了**基于对象**的类似方式。与 `finally` 不同，该语句还支持**进入**（entry）动作，但它的适用范围限于实现了它所使用的上下文管理器协议的对象。

### 深度理解

- **核心概念**：`finally` 是"出逃通道上的守门员"——无论 `try` 块是正常退出、被 `except` 处理后退出、还是异常未捕捉直接弹出，`finally` 都必然执行。它不"处理"异常，只保证"收尾"。
- **底层实现**：字节码层面，`finally` 块会被编译为可被两种路径进入的代码：正常路径（`try` 结束后顺序执行）和异常路径（解释器展开栈时通过 `SETUP_FINALLY` 处理器跳入）。`finally` 块执行完，异常若仍存在则继续传播（`RERAISE` 指令），这就是"不终结异常"的实现。
- **设计原因**：资源（文件、锁、数据库连接）的生命周期管理是编程的永恒难题——忘记释放 = 资源泄漏。`finally` 把"必然清理"从程序员的自觉变成语言的保证。
- **实际问题**：任何"打开就必须关闭"的资源都该配 `finally`：文件、socket、数据库游标、GUI 窗口、进程锁。这也是 `with` 语句存在的动机——它在对象层面自动化了这套模式。
- **初学者误区**：以为"有 `finally` 就能吞掉异常"——不能！`finally` 不匹配、不拦截、不终结异常，它只是"顺便打扫战场"。另一个经典误区：在 `finally` 里 `return` 会覆盖 `try` 中的返回值（高级陷阱，但本书此处不展开）。

### 代码分析

```python
try:
    statements                      # 先运行这个动作
finally:
    statements                      # 退出时总是运行这段代码
```

- **解释器如何处理**：解释器把 `finally` 块安装为"两条路的汇合点"：若 `try` 正常完成，直接落入 `finally`；若中途异常，先保存异常状态，执行 `finally` 块，再把保存的异常恢复并继续向上传播（若存在匹配的外层 `except` 则交给它）。这保证了三条路径（匹配/不匹配/无异常）都经过 `finally`。
- **设计思想**："围绕（work around）异常"这个说法很精辟：`finally` 不在"异常是否发生"的决策线上，而在"退出路径"上——它的语义是"离开必经过"，与异常种类完全解耦。

## 34.5.1 Example: Coding Termination Actions with try/finally（示例：用 try/finally 编写终止动作）

### 英文原文

> We coded some simple `try`/`finally` examples in the prior chapter. Example 34-3 lists a more tangible example that illustrates a typical role for this statement.
>
> **Example 34-3. `closer.py`**
>
> ```python
> class MyError(Exception): pass
>
> def stuff(file):
>     file.write('Hello?')                    # 可能滞留在文件缓冲区
>     raise MyError()                          # <= 用 # 启用或禁用我
>
> if __name__ == '__main__':
>     file = open('temp.txt', 'w')            # 打开输出文件（这步也可能失败）
>     try:
>         stuff(file)                          # 引发异常
>     finally:
>         file.close()                         # 总是关闭文件以刷新输出缓冲区
>     print('Am I reached?')                   # 仅当无异常时才继续到这里
> ```
>
> When the function in this code raises its exception, the control flow jumps back and runs the `finally` block to close the file. The exception is then propagated on to either another `try` or the default top-level handler, which prints the standard error message and shuts down the program. Hence, the statement after this `try` is never reached:
>
> ```text
> $ python3 closer.py
>
> Traceback (most recent call last):
>   File "/…/LP6E/Chapter34/closer.py", line 10, in <module>
>     stuff(file)                     # 引发异常
>   File "/…/LP6E/Chapter34/closer.py", line 5, in stuff
>     raise MyError()                  # <= 用 # 启用或禁用我
> MyError
> ```
>
> If the function here did *not* raise an exception (e.g., by disabling its `raise` line with an added `#`), the program would still execute the `finally` block to close the file, but it would then continue below the entire `try` statement:
>
> ```text
> $ python3 closer.py
>
> Am I reached?
> ```
>
> In this specific case, we've wrapped a call to a file-processing function in a `try` with a `finally` clause to make sure that the file is always closed, and thus finalized, whether the function triggers an exception or not. This way, later code can be sure that the file's output buffer's content has been flushed from memory to disk. A similar code structure can guarantee that server connections are closed, GUI windows are closed, and so on.
>
> As we learned in Chapter 9, file objects are automatically closed on garbage collection in standard Python (CPython); this is especially useful for temporary files that we don't assign to variables. However, it's not always easy to predict when garbage collection will occur, especially in larger programs or alternative Python implementations with differing garbage collection policies. The `try` statement makes file closes more explicit and predictable: it ensures that the file will be closed on block exit, regardless of whether an exception occurs or not.
>
> This particular example's function isn't all that useful (it always raises an exception!), but wrapping calls in `try`/`finally` statements is a good way to ensure that your closing-time termination activities always run. All bets are off if Python itself crashes completely, of course, but this is exceedingly rare; because it detects errors as a program runs, hard crashes are usually caused by linked-in C extension code, outside of Python's scope.
>
> As a preview, notice how the user-defined exception in Example 34-3 is defined with a `class`; as you'll learn more formally in the next chapter, exceptions must all be class instances, for reasonably good causes.

- **核心概念**：`try/finally` 的经典资源管理模式——"打开 → 处理 → 必然关闭"。异常发生时清理动作照样执行，这就是"终止动作（termination actions）"的含义。
- **底层实现**：`file.close()` 会把文件对象中缓冲区（buffer）里滞留的数据写回磁盘。`write()` 只是写入内存缓冲区，`close()` 触发 flush——这就是为什么"不关闭文件 = 丢数据"。
- **设计原因**：CPython 的引用计数保证文件对象在失去引用时立即关闭，但这是**实现细节**而非语言承诺（Jython、PyPy 等可能延迟）；`try/finally` 把"何时关闭"从"垃圾回收的运气"变成"代码的确定性"。作者强调这点，是为了说明：不要依赖隐式行为。
- **实际问题**：这是 `with` 语句的直接前身——每写一次 `try/finally` 的打开-关闭都要 4 行样板代码，所以后来 Python 2.5 引入了 `with` 来压缩它。本章后半部分会正式对比两者。
- **初学者误区**：以为"反正垃圾回收会关文件"，于是在循环里大量打开文件却不关闭——缓冲区数据可能永远不落盘，程序也可能耗尽文件描述符。另一个误区：以为 `finally` 会阻止异常传播——`closer.py` 的输出显示异常照常打印 traceback。

### 代码分析

```python
class MyError(Exception): pass              # 自定义异常：继承内置 Exception

def stuff(file):
    file.write('Hello?')                    # 写进内存缓冲区，未必立刻落盘
    raise MyError()                          # <= 用 # 启用或禁用我

if __name__ == '__main__':
    file = open('temp.txt', 'w')            # 打开输出文件（这步也可能失败）
    try:
        stuff(file)                          # 引发异常
    finally:
        file.close()                         # 总是关闭文件以刷新输出缓冲区
    print('Am I reached?')                   # 仅当无异常时才继续到这里
```

- **解释器如何处理**：执行 `stuff(file)` 时先 `write` 再 `raise MyError()`。异常弹出时解释器先执行 `finally` 块：`file.close()` 把缓冲的 `'Hello?'` 落盘。之后异常继续传播到顶层，打印 `MyError` 的 traceback 并终止程序，所以 `print('Am I reached?')` 永远不执行。若注释掉 `raise` 行：`try` 正常结束，`finally` 仍执行（关闭文件），然后打印 `Am I reached?`。
- **设计思想**：`close()` 语义 = "终结化（finalize）"——它不只释放文件描述符，还保证缓冲数据完整交付。这个例子点出关键教训：**清理动作的价值在于"无论成败都执行"**，因为成败本身不是我们能提前预知的。同时注意 `raise MyError()` 中 `MyError(Exception)` 的定义——异常是类，这是第 35 章的主线。

## 34.6 Combined try Clauses（组合 try 子句）

### 英文原文

> For the first 15 years of Python's tenure (more or less), the `try` statement came in two flavors and was two separate statements—we could either use a `finally` to ensure that cleanup code was always run, or write `except` blocks to catch and recover from specific exceptions and optionally specify an `else` clause for when exceptions occurred.
>
> That is, the `finally` clause could not be *mixed* with `except` and `else`. This was partly because of implementation issues, and partly because the meaning of mixing the two seemed obscure—catching and recovering from exceptions seemed a disjoint concept from performing cleanup actions.
>
> For better or worse, the two statements eventually merged. Today, we can mix `finally`, `except`, and `else` clauses in the same statement—in part because of similar utility in the Java language (alas, many a programming-language mod owes to imitation). That is, the `try` statement in its most complete form looks like this:
>
> ```python
> try:                                    # 组合 try 语句
>     main-action
> except Exception1:                       # 捕捉特定异常
>     handler1
> except Exception2:
>     handler2
> except:                                 # 捕捉所有（其他）异常
>     handler3
> else:                                   # 无异常处理器
>     handler4
> finally:                                # finally 包裹一切
>     finally-block
> ```
>
> The code in this statement's `main-action` block is executed first, as usual. If that code raises an exception, all the `except` blocks are tested, one after another, for a match to the exception raised: `handler1` is run for `Exception1`, `handler2` for `Exception2`, and `handler3` for all others. If no exception is raised, `handler4` is run.
>
> No matter what's happened previously, the `finally-block` is executed once, after the main action block is exited and any handler block has been run. In fact, the code in the `finally-block` will be run even if an error or `raise` in an `except` or `else` block causes a new exception to be raised.
>
> As outlined earlier, even in mixed usage like this, the `finally` clause does not end the exception—if an exception is active when the `finally-block` is executed, it continues to be propagated after the `finally-block` runs, and control jumps somewhere else in the program (to an earlier `try`, or to the default top-level handler). If no exception is active when the `finally` is run, control resumes after *the entire* `try` statement.
>
> The net effect is that the `finally` is always run, regardless of whether:
>
> - An exception occurred in the main action and was handled.
> - An exception occurred in the main action and was not handled.
> - No exceptions occurred in the main action.
> - A new exception was triggered in one of the handlers.
>
> Again, the `finally` serves to specify cleanup actions that must always occur on the way out of the `try`, regardless of what exceptions have been raised or handled.

### 中文翻译

> 在 Python 历史的前 15 年（大致如此），`try` 语句有两种形态、是两条独立的语句——我们要么用 `finally` 确保清理代码总是运行，要么写 `except` 块来捕捉特定异常并恢复、可选地为"发生异常时"指定一个 `else` 子句。
>
> 也就是说，`finally` 子句**不能**与 `except` 和 `else` **混用**。这部分是因为实现上的问题，部分是因为两者混用的含义似乎很晦涩——"捕捉并恢复异常"与"执行清理动作"看起来是两个不相干的概念。
>
> 不管好坏，这两条语句最终还是合并了。今天，我们可以在同一条语句中混用 `finally`、`except` 和 `else` 子句——部分原因是 Java 语言中有类似的实用设计（唉，编程语言界的许多变革都要归功于模仿）。也就是说，`try` 语句最完整的形式长这样：
>
> ```python
> try:                                    # 组合 try 语句
>     main-action
> except Exception1:                       # 捕捉特定异常
>     handler1
> except Exception2:
>     handler2
> except:                                 # 捕捉所有（其他）异常
>     handler3
> else:                                   # 无异常处理器
>     handler4
> finally:                                # finally 包裹一切
>     finally-block
> ```
>
> 本语句 `main-action` 块中的代码照常先执行。如果该代码引发异常，所有 `except` 块会一个接一个地测试是否与引发的异常匹配：`Exception1` 运行 `handler1`，`Exception2` 运行 `handler2`，其他一切运行 `handler3`。如果没有引发异常，则运行 `handler4`。
>
> 无论之前发生了什么，`finally-block` 都会执行**一次**——在退出主动作块、且任何处理器块已运行之后。事实上，即使 `except` 或 `else` 块中的错误或 `raise` 引发了新异常，`finally-block` 中的代码也照样运行。
>
> 如前所述，即使这样混用，`finally` 子句也不会终结异常——如果执行 `finally-block` 时异常仍处于活跃状态，它在 `finally-block` 运行后会继续被传播，控制流跳到程序中的别处（某个更早的 `try`，或默认顶层处理器）。如果执行 `finally` 时没有活跃异常，控制流在**整条** `try` 语句之后继续。
>
> 净效果是：无论以下哪种情况，`finally` 都总是运行：
>
> - 主动作中发生异常且已被处理。
> - 主动作中发生异常且未被处理。
> - 主动作中没有任何异常发生。
> - 某个处理器中触发了新异常。
>
> 再说一次，`finally` 服务于"指定在离开 `try` 时必须发生的清理动作"，无论引发或处理了哪些异常。

### 深度理解

- **核心概念**：组合 `try` = 一张"完整保险单"：`except` 是分险种理赔、`else` 是"没出事"奖励、`finally` 是"无论是否理赔都要走完的流程"。四种场景下 `finally` 都执行。
- **底层实现**：CPython 对组合形式生成的字节码实际上等价于"`try/finally` 里嵌套 `try/except/else`"——`finally` 被实现为最外层的处理器，任何内部路径（包括 `except` 里再抛异常）都必须穿过它。
- **设计原因**：历史合并动机：Java 的 `try-catch-finally` 已经证明了组合的实用性；同时实现障碍（旧编译器难处理混合）最终被克服。作者调侃"编程语言的变革多源于模仿"。
- **实际问题**：最完整的错误处理结构——"分类型处理错误、成功分支做事后动作、无论如何都释放资源"——在一个语句里表达，不再需要嵌套两层 `try`。
- **初学者误区**：以为 `except` 处理完异常后，`finally` 之前还有"继续往下"的机会——实际上 `finally` 是最后一站。还有人不理解"`finally` 不终结异常"：即使有 `finally`，未处理的异常照样杀死程序。

### 代码分析

```python
try:                                    # 组合 try 语句
    main-action                          # 主动作：可能出错的代码
except Exception1:                       # 捕捉特定异常
    handler1
except Exception2:
    handler2
except:                                 # 捕捉所有（其他）异常
    handler3
else:                                   # 无异常处理器：只有主动作成功才运行
    handler4
finally:                                # finally 包裹一切：总是运行
    finally-block
```

- **解释器如何处理**：执行顺序为：主动作 → 若有异常按 `Exception1 → Exception2 → 兜底` 顺序匹配并执行对应处理器（`else` 跳过）；若无异常执行 `handler4`。无论哪条路径，最后必然执行 `finally-block`。若某处理器自身抛出新异常，`finally` 照常执行，新异常随后向外传播。读者可自测四种情况：异常被处理、异常未处理、无异常、处理器抛新异常——`finally` 均执行。
- **设计思想**：这张结构图就是全书最完整的异常语法速查表。注意 `except:` 空兜底与 `else:` 相邻出现——前者是"最后一个异常选项"，后者是"唯一一个无异常选项"，一字之差，天壤之别。

## 34.6.1 Combined-Clause Syntax Rules（组合子句的语法规则）

### 英文原文

> When combined like this, the `try` statement *must* have either an `except` or a `finally`, and the order of its parts must be like this (where "->" means "is followed by"):
>
> `try -> except -> else -> finally`
>
> In this, the `else` and `finally` are optional, and there may be zero or more `except`s, but there must be at least one `except` if an `else` appears. Really, the `try` statement consists of two parts: `except`s with an optional `else`, and/or the `finally`.
>
> In fact, it's more accurate to describe the combined `try` statement's syntactic by the following two alternative formats (where square brackets mean optional and star means any number of what precedes it):
>
> ```python
> try:                                    # 格式 1
>     statements
> except [type [as value]]:
>     statements
> [except [type [as value]]:
>     statements
> ]*
> [else:
>     statements
> ]
> [finally:
>     statements
> ]
>
> try:                                    # 格式 2
>     statements
> finally:
>     statements
> ```
>
> Because of these rules, the `else` can appear only if there is at least one `except`, and it's always possible to mix `except` and `finally`, regardless of whether an `else` appears or not. It's also possible to mix `finally` and `else`, but only if an `except` appears too (though the `except` can omit an exception name to catch everything and run a `raise` statement, described later, to reraise the current exception). If you violate any of these (arguably intricate!) ordering rules, Python will raise a syntax error exception before your code runs.

### 中文翻译

> 像这样组合时，`try` 语句**必须**包含 `except` 或 `finally` 之一，而且各部分的顺序必须如此（其中"->"表示"后面跟着"）：
>
> `try -> except -> else -> finally`
>
> 其中 `else` 和 `finally` 都是可选的；`except` 可以有零个或多个；但只要出现 `else`，就**必须**至少有一个 `except`。实际上，`try` 语句由两部分组成：带可选 `else` 的若干 `except`，和/或 `finally`。
>
> 事实上，用下面两种替代格式来描述组合 `try` 语句的语法更准确（方括号表示可选，星号表示前面内容可出现任意多次）：
>
> ```python
> try:                                    # 格式 1
>     statements
> except [type [as value]]:
>     statements
> [except [type [as value]]:
>     statements
> ]*
> [else:
>     statements
> ]
> [finally:
>     statements
> ]
>
> try:                                    # 格式 2
>     statements
> finally:
>     statements
> ```
>
> 由于这些规则，`else` 只有在至少有一个 `except` 时才能出现；而且无论是否出现 `else`，`except` 与 `finally` 总是可以混用。`finally` 与 `else` 也可以混用，但前提是**必须同时**有一个 `except`（不过这个 `except` 可以省略异常名以捕捉一切，并运行一条稍后介绍的 `raise` 语句来重新引发当前异常）。如果你违反任何一条这些（可以说相当精细的！）顺序规则，Python 会在你的代码运行之前引发一个语法错误异常（syntax error exception）。

### 深度理解

- **核心概念**：语法规则一句话：`try -> except* -> else? -> finally?`，且"`else` 需要至少一个 `except`；`try` 至少要有 `except` 或 `finally` 之一"。这是异常语法的"文法宪法"。
- **底层实现**：这些规则在**编译期**执行——Python 解析器（parser）在把源码编译成字节码时检查子句顺序，违规直接抛 `SyntaxError`，程序根本不会开始运行。
- **设计原因**：`else` 依赖 `except` 的语义理由是：`else` 是"`except` 体系的补充分支"——没有 `except`，"有异常 vs 无异常"的二分就不存在，`else` 也就失去参照。顺序固定则让解析器与读者都无需猜测。
- **实际问题**：写代码时最常见的语法错误就是顺序颠倒：`finally` 写在 `except` 前面、或 `else` 放在 `except` 前面。编译器会立刻报错，但报错位置有时令人困惑——记住这条顺序链就能少走弯路。
- **初学者误区**：以为"`try` 可以只有 `else` 没有 `except`"（想当然地觉得"无异常就干某事"）；或者写 `try: ... finally: ... except:`——顺序违规。这些都会在运行前被语法检查拦下。

### 代码分析

```python
try:                                    # 格式 1：完整版（except 系 + 可选 else + 可选 finally）
    statements
except [type [as value]]:
    statements
[except [type [as value]]:
    statements
]*
[else:
    statements
]
[finally:
    statements
]

try:                                    # 格式 2：纯清理版（只有 finally）
    statements
finally:
    statements
```

- **解释器如何处理**：格式 1 与格式 2 是 `try` 的全部合法形态。格式 1 中 `except` 可重复零到多次、`else` 和 `finally` 各至多一次；格式 2 是"只要清理、不要捕捉"的极简形态。任何其他组合（如 `try/else`、`try/finally/except`）在解析阶段即被拒绝。
- **设计思想**：方括号与星号的文法表示法本身就是教学工具——它把"可选"与"可重复"可视化，比大段文字描述更精确。记住：**格式 2 的存在说明"清理"是独立于"捕捉"的第一等需求**。

## 34.6.2 Combining finally and Except by Nesting（通过嵌套组合 finally 与 except）

### 英文原文

> It may help to realize that it's also possible to combine `finally` and `except` clauses in a `try` by syntactically nesting a `try`/`except` in the `try` block of a `try`/`finally` statement. We'll explore this technique more fully in Chapter 36, but the following has the same effect as the combined form shown at the start of this section:
>
> ```python
> try:                                    # 与组合形式等价的嵌套形式
>     try:
>         main-action
>     except Exception1:
>         handler1
>     except Exception2:
>         handler2
>     except:
>         handler3
>     else:
>         handler4
> finally:
>     finally-block
> ```
>
> Again, the `finally` block is always run on the way out, regardless of what happened in the main action and regardless of any exception handlers run in the nested `try` (trace through the four cases listed previously to see how this works the same). Since an `else` always requires an `except`, this nested form even sports the same mixing constraints of the combined form outlined in the preceding section.
>
> However, this nested equivalent seems more obscure to some people and requires more code than the new merged form—though just one four-character line plus extra indentation. Mixing `finally` into the same statement might make your code easier to write and read, though this also might depend on who you ask.

### 中文翻译

> 认识到这一点也许有帮助：你也可以通过**语法嵌套**来组合 `finally` 和 `except` 子句——把一条 `try`/`except` 放在一条 `try`/`finally` 语句的 `try` 块里。我们将在第 36 章更全面地探索这项技术，不过下面的写法与本小节开头展示的组合形式效果相同：
>
> ```python
> try:                                    # 与组合形式等价的嵌套形式
>     try:
>         main-action
>     except Exception1:
>         handler1
>     except Exception2:
>         handler2
>     except:
>         handler3
>     else:
>         handler4
> finally:
>     finally-block
> ```
>
> 再说一次，`finally` 块在退出时总是运行——无论主动作发生了什么，也无论嵌套 `try` 中运行了哪些异常处理器（把前面列出的四种情况逐个推演一遍，就能看到运行方式完全一致）。由于 `else` 总是要求有 `except`，这个嵌套形式甚至与上一节所述组合形式有着相同的混用约束。
>
> 不过，对有些人来说这个嵌套等价形式显得更晦涩，而且比新的合并形式需要更多代码——虽然只是多了一行四个字符的 `try:` 和额外的缩进。把 `finally` 混进同一条语句或许能让你的代码更易写易读，不过这也可能取决于你问谁。

### 深度理解

- **核心概念**：组合形式**只是**嵌套形式的语法糖——两者语义完全等价。这个等价关系是理解"组合 `try`"的钥匙。
- **底层实现**：CPython 在解析组合形式时，内部正是按"嵌套"来生成代码对象的——`finally` 永远是外层保护，`except` 在里层。这解释了为什么 `finally` 能在 `except` 抛新异常时依然执行。
- **设计原因**：先有嵌套，后有合并。作者展示嵌套形式，是为了让读者明白：合并形式不是"魔法"，而是"语法糖"——理解嵌套模型，就能推演组合形式的一切行为。
- **实际问题**：调试时，如果你怀疑 `finally` 与 `except` 的交互诡异，可以把组合形式"拆开"成嵌套形式一步步看——两种写法运行时行为完全一样，拆开往往更清晰。
- **初学者误区**：有人以为嵌套形式与组合形式"略有不同"（比如异常处理时机）——没有任何不同，它们是同一语义的两副面孔。区别只在代码风格与行数。

### 代码分析

```python
try:                                    # 外层：try/finally
    try:                                # 内层：try/except/else
        main-action                      # 主动作
    except Exception1:
        handler1
    except Exception2:
        handler2
    except:
        handler3
    else:
        handler4
finally:
    finally-block                        # 外层收尾：总执行
```

- **解释器如何处理**：异常发生时，先查**最近进入**的内层 `try` 的 `except` 链：命中则执行处理器并清除异常，内层正常结束；不命中则内层异常向外抛，但**在离开内层之前**，解释器会执行外层 `try` 的 `finally`——于是异常经过 `finally` 后继续向外传播。这正是"异常穿透嵌套帧时逐层展开"的生动演示。
- **设计思想**：这段代码是"异常传播的解剖图"：内层 `try` 决定"谁来处理"，外层 `finally` 决定"走前必须干什么"。二者职责不同、层级不同，组合形式的合并不过是一次文法的压缩。

> 这个示例在主动作中使用内置运算来触发（或不触发）异常，它依赖的事实是：Python 总会在代码运行时检查错误。下一节将展示如何改为**手动**引发异常。

### 深度理解

- **核心概念**：四个实验 = 四种运行模式的"打印实验"：①异常被捕捉 → `except` + `finally` 都运行；②无异常 → 只有 `finally`；③无异常带 `else` → `else` + `finally`；④异常未捕捉 → 只有 `finally`，然后程序崩溃。**四种场景 `finally` 全勤**。
- **底层实现**：`'hack'[99]` 在解释器求值下标时做边界检查，越界抛 `IndexError`；`1 / 0` 在 C 层除法例程中抛 `ZeroDivisionError`——这些都是"运行时自动错误检查"的实例，无需程序员手动 `raise`。
- **设计原因**：用输出而非文字讲语义，是教学上的高招——读者亲手"推演 + 验证"一遍，比背规则记十年都牢。四条输出构成了 `try` 子句行为的完整测试矩阵。
- **实际问题**：这套组合是生产代码里最常用的错误处理骨架：`try`（危险操作）→ `except`（针对性恢复）→ `else`（成功善后）→ `finally`（资源清理）。可以把第④种场景理解为"兜底恢复失败"时程序的最终命运。
- **初学者误区**：从第①场景误以为"`except` 之后程序就结束"——不是，`after run` 照常打印，异常已死。从第④场景误以为"`finally` 会打印后程序继续"——不，`finally` 打印完，`ZeroDivisionError` 继续传播，程序被终止，`after run` 没有机会打印。

### 代码分析

```python
sep = '-' * 45 + '\n'                        # 45 个连字符作分隔线

# 场景 1：异常被引发并被捕捉
try:
    x = 'hack'[99]                           # 'hack' 只有 4 个字符，越界！
except IndexError:
    print('except run')                      # 匹配 IndexError → 执行
finally:
    print('finally run')                     # 收尾必执行
print('after run')                           # 异常已死，继续执行

# 场景 4：异常被引发但未被捕捉（摘录）
try:
    x = 1 / 0                                # ZeroDivisionError ≠ IndexError
except IndexError:
    print('except run')                      # 不匹配，不执行
finally:
    print('finally run')                     # 仍执行！
print('after run')                           # 永不执行：程序已终止
```

- **解释器如何处理**：场景 1：字符串下标 99 触发 `IndexError` → 匹配 `except IndexError` → 打印 `except run` → 异常清除 → 执行 `finally` 打印 `finally run` → 继续打印 `after run`。场景 4：`ZeroDivisionError` 与 `IndexError` 无子类关系，不匹配 → 仍执行 `finally` 打印 `finally run` → 异常继续传播到顶层 → 打印 traceback、进程终止 → `after run` 永不可达。这正是"`finally` 不终结异常"的最直观演示。
- **设计思想**：四个场景按"异常强度"递进排列（被接住 → 没发生 → 没发生+else → 没人接），每个场景只改一个变量，让读者像做对照实验一样精确归因：`except` 管"接住"，`else` 管"平安"，`finally` 管"收尾"——各司其职，互不越界。
