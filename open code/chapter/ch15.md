### 深度理解

- **核心概念**：这张表是 Python 文档体系的"地图"——从上到下，信息量越来越大：`#` 注释只存在于源码里，`dir()` 只给名字，docstring 给一段描述，`help()` 组装成完整报告，HTML 报告带排版和搜索，手册是权威参考，网络资源无穷无尽。**层次越高，越适合"查证"；层次越低，越贴近"写作"**。

## 15.3 # 注释（# Comments）

### 英文原文

> As we've learned—and used in most example listings so far—hash-mark comments are the most basic way to document your code. Python simply ignores all the text following a `#` (as long as it's not inside a string literal), so you can follow this character with any words and descriptions meaningful to programmers. Such comments are accessible only in your source files, though; to code comments that are more widely available, you'll use docstrings (ahead).
>
> In fact, current best practice (generally accepted convention) dictates that docstrings are best for larger functional documentation (e.g., "my script does this"), and `#` comments are best limited to smaller code documentation (e.g., "this strange expression does that") and are best limited in scope to a statement or small group of statements within a script or function. Docstrings are a broader topic we'll get to in a moment; first, let's see how to explore objects.

### 中文翻译

> 正如我们学过的——而且到目前为止大多数示例列表都在用——井号（hash-mark）注释是记录代码最基本的方式。Python 会直接忽略 `#` 后面的所有文本（只要它不在字符串字面量内部），所以你可以在这个字符后面写上任何对程序员有意义的词句和描述。不过，这类注释只能在你自己的源文件中看到；若要写适用范围更广的代码注释，就要用 docstring 了（稍后讲到）。
>
> 事实上，当前的**最佳实践**（被普遍接受的惯例）规定：docstring 最适合较大规模的功能性文档（例如"我的脚本做这件事"），而 `#` 注释最好局限于较小规模的代码说明（例如"这个奇怪的表达式做那件事"），其范围最好限制在脚本或函数中的一条语句或一小群语句。docstring 是个更宏大的话题，我们一会儿就会讲到；首先，让我们看看如何探索对象。

### 深度理解

- **核心概念**：`#` 注释是"就地"注释——解释器在词法分析阶段就把 `#` 到行尾的内容当作空白丢弃，**完全不影响字节码**。注意书里强调"只要不在字符串字面量内"：`"abc # def"` 里的 `#` 是字符串内容，不是注释。
- **最佳实践的分工**：docstring 回答"这是什么"（面向使用者），`#` 注释回答"这里为什么这么写"（面向维护者）。这是社区约定（可追溯至 PEP 8 和 PEP 257 的精神），不是语法强制。
- **生活类比**：`#` 注释像课文里的页边批注，docstring 像每章的"本章概述"——批注属于某一行，概述属于整个章节。
- **初学者误区**：① 用 `#` 写整段功能说明——程序运行时别人根本看不到它；② 注释废话（"x = 1 # 把 1 赋给 x"）——注释应该解释"为什么"，不是复述"是什么"。

## 15.4 dir 函数（The dir Function）

### 英文原文

> As we've also seen, the built-in `dir` function is an easy and automatic way to list all of the attributes available inside an object (i.e., its methods and simpler data items). It can be called with no arguments to list variables in the caller's scope, something the next part of this book will define in full. More usefully, it can also be called with any object that has attributes, including imported modules and objects of built-in types, as well as the name of a data type itself. For example, to find out what's available in a module, such as the standard library's `sys`, import it and pass it to `dir`:
>
> ```
> $ python3
> >>> import sys
> >>> dir(sys)
> [… many names here …]
> ```
>
> The list of attribute name strings you'll get back is omitted here because it's not small and is prone to vary per Python version; run this on your own for a better look. In fact, there are currently 110 attributes in `sys`, though we generally care only about the 97 that do not have leading double underscores (two underscores usually means interpreter-related), or the 83 that have no leading underscore at all (one underscore usually means implementation private, informally). Rooting out such numbers is a prime example of the preceding chapter's list comprehension at work:
>
> ```
> >>> len(dir(sys))                                  # Number names in sys
> 110
> >>> len([x for x in dir(sys) if not x.startswith('__')])  # Non __X names only
> 97
> >>> len([x for x in dir(sys) if not x[0] == '_'])  # Ignore _X names too
> 83
> ```
>
> To find out what attributes are provided in objects of built-in types, run `dir` on a literal, an existing instance, or the name of the desired type. For example, to see all text-string attributes, you can pass an empty or the type name `str`:
>
> ```
> >>> dir('')
> ['__add__', … more names here …, 'zfill']
> >>> dir(str) == dir('')
> True
> ```
>
> The `dir` result for any built-in type includes a set of attributes that are related to the implementation of that type (mostly, for expression operators). Much as in modules, they all begin and end with double underscores to make them distinct, and you can safely ignore them at this point in the book (they'll resurface later for OOP). For instance, there are 81 text-string attributes, but only 47 that correspond to named methods or data; lists have even fewer:
>
> ```
> >>> len(dir('')), len([x for x in dir('') if not x.startswith('__')])
> (81, 47)
> >>> len(dir([])), len([x for x in dir([]) if not x.startswith('__')])
> (48, 11)
> ```
>
> To list names, filter out double-underscored items that are not of common program interest by running the same list comprehensions, but print the attributes. To demo, here are the named attributes in lists and dictionaries:
>
> ```
> >>> [a for a in dir(list) if not a.startswith('__')]
> ['append', 'clear', 'copy', 'count', 'extend', 'index', 'insert', 'pop',
>  'remove', 'reverse', 'sort']
> >>> [a for a in dir(dict) if not a.startswith('__')]
> ['clear', 'copy', 'fromkeys', 'get', 'items', 'keys', 'pop', 'popitem',
>  'setdefault', 'update', 'values']
> ```
>
> This may seem like a lot to type to get an attribute list, but beginning in the next chapter, you'll learn how to wrap such code in a simple, importable, and reusable function so you don't need to type it again.
>
> Aside: type names like `str`, `list`, and `dict` work in `dir` because they are actually names of types in Python today, not just type-converter functions; calling one of these invokes its constructor to generate an instance of that type. Part VI will have more to say about constructors and operator overloading methods when we discuss classes.
>
> The `dir` function is mostly a memory jogger—it provides a list of attribute names, but it does not tell you anything about what those names mean. For such extra information, we need to move on to the next documentation source.
>
> **NOTE — Attributes in IDEs**: Some GUIs for Python work, including IDLE, have features that list attributes on objects automatically, which can be viewed as alternatives to `dir`. IDLE, for example, will list an object's attributes in a pop-up selection window when you type a period after the object's name and pause or press Tab. This is mostly meant as an autocomplete feature, though, not an information source. Chapter 3 and Appendix A have introductory info on IDLE.

### 中文翻译

> 正如我们已经见过的，内置 `dir` 函数是列出对象内所有可用属性（即它的方法和更简单的数据项）的一种简单而自动的方式。它可以不带参数调用，以列出调用者作用域中的变量——这是本书下一部分将完整定义的内容。更有用的是，它也可以接受任何带有属性的对象，包括导入的模块、内置类型的对象，以及数据类型本身的名字。例如，想了解 `sys` 这样的标准库模块里有什么，导入它再传给 `dir` 即可：
>
> ```
> $ python3
> >>> import sys
> >>> dir(sys)
> […很多名字……]
> ```
>
> 你拿回来的属性名字符串列表在这里被省略了，因为它的规模不小，而且容易随 Python 版本变化；最好自己运行一下看看。事实上，`sys` 目前有 110 个属性，但我们一般只关心其中 97 个不以双下划线开头的（两个下划线通常意味着与解释器相关），或者 83 个完全没有前导下划线的（一个下划线通常非正式地表示实现私有的）。挖出这类数字，正是上一章列表推导式（list comprehension）大显身手的好例子：
>
> ```
> >>> len(dir(sys))                                  # 计算 sys 中的名字数量
> 110
> >>> len([x for x in dir(sys) if not x.startswith('__')])  # 只要非 __X 名字
> 97
> >>> len([x for x in dir(sys) if not x[0] == '_'])  # 连 _X 名字也忽略
> 83
> ```
>
> 想找出内置类型的对象提供了哪些属性，可以对一个字面量、一个现有实例、或目标类型的名字运行 `dir`。例如，要看字符串的全部属性，可以传一个空字符串或类型名 `str`：
>

> >>> dir(str) == dir('')
> True
> ```
>
> 任何内置类型的 `dir` 结果都包含一组与该类型实现相关的属性（大多是表达式运算符）。与模块类似，它们都以双下划线开头和结尾以示区别，在本书当前阶段你可以安全地忽略它们（OOP 部分它们会再次出现）。例如，字符串有 81 个属性，但只有 47 个对应命名的（named）方法或数据；列表的更少：
>
> ```
> >>> len(dir('')), len([x for x in dir('') if not x.startswith('__')])
> (81, 47)
> >>> len(dir([])), len([x for x in dir([]) if not x.startswith('__')])
> (48, 11)
> ```
>
> 要列出名字，运行同样的列表推导式，过滤掉双下划线的、一般程序不感兴趣的项目，但这次打印属性。作为演示，下面是列表和字典中"有名有姓"的属性：
>
> ```
> >>> [a for a in dir(list) if not a.startswith('__')]
> ['append', 'clear', 'copy', 'count', 'extend', 'index', 'insert', 'pop',
>  'remove', 'reverse', 'sort']
> >>> [a for a in dir(dict) if not a.startswith('__')]
> ['clear', 'copy', 'fromkeys', 'get', 'items', 'keys', 'pop', 'popitem',
>  'setdefault', 'update', 'values']
> ```
>
> 为了得到一个属性列表要打这么多字，看起来挺费劲，但从下一章开始，你会学会把这类代码包进一个简单、可导入、可复用的函数里，这样就不用再重复输入了。
>
> 附注（Aside）：`str`、`list`、`dict` 这类类型名能用于 `dir`，是因为它们在今天的 Python 中其实是类型的名字，而不只是类型转换函数；调用其中一个会调用它的构造器（constructor）来生成该类型的一个实例。第六部分讨论类时，会对构造器和运算符重载方法有更多说明。
>
> `dir` 函数主要是个"记忆辅助器"（memory jogger）——它给出属性名的列表，但不告诉你这些名字是什么意思。要获取这类额外信息，我们需要进入下一个文档来源。
>
> **注意——IDE 中的属性（Attributes in IDEs）**：一些 Python 的 GUI 环境（包括 IDLE）有自动列出对象属性的功能，可以看作 `dir` 的替代品。例如，IDLE 在你输入对象名后的句点并暂停或按 Tab 键时，会在弹出选择窗口中列出对象的属性。不过这主要是一个**自动补全**（autocomplete）功能，而不是信息源。第 3 章和附录 A 有 IDLE 的入门介绍。

### 深度理解

- **核心概念**：`dir()` 返回的是**属性名的字符串列表**，它做的是"目录索引"而不是"内容解释"。三个级别：`dir()`（当前作用域的变量）→ `dir(对象)`（对象的属性）→ 对类型名调用（该类型实例共有的属性）。
- **底层实现**：`dir()` 的实现本质是调用对象的 `__dir__()` 方法（若无则回退到 `__dict__` + 类型属性扫描）。它列出的东西包括：实例属性、类属性、继承来的属性。你看到的 `__add__`、`__len__` 这类双下划线属性，是解释器让对象支持 `+`、`len()` 等运算符的内部钩子——这为第六部分 OOP 埋下伏笔。
- **为什么按版本变化**：属性列表来自 Python 的 C 实现（CPython 的内置类型），每版本都可能增删内部属性，所以书里给出的数字（110/97/83、81/47、48/11）只是写作时的快照。**不要背这些数字，要背方法**。
- **列表推导式在这里的作用**：`[x for x in dir(sys) if not x.startswith('__')]` 是一个"过滤管道"——把无关的机器内部名字剔除。这是上一章学到的推导式最典型的实战用途之一：**处理集合数据时优先想到推导式**。
- **初学者误区**：① 以为 `dir()` 会给出方法的用法说明——不，它只给名字；② 试图用 `dir()` 查模块时忘记先 `import`——没导入的对象根本不存在；③ 把 `dir('')` 与 `dir('abc')` 当成不同结果——其实字符串类型相同，结果相同（书里用 `dir(str) == dir('')` 验证了这一点）。
- **生活类比**：`dir()` 像超市货架上的**商品分类标签**（列出所有商品名），但不告诉你每件商品怎么用——想知道用法得看说明书（docstring），而 `help()` 是自动帮你翻说明书。

### 代码分析

```python
>>> import sys                      # 先导入，sys 模块才存在于内存中
>>> dir(sys)                        # 列出 sys 模块的所有属性名（字符串列表）

# 解释器处理流程：dir(sys) 先查找 sys 对象的 __dir__，没有则遍历其
# 命名空间字典（模块的 __dict__）与类型属性，收集全部名字符串后返回列表。

>>> len(dir(sys))                   # 总属性数
110
>>> len([x for x in dir(sys) if not x.startswith('__')])  # 排除 __X__ 双下划线类
97
>>> len([x for x in dir(sys) if not x[0] == '_'])         # 连 _X 也排除
83

# 这三个数字 110 > 97 > 83 的递减关系说明：sys 里有 13 个 __X__ 名字
# （解释器内部），还有 14 个 _X 名字（非正式"私有"约定），真正面向用户的
# 只有 83 个。

>>> dir('')                         # 传空字符串字面量，列出 str 类型全部属性
['__add__', ...更多名字..., 'zfill']
>>> dir(str) == dir('')             # 类型名与实例的结果完全相同
True

# 设计思想：str 是类型，'' 是该类型的一个实例——同一类型共享同一组属性，
# 所以二者结果一致。这就是"类即类型、类型即类"的统一对象模型。

>>> len(dir('')), len([x for x in dir('') if not x.startswith('__')])
(81, 47)                            # 字符串：81 个总属性，47 个"用户可见"
>>> len(dir([])), len([x for x in dir([]) if not x.startswith('__')])
(48, 11)                            # 列表：48 个总属性，只有 11 个用户可见

>>> [a for a in dir(list) if not a.startswith('__')]
['append', 'clear', 'copy', 'count', 'extend', 'index', 'insert', 'pop',
 'remove', 'reverse', 'sort']
>>> [a for a in dir(dict) if not a.startswith('__')]
['clear', 'copy', 'fromkeys', 'get', 'items', 'keys', 'pop', 'popitem',
 'setdefault', 'update', 'values']
```

- **解释器如何处理**：`dir(list)` 不需要创建任何实例——类型本身就是对象，直接传即可。内部的"列出属性"其实是遍历 `PyObject` 类型结构（C 层的 `tp_dict`）以及其继承链，把名字收集成列表。
- **数字背后的信息**：字符串 81 个属性中 34 个是双下划线（`__add__`、`__contains__` 等运算符协议方法），列表 48 个中 37 个是双下划线。可见**运算符重载协议是内置类型"内存"的大头**——这些正是第六部分类要学的魔法方法。

## 15.5 文档字符串与 __doc__（Docstrings and __doc__）

### 英文原文

> Besides `#` comments, Python supports documentation that is automatically attached to objects and retained at runtime for inspection. Syntactically, such comments are coded as string literals of any type, except bytes and f-strings. They are located at the tops of code components (module files and function and class statements), and before any other executable code (`#` comments, including Unix-style `#!` lines, are OK before them). When present, the text of such strings, known as docstrings, is automatically stuffed into the `__doc__` attributes of the corresponding objects.

### 中文翻译

> 除了 `#` 注释，Python 还支持自动附着到对象上、并在运行时保留供检视（inspection）的文档。从语法上讲，这种注释被写成任意类型的字符串字面量——但 bytes 和 f-string 除外。它们位于代码组件（模块文件、函数和类语句）的顶部，且必须在任何其他可执行代码之前（`#` 注释，包括 Unix 风格的 `#!` 行，可以放在它们前面）。当存在时，这类字符串的文本——称为 docstring——会被自动塞进相应对象的 `__doc__` 属性中。

### 深度理解

- **核心概念**：docstring 是**有语法位置的字符串**——Python 编译器在解析 `def`/`class`/module 时，若第一个语句（除注释外）是一个字符串字面量，就把它编译成该对象的文档，存入 `__doc__` 属性。它同时是"注释"和"运行时可访问的数据"。
- **为什么排除 bytes 和 f-string**：bytes 不是给人读的文本；f-string 是"带求值"的字符串——docstring 必须是**编译期可静态确定**的常量文本，f-string 的内容在运行时才计算，无法可靠地作为文档存储。这是 Python 3.12 之前的经典限制，也正是书里示例用 `r'...'` 和普通字符串的原因。
- **"自动"二字的关键**：你不需要写任何赋值语句——只要字符串出现在正确位置，解释器自动完成"存入 `__doc__`"这一动作。这是"约定优于配置"（convention over configuration）的早期体现。
- **生活类比**：docstring 像公司入职时贴在工位上的"岗位说明书"——你入职（定义对象）时人事自动贴好（编译器自动写入 `__doc__`），任何人路过（运行时）都能查看。

### 15.5.1 用户自定义 docstring（User-defined docstrings）

### 英文原文

> For example, consider the file `docstrings.py` in Example 15-1. You can safely ignore most of its code here (we'll study functions, modules, and classes in the next three parts of this book), but notice its three string literals: because they are coded at the beginning of the file, and at the start of a function (`def`) and class (`class`) within it, they are taken as docstrings and are saved in the associated object's `__doc__` when this file is loaded by a run or import.
>
> **Example 15-1. docstrings.py**
>
> ```python

> This module defines a name, function and class.
> """
> edition = 6
> def square(x):
>  r'''

>  Returns the \square\ of its \numeric\ argument.
>  '''
>  return x ** 2 # power operator
> class PartVI:
>  "Class documentation for \U0001F40D "
>  pass
> # Top-level code
> print(square(edition))
> print(square.__doc__)
> print(PartVI.__doc__)
> ```
>
> Some fine points about this example's docstrings:
>
> **Literals**: the first of this file's docstrings uses a triple-quoted block at the top of the file. This is common for docstrings as it allows for multiline comments, but any sort of text string (except f-strings) will work. Both single- or double-quoted one-liners like that in the class are fine, but don't readily support multiline text.
>
> **Raw strings**: as the function demos, `r'…'` strings work too—and may even be required to suppress unwanted backslash escapes and avoid a syntax warning (and eventual error!) for unrecognized escapes each time code is run or recompiled to bytecode (see Chapter 7's coverage of new `\` deprecations in Python 3.12).
>
> **Content**: docstrings can contain any sort of text, including the class's Unicode escape and raw emoji (per the Unicode intro in Chapter 4 and the whole story in Chapter 37). Notice that the `\U` Unicode escape requires backslashes to be used, so it precludes using raw strings to avoid syntax errors in the future (use `\\`).
>
> The whole point of this documentation protocol is that your comments are retained for inspection in `__doc__` attributes after the file is loaded. Thus, to display the docstrings associated with the module and the two code components it defines, we simply import the file and print their `__doc__` attributes, where Python has saved the text. Assuming this module is located in the directory in which we're currently working (and deferring to Chapter 3's note about imports and directories for background info on why that matters):
>
> ```
> $ python3
> >>> import docstrings
> 36
>  Function documentation
>  Returns the \square\ of its \numeric\ argument.
>  
> Class documentation for 
>  
> >>> print(docstrings.__doc__)
> Module documentation
> This module defines a name, function and class.
> >>> print(docstrings.square.__doc__)
>  Function documentation
>  Returns the \square\ of its \numeric\ argument.
>  
> >>> print(docstrings.PartVI.__doc__)
> Class documentation for 
>  
> ```
>
> You will usually want to use `print` like this to view docstrings; otherwise, you'll get a single string with embedded `\n` newline characters. Also note that `import` runs the file's top-level prints (hence the output immediately following the `import`), as does launching it as a top-level script. Within the file, `square` is just `square`, a simple variable:
>
> ```
> $ python3 docstrings.py
> 
> 36
>  Function documentation
>  Returns the \square\ of its \numeric\ argument.
>  
> Class documentation for 
>  
> ```
>
> You can also attach docstrings to methods of classes (covered in Part VI too), but because, as you'll learn, these are just `def` statements nested in `class` statements, they're not a special case. For instance, to fetch the docstring of a method function inside a class within a module, you would simply extend the path to go through the class: `module.class.method.__doc__`. We'll code an example of method docstrings in Chapter 29.
>
> **NOTE — Docstrings futurism**: If you look closely, you'll notice that multiline docstrings, like that of `square`, retain their leading indentation as it was in the code. Python 3.13, still on the drawing board as this note is being written, plans to remove leading indentation from docstrings, mostly to save space in bytecode files and memory. Even before this mod, though, you won't normally see the indents in docs, because tools like Pydoc already strip and reformat, as you'll learn shortly.

> 例如，看看示例 15-1 中的文件 `docstrings.py`。这里你可以放心忽略它的大部分代码（我们会在本书接下来的三个部分研究函数、模块和类），但请注意它的三个字符串字面量：因为它们被写在文件的起始处，以及文件内一个函数（`def`）和一个类（`class`）的开头，所以它们被视为 docstring，并在该文件被运行或导入加载时，保存到相关对象的 `__doc__` 中。

> **原始字符串（Raw strings）**：正如函数演示的，`r'…'` 字符串也能用——甚至可能是必需的：它可以抑制不想要的转义、避免每次运行或重新编译成字节码时出现无法识别转义的语法警告（乃至最终报错！）（见第 7 章关于 Python 3.12 中新的 `\` 弃用警告的讲解）。

> **注意——docstring 的未来（Docstrings futurism）**：如果仔细观察，你会发现像 `square` 这样的多行 docstring 会原样保留代码里的前导缩进。写这条注记时还在酝酿中的 Python 3.13 计划移除 docstring 的前导缩进，主要是为了节省字节码文件和内存的空间。不过，即使在这个改动之前，你通常也不会在文档里看到这些缩进，因为 Pydoc 之类的工具会剥离并重新排版——你稍后就会学到。

### 深度理解

- **核心概念**：docstring 的三个位置 = 三种对象：文件顶部 → 模块的 `__doc__`；`def` 块首部 → 函数的 `__doc__`；`class` 块首部 → 类的 `__doc__`。规则只有一条：**组件定义体中的第一个语句是字符串字面量**（允许 `#` 注释和 `#!` 行打头），它就自动成为 docstring。
- **底层实现**：CPython 编译器（`compile()` 阶段）解析到函数/类/模块体时，检查第一条语句；若是字符串常量（`const`），则把它作为 `__doc__` 存入该对象的属性，**同时不生成任何"执行该字符串"的字节码**——它被消耗掉了，不再作为普通表达式求值。这也是为什么它在运行时"消失"而出现在 `__doc__` 里。
- **原始字符串为什么"可能必需"**：Python 3.12 开始对未知转义序列（如 `\s`）发 `SyntaxWarning`，未来版本会升级为 `SyntaxError`。docstring 里若有 `\square` 这样的文字，普通字符串会把 `\s` 当转义；用 `r'...'` 则原样保留反斜杠——示例中 `r'''` 正是这个用途。
- **`\U0001F40D` 的细节**：`\U` 转义（8 位十六进制 Unicode 码点）必须写在普通字符串里才能生效，原始字符串中它是字面文字；若想在原始字符串里写真实反斜杠要用 `\\`。这是书里特意展示的"raw 字符串不等于万能"的边界情况。
- **导入会执行顶层代码**：`import docstrings` 后立刻看到 `36`、`Function documentation` 等输出，是因为导入会运行文件的全部顶层语句（第三部分的 `print` 也是顶层语句）。这是第 3 章的知识，也是后文"Pydoc 查看脚本文档会运行脚本"的伏笔。
- **为什么要用 `print` 而不是直接敲变量名**：REPL 直接求值 `square.__doc__` 会显示带 `\n` 转义的原始字符串；`print()` 则把转义渲染成真实换行，可读。这是新手常忽略的 REPL 显示差异。
- **缩进的保留与剥离**：多行 docstring 原样保留代码缩进（存进 `__doc__` 时不去缩进），工具（Pydoc、`inspect.getdoc`）负责剥离。Python 3.13 后编译器层面会做类似处理以省空间。
- **初学者误区**：① 把 docstring 写在 `def` 后面第二、第三行——只有"第一个语句"才算数；② 以为 docstring 必须是三引号——单行双引号也行；③ 忘记 docstring 的读取路径——模块是 `mod.__doc__`，函数是 `mod.func.__doc__`，方法要一路穿到 `mod.Class.method.__doc__`。

### 代码分析

```python
"""
Module documentation
This module defines a name, function and class.
"""
edition = 6                       # 普通赋值语句，会被真实执行

def square(x):
    r'''
    Function documentation
    Returns the \square\ of its \numeric\ argument.
    '''
    return x ** 2                 # 幂运算符，返回 x 的平方

class PartVI:
    "Class documentation for \U0001F40D "   # \U0001F40D 是蛇的 Unicode 码点
    pass

# Top-level code（顶层代码：import 或直接运行时都会执行）
print(square(edition))            # 输出 36（6 的平方）
print(square.__doc__)             # 打印函数 docstring
print(PartVI.__doc__)             # 打印类 docstring
```

- **解释器如何处理**：
  1. **编译阶段**：编译 `docstrings.py` 时，模块体的第一个语句是三引号字符串 → 存入 `docstrings.__doc__`；编译 `square` 函数体时，第一个语句是 `r'''...'''` → 存入 `square.__doc__`；编译 `PartVI` 类体时，第一个语句是 `"..."` 单行字符串 → 存入 `PartVI.__doc__`。三个字符串都被"消耗"，不会生成求值字节码。
  2. **运行时**：`edition = 6` 给模块命名空间添加变量；`def square` 创建函数对象（其 `__doc__` 已就位）；`class PartVI` 创建类对象。最后的三个 `print` 依次取用 `__doc__` 属性并打印。
  3. **注意 `print(square.__doc__)` 与直接在 REPL 敲 `square.__doc__` 的区别**：前者渲染换行，后者显示带 `\n` 的原始字符串。
- **设计思想**：docstring 与普通注释的关键区别——注释被编译器丢弃，docstring 是"可编程访问的文档"。这让工具（help、Pydoc、Sphinx、doctest）都能用统一接口 `obj.__doc__` 取文档，形成了 Python 文档生态的基石。
- **运行方式影响输出**：`python3 docstrings.py`（顶层脚本）与 `import docstrings`（模块导入）都会执行顶层 `print`，输出相同——因为模块在两种情况下都是"从第一行执行到最后一行"。

### 15.5.2 Docstring 规范（Docstring standards）

### 英文原文

> As mentioned earlier, common practice today recommends hash-mark comments for only smaller-scale documentation about an expression, statement, or small group of statements. Docstrings are better used for higher-level and broader functional documentation for a file, function, or class, and have become an expected part of Python software. Beyond these guidelines, though, you still must decide what to write.
>
> Although some companies have internal standards, there is no broad consensus about what should go into the text of a docstring. There have been various markup language and template proposals, including HTML, but they don't seem to have caught on in the Python world. Frankly, convincing programmers to document their work using handcoded HTML probably won't happen in our lifetimes, but this shouldn't apply to documentation in general.
>
> Documentation tends to have a lower priority than it should. Too often, if you get any docs in a file at all, you count yourself lucky (and even better if they're accurate and up to date). While technically optional, documentation is a crucial part of well-written programs, and you're encouraged to comment your code liberally. When you do, though, there is no standard docstring format; if you want to use them, anything goes today. Just as for writing code itself, it's up to you to create docstring content and keep it up to date, but common sense is probably your best ally in both tasks.

### 中文翻译

> 如前所述，如今的常见做法建议：`#` 注释只用于较小规模的、针对某条表达式、语句或一小群语句的文档；docstring 更适合用作文件、函数或类的高层次、较宽泛的功能性文档，它已经成为 Python 软件中可预期的组成部分。不过，除了这些指导原则，写什么内容仍然要由你自己决定。
>
> 虽然一些公司有内部标准，但关于 docstring 文本里应该写什么，并没有广泛的共识。曾经有过各种标记语言和模板提案，包括 HTML，但它们似乎在 Python 世界没有流行起来。坦率地说，在我们有生之年，说服程序员用手写 HTML 来记录自己的工作大概不会发生——不过这不适用于一般意义上的文档。
>
> 文档的优先级往往低于它应有的水平。太常见了：一个文件里只要能有点文档，你就该谢天谢地了（要是还准确、还跟得上代码，那就更好了）。虽然从技术上说是可选的，但文档是编写良好的程序中至关重要的一部分，我们鼓励你大量注释自己的代码。不过，当你真要写时，并没有标准的 docstring 格式；如今你爱怎么用就怎么用。就像写代码本身一样，创建 docstring 内容并保持更新是你的责任，而在两项任务中，常识大概是你最好的盟友。

### 深度理解

- **核心概念**：这段讲的是**社区惯例而非语法强制**——"docstring 管大、注释管小"是推荐分工；docstring 里写什么，没有强制标准（宽松性：anything goes）。这是 Python 社区"文档自由"文化的一部分。
- **PEP 257 是什么**：作者没有点名，但官方对 docstring 约定的权威出处是 **PEP 257（Docstring Conventions，2001 年）**。它规定：docstring 用三引号 `"""` 包裹；首行是简洁的摘要句（一句话概括用途，以句号结尾）；多行 docstring 摘要后空一行，再写详细说明；函数 docstring 应说明参数、返回值、异常。PEP 257 约束的是**格式约定**，与书里说的"内容无共识"并不矛盾——写什么内容仍是你的自由。
- **为什么"用手写 HTML 写文档"行不通**：HTML 标签噪音大、可读性差、难维护——所以 Sphinx 选择了 reStructuredText（后文 15.8 节）这种"接近纯文本"的轻量标记。这是"文档语言必须比代码语言简单"的教训。
- **"文档优先级低"是行业普遍现象**：软件工程里有句老话："代码被阅读的次数远多于被编写的次数"，而文档是被阅读者最先看的东西。Lutz 的建议朴素而实用：**用常识判断，写自己六个月后能看懂的文本**。
- **初学者误区**：① 以为 docstring 有"必须遵守"的标准格式，看到别人用不同风格就纠结——没有；② 把 docstring 写成复述代码的流水账——好的 docstring 说"用途与契约"（输入、输出、副作用），不说"实现细节"；③ 写完 docstring 就再也不更新——过时文档比没有文档更危险。
- **现代实践补充**：如今大型项目普遍采用 docstring 模板（如 Google style、NumPy style），并为参数类型加注解（type hints），配合 mypy 等工具做静态检查——但这些都是社区约定，不是语言强制。

### 深度理解

- **核心概念**：docstring 机制是**统一的**——你自己的模块用，CPython 的内置模块（C 语言写的 `sys`、`map` 等）也用。`sys.getrefcount.__doc__` 说明即使是 C 实现的函数，其文档也挂在 `__doc__` 属性上，对 Python 程序员完全透明。

- **初学者误区**：① 以为内置对象没有文档，只能上网查——其实文档就在对象身上；② 直接敲 `sys.__doc__` 而不加 `print`，看到一堆 `\n` 就以为坏了。

## 15.6 Pydoc：help 函数（Pydoc: The help Function）

### 英文原文

> The docstring technique proved to be so useful that Python eventually added a tool that makes docstrings even easier to display. Namely, Pydoc is Python code that knows how to extract docstrings and associated structural information and format them into nicely arranged reports of various types. Additional tools for extracting and formatting docstrings are available in the open source domain (including third-party tools that may support structured text—search the Web for pointers), but Python ships with Pydoc in its always-present standard library.
>
> There are a variety of ways to launch Pydoc, but the two most prominent are the built-in `help` function and the Pydoc browser-based interface. Of these, `help` may be the most straightforward to use and is always available in a REPL.
>
> We met `help` briefly in Chapter 4. It invokes Pydoc to generate a simple plain-text report for any Python object. In this mode, help text looks much like a "manpage" on Unix-like systems. In fact, outside GUIs like IDLE, help text works the same way as a Unix "more" when there are multiple pages of text—press the space bar to move to the next page, Enter (or your keyboard's equivalent) to go to the next line, and Q to quit the display. GUIs generally scroll help text instead. Let's turn to a few examples to see how this works.

### 中文翻译

> docstring 技术被证明如此有用，以至于 Python 最终添加了一个让 docstring 更容易显示的工具。它就是 Pydoc——一段知道如何提取 docstring 及相关结构信息、并把它们排版成各种类型漂亮报告的 Python 代码。开源领域还有更多提取和排版 docstring 的工具（包括支持结构化文本的第三方工具——上网搜索即可找到线索），但 Python 在它永远随身的标准库中自带了 Pydoc。
>
> 启动 Pydoc 的方式有多种，但最主要的是两种：内置 `help` 函数和 Pydoc 的浏览器界面。其中，`help` 可能是最直接易用的，而且在 REPL 中随时可用。
>
> 我们在第 4 章已经简单见过 `help`。它为任何 Python 对象调用 Pydoc 生成一份简单的纯文本报告。在这种模式下，帮助文本看起来很像 Unix 类系统上的"manpage"（手册页）。事实上，在 IDLE 这类 GUI 之外，当帮助文本有多页时，它的翻页方式与 Unix 的 "more" 命令一致——按空格键翻到下一页，按回车（或键盘上的等价键）到下一行，按 Q 退出显示。GUI 环境一般直接滚动显示帮助文本。下面看几个例子，看看它是怎么工作的。

### 深度理解

- **核心概念**：`help()` 是 Pydoc 的"前台"，Pydoc 是标准库 `pydoc` 模块的"后台"。`help(obj)` = 让 Pydoc 提取 obj 的 `__doc__` + 结构信息（签名、类层次、数据成员）→ 排版成报告 → 送进分页器显示。**help 的底层就是 pydoc 模块**（`import pydoc` 可见），它是用 Python 自己写的。
- **底层实现（help 的完整机制）**：内置的 `help` 是 `site` 模块启动时注册的一个 `_Helper` 实例。它拿到对象后调用 `pydoc.render_doc()`：① 用 `inspect` 模块获取对象的类型与签名（`inspect.signature`/`inspect.getdoc`）；② `inspect.getdoc` 会取 `__doc__` 并做 `textwrap.dedent`（剥离公共前导缩进）和清理；③ 对模块/类还会遍历 `dir()` 结果分类整理（FUNCTIONS、DATA、CLASSES 等章节）；④ 输出交给分页器（Unix 的 `more`/`less` 或 Windows 的 `more.com`）。所以你在 `help()` 报告里看到的结构，是你也能用 `dir()`/`inspect` 自己拿到的——Pydoc 只是"拼装工"。
- **为什么 help 显示有分页**：UNIX 哲学——长文本用管道交给分页器，按需翻页，不刷屏。空格翻页、回车逐行、Q 退出，正是 `more` 的交互约定。
- **生活类比**：`help()` 像"点菜时叫服务员来讲解"——服务员（Pydoc）手里有完整的菜单资料（`__doc__`），还知道每道菜的构成（签名、参数），用统一话术讲给你听。

### 中文翻译

> 最后，`help` 函数对待你自己的模块和对待内置对象一样好。下面是它对我们前面在示例 15-1 里编写的 `docstrings.py` 文件中各组件的报告。同样，有些内容是我们写的 docstring，有些则是通过检视对象结构自动提取的信息：
>
> ```
> >>> import docstrings
> >>> help(docstrings.square)
> Help on function square in module docstrings:
>
> square(x)
>
>  Function documentation
>  Returns the \square\ of its \numeric\ argument.
> >>> help(docstrings.PartVI)
> Help on class PartVI in module docstrings:
> class PartVI(builtins.object)
>  | Class documentation for 
>  |
>  | Data descriptors defined here:
>  | …更多省略……
> ```
>
> 对整个模块请求帮助，则一次性汇集所有部分，你的 docstring 也在其中：
>
> ```
> >>> help(docstrings)
> Help on module docstrings:
>
> NAME
>  docstrings
> DESCRIPTION
>  Module documentation
>  This module defines a name, function and class.
> CLASSES
>  builtins.object
>  PartVI
>  class PartVI(builtins.object)
>  | Class documentation for 
>  |
>  | Data descriptors defined here:
>  | …更多省略……
> FUNCTIONS
>  square(x)
>  Function documentation
>  Returns the \square\ of its \numeric\ argument.
> DATA
>  edition = 6
> FILE
>  /Users/me/MY-STUFF/Books/Dev/6E/LP6E/LP6E/Examples/Chapter15/docstrings.py
> ```
>
> 如果仔细看，你会发现这次导入时没有看到我们文件里打印的输出——只是因为它在前面已经被导入过了；如第 3 章所述，每个会话中每个文件的导入只执行一次（第五部分有更多说明）。

### 深度理解

- **核心概念**：`help()` 对"自己写的代码"和"内置代码"一视同仁——因为机制相同：都读 `__doc__` + 结构检视。**你从第一行 docstring 开始，就已经在为你的模块免费生成"manpage"了**。
- **`square(x)` 这一行从哪来**：函数签名不是 docstring 内容，而是 Pydoc 用 `inspect.signature` 从函数对象上自动提取的。你的 `def square(x)` 定义决定了它显示 `square(x)`。这就是"结构信息自动提取"的含义。
- **`class PartVI(builtins.object)` 的含义**：类名后的括号显示继承关系——`PartVI` 继承自 `builtins.object`（所有类的根）。`Data descriptors` 一节显示的是类属性里的描述符（如方法对象），第六部分详细讲。
- **FILE 路径**：报告底部显示的 `FILE` 是模块的源文件路径——Pydoc 通过模块对象的 `__file__` 属性获取。这提示你：**`mod.__file__` 是找"这个模块代码在哪"的快捷方式**（本书后文也用它定位 `_pydoc.css`）。
- **模块只导入一次**：第二次 `import docstrings` 不再重复执行顶层 `print`——Python 的模块缓存机制（`sys.modules`）保证同一会话内一个文件只加载一次。第五部分会深入。
- **初学者误区**：① 以为 `help()` 只对内置对象有效——自己的模块同样受益，前提是**写了 docstring**（没有 docstring 时 help 就只剩签名，形同 `dir`）；② 以为 `help()` 会执行你的模块代码——`import` 时执行，`help()` 本身只读取已加载的对象。

## 15.7 Pydoc：HTML 报告（Pydoc: HTML Reports）

### 英文原文

> The text displays of the `help` function are adequate in many contexts, especially at the interactive prompt. To readers who've grown accustomed to richer presentation mediums, though, they may seem a bit rudimentary. This section presents the HTML-based flavor of Pydoc, which renders module documentation more graphically for viewing in a web browser, and can even open one automatically for you. This browser interface scheme combines both search and display in a web page that communicates with an automatically started local server.

### 中文翻译

> `help` 函数的文本显示在许多场合都够用，尤其是在交互式提示符下。不过，对已习惯于更丰富呈现媒介的读者来说，它可能显得有点简陋。本节介绍 Pydoc 的 HTML 版形态：它把模块文档渲染得更具图形化，供 Web 浏览器查看，甚至能自动为你打开一个浏览器。这套浏览器界面方案把搜索和显示都整合在一个网页里，该网页与一个自动启动的本地服务器通信。

### 深度理解

- **核心概念**：Pydoc 的两种模式是**同一引擎的两套外壳**——纯文本报告（`help` 函数）和 HTML 报告（`pydoc -b`），数据都来自对象检视，只是渲染目标不同。HTML 版的价值在于：可点击的交叉链接、搜索框、常驻浏览器随时查阅。
- **架构**：`pydoc -b` 启动两个本地组件——文档**服务器**（监听 localhost 的随机空闲端口）和**客户端**（你的浏览器，向服务器请求页面）。这与生产环境里的 Web 架构（客户端-服务器）同构，只是全在本机。
- **为什么用随机端口**：`localhost:53965` 里的端口是"默认任意未占用端口"——避免与已运行的 Web 服务冲突。若想固定端口，不带 `-b` 启动 Pydoc 即可看到更多选项。
- **生活类比**：`help()` 是打印在便签上的说明书，`pydoc -b` 是图书馆的检索终端——前者看单件物品，后者在整座图书馆里浏览、搜索、翻页。

A command line like the following starts the show:

You'll see links to the docs of every module on your module search path, including the directory where Pydoc is launched.

Figure 15-2, for example, shows the page we get for the `docstrings` module we coded earlier in Example 15-1. It's the same report created for `help(docstrings)` with a simple HTML layout.
>
> (Figure 15-2: Pydoc browser interface displaying a user-defined module's docs)
>

> 要在浏览器中查看文档，你通常用 `pydoc -b` 命令行启动 Pydoc 的主脚本。这会启动运行在你设备本地的两个组件：一个文档**服务器**，和一个 Web 浏览器**客户端**——后者为从服务器获取的内容提供页面显示和搜索输入。类似下面的命令行就开始了：

- **核心概念**：`python3 -m pydoc -b` 的 `-m` 参数是关键语法——"把 `pydoc` 这个模块当作脚本运行"。解释器会沿模块搜索路径（`sys.path`）找到 `pydoc.py` 并执行它。这与 `python3 -m pip`、`-m http.server` 是同一机制。
- **索引页 = 你的 `sys.path` 地图**：索引页列出的每个模块都来自模块搜索路径——包括标准库目录和当前工作目录。这意味着你启动 Pydoc 的目录决定你"能看到哪些自写模块的文档"。这是理解"Pydoc 只能访问可导入文件夹中的文件"的基础（15.7.3 节还会强调）。
- **`server>` 提示符是 Pydoc 自己的命令行**：输入 `b` 打开浏览器、`q` 退出服务。它是个小小的交互式 REPL，只是换了个提示符。
- **平台差异**：Windows 没有 `python3` 命令（用 `py`）、没有 `pydoc3` 命令（用开始菜单 "Module Docs"）——这是 Python 打包分发历史的遗留，第 3 章和附录 A 的细节在此复用。
- **初学者误区**：① 直接双击运行 `pydoc.py` 而不带 `-b`——那只是显示命令行选项；② 在非工作目录启动 `pydoc -b` 后找不到自己的模块——因为 Pydoc 只能看到启动目录及 `PYTHONPATH` 里的东西；③ 忘记端口号是随机的——每次启动都可能不同，看终端输出的 URL。

### 15.7.2 定制 Pydoc（Customizing Pydoc）

### 英文原文

> If you run this live, your Pydoc will probably look different than the screenshots in the book, because colors were customized on the machine used to capture the images. Though this is entirely optional and requires some web-development knowledge, you can customize Pydoc's appearance, too, by editing the simple CSS file it uses to render its pages. To modify colors, edit file `_pydoc.css` stored in the `pydoc_data` folder alongside Pydoc's module—which you can locate on any platform by importing Pydoc's module and inspecting its `__file__` attribute:
>
> ```
> $ python3 -c "import pydoc; print(pydoc.__file__)"
> … foldepath …/pydoc.py
> $ ls … foldepath …/pydoc_data   # Pydoc's CSS customization file is in here
> __init__.py topics.py
> __pycache__  _pydoc.css
> ```
>
> On Windows, use `py` and `dir` instead of `python3` and `ls`. This uses the Python `-c` command-line argument to submit code to be run as a string, which is handy for short bits of one-off code like this; here, the two statements separated by a semicolon run the same as they would if they were typed one at a time at a REPL's `>>>` prompt.
>
> You can also find the path to Pydoc by running `help('pydoc')`: its path shows up at the bottom of the display. Once you've located the CSS file, edit it to customize as you like (but save the original first as a fallback). As an example, this book's captures use RGB color string `#173166` for `index-decor`. All of which assumes CSS skills beyond this book's scope (plus an undocumented config file that's prone to change or vanish in the future!), but is probably enough to get you started if you want to have a go.

### 中文翻译

> 如果你实际运行一下，你的 Pydoc 看起来大概和书里的截图不一样，因为截图机器的颜色被定制过。虽然这完全可选、而且需要一些 Web 开发知识，但你也可以通过编辑 Pydoc 渲染页面所用的简单 CSS 文件来定制它的外观。要修改颜色，编辑存储在 `pydoc_data` 文件夹里的 `_pydoc.css` 文件——它就在 Pydoc 模块旁边；在任何平台上，你都可以通过导入 Pydoc 模块并检视它的 `__file__` 属性来定位它：
>
> ```
> $ python3 -c "import pydoc; print(pydoc.__file__)"
> …路径…/pydoc.py
> $ ls …路径…/pydoc_data   # Pydoc 的 CSS 定制文件在这里面
> __init__.py topics.py
> __pycache__  _pydoc.css
> ```
>
> 在 Windows 上，用 `py` 和 `dir` 代替 `python3` 和 `ls`。这里用到 Python 的 `-c` 命令行参数，把要运行的代码作为字符串提交——很适合这种一行的一次性代码；此处用分号分隔的两个语句，其运行效果与在 REPL 的 `>>>` 提示符下一句一句输入相同。
>
> 你也可以通过运行 `help('pydoc')` 找到 Pydoc 的路径：它的路径显示在显示内容的底部。一旦定位了 CSS 文件，就可以按喜好编辑定制（但先保存原件作回退）。举个例子，本书截图用 RGB 颜色字符串 `#173166` 作为 `index-decor` 的颜色。这一切都假定你具备超出本书范围的 CSS 技能（外加一个未文档化的、将来容易改变甚至消失的配置文件！），但如果你想试试，这些大概足够你起步了。

### 深度理解

- **核心概念**：Pydoc 的页面外观由它自带的 CSS 文件 `_pydoc.css` 控制——`__file__` 属性是定位"模块源代码/资源文件在哪"的万能钥匙：`import pydoc` 后 `pydoc.__file__` 给出 `pydoc.py` 的绝对路径，旁边的 `pydoc_data` 目录存着页面资源。
- **`-c` 参数的本质**：`python3 -c "代码字符串"` 让解释器把命令行里的字符串当模块体编译执行——注意字符串里是**两条语句用分号连接**，而 REPL 中分号的效果也是"一行内依次执行两条语句"，所以两者等价。这是"代码即数据、一行代码跑一次"的快捷方式。
- **为什么改颜色要先备份**：修改标准库文件有风险——Python 升级可能覆盖你的改动，且该配置文件"未文档化、可能改变或消失"。作者的潜台词：**定制有风险，动手需谨慎，功能优先于外观**。
- **web 开发知识门槛**：CSS 是另一个领域。作者故意带过这个"劝退"话题——本章目标是"会用文档工具"，不是"美化文档工具"。
- **生活类比**：`__file__` 像"正品溯源二维码"——任何模块都能查到它出生（安装）的位置；改 `_pydoc.css` 像给公开图书馆的书换封面——能改，但别人升级馆藏时你的封面会被换掉。

### 15.7.3 更多 Pydoc 技巧（More Pydoc tips）

### 英文原文

> Pydoc works by importing selected files to extract their documentation. This has two usage implications. First, Pydoc can access only files in folders included on the module search path used by imports. This path automatically includes Python's standard library, so you can view docs for all built-in modules. It also includes the current working directory—the folder from which Pydoc was started—but that may be meaningless when started from a Windows Start button. Change your `PYTHONPATH` setting to include other code folders as needed, per Appendix A.
>
> Second, although Pydoc can render docs for both importable modules and runnable scripts in accessible folders, script docs comes with a catch: when a file is selected for help, Pydoc must import it in order to collect its documentation, and as we learned in Chapter 3, importing runs a file's top-level code. Hence, script help implies a script run.
>
> Imported modules normally just define tools when run, so this is usually irrelevant. If you ask for the documentation of a top-level script file, though, the script will be run, and the console window where you launched Pydoc serves as the script's standard input and output for any user interaction. This may work better for some scripts and modes than others; script IO may appear before or after help is dismissed in console mode, before help is scrolled in a GUI like IDLE, or interleaved oddly with Pydoc's own server-command prompts in browser mode.
>
> Later in the book you'll learn ways to code top-level logic that's kicked off only when a file is run, not when it is imported (e.g., by nesting it under a test for variable `__name__` being `'__main__'`). If scripts use these protocols, they're safe to view in Pydoc, because it won't run any top-level code as an inadvertent side effect of viewing docs.
>
> Finally, Pydoc has additional tools we'll skip here for space, including a `-w` switch for saving HTML docs to a file for later viewing, and a plain-text mode run from a command line with just a topic name that works the same as `help` in a REPL. Again, run Pydoc without any command-line arguments for its full set of options.
>
> **NOTE — Blast from the past**: Pydoc once had a simple GUI mode, invoked by flag `-g`, that launched a tkinter GUI client that communicated with the server. This was available until Python 3.2, when the current browser-only mode was deemed sufficient to warrant dropping the longstanding GUI mode in full. Browsers are GUIs too, of course, and the CSS configuration scheme for Pydoc that arose with the browser mode assumes extra web-development knowledge that many Python users won't have. In open source, those with time and desire to change things define the future for everyone.

### 中文翻译

> Pydoc 的工作方式是**导入**选中的文件来提取它们的文档。这带来两个使用层面的含义。第一，Pydoc 只能访问导入搜索路径（module search path）所含文件夹里的文件。这条路径自动包含 Python 的标准库，所以你可以查看所有内置模块的文档。它还包含当前工作目录——即启动 Pydoc 的那个文件夹——但从 Windows 开始菜单启动时，这个目录可能没什么意义。按附录 A 的说法，按需修改 `PYTHONPATH` 设置以包含其他代码文件夹。
>
> 第二，虽然 Pydoc 既能渲染可访问文件夹中可导入的**模块**、也能渲染可运行的**脚本**的文档，但脚本文档有个坑：当一个文件被选中请求帮助时，Pydoc 必须先**导入**它以收集文档，而正如我们在第 3 章学过的，导入会运行文件的顶层代码。因此，查看脚本帮助就意味着脚本会被运行。
>
> 导入的模块运行起来通常只是定义工具，所以这通常无关紧要。但如果你请求的是一个顶层脚本文件的文档，脚本就会被运行，你启动 Pydoc 的那个控制台窗口将充当脚本的标准输入输出，供任何用户交互使用。这对某些脚本和某些模式可能好些、对另一些就差些；脚本的 IO 在控制台模式下可能出现在帮助被关闭之前或之后，在 IDLE 这类 GUI 里出现在帮助滚动之前，或者在浏览器模式下与 Pydoc 自己的服务命令提示符奇怪地交错。
>
> 本书后面你会学到编写顶层逻辑的方法，让它们只在文件被**运行**时触发、而导入时不触发（例如把它嵌套在变量 `__name__` 是否为 `'__main__'` 的判断下）。如果脚本使用这些协议，它们在 Pydoc 中查看就是安全的，因为查看文档不会意外地触发任何顶层代码的副作用。
>
> 最后，Pydoc 还有一些此处因篇幅而略过的工具，包括把 HTML 文档保存到文件以便日后查看的 `-w` 开关，以及一个纯文本模式——在命令行只给一个主题名即可运行，效果与 REPL 里的 `help` 相同。再说一次，不带任何命令行参数运行 Pydoc 可查看其全部选项。
>
> **注意——往日回声（Blast from the past）**：Pydoc 曾经有一个简单的 GUI 模式，由 `-g` 标志调用，会启动一个与服务器通信的 tkinter GUI 客户端。这个模式一直可用到 Python 3.2，当时认为目前的纯浏览器模式已经足够，于是把存在已久的 GUI 模式整个砍掉了。当然，浏览器也是 GUI，而且随浏览器模式出现的 Pydoc CSS 配置方案，假定用户具备许多 Python 用户不具备的额外 Web 开发知识。在开源世界里，那些有时间也有意愿去改变事物的人，为所有人定义了未来。

### 深度理解

- **核心概念（关键警告）**：Pydoc 提取文档的机制 = 导入文件。导入 = 执行顶层代码。所以**给脚本文件看文档 = 运行一次脚本**——这是"Pydoc 会执行你的代码"的真相，也是本章最重要的实用警告之一。
- **`if __name__ == '__main__':` 的伏笔**：把"只有作为脚本运行时才执行"的代码包进这个判断，是 Python 项目的标准防御写法——它的作用正在于：文件被导入时（包括被 Pydoc 导入）顶层只定义名字、不执行动作。这个模式在第五部分（模块）正式学习，但作者在这里就让你知道"为什么需要它"。
- **模块搜索路径与 Pydoc 的可见范围**：Pydoc 的索引页 = `sys.path` 上的内容。理解这一点，就能解释：为什么标准库永远可见（路径包含标准库目录）、为什么自写模块时有时无（取决于启动目录与 `PYTHONPATH`）。
- **`-w` 保存 HTML 的实用场景**：生成静态文档页，脱离 Pydoc 服务器也能分发查看——这是"文档产品化"的第一步，Sphinx 做的正是这件事的工程化版本。
- **`-g` 被砍的历史**：tkinter GUI 被浏览器模式取代，是因为浏览器本身就是 GUI、且免维护。这个例子完美诠释了"开源社区如何决定工具命运"：不再维护的功能会被淘汰，替代方案足够好就足以清退旧方案。
- **初学者误区**：① 用 Pydoc 查一个"会弹输入框"的脚本，结果控制台被脚本 IO 搞乱——这不是 bug，是机制使然；② 以为 `help()` 和 Pydoc 对文件内容做静态分析——不，它**真的导入并运行**模块（对模块而言通常无副作用，因为模块只定义不执行）。

## 15.8 超越 Docstring：Sphinx（Beyond Docstrings: Sphinx）

### 英文原文

> If you're looking for a way to document your Python programs in a more sophisticated way, you may wish to check out Sphinx—a documentation generator system used to create Python's standard manuals described in the next section, as well as docs for many other software projects. It uses simple reStructuredText as its markup language and inherits much from the Docutils suite of parsing and translating tools.
>
> Among other things, Sphinx supports a variety of output formats, automatic cross-references and indexes, and automatic code highlighting (colorization) using Pygments, which is itself a noteworthy Python tool. This is probably overkill for smaller programs where docstrings and `help` may suffice, but can yield higher-grade documentation for larger projects. See the web for more details on Sphinx, its related tools, and other options in the docs domain.

### 中文翻译

> 如果你在寻找一种更精致的方式来记录你的 Python 程序，可以看看 Sphinx——一个文档生成器系统，用于创建下一节描述的 Python 标准手册，以及许多其他软件项目的文档。它用简单的 reStructuredText 作为标记语言，并从 Docutils 这套解析和翻译工具中继承了相当多东西。
>
> 除此之外，Sphinx 支持多种输出格式、自动交叉引用（cross-references）和索引，以及用 Pygments 做自动代码高亮（着色）——Pygments 本身就是个值得注意的 Python 工具。对 docstring 和 `help` 可能就够用的小程序来说，Sphinx 大概是杀鸡用牛刀；但对大型项目，它能产出更高档次的文档。Sphinx 及其相关工具、以及文档领域的其他选择，更多细节请上网搜索。

### 深度理解

- **核心概念**：Sphinx 是文档"工程化"工具——docstring 是"贴纸"，Sphinx 是"出版社"：从 docstring + 手写 reStructuredText 页面出发，自动生成带目录、交叉引用、索引、高亮代码的完整文档站点（默认 HTML，也可输出 PDF、ePub 等）。
- **它的血缘**：Sphinx 构建在 Docutils（解析 reStructuredText 的工具套件）之上；Pygments（高亮库）负责代码着色。**这三个都是 Python 生态的文档基础设施**——python.org 的官方文档就是 Sphinx 生成的（下一节会讲到）。
- **为什么选 reStructuredText 而不是 Markdown 或 HTML**：reStructuredText 比 HTML 简单得多（人写易读），比 Markdown 更严谨（有确定的语义结构，能支持交叉引用、索引这类"结构化文档"需求）。这正是 15.5.2 节"手写 HTML 行不通"讨论的答案——社区最终选择了轻量标记语言。
- **何时该用**：判断标准是**项目规模**——小型脚本用 docstring + `help()` 足够；发布给他人使用的库/框架、需要版本化文档站点的项目，才值得引入 Sphinx（现代备选还有 MkDocs + Material、Sphinx 的 Markdown 方言 MyST）。
- **生活类比**：docstring 是日记，Sphinx 是出版成书——日记随手写，出版需要编辑、目录、索引、装帧，但读者体验完全不同。
- **初学者误区**：过早学 Sphinx——它需要额外学习 reStructuredText 语法，对还在学语言的新手是负担。作者的排序（先 docstring，后 help，最后才提 Sphinx）本身就是推荐的学习顺序。

## 15.11 常见编码陷阱（Common Coding Gotchas）

### 英文原文

> Before the programming exercises for this part of the book, let's run through some of the most common mistakes beginners make when coding Python statements and programs. Many of these are warnings issued earlier in this part of the book, collected here for ease of reference. You'll learn to avoid these pitfalls once you've gained a bit of Python coding experience, but a few words now might help you avoid falling into some of these traps initially:
>
> **Don't forget the colons.** Always remember to type a `:` at the end of compound statement headers—the first line of an `if`, `match`, `while`, `for`, etc. You'll probably forget at first (as have thousands of Python students over the years), but you can take some comfort from the fact that it will soon become an unconscious habit.
>
> **Start in column 1.** Be sure to start top-level (unnested) code in column 1. That includes unnested code typed into module files, as well as unnested code typed at the interactive prompt (a.k.a. REPL). Indented means nested in Python, so it doesn't work at the top.
>
> **Blank lines matter at the interactive prompt.** Blank lines in compound statements are always irrelevant and ignored in module files, but when you're typing code at the interactive prompt, they end the statement. In other words, blank lines tell the interactive REPL that you've finished a compound statement; if you want to continue, don't hit the Enter key at the `...` prompt (if shown) until you're really done. This also means you can't paste multiline code at this prompt; it must run one full statement at a time, with blank lines as needed.
>
> **Indent consistently.** Avoid mixing tabs and spaces in the indentation of a nested block. Otherwise, what you see in your editor may not be what Python sees when it counts tabs as a number of spaces. This is true in any block-structured language, not just Python—if the next programmer has tabs set differently, it will be difficult or impossible to understand the structure of your code. It's safer to use all tabs or all spaces for each block.
>
> **Don't code C in Python.** A reminder for C/C++ programmers: you don't need to type parentheses around tests in `if` and `while` headers (e.g., `if (X==1)`). You can if you like (any expression can be enclosed in parentheses), but they are fully superfluous in this context. Also, do not terminate all your statements with semicolons; it's technically legal to do this in Python as well, but it's totally useless unless you're placing more than one statement on a single line (the end of a line normally terminates a statement). And remember, don't use `{}` around blocks (indent your nested code blocks consistently instead), and avoid embedding assignment statements in `while` loop tests unless they're simple (even though Python now enables this with `:=`).
>
> **Use simple `for` loops instead of `while` or `range`.** Another reminder: a simple `for` loop (e.g., `for x in y`) is almost always simpler to code and often quicker to run than a `while`- or `range`-based counter loop. Avoid the temptation to count things in Python; though occasionally required, it's usually subpar.
>
> **Beware of mutables in assignments.** As cautioned before, be careful about using mutables in a multiple-target assignment (`a = b = []`), as well as in an augmented assignment (`a += [1, 2]`). In both cases, in-place changes may impact other variables. See Chapter 11 for details if you've forgotten why this is true.
>
> **Don't expect results from functions that change objects in place.** We encountered this nag earlier, too: in-place change operations like the `list.append` and `list.sort` methods presented in Chapter 8 do not return values (other than `None`), so you should call them without assigning the result. It's not uncommon for beginners to say something like `mylist = mylist.append(X)` to try to get the result of an `append`, but this assigns `mylist` to `None`, not to the modified list (in fact, you'll lose your reference to the list altogether).
>
> **Always use parentheses to call a function.** You must add parentheses after a function name to call it, whether it takes arguments or not (e.g., use `function()`, not `function`). In the next part of this book, you'll learn that functions are simply objects that have a special operation—a call that you trigger with the parentheses—but they can be referenced like any other object without triggering a call. This often crops up with files; it's common for beginners to type `file.close` to close a file, rather than `file.close()`. Because it's legal to reference a function without calling it, the first version succeeds silently, but it does not close the file.
>
> **Don't use extensions or paths in imports and reloads.** Omit directory paths and file extensions in `import` statements—say `import mod`, not `import mod.py`. We discussed module basics in Chapter 3 and will continue studying modules in Part V. Because modules may have other extensions besides `.py` (e.g., `.pyc` for bytecode), hardcoding a particular extension is not only invalid syntax; it doesn't make sense. Python picks an extension automatically, and any platform-specific directory path syntax comes from module search path settings, not the `import` statement. Until we explore this in more depth, use just a simple name in imports.
>
> **And other pitfalls in other parts.** Be sure to also see the built-in type warnings at the end of Part II, as they may qualify as coding issues too. There are additional "gotchas" that crop up commonly in Python coding—losing a built-in function by reassigning its name, hiding a library module by using its name for one of your own, changing mutable argument defaults, and so on—but we don't have enough background to cover them yet. To learn more about both what you should and shouldn't do in Python, you'll have to read on; later parts extend the set of "gotchas" and fixes we've enumerated here.

### 中文翻译

> 在本书这一部分的编程练习之前，让我们过一遍初学者编写 Python 语句和程序时最常犯的一些错误。其中许多是本部分前面章节已经发出的警告，为了便于查阅，这里集中在一起。一旦你有了一些 Python 编码经验，你就会学会避开这些坑，但现在说几句，也许能帮你一开始就不掉进这些陷阱：
>
> **别忘了冒号。** 永远记得在复合语句头（compound statement headers）末尾输入 `:`——即 `if`、`match`、`while`、`for` 等语句的第一行。你一开始大概会忘（多年来成千上万的 Python 学生都是如此），但可以宽慰的是，它很快会变成无意识习惯。
>
> **从第 1 列开始。** 一定要把顶层（不嵌套的）代码放在第 1 列开始。这包括输入模块文件的非嵌套代码，也包括在交互提示符（即 REPL）下输入的非嵌套代码。缩进在 Python 里意味着嵌套，所以顶层不能用缩进。
>
> **交互提示符下空行很重要。** 复合语句中的空行在模块文件中总是无关紧要、会被忽略的；但在交互提示符下输入代码时，空行会**结束**语句。换句话说，空行告诉交互式 REPL"你已经写完一条复合语句了"；如果想继续，在真正写完之前别在 `...` 提示符（如果显示）处按回车。这也意味着你不能在这个提示符下粘贴多行代码；它必须一次运行一整条语句，按需留空行。
>
> **缩进要一致。** 避免在嵌套块的缩进中混用制表符（Tab）和空格。否则，当 Python 把 Tab 按一定空格数计算时，你在编辑器里看到的可能与 Python 看到的不是一回事。这适用于任何块结构语言，不限于 Python——如果下一位程序员 Tab 设置不同，理解你的代码结构将困难甚至不可能。对每个块，全用 Tab 或全用空格更安全。
>
> **别用 C 的风格写 Python。** 给 C/C++ 程序员的提醒：`if` 和 `while` 头的测试条件不需要加括号（如 `if (X==1)`）。你想加也行（任何表达式都可以括在括号里），但在此语境下完全是多余的。同样，不要用分号结束所有语句；Python 里这样做技术上合法，但完全没用——除非你要在一行里放多条语句（行尾通常就是语句的终止）。还有，记住别用 `{}` 包代码块（要一致地缩进你的嵌套代码块），并且除非很简单，否则避免在 `while` 循环测试里嵌赋值语句（虽然 Python 现在用 `:=` 支持了这一点）。
>
> **用简单的 `for` 循环而不是 `while` 或 `range`。** 再提醒一次：简单的 `for` 循环（如 `for x in y`）几乎总是比基于 `while` 或 `range` 的计数器循环更容易编写，而且往往运行更快。在 Python 里要抵制"数数"的诱惑；虽然偶尔必需，但通常都是次优方案。
>
> **当心赋值中的可变对象（mutables）。** 正如之前警告过的，在多目标赋值（`a = b = []`）以及增强赋值（`a += [1, 2]`）中使用可变对象时要小心。两种情况下的原地修改都可能影响其他变量。如果忘了为什么，参见第 11 章的细节。
>
> **别指望原地修改对象的函数有返回值。** 我们之前也遇到过这个老问题：`list.append` 和 `list.sort` 这类原地修改操作（第 8 章介绍）不返回值（除了 `None`），所以调用它们时不应把结果赋给变量。新手常说 `mylist = mylist.append(X)` 想拿到 `append` 的结果，但这会把 `mylist` 赋成 `None`，而不是修改后的列表（事实上你会彻底丢掉对这个列表的引用）。
>
> **调用函数一定要用括号。** 函数名后面必须加括号才能调用它，无论它有没有参数（例如用 `function()`，而不是 `function`）。在本书下一部分你会学到：函数只是带有一种特殊操作（用括号触发的调用）的对象——但你可以像引用任何其他对象一样引用函数而不触发调用。这在文件操作上经常出问题；初学者常用 `file.close` 而不是 `file.close()` 来关闭文件。因为"引用而不调用"是合法的，第一种写法会静默成功，但它并没有关闭文件。
>
> **import 和 reload 不要带扩展名或路径。** 在 `import` 语句里省略目录路径和文件扩展名——写 `import mod`，而不是 `import mod.py`。我们在第 3 章讨论过模块基础，第五部分将继续研究模块。因为模块可能有 `.py` 之外的其他扩展名（如字节码的 `.pyc`），硬编码特定扩展名不只是语法无效，更是不合逻辑。扩展名由 Python 自动挑选，任何平台相关的目录路径语法都来自模块搜索路径设置，而不是 `import` 语句。在我们深入探索之前，import 里就用一个简单的名字。
>
> **其他部分的更多坑。** 也别忘了看第二部分末尾的内置类型警告，它们可能也够格算编码问题。Python 编码中还有一批常见的"坑"——把内置函数的名字重新赋值而弄丢它、用自己的模块名遮蔽库模块、修改可变的参数默认值等等——但我们目前的背景知识还不够覆盖它们。要了解更多 Python 中该做什么、不该做什么，你得继续读下去；后面的部分会扩展我们在这里列出的"坑"和修复方法的清单。

### 深度理解

- **核心概念**：这十一条是第三部分全部"前车之鉴"的集中营——每条都对应一个真实报错或静默 bug。它们的共性：**Python 的语法规则大多来自"缩进即结构"这一个核心决策**（冒号引入块、缩进表示嵌套、行尾结束语句），理解了这一条，一半陷阱自动消失。
- **为什么空行在 REPL 和文件里行为不同**：模块文件由编译器一次解析整个文件，空行自然无关紧要；REPL 是"逐条语句解析"的——空行是解释器判断"复合语句是否输入完毕"的哨兵信号。这是交互式解释执行的直接后果，也是"粘贴多行代码失败"的根源。
- **Tab 与空格混用的本质**：Python 把 Tab 当做一个逻辑缩进单位（对 8 个空格），与编辑器显示宽度可能不同——"所见非所得"。这就是 PEP 8 推荐 4 空格且禁 Tab 混用的原因。
- **"别用 C 风格写 Python"的深层原因**：括号、分号、花括号在 C 里是语法必需，在 Python 里是纯噪音——因为 Python 的设计目标是"可读代码优先"，语法元素越少，代码越干净。`:=` 海象运算符（第 11 章）虽支持在条件里赋值，但"简单才用"是社区共识。
- **可变对象陷阱回顾**：`a = b = []` 让两个名字指向**同一个**列表对象，任何 `a.append()` 都会影响 `b`；`a += [1,2]` 对列表是原地扩展，同样会影响其他引用者。根因是"名字是引用、可变对象原地变化"的内存模型（第 6、11 章）。
- **`mylist = mylist.append(X)` 的经典事故**：`append` 返回 `None`——把 `mylist` 覆盖为 `None` 就再也找不到原列表。这个 bug 新手几乎必踩一次，根因是把"原地修改"方法当成"返回新值"的函数。对比：`sorted()` 返回新列表，`list.sort()` 原地修改——**记住"原地修改的方法返回 None"这个规律**。
- **`file.close` 不调用 bug**：函数是对象，引用它合法且静默——错误不会报，文件却没关。这也是"函数调用必须带括号"为什么是 Python 新手第一条铁律。
- **初学者误区总结**：① 以为这些"坑"会随经验自然消失——不会，它们会换个样子出现；② 只记报错信息不记根因——报错（如 SyntaxError）反而好修，静默错误（`None` 赋值、`file.close`）才致命；③ 把"能运行"当"正确"——许多陷阱正是"运行了但行为不对"。

### 参考答案

> 1. Documentation strings (docstrings) are considered best for larger, functional documentation, describing the use of modules, functions, classes, and methods in your code. Hash-mark comments are better limited to smaller-scale documentation about arcane expressions or statements at strategic points on your code. This is partly because docstrings are easier to find in a source file (they have specific locations), but also because they can be extracted and displayed by the Pydoc system.
>    文档字符串（docstring）被认为最适合较大规模的功能性文档，描述你代码中模块、函数、类和方法的使用。井号注释更适合局限于较小规模的文档——针对代码中战略位置的晦涩表达式或语句。这既是因为 docstring 在源文件中更容易找到（它们有特定位置），也是因为它们能被 Pydoc 系统提取和显示。

> 2. You can see docstrings by printing an object's `__doc__` attribute, by passing it to Pydoc's `help` function, and by selecting modules in Pydoc's HTML-based browser interface. The latter is launched with a `-b` command-line switch, and runs a client/server system that displays documentation in a popped-up web browser. Pydoc can also be run to save a module's documentation in an HTML file for later viewing or printing.
>    查看 docstring 的方式：打印对象的 `__doc__` 属性；把它传给 Pydoc 的 `help` 函数；以及在 Pydoc 的 HTML 浏览器界面中选择模块。后者用 `-b` 命令行开关启动，运行一个客户端/服务器系统，在弹出的 Web 浏览器中显示文档。Pydoc 也可以运行来把模块文档保存为 HTML 文件，供日后查看或打印。

>    内置 `dir(X)` 函数返回附着在任何对象上的所有属性的列表。像 `[a for a in dir(X) if not a.startswith('__')]` 这样的列表推导式可以用来过滤掉带下划线的内部名字（本书下一部分你会学到如何把它包进函数以复用）。

### 15.14.4 练习 4：字典排序（Sorting dictionaries）

### 深度理解（练习 4 详解）

- **关键背景**：Python 3.7+ 字典**保持插入顺序**（这是 CPython 3.6 的实现细节升级为语言保证）——但"插入顺序"≠"排序顺序"。要按升序打印，必须显式排序。
- **两条路线**：① 传统：`keys = list(d.keys())` + `keys.sort()` 再遍历；② 现代：`for k in sorted(d): print(k, d[k])`——`sorted()` 返回新排序列表，不修改原字典。第二条更 Pythonic（`sorted` 是 15.11 节"用简单工具"精神的体现）。
- **这个练习的深意**：把"数据"与"呈现顺序"分离——排序是视图层面的需求，不该改动存储结构。这也是后面学函数/类时"职责分离"思想的雏形。

### 深度理解（练习 5 详解）

- **这个练习的主题：渐进式简化（refactoring）**。五步改造的本质是同一逻辑的五个表达层次：手工计数器（while+flag）→ 循环语义（while-else）→ 迭代（for-else）→ 成员测试（`in`）→ 数据生成（append 循环 / map / 推导式）。**每一步都在把"实现细节"换成"意图表达"**——这是 Pythonic 编程的核心训练。
- **`while...else` / `for...else` 的语义**：循环正常结束（未被 `break` 打断）时执行 `else` 块。用它做"查找成功/失败"的分支，天然替代 flag——这是许多语言没有的语法，也是新手最容易忽略的 Python 特性。
- **`in` 运算符一行解决**：`32 in L` 由解释器调用列表的 `__contains__` 完成查找——C 层实现，快且干净。查找类需求优先想 `in` 而不是自己写循环。
- **性能问题的标准答案**：`2 ** X` 不依赖循环变量 `i`，是**循环不变式**（loop-invariant）——应在循环前算出一次：`p = 2 ** X`。解释器虽然不会自动提升它（Python 无此优化，每次迭代都重新求值），但程序员手动提升是常识。
- **`map(lambda x: 2 ** x, range(7))`**：`lambda` 是匿名函数（第 19 章），`map` 惰性求值（第 14 章）——返回迭代器而非列表，需 `list()` 包一层才见结果。列表推导式 `[2 ** x for x in range(7)]` 更直白——这正是"推导式常优于 map+lambda"的著名论战主题。
- **初学者误区**：① 写 `while` 循环时忘了 `i = i + 1` 导致死循环；② 不知道 `else` 子句存在，全靠 flag；③ 以为"循环越多代码越正规"——恰恰相反，Python 鼓励用更高级的抽象（in、推导式、map）消灭循环。

# 本章总结

## 技术拓展（Technical Expansion）

### 1. 实际项目中的应用场景

- **docstring + `__doc__`**：团队代码库的"组件说明书"。现代 Python 库（pandas、requests、Django）的每个公开函数都带 docstring——它同时服务人类阅读（`help()`）和机器提取（Sphinx 生成 API 文档）。
- **`help()` 的日常地位**：任何 REPL/IPython/Jupyter 环境里，"不会用的函数先 `help()` 一下"是职业习惯。`help()` 里没有的细节再查官方 Library Reference——这是"自学闭环"的标准路径。
- **`dir()` 的探测价值**：接手陌生对象（尤其第三方库实例）时，`dir(obj)` + 推导式过滤是"逆向侦察"的第一步——先看有哪些属性，再逐一对感兴趣的属性 `help()`。
- **Pydoc 与团队内部文档**：`python3 -m pydoc -w 你的模块` 可以把模块文档导出成 HTML 文件，直接挂到内网文档站——不引入 Sphinx 也能享受"文档产品化"。
- **doctest 的相关性**：本书本章未展开，但值得知道——标准库 `doctest` 模块会**运行 docstring 里的示例代码并比对输出**，把文档变成可执行的测试（`python -m doctest -v 文件.py`）。docstring 因此可以一鱼两吃：文档 + 回归测试。这是 Python 文档生态的独特优点（其他语言少有"注释即测试"）。

### 2. 与其他语言（Java/C++）的区别

| 维度 | Python | Java | C++ |
|---|---|---|---|
| 注释类型 | `#` 注释 + docstring（运行时对象属性） | `//`、`/* */` + Javadoc（独立注释格式） | `//`、`/* */`（无官方文档格式） |
| 文档可编程性 | `__doc__` 是真实属性，运行时可用 | Javadoc 注释经工具提取，运行时不可见 | 注释纯文本，运行时不可见 |
| 内置文档工具 | `help()`、Pydoc 随标准库自带 | javadoc 命令需 JDK 自带工具 | Doxygen 需第三方安装 |
| 文档与测试联动 | doctest 直接执行 docstring 示例 | JUnit 需另写测试类 | Google Test 等需另写 |
| 注释风格 | 缩进即结构，无块注释语法 | 块注释丰富 | 块注释丰富 |
| 标准参考 | 官方手册（Library + Language Reference）在线权威 | JavaDoc + 官方规范（JLS） | cppreference、ISO 标准 |

**核心洞察**：Python 是唯一把"文档作为运行时数据"的主流语言——Javadoc 注释在编译器眼里就是垃圾，而 Python 的 docstring 是对象的一部分。这带来连锁反应：`help()`、Pydoc、Sphinx、doctest 全部建立在这一个设计决定之上。

### 3. Python 发展历史背景

- **docstring 的起源**：Python 1.x 时期，Guido 从 Unix 手册页文化和 Lisp 的"属性即数据"思想获得启发，把"字符串放在定义体开头"约定为文档，并存入 `__doc__`。这是"约定优于配置"的早期范例。
- **Pydoc 的诞生**：1998 年前后由 Ka-Ping Yee 编写，2000 年随 Python 1.6/2.0 进入标准库。它的设计目标就是让文档"像 man 手册一样"触手可得。
- **PEP 257（2001）**：正式规范 docstring 约定——三引号、首行摘要句、多行结构。它和 PEP 8 一起成为 Python 代码外观的"宪法"。
- **Sphinx（2008，Python 2.6/3.0 时代）**：由 Georg Brandl 开发，替代了旧的 LaTeX 文档方案——python.org 官方文档自此用 Sphinx 生成，并迅速成为开源文档的事实标准（Read the Docs 平台即基于它）。
- **`help()` 与 REPL 文化**：Python 的交互式哲学（"REPL 是第一文档"）由 IDLE 和 pydoc 共同塑造——在任何环境里按 `help()` 就能读书，这种体验至今是 Python 学习者的特权。
- **3.13 的 docstring 演进**：编译器层面剥离 docstring 前导缩进以节省字节码空间——说明"文档基础设施"仍在持续优化，即使功能上早已成熟。

### 4. 高级开发者需要掌握的相关知识

- **`inspect` 模块**：Pydoc 的"侦察兵"。`inspect.getdoc`（取 `__doc__` 并清理缩进）、`inspect.signature`（取签名）、`inspect.getsource`（取源码文本）——写调试工具、测试框架、ORM 的必备。
- **`__doc__` 与元编程**：装饰器（第 19 章）和类装饰器（第 32 章）容易"吞掉"被包装对象的 `__doc__`，工程上常用 `functools.wraps` 修复——这是"文档作为运行时数据"在实际工程中的著名坑点。
- **文档生成工程**：Sphinx + autodoc（从 docstring 自动提取）、MkDocs + Material、MyST（reStructuredText 的 Markdown 方言）、Read the Docs 发布流程——一个正规开源项目的文档管线。
- **typing 与文档的融合**：PEP 484 类型注解 + PEP 257 docstring + `sphinx-autodoc-typehints`，让"签名、类型、说明"三位一体。现代大型项目（如 pandas）已全面采用。
- **`sys.modules` 与导入副作用**：理解"导入即执行"模型（Pydoc 的运行基础），以及 `if __name__ == '__main__'` 守卫的工程意义——这是所有"可导入又可运行"模块的规范写法。
- **doctest / pytest --doctest-modules**：把 docstring 示例纳入自动化测试套件——文档漂移（doc rot）的天敌。
