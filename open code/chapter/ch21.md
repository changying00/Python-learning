## 21.2 使用自制工具进行基准测试（Benchmarking with Homegrown Tools）

### 英文原文

> We've met quite a few iteration alternatives in this book. Like much in programming, they represent trade-offs—in terms of both subjective factors like expressiveness, and more objective criteria such as performance. Part of your job as a programmer and engineer is selecting tools based on factors like these.
>
> In terms of performance, this book has mentioned a few times that list comprehensions and *map* calls sometimes have a speed advantage over *for* loop statements. It has also noted that sorting speed varies with ordering, and the generator functions and expressions of the preceding chapter tend to be slower than all the others, though they minimize memory space requirements and don't delay the caller for result generation when there are many results to generate.
>
> All that is generally true today in common usage. That being said, benchmarking comes with some big caveats: both code structure and host architecture can influence speed arbitrarily; Python's performance can vary over time because its internals are constantly being changed and optimized; and the speed of alternative Pythons may differ widely. As noted in Chapter 2, for example, the standard *CPython* may adopt a standard JIT in the future which could change its speed in some contexts, and optimized Pythons like *PyPy* have very difference performance profiles.
>
> In short, if you want to verify speed for yourself, you need to time your code, on your own device, with the Python or Pythons you plan to use, and in the here and now. That's a lot of qualifiers, but benchmarking is an empirical task.

### 中文翻译

> 我们在本书中已经遇到过相当多的迭代替代方案。和编程中的大多数事情一样，它们代表着权衡（trade-offs）——既涉及"表达力"这类主观因素，也涉及"性能"这类更客观的标准。作为程序员和工程师，你的部分工作就是根据这些因素挑选工具。
>
> 就性能而言，本书已经提过几次：列表推导（list comprehensions）和 *map* 调用有时比 *for* 循环语句更快。书中也指出过：排序速度随数据顺序变化，上一章的生成器函数（generator functions）和生成器表达式（generator expressions）往往比所有其他方案都慢——尽管它们把内存空间需求降到最低，而且在结果很多时不会让调用方在生成结果这件事上等待。
>
> 在今天的常见用法中，上述说法大体上都成立。话虽如此，基准测试附带着一些重大警告：代码结构和宿主架构都可能任意影响速度；Python 的性能会随时间变化，因为它的内部实现一直在被修改和优化；不同 Python 实现的速度可能差异巨大。例如，正如第 2 章所述，标准的 *CPython* 未来可能采用标准 JIT，这会在某些场景下改变它的速度；而像 *PyPy* 这样的优化版 Python 有着非常不同的性能画像（performance profiles）。
>
> 简言之，如果你想亲自验证速度，就需要**在自己的设备上、用你计划使用的那个或那些 Python、在此时此刻**给代码计时。限定条件很多，但基准测试本来就是一个经验性（empirical）任务。

### 深度理解

- **核心概念**：迭代工具的取舍 = 主观维度（可读性、表达力）+ 客观维度（速度、内存）。本章只量化"速度"这一维，但选择工具时必须综合权衡——生成器虽然最慢，却是内存冠军。
- **底层视角**：速度差异来自解释器内部实现的差别：`map` 的循环在 C 层运行，列表推导有专门的字节码优化，而生成器每次产出值都要保存/恢复执行状态（帧对象的状态机）。这些差异要到本章后面才会用数据揭示。
- **设计原因**：作者反复加限定词（"一般来说""今天的常见用法"），是因为 Python 内部变化太快，任何绝对论断都会过时。JIT 与否、版本差异、宿主架构都是变量。
- **实际问题**：如果程序要处理海量数据，迭代方式的选择可能决定运行时间是几秒还是几分钟；但若数据量很小，任何方式都快，可读性才是首要的。
- **初学者误区**：把"书上说 map 快"当成普适结论，不做任何验证。作者的忠告很直白：**测速是一个经验任务**——就像称体重，别人的秤不能代表你的体重。

## 21.3 计时模块：第一版（Timer Module: Take 1）

### 英文原文

> Luckily, Python makes it easy to time code with custom tools—though perhaps deceptively so. For example, to get the total time taken to run multiple calls to a function with arbitrary positional arguments, Example 21-1's function coded in a module file might suffice as a first cut.

### 中文翻译

> 幸运的是，用自定义工具给代码计时在 Python 中很容易——尽管也许容易得具有欺骗性。例如，要获得"用任意位置参数多次调用一个函数"所花的总时间，把 Example 21-1 的函数写进一个模块文件，作为第一版或许就够用了。

### 代码分析

```python
"""极简计时函数"""
import time

def timer(func, *args):                       # 任意位置参数（仅此而已）
    start = time.perf_counter()               # 记录起始时间
    for i in range(100_000):                  # 写死的重复次数，range() 也被计时
        func(*args)                           # 调用被测函数
    return time.perf_counter() - start        # 总耗时（秒）
```

- **解释器如何处理**：`time.perf_counter()` 是标准库 `time` 模块提供的高分辨率时钟，专为测量短时耗时设计，跨平台可移植。它返回系统级时间（包含 sleep 的时间、受系统负载影响）。`time.process_time()` 则是"本进程 CPU 时间"，不含睡眠和系统其他活动，在某些场合更合适。本书上一版用的 `time.clock()` 已被弃用并从 Python 中删除。
- **设计思想**：这是"第一版"，作者故意让它犯下一系列经典错误，好引出改进版。它把重复次数硬编码为 100k；`range(100_000)` 的构造与迭代开销被计入被测函数的时间；不支持关键字参数；不返回被测函数的结果，调用方无法验证函数是否真的正常工作；只给总时间，在繁忙的宿主机器上会波动。

### 英文原文

> This function fetches time values from Python's standard-library *time* module, and subtracts the system start time from the stop time after running 100,000 calls to the passed-in function with the passed-in arguments.
>
> Time comes from *time.perf_counter*, which is defined to be a portable clock with the best resolution to measure a short duration. The difference between two calls is generally used for performance measurement, but includes time for sleeps and is system-wide time. The alternative *time.process_time* is per-process CPU time, and may also be useful in some roles. See Python's manuals for more details; these calls replace the former and less portable *time.clock*, which was deprecated and dropped since this book's prior edition (breaking most examples here!).
>
> Apart from its *time* calls, the code in Example 21-1 is straightforward and uses tools we've already met. When used on this book's main development computer using macOS and CPython 3.12, its results are these in a REPL:

### 中文翻译

> 这个函数从 Python 标准库的 *time* 模块取时间值，在调用传入函数 10 万次之后，用停止时间减去系统起始时间。
>
> 时间来自 *time.perf_counter*，它被定义为一个可移植的时钟，具有测量短时耗时的最佳分辨率。两次调用的差值通常用于性能测量，但它包含睡眠时间，并且是系统范围的时间。另一个选择 *time.process_time* 是每进程的 CPU 时间，在某些角色中也可能有用。更多细节见 Python 手册；这些调用取代了以前那个可移植性较差的 *time.clock*，后者在本书上一版之后已被弃用并移除（导致这里大多数示例崩掉！）。

> Though functional and simple, the preceding timer is also fairly limited, and deliberately exhibits some classic mistakes in both function design and benchmarking. Among these, it:

### 中文翻译

> 尽管功能可用、写法简单，上面的计时器也相当受限，而且作者故意让它表现出函数设计和基准测试方面的一些经典错误。其中包括：
>
> - 把*重复次数*硬编码为 10 万次
> - 把 *range* 的成本计进了被测函数的时间
> - 不支持被测函数使用*关键字*参数
> - 没有给调用方*验证*被测函数是否真正工作的途径
> - 只给出*总*时间，在忙碌的宿主机器上可能会波动
>
> 换句话说，计时代码比你想象的更复杂！

### 深度理解

- **核心概念**：好的计时工具必须做到"**测量的纯粹性**"——只测被测函数本身的开销，不掺入计时器自己（如 `range` 的构造、参数打包解包、额外的打印）的开销；还要"**可验证性**"——返回函数的结果，确认测的是正确的计算。
- **底层实现**：`time.perf_counter` 在 CPython 中最终落到操作系统提供的高分辨率时钟（Windows 上是 `QueryPerformanceCounter`，Linux 上是 `clock_gettime(CLOCK_MONOTONIC)`，macOS 上是 `mach_absolute_time`）。它是"单调"（monotonic）时钟——不会因为系统时间被调整而跳变，适合做差值测量。这就像用高精度秒表，而不是看墙上的挂钟。
- **设计原因**：第一版如此简陋，是教学上的"诱饵"：让你亲身体会"计时代码为何比想象复杂"。每一条缺陷都会在第二版中被对应地修复，形成强烈的对比记忆。
- **实际问题**：真实世界里，重复次数必须可调（太快的一次调用测不出有效数据，太慢的又浪费时间）；被测函数可能既有位置参数又有关键字参数；忙碌机器上单次总时间会抖动，需要"取多轮最小值"来过滤。
- **初学者误区**：把 `time.clock()` 当标准写法（它已随 Python 3.8 移除）；只测一次就下结论；或者忘了验证被测函数真的干活了——如果函数因为 bug 瞬间返回，时间会"快"得让你误判。

## 21.4 计时模块：第二版（Timer Module: Take 2）

### 英文原文

> To be more general and accurate, let's rewrite the preceding section's code to define still simple but more useful *timer* utility functions we can both use to see how iteration alternative options stack up now, and apply to other timing needs in the future. These functions, in Example 21-2, are coded in a module file again so they can be used in a variety of programs, and have docstrings giving some basic usage details that *help* and PyDoc can display; see Chapter 15 for tips on viewing the in-code documentation of this chapter's timing modules.

### 中文翻译

> 为了更通用、更准确，让我们重写上一节的代码，定义依然简单但更有用的 *timer* 工具函数——既用于评估各种迭代替代方案当下的表现，也可在未来应用到其他计时需求。Example 21-2 中的这些函数仍然写在一个模块文件里，这样就能被各种程序复用；它们带有 docstring，给出一些基本用法说明，*help* 和 PyDoc 可以显示这些文档；查看本章计时模块代码内文档的技巧见第 15 章。

### 代码分析

```python
"""
自制通用函数调用计时工具。
对单次调用、N 次总计、N 次最佳、以及"N 组总计"的最佳计时。
每个 func 可传任意数量的位置参数和关键字参数。
"""
import time
timer = time.perf_counter                          # 也可以换成 time.process_time()

def once(func, *pargs, **kargs):                   # 收集 func 的参数
    """
    运行 func(...) 一次的时间。
    返回 (时间, 结果)。
    """
    start = timer()                                # 记录起始时间
    result = func(*pargs, **kargs)                 # 解包参数调用 func
    elapsed = timer() - start                      # 计算耗时
    return (elapsed, result)                       # 返回结果以便验证

def total(reps, func, *pargs, **kargs):            # 收集 func 的参数
    """
    func(...) 运行 reps 次的总时间。
    返回 (总时间, 最后一次的结果)。
    """
    total = 0                                      # 不把 range() 的时间计入
    for i in range(reps):
        time, result = once(func, *pargs, **kargs)
        total += time
    return (total, result)                         # 返回最后一次结果以便验证

def bestof(reps, func, *pargs, **kargs):
    """
    func(...) 运行 reps 次中的最佳时间。
    返回 (最佳时间, 最佳时间对应的结果)。
    """
    return min(once(func, *pargs, **kargs) for i in range(reps))

def bestoftotal(reps1, reps2, func, *pargs, **kargs):
    """
    在 reps1 组 [每组运行 func(...) 共 reps2 次] 中取最佳总时间。
    返回 (最佳总时间, 最佳总时间对应的最后一次结果)。
    """
    return min(total(reps2, func, *pargs, **kargs) for i in range(reps1))
```

- **解释器如何处理**：`*pargs, **kargs` 是星号参数（starred arguments）：在函数头部把调用时多余的位置参数收进元组、关键字参数收进字典；调用 `func(*pargs, **kargs)` 时再反向解包。这两步都有微小开销，但换来的是"任意参数形状的被测函数都能测"。`once` 返回 `(elapsed, result)` 元组：时间在前、结果在后——这个顺序是刻意的，因为后面 `min` 比较元组时"从左到右逐项比较"，时间项先比，就能按时间取最小。
- **设计思想**：**把"测一次"做成原子操作**（`once`），其他模式（total/bestof/bestoftotal）都建立在它之上。这样 `range(reps)` 的构造与迭代成本只发生在 `total` 的外层，不再混入被测函数的时间——这正是第一版"range 被计时"缺陷的修复。

### 英文原文

> Operationally, this module implements both *total* and *best* times, and a *best of totals* that combines the other two. In each mode, it times calls to any subject function that takes any positional and keyword arguments, by fetching the start time, calling the function with arbitrary arguments, and subtracting the start time from the stop time. Here are the salient points to notice about how this version addresses the shortcomings of its predecessor:
>
> - The *repetitions* count is no longer hardcoded, but passed in as a required argument (or arguments) before the test function and its own arguments, to allow repetitions to vary per call.
> - The *range* call's construction and iteration costs are no longer charged to timed functions, because timing has been factored out to the separate *once* function that times just the subject function.
> - Any number of both positional and *keyword* arguments for the timed function are now collected and unpacked with starred-argument syntax. They must be sent individually, not in a sequence or dictionary, though callers can unpack argument collections into individual arguments with stars in the top-level call.
> - All functions in this module return one of the timed function's *return values* so callers can verify that the function worked. The return value is provided in a two-item result tuple, along with the requested time result.
> - New best-of modes return *minimum* times to address fluctuations on the host device, per the next paragraph.
>
> This version's functions also support multiple use cases: *once* times a single call for simple cases; *total* runs many calls, to allow time to accumulate for short-lived functions; *bestof* returns the minimum time among all single calls, to filter out the impacts of other activity on the host; and *bestoftotal* selects the minimum of nested total-time tests, to both apply a best-of filter and run many calls for functions too fast to produce meaningful times.
>
> Importantly, the *min* calls in the best-of variants work to select the best and lowest time, because Python compares collections recursively (from left to right) as we've learned, and result tuples begin with *time*: because it's first in these (*time*, *result*) tuples, time dominates and determines the *min* calls' results:

### 中文翻译

> 在操作层面，这个模块同时实现了 *total*（总计）和 *best*（最佳）时间，以及把两者结合的 *best of totals*（总计中的最佳）。每种模式下，它都是取开始时间、用任意参数调用被测函数、再用停止时间减去开始时间，从而对任何接受任意位置参数和关键字参数的被测函数计时。下面是要注意的要点，说明这一版如何解决前一版的缺陷：
>
> - *重复次数*不再硬编码，而是作为必需参数传在测试函数及其自身参数之前，从而允许每次调用按需变化重复次数。
> - *range* 调用的构造与迭代成本不再计入被测函数，因为计时已被拆到独立的 *once* 函数，它只测被测函数本身。
> - 被测函数的任意数量的位置参数和*关键字*参数现在都用星号参数语法收集和解包。它们必须逐个发送，不能装在序列或字典里——不过调用方可以在顶层调用中用星号把参数集合展开成单个参数。
> - 这个模块的所有函数都返回被测函数的某个*返回值*，让调用方可以验证函数确实工作了。返回值连同请求的时间结果一起，放进一个二元组返回。
> - 新的 best-of 模式返回*最小*时间，用于应对宿主设备的波动，详见下一段。
>
> 这一版的函数还支持多种使用场景：*once* 对单次调用计时，用于简单情形；*total* 运行多次调用，让时间在短命函数上得以累积；*bestof* 返回所有单次调用中的最小时间，过滤掉宿主机上其他活动的影响；*bestoftotal* 在嵌套的总时间测试中取最小，既应用了 best-of 过滤，又对快得测不出有意义时间的函数运行多次调用。
>

### 深度理解

- **核心概念**：一个成熟的计时器需要四种模式：`once`（单次）、`total`（多次累积，对付太快的函数）、`bestof`（多次取最小，过滤宿主抖动）、`bestoftotal`（嵌套组合：既取最小又累积次数）。每种模式应对一种真实测量场景。
- **底层实现**：`min` 比较元组时按元素从左到右递归比较——`(time, result)` 中 time 在前，所以当 time 不同时 result 根本不会被比较。这是元组排序语义的巧妙利用：**零额外代码就实现了"按时间取最小，结果作陪跑"**。若把 result 放前面，min 就会按结果比较，逻辑立刻出错。
- **设计原因**：所有函数都返回 `(时间, 结果)` 元组，是为了让调用方既能看时间又能验证正确性——计时和正确性必须绑定，否则测出的"快"可能是 bug 造成的。
- **实际问题**：嵌套调用（把 `timer.total` 当被测函数传给 `bestof`）会把 total 自己的管理代码（`for i in range(reps)`、累加 `total += time`）也计进时间，导致数据偏高。这就是"测谁、就只该包含谁的开销"的测量原则。
- **初学者误区**：以为"结果元组里有什么"无所谓；或者想当然认为嵌套组合等价。实际上参数顺序、元组元素顺序、嵌套层级都会改变测量语义——基准测试是**极其挑剔**的活。

## 21.5 计时运行器与脚本（Timing Runner and Script）

### 英文原文

> Now, to time iteration tool speed (our original goal), we'll write a script that defines and submits test *functions* to the *timer* module. To make it easy to code a variety of tests, let's first define a utility module that does the heavy lifting as a reusable intermediary. ### 中文翻译

### 代码分析

```python
"""用 timer.py 模块运行传入的测试函数"""
import timer, sys

def runner(*tests):
    results = []
    print('Python', sys.version.split()[0], 'on', sys.platform)  # 显示运行环境

    # 计时
    for test in tests:
        besttime, result = timer.bestoftotal(10, 1000, test)    # 10 组、每组 1000 次
        results.append(result)
        print(f'{test.__name__:<9}: '      # 左对齐占 9 个字符，输出函数名
              f'{besttime:.5f} => [{result[0]}…{result[-1]}]')  # 5 位小数 + 首尾元素

    # 验证
    print('Results differ!'                # 只要有结果不同就报警
          if any(result != results[0] for result in results[1:])
          else 'All results same.')
```

- **解释器如何处理**：`sys.version.split()[0]` 取出版本号字符串（如 "3.12.2"），`sys.platform` 是平台名（如 'darwin'/'win32'）。`test.__name__` 是函数的天然属性——函数对象上挂着一个名字属性。最后的输出用一个三元表达式做"全等性验证"：把每个测试函数的结果与第一个对比，任何一个不同就打印 'Results differ!'。这是**对照实验的校验环节**：如果五种写法结果都不同，说明被测代码本身有 bug，计时毫无意义。
- **设计思想**：runner 是"测试框架"的雏形——把"计时"和"被测内容"分离。后面换被测函数、换测试语句，runner 一行不用改。

### 英文原文

> Fine points here: this module's *runner* function displays context with *sys* tools documented in Python's manuals, and steps through all the passed-in functions, printing the *__name__* of each (as we've seen, this is a built-in attribute that gives a function's name). The test-runner code also saves results to verify that they are all the same in a ternary expression at the very end of the process, to be sure we're comparing apples to apples.
>
> Last but not least, the script in Example 21-4 defines the actual tests to be timed and passes them to the imported runner of Example 21-3, which hands them off to the imported timer of Example 21-2. We'll run the file in Example 21-4 as a top-level script to time the relative speeds of the various iteration codings we've studied in this book so far.

> 这里的细节：这个模块的 *runner* 函数用 Python 手册中记载的 *sys* 工具显示运行环境，并遍历所有传入的函数，打印每个函数的 *__name__*（如我们所见，这是一个内建属性，给出函数的名字）。测试运行器代码还保存了各结果，在过程最末尾用一个三元表达式验证它们全部相同，确保我们在拿苹果和苹果比。

### 代码分析

```python
"""测试各种迭代写法替代方案的相对速度。"""
from timer_runner import runner

repslist = list(range(10_000))        # 升到模块顶层：range 构造成本不计入总时间

def forLoop():                        # for 循环 + append 写法
    res = []
    for x in repslist:
        res.append(abs(x))
    return res

def listComp():                       # 列表推导写法
    return [abs(x) for x in repslist]

def mapCall():                        # map 调用写法
    return list(map(abs, repslist))   # 用 list() 强制产生结果

def genExpr():                        # 生成器表达式写法
    return list(abs(x) for x in repslist)   # 用 list() 强制产生结果

def genFunc():                        # 生成器函数写法
    def gen():
        for x in repslist:
            yield abs(x)
    return list(gen())                # 用 list() 强制产生结果

runner(forLoop, listComp, mapCall, genExpr, genFunc)
```

- **解释器如何处理**：三种惰性对象必须被"激活"——`map` 结果、生成器表达式、生成器函数返回的都是惰性迭代器，不消费就不会执行任何实际计算。用 `list()` 包装后，所有元素被逐一取出放入列表，实际工作才发生。`repslist = list(range(10_000))` 被提到模块顶层：`range` 本身是惰性序列，直接 `for x in range(...)` 会让"构造并遍历 range"的开销混进被测时间，先转成列表就能把这部分成本移出测量窗口。作者实测：去掉这个 list 包装，测试时间会膨胀约 25%。
- **设计思想**：**控制变量**是基准测试的灵魂。五种写法除了"迭代机制"不同，其余一切（数据、强制求值方式、列表构建）都保持相同，这样测得的时间差异才能归因于迭代机制本身。

### 英文原文

> This script tests five alternative ways to build lists of results. In combination with the test runner, its reported times reflect some 100 million steps for each of the 5 test functions—each builds a list of 10,000 items 1,000 times, and this process is repeated 10 times to get the best-of times. Applying this for each of the 5 test functions yields a whopping 500 million total steps for the script at large (impressive but reasonable on most machines these days).
>
> Notice how we have to run the results of the generator expression and function through the built-in *list* call to force them to yield all of their values; if we did not, we would just produce generators that never do any real work. We must do the same for the *map* result, since it is an iterable, on-demand object as well. For similar reasons, the inner loops' *range* result is hoisted out to the top of the module to remove its construction cost from total time, and wrapped in a *list* call so that its traversal cost isn't skewed by being a generator. This may be overshadowed by the cost of the inner iterations' loops, but it's best to remove as many variables as we can. For example, though *range* supports multiple scans, tests' times inflate by some 25% if its *list* wrapper is removed.

### 中文翻译

> 这个脚本测试了构建结果列表的五种替代方式。与测试运行器配合后，它报告的时间对应每个测试函数约 1 亿步的工作量——每个函数构建 1 万个元素的列表 1000 次，这个过程再重复 10 次以取得 best-of 时间。对 5 个测试函数逐一应用，整个脚本合计高达 5 亿步（在如今的多数机器上很惊人，但也算合理）。
>
> 注意，我们必须把生成器表达式和生成器函数的结果送入内置 *list* 调用，强制它们产出所有值；如果不这么做，我们得到的只是从不干活的生成器。*map* 结果也必须同样处理，因为它同样是一个按需迭代的可迭代对象。出于类似原因，内层循环的 *range* 结果被提升到模块顶部，以把它构造的成本移出总时间，并且用 *list* 调用包住，使遍历成本不会因为它是生成器而失真。这也许会被内层迭代循环的开销掩盖，但最好还是尽可能移除变量。例如，尽管 *range* 支持多次扫描，但如果去掉它的 *list* 包装，测试时间会膨胀约 25%。

### 深度理解

- **核心概念**：**控制变量法**——被测的五种写法唯一区别是"迭代机制"。列表推导/生成器都用 `list()` 强制求值，`range` 提前转成列表，参数统一，返回结构统一（首尾元素一样）。
- **底层实现**：惰性（lazy）对象只在你真正迭代它时才干活：`map` 返回的 map 对象、生成器表达式返回的生成器，都是一次性、按需产出的状态机。不 `list()` 包一层，计时器测到的是"创建一个不干活的生成器"的时间——约等于零，数据完全失真。
- **设计原因**：`range` 提为模块级 `repslist`，是因为 `range(10_000)` 每次执行都要构造对象，虽然便宜，但在 5 亿步的测量中任何一点无关开销都会污染结论。作者实测其影响高达 25%——**测量时必须把"被测代码"以外的成本降到最低**。
- **实际问题**：生成器表达式必须在循环体外用 `list()` 收集，这正是它"延迟产出"特性的代价；这个代价本身也是它比列表推导慢的部分原因（后面会看到数据）。
- **初学者误区**：直接写 `map(abs, repslist)` 或裸生成器表达式去测时间，测出"0 秒"就以为 map 无敌——其实是生成器没被消费，什么也没发生。惰性对象必须被耗尽，测量才有意义。

> 对生成器测试来说，我们实际上也把 *list* 调用的时间计了进去，但考虑到这似乎并没有拖累 *map*，很可能无关紧要。尽管造成差异的确切原因需要更深入的分析（可能要钻源码），但考虑到生成器表达式在产出值时必须做额外的保存/恢复状态的工作，这个差异就说得通了；列表推导不需要这些，因此在本文以及后面其他测试中跑得更快。

### 深度理解

- **核心概念**：在 CPython 3.12 上、这个测试场景里，速度排名是：`map` > 列表推导 > `for` 循环 > 生成器表达式 ≈ 生成器函数。**"All results same."** 这一行是结论可靠性的基石——五种写法产出相同的结果，速度差异才归因于实现方式。
- **底层实现**：`map` 的迭代循环整体运行在 C 层（每步只调用一次 Python 函数）；列表推导有专门的字节码（BUILD_LIST、迭代器协议内联优化）；`for` 循环要频繁执行 `append` 方法查找和调用；生成器则每产出一次值都要保存/恢复帧状态（即"状态机"开销）。生成器表达式比列表推导慢一倍，正是这种每步状态保存/恢复成本的实证。
- **设计原因**：作者特意选择 `abs`（内置函数）作为每步操作，是想让五种写法处在"都必须调用函数"的同一起跑线上；在这个场景下 map 因 C 层循环获胜。
- **实际问题**：如果程序是 CPU 密集型的纯迭代，选 map 或列表推导能省三分之一以上的时间；但内存敏感场景（处理超大数据流）生成器的内存优势可以轻松抵消速度劣势。
- **初学者误区**：把这次测试的排名当成永恒真理——换 Python 版本、换操作符、换机器，排名都可能变（本章后面 PyPy、`+` 运算两个测试就当场打脸）。

### 代码分析

```python
"""对 reps 使用带默认值的关键字专用参数，对 func 使用仅限位置的参数。"""
import time
timer = time.perf_counter

def once(func, /, *pargs, **kargs):
    start = timer()
    result = func(*pargs, **kargs)
    elapsed = timer() - start
    return (elapsed, result)

def total(func, /, *pargs, _reps=100_000, **kargs):
    total = 0
    for i in range(_reps):
        time, result = once(func, *pargs, **kargs)
        total += time
    return (total, result)

def bestof(func, /, *pargs, _reps=5, **kargs):
    return min(once(func, *pargs, **kargs) for i in range(_reps))

def bestoftotal(func, /, *pargs, _reps1=50, **kargs):
    return min(total(func, *pargs, **kargs) for i in range(_reps1))   # _reps 走 **kargs
```

- **解释器如何处理**：`/` 是 Python 3.8+ 的"仅限位置"参数分隔符——`/` 之前的参数（这里是 `func`）只能按位置传，绝不能写成 `func=...` 这样的关键字形式。这样被测函数即使有名为 `func` 的关键字参数，也不会与计时器自己的形参冲突。`_reps` 放在 `*pargs` 之后、`**kargs` 之前，是"关键字专用"（keyword-only）参数——只能以 `_reps=100_000` 形式传入。注意 `_reps1`（在 bestoftotal 中）是单独命名的：当 `total` 被调用时，调用方传入的 `_reps` 无法匹配 total 的任何普通形参，于是被收集进 `**kargs` 继续传给 `total`，total 再把它匹配给自己的 `_reps`——作者特意用注释 `# _reps => **` 标注了这个传播链路。
- **设计思想**：这一版是对第 18 章"参数匹配规则"的一次活学活用：仅限位置 + 关键字专用 + 星号收集三个特性组合，让"计时器自己的参数"和"被测函数的参数"彻底隔离，永不冲突。

## 21.11 timeit 基本用法（Basic timeit Usage）

### 英文原文

> Let's start with this module's fundamentals before leveraging them in larger scripts. With *timeit*, tests are specified by either *callable objects* or *statement strings*; the latter can hold multiple statements if they use *;* separators or *\\n* characters for line breaks, and spaces or tabs to indent statements in nested blocks (e.g., *\\n\\t*). Tests may also give setup actions, and can be launched from both *command lines* and *API calls*, and from both scripts and the REPL.

### 中文翻译

> 在更大的脚本里使用这个模块之前，先讲它的基础。用 *timeit* 时，测试既可以由*可调用对象*（callable objects）指定，也可以由*语句字符串*（statement strings）指定；后者可以用 *;* 分隔符或 *\\n* 字符换行来容纳多条语句，用空格或制表符给嵌套块中的语句缩进（例如 *\\n\\t*）。测试还可以给出 setup（初始化）动作，并且既可以从*命令行*启动，也可以从 *API 调用*启动，脚本和 REPL 里都行。

### 深度理解

- **核心概念**：timeit 接受两种被测对象：字符串（编译执行）和零参数的可调用对象。字符串更灵活（可含多条语句），但要受字符串转义规则约束；可调用对象没有转义问题，但被限制为无参数。
- **底层实现**：语句字符串最终会被包进一个合成的 `def` 函数体再编译执行，所以字符串里的 `\\n`、`\\t` 要按 Python 字符串字面量的规则写（比如 `'\\n\\t'` 表示"换行后缩进"）。
- **设计原因**：支持命令行和 API 两种模式，是为了覆盖"快速试一下"（命令行）和"写进脚本/CI"（API）两类使用场景。
- **实际问题**：一条语句如果含嵌套块（如 while 循环体），字符串里必须用 `\\n\\t` 表达缩进；漏掉一个转义字符，代码就编译失败。
- **初学者误区**：把代码字符串里的 `\\n` 当成真的回车——在 Python 字符串里它是转义序列，必须写成反斜杠加 n；不转义直接敲回车会产生语法错误。

## 21.12 API 调用模式（API-calls mode）

### 英文原文

> For example, the *timeit* module's *repeat* call returns a list giving the total time taken to run a test a *number* of times, for each of *repeat* runs—the *min* of this list yields the best time among the runs, and helps filter out system load fluctuations that can otherwise skew timing results artificially high (like our earlier *bestoftotal*). Code to be timed is passed to the *stmt* keyword (or first positional) argument, and may be a string or no-argument function.
>
> The following shows this call in action in REPLs on macOS, timing a list comprehension on both CPython 3.12 and the optimized *PyPy* implementation of Python described in Chapter 2 (as earlier, its tested 7.3 release implements the Python 3.10 language). The results here give the best total time in seconds among 5 runs that each execute the code string 1,000 times; the code string itself constructs a 1,000-item list of integers each time through (*timeit* also has reasonable defaults for repeat counts, but being explicit ensures comparability):

### 中文翻译

> 例如，*timeit* 模块的 *repeat* 调用返回一个列表：对每一轮 *repeat* 运行，给出"把测试运行 *number* 次"所花的总时间——对这个列表取 *min* 就能得到各轮中的最佳时间，并有助于过滤掉系统负载波动（否则它们会把计时结果人为抬高）（就像我们之前的 *bestoftotal*）。被测代码通过 *stmt* 关键字参数（或第一个位置参数）传入，可以是字符串，也可以是零参数函数。

### 中文翻译

> 你会注意到 PyPy 以比 CPython 3.12 *快 20 倍*的成绩登场。这当然是个小型的人工基准，但依然令人震撼，而且反映了一个大体被本书其他测试支持的速度排名（不过在后面某些类型的代码上 CPython 仍然会赢过 PyPy，而且如前所述，CPython 可能会靠未来的 JIT 进步）。公平地说，这个特定测试同时测了列表推导和整数运算的速度，但整数运算在 Python 代码中无处不在，而且 PyPy 在非整数测试上赢面更大（你可以自己试试对一个浮点数求平方）。
>
> 这些结果与上一节"PyPy 对列表推导约快 10 倍"的相对速度也不同。除了被测代码类型不同之外，*timeit* 内部不同的代码构造方式也可能有影响——对这里这类代码字符串，*timeit* 会构建、编译并执行一个嵌入了测试字符串的函数 *def* 语句字符串，从而避免了内层循环每轮一次的函数调用。不过，从相对速度的角度看这无关紧要：同一工具测得的时间是可比的。
>
> 你还会注意到，这里的被测代码是*字符串*。正如你接下来会看到的，这在某些使用模式下需要手工编写换行和缩进，而且所有这样被测的代码都必须符合 Python 字符串字面量、引号和转义的规则。例如，代码字符串不能嵌入与包裹它的引号相同的引号，除非加以转义。你可以通过测可调用对象来避开这个潜在缺点，不过它们被限制为零参数。

### 深度理解

- **核心概念**：`repeat(stmt, number, repeat)` 的三层语义——`stmt` 是被测语句，`number` 是每轮执行的次数，`repeat` 是轮数；对返回列表取 `min`，得到"最佳轮"。这与你自建的 `bestoftotal(50, 100_000, ...)` 完全同构。
- **底层实现**：timeit 把 stmt 字符串嵌入一个合成的 `def` 函数体内编译执行，这样**内层循环不会再有每次迭代的函数调用开销**（比直接 `exec` 字符串或逐条执行更贴近真实场景）。这就是"为什么自建 timer 与 timeit 结果略有不同"的机理之一。
- **设计原因**：字符串模式的存在，是为了能在命令行里直接写代码测速；它的代价是转义规则的折磨。两害相权，timeit 两种模式都给。
- **实际问题**：PyPy 对这份代码快 20 倍，但上一节同是 PyPy 只有 10 倍——比例本身在不同测试里都不同，更别说绝对时间。这再次证明：**倍数也不是常数**。
- **初学者误区**：把 `stmt='...'` 里的单引号与被测代码的引号混用导致语法错误（例如 `stmt="'hack' * 5"` 外层双引号包内层单引号才行）；或者想当然认为 timeit 与自制 timer 的绝对数值应该一致——不同工具、不同结构，绝对数不同很正常，比相对排名即可。

## 21.15 timeit 的其他用法模式（Other timeit usage modes）

### 英文原文

> The *timeit* module also allows you to provide *setup* code that is run in the main statement's scope, but whose time is not charged to the main statement's total—useful for initialization code you wish to exclude from total time, such as imports of required modules and builds of test data. Because they're run in the same scope, any names created by setup code are available to the main test statement; names defined in the interactive shell generally are not.
>
> To specify setup code, use a *–s* in command-line mode (or many of these for multiline setups) and a *setup* argument string in API-call mode. This can focus tests more sharply, as in the following, whose second command splits list initialization off to a setup statement to time just iteration in command-line mode. As a general rule of thumb, though, the more code you include in a test statement, the more applicable its results will generally be to realistic code:

### 中文翻译

> *timeit* 模块还允许你提供 *setup* 代码：它在主语句的作用域中运行，但它的时间**不计入**主语句的总时间——这对你想从总时间里排除的初始化代码很有用，比如导入所需模块、构建测试数据。由于它们在同一作用域中运行，setup 代码创建的任何名字对主测试语句都是可见的；而交互式 shell 里定义的名字一般不可见。
>
> 指定 setup 代码的方式：命令行模式用 *–s*（多行 setup 可以多次使用），API 调用模式用 *setup* 参数字符串。这可以让测试更聚焦，如下所示：第二条命令把列表初始化拆到 setup 语句里，从而在命令行模式下只测迭代部分。不过一般来说，一个经验法则：**测试语句里包含的代码越多，其结果通常越接近真实代码**：

### 英文原文（运行结果）

```
$ python3 -m timeit -n 100000 -r 5 "L = [1,2,3,4,5]" "M = [x + 1 for x in L]"
100000 loops, best of 5: 211 nsec per loop
$ python3 -m timeit -n 100000 -r 5 -s "L = [1,2,3,4,5]" "M = [x + 1 for x in L]"
100000 loops, best of 5: 175 nsec per loop
```

### 中文翻译（运行结果）

```
$ python3 -m timeit -n 100000 -r 5 "L = [1,2,3,4,5]" "M = [x + 1 for x in L]"
100000 loops, best of 5: 211 nsec per loop
$ python3 -m timeit -n 100000 -r 5 -s "L = [1,2,3,4,5]" "M = [x + 1 for x in L]"
100000 loops, best of 5: 175 nsec per loop
```

### 深度理解

- **核心概念**：setup 把"初始化"与"被测主体"分开计时：`-s "L = [... ]"` 之后主语句只测 `M = [x + 1 for x in L]`。同样的代码，一次拆一次不拆，结果是 175 vs 211 nsec——差出的 36 nsec 正是列表构造的时间。
- **底层实现**：setup 与主语句被编译进**同一个**合成函数体（setup 在前、stmt 在后），所以 setup 创建的 `L` 对主语句可见；而 REPL 里敲的全局名则不在该函数的作用域链上，所以不可见。这正是"为什么 `-s` 里必须导入模块"的原因。
- **设计原因**：timeit 提供了 setup 能力，但作者同时强调反直觉的经验法则——**测的代码越"真实"（包含初始化），结果越有参考价值**。极端"纯净"的微基准往往与真实程序相去甚远。
- **实际问题**：如果被测函数需要 import，必须在 setup 里 import（`-s "from mymod import func"`），否则每次运行都会找不到名字；而把 import 放主语句里测，则会连 import 的耗时一起算进去。
- **初学者误区**：想当然地以为 REPL 里定义好的名字能直接用于 stmt 字符串——不行！timeit 执行的是一个全新函数体，只认识 setup 创建的名字。这是新手误用 timeit 的高频雷区。

### 中文翻译（REPL 运行结果）

```
>>> from timeit import repeat                    # 标准库模块
>>> min(repeat(number=1000, repeat=5,            # 在 min4 中排序一个有序列表
        setup='from mins import min4\n'          # 相邻字符串自动拼接
        'vals=list(range(1000))',                # () 内的代码可以跨行书写
        stmt='min4(*vals)'))                     # 首次 import 会打印输出
0.011066518723964691
>>> min(repeat(number=1000, repeat=5,            # 排序一个随机顺序的列表
        setup='from mins import min4\n'
        'import random\n'
        'vals=[random.random() for i in range(1000)]',
        stmt='min4(*vals)'))
0.068130933213979
```

### 深度理解

- **核心概念**：这个测试演示了 setup 在 API 模式下的标准写法：多行 setup 用相邻字符串字面量拼接（`'from mins import min4\n' 'vals=...'`，括号内可跨行）。结果 0.011 vs 0.068 秒——**有序数据比随机数据快 6 倍**。
- **底层实现**：Python 的排序是 Timsort：它擅长识别"已排序的连续片段"（runs），有序数据近乎 O(n) 扫描即可完成；随机数据则进入完整的归并排序流程。`min4` 用排序取第一个元素，间接暴露了排序对数据顺序的敏感性。
- **设计原因**：作者故意用"排序后取 [0]"而不是 min()，一方面呼应第 18 章的示例，另一方面展示"排序速度随数据顺序变化"这一早前提过的论断。
- **实际问题**：真实程序中，如果数据本来就接近有序（如日志时间戳、增量更新的 ID），Timsort 会快得多；反之随机数据的排序成本才是基准值。设计算法时要利用这一特性。
- **初学者误区**：以为 `sorted()` 对所有数据耗时恒定；或者以为测试结果可以脱离"数据分布"谈。同样的排序代码，换个数据顺序，耗时差 6 倍。

### 中文翻译

> 先说入门：Example 21-8 的模块文件 *pybench.py* 被设计用来给一串语句计时——这些语句写在导入并使用它的脚本里；它可以只用正在运行其代码的那个 Python，也可以使用列表中列出的所有 Python 版本。它用了一些后面会介绍的应用程序级工具。不过，由于它主要应用我们已经探索过的理念，且文档完备，它被定位为基本上属于自学材料，也是一次阅读 Python 代码的练习。

### 代码分析

```python
r"""
用 timeit 测量一个或多个 Python 在多个代码字符串基准上的速度。
这是一个函数，以便让被测测试可以变化。它对传入列表中的所有
代码字符串计时，有两种模式：
1) 用 timeit API 调用，测运行本脚本的那个 Python
2) 用 os.popen 运行 timeit 命令行（利用 Python 的 -m 开关在
   模块搜索路径上找到 timeit），测列表中给出的多个 Python
仅在命令行模式（2）中：把被测代码中所有 " 换成 '，避免与参数
引号冲突；把多行语句按每行拆成一个带引号的参数，确保全部能运行；
把缩进中的 \t 统一替换为 4 个空格。
注意事项：
- 命令行模式（仅此模式）使用朴素的引号处理，如果代码嵌入并需要
  双引号、被引号包裹的代码与宿主 shell 不兼容、或命令长度超过
  shell 限制，则可能失败。
- PyPy 今天在命令行模式（2）下基本不可用，因为它修改过的 timeit
  输出在这个模式下对报告非常刺眼。
- 任何模式下都（尚未？）支持 setup 语句：测试 stmt 中所有代码的
  时间都会计入总时间。
失败时的备选方案：用本模块的 API 调用模式一次测一个 Python，
或者用自制的 timer.py 模块。
"""
import sys, os, time, timeit
defnum, defrep = 1000, 5                         # 每语句可变化

def show_context():
    """
    显示运行环境：使用一个略显多余的 f-string，
    若无 "..." 处理嵌套 ' 引号，在 3.10 PyPy 上会失败。
    """
    print(f"Python {'.'.join(str(x) for x in sys.version_info[:3])}"
          f' on {sys.platform}'
          f" at {time.strftime('%b-%d-%Y, %H:%M:%S')}")

def runner(stmts, pythons=None, tracecmd=False):
    """
    主逻辑：按输入列表运行测试，输入列表决定使用模式。
    stmts: [(number?, repeat?, stmt-string)]
    pythons: None=只测宿主 python，或 [python 可执行文件路径]
    """
    show_context()
    for (number, repeat, stmt) in stmts:
        number = number or defnum                 # 0 表示用默认值
        repeat = repeat or defrep                 # 0 表示用默认值
        if not pythons:
            # 在本 python 上运行 stmt：API 调用
            # 这里无需拆行或加引号
            best = min(timeit.repeat(stmt=stmt, number=number, repeat=repeat))
            print(f'{best:.4f} {stmt[:70]!r}')
        else:
            # 在所有 python 上运行 stmt：命令行
            # 把各行拆成带引号的参数
            print('-' * 80)
            print(repr(stmt))                     # 显示引号
            for python in pythons:
                stmt = stmt.replace('"', "'")     # 所有 " => '
                stmt = stmt.replace('\t', ' ' * 4)  # 制表符 => 4 个空格
                lines = stmt.split('\n')          # 每行 => 一个参数
                args = ' '.join(f'"{line}"' for line in lines)  # 参数 => "参数"
                oscmd = f'{python} -m timeit -n {number} -r {repeat} {args}'
                print(oscmd if tracecmd else python)
                print('\t' + os.popen(oscmd).read().rstrip())
```

- **解释器如何处理**：`runner` 是核心。无 `pythons` 时走 API 分支：`min(timeit.repeat(...))` 与前面 REPL 用法一致。有 `pythons` 时走命令行分支，对每条语句做四步"驯服"：(1) `"` 全部替换成 `'`（避免与 shell 参数引号冲突）；(2) `\t` 替换成 4 空格（消除制表符在不同 shell 下的不确定性）；(3) 按 `\n` 拆成一行一个参数；(4) 用 f-string 拼出 `python -m timeit -n N -r R "line1" "line2"` 命令，`os.popen` 执行并读取输出。`oscmd if tracecmd else python` 控制是否打印完整命令。
- **设计思想**：这是"用 Python 写 shell 自动化"的典型样板：字符串替换、拆行、拼接、子进程调用。docstring 里的 Caveats 就是工程复盘——作者把已知的失败模式写在文档里，是专业软件应有的诚实。

### 深度理解

- **核心概念**：pybench 把 timeit 的两种模式统一成一个入口：API 模式测"本机 Python"，命令行模式测"任意列表里的 Python"。两种模式共用同一种测试描述格式 `(number, repeat, stmt)`。
- **底层实现**：`os.popen(oscmd).read()` 会启动一个子 shell 执行命令并捕获标准输出——命令字符串是拼出来的，所以引号、缩进、换行都必须精确。f-string 里 `{stmt[:70]!r}` 用 `!r` 转换符输出 repr（带引号的形式），便于复制回命令行验证。
- **设计原因**：作者把 f-string 的嵌套引号问题（PyPy 3.10 上对 `'` 的处理失败）也当教材——`f"..."` 外层双引号内嵌 `'...'` 在标准 CPython 3.12 已允许，但 PyPy 3.10 实现的是更早的语法规则，会报错。工具代码也要考虑运行平台的语言版本。
- **实际问题**：命令行模式对"嵌入双引号的代码"直接失败（替换成单引号就改变了语义）；PyPy 修改过的 timeit 输出让报告难看——这些"现实阻力"正是文档里 Caveats 存在的意义。
- **初学者误区**：在字符串处理代码里随手拼接命令而不考虑 shell 的引号规则；或者以为 `os.popen` 的输出可以无条件信任。命令注入、引号转义、输出格式漂移，都是这类自动化的真实风险。

### 英文原文

> This preceding file is really only half the picture. Testing scripts use this module's function, passing in concrete though variable lists of statements and Pythons to be tested, as appropriate for the usage mode desired. For example, the script in Example 21-9, *pybench_tests.py*, tests a handful of statements and Pythons by importing and using Example 21-8, and allows command-line arguments to determine part of its operation: *–a* tests all listed Pythons instead of just one, and an added *–t* traces constructed command lines in full so you can see how quotes, multiline statements, and tabs are handled per *timeit*'s command-line formats shown earlier (see both files' docstrings for more details).

> 上面这个文件其实只讲了一半。测试脚本使用这个模块的函数，传入具体但可变的语句列表和待测 Python 列表，随所需的用法模式而定。例如 Example 21-9 的脚本 *pybench_tests.py* 通过导入和使用 Example 21-8 来测试若干语句和 Python，并允许命令行参数决定它的一部分行为：*–a* 测试列出的所有 Python 而不仅是当前这一个，额外加的 *–t* 则完整追踪构造出的命令行，让你看到引号、多行语句和制表符如何按照前面展示的 *timeit* 命令行格式被处理（更多细节见两个文件的 docstring）。

### 代码分析

```python
"""
运行 pybench.py，在一个或多个 Python 上给多个代码字符串计时。
用命令行参数（出现在 sys.argv 中）选择模式：
<python> pybench_tests.py
    只对下方 stmts 中列出的所有代码给宿主 Python 计时

python3 pybench_tests.py -a
    给下面列出的所有 python 路径的所有 stmts 计时
python3 pybench_tests.py -a -t
    与 -a 相同，但额外完整追踪命令行
编辑下面的 stms 以改变被测代码；编辑下面的 pythons 以给出
-a 模式下要测试的 Python 可执行文件路径。要找到某个 Python 的
路径，启动它的 REPL，运行 "import sys"，查看 "sys.executable"。
"""
import pybench, sys

pythons = [
    '/Library/Frameworks/Python.framework/Versions/3.12/bin/python3',
    '/Users/me/Downloads/pypy3.10-v7.3.16-macos_x86_64/bin/pypy3',
]
stmts = [
    # 迭代
    (0, 0, '[x ** 2 for x in range(1000)]'),              # (次数,轮数,语句)
    (0, 0, 'res=[]\nfor x in range(1000): res.append(x ** 2)'),  # \n=多语句
    (0, 0, 'list(map(lambda x: x ** 2, range(1000)))'),   # \n\t=缩进
    (0, 0, 'list(x ** 2 for x in range(1000))'),
    # 字符串操作
    (0, 0, "s = 'hack' * 2500\nx = [s[i] for i in range(10_000)]"),
    (0, 0, "s = '?'\nfor i in range(10_000): s += '?'"),  # PyPy 会输的一项！
]
tracecmd = '-t' in sys.argv                # -t: 追踪命令行？
pythons = pythons if '-a' in sys.argv else None   # -a: 测列表中全部，否则只测一个？
pybench.runner(stmts, pythons, tracecmd)   # 在所有 stmts 上给 pythons 计时
```

- **解释器如何处理**：`sys.argv` 是命令行参数列表（脚本名 + 各参数）。`'-t' in sys.argv` 就是"命令行里有没有 -t"这一布尔判断——用列表成员测试实现简单参数解析。`pythons if '-a' in sys.argv else None` 把 `-a` 的有无翻译成 runner 的两种模式：传路径列表 = 命令行模式，传 None = API 模式。`stmts` 里每组 `(0, 0, stmt)` 中的 0 表示"用默认值"（defnum=1000、defrep=5），由 runner 里的 `number or defnum` 兜底替换。
- **设计思想**：测试定义（stmts/pythons）与执行逻辑完全分离：想加测试，改列表；想换 Python，改路径列表。这是"配置驱动"的极简形式。

### 深度理解

- **核心概念**：一个测试脚本 = 数据（stmts/pythons 列表）+ 开关（sys.argv 里的 -a/-t）+ 执行（runner）。用 `in` 判断 argv 就能做出 CLI 选项，无需 argparse。
- **底层实现**：`sys.argv` 里存的是**字符串**；`(0, 0, stmt)` 里的 0 是"假值"，`number or defnum` 利用"假值替换"语义把 0 换成默认值——这是 Python 里 `or` 返回操作数的经典用法。
- **设计原因**：把不同代码（列表推导 vs for 循环 vs map vs 生成器）和不同字符串操作（索引遍历 vs 字符串拼接）放进同一批 stmts，是为了在**一个报告里对比多个维度**。
- **实际问题**：`s += '?'` 这种循环字符串拼接在 CPython 里因字符串不可变要反复创建新对象，是最慢的写法之一；PyPy 的 JIT 优化下它反而可能是软肋——这为后面"PyPy 输掉最后一个测试"埋下伏笔。
- **初学者误区**：想当然以为 `-a` 就是"所有 Python 都能测"。跨实现自动化的输出格式耦合问题（PyPy 改了 timeit 输出）会让这个模式几乎不可用——工具链的"立场"是设计自动化时必须考虑的。

## 21.22 测试集合与字典迭代（Timing set and dictionary iterations）

### 英文原文

> The good news is that *single-Python* mode still allows us to easily script a set of benchmarks—even on PyPy. The script in Example 21-10, for instance, uses the driver module in Example 21-8 to see how sets and dictionaries fare.

### 中文翻译

> 好消息是，*单 Python* 模式仍然让我们能轻松地脚本化一组基准测试——即使在 PyPy 上也可以。例如 Example 21-10 的脚本使用 Example 21-8 的驱动模块，看看集合和字典的表现如何。

### 代码分析

```python
import pybench

stmts = [
    # 集合
    (0, 0, '{x ** 2 for x in range(1000)}'),
    (0, 0, 'set(x ** 2 for x in range(1000))'),
    (0, 0, 's=set()\nfor x in range(1000): s.add(x ** 2)'),
    # 字典
    (0, 0, '{x: x ** 2 for x in range(1000)}'),
    (0, 0, 'dict((x, x ** 2) for x in range(1000))'),
    (0, 0, 'd={}\nfor x in range(1000): d[x] = x ** 2'),
]
pybench.runner(stmts, None, False)     # 本脚本不用 -a 模式
```

- **解释器如何处理**：六条语句分成三组对照：集合的推导式 / 把生成器传给 set() / for 循环 add；字典的推导式 / 把生成器传给 dict() / for 循环赋值。`pybench.runner(stmts, None, False)` 中 `None` 表示只用当前 Python，`False` 表示不追踪命令——全部走 API 模式。
- **设计思想**：这三组对照精确复刻了前面迭代测试的设计：**同一个目标结果，三种构建机制**。上一章预告过的"把生成器传给类型名是最慢方案"在这里得到验证。

## 21.25 局部名字是静态检测的（Local Names Are Detected Statically）

### 英文原文

> As you've learned, Python classifies names *assigned* in a function as *locals* by default; they live in the function's scope and exist only while the function is running. What you may not realize is that Python detects locals *statically*, when it compiles the *def*'s code, rather than by noticing assignments as they happen at runtime. This leads to one of the most common oddities posted on the Python newsgroup by beginners.
>
> Normally, a name that isn't assigned in a function is looked up in the enclosing module:

### 中文翻译

> 正如你已经学到的，Python 默认把函数中*被赋值*的名字归类为*局部*（locals）；它们存活于函数的作用域中，只在函数运行期间存在。你可能没意识到的是：Python 是**静态**地检测局部名字的——在编译 *def* 的代码时——而不是在运行时观察赋值何时发生。这导致了初学者贴在 Python 新闻组上的最常见的怪现象之一。
>
> 通常，函数里没有被赋值的名字会在外层模块中查找：

### 英文原文（REPL 演示）

```
>>> X = 99
>>> def selector():
        print(X)                  # X used but not assigned
>>> selector()                    # X found in global scope
99
```

### 中文翻译（REPL 演示）

```
>>> X = 99
>>> def selector():
        print(X)                  # X 被使用但未被赋值
>>> selector()                    # X 在全局作用域中找到
99
```

### 英文原文

> Here, the *X* in the function resolves to the *X* in the module. But watch what happens if you add an assignment to *X* after the reference:

### 中文翻译

> 这里，函数中的 *X* 解析到模块中的 *X*。但注意：如果在引用之后给 *X* 加一个赋值，会发生什么：

### 英文原文（REPL 演示）

```
>>> def selector():
        print(X)                  # Does not yet exist!
        X = 88                    # X classified as a local name (everywhere)
>>> selector()                    # Can also happen for "import X", "def X"...
UnboundLocalError: cannot access local variable 'X' where it is not associated with
a value
```

### 中文翻译（REPL 演示）

```
>>> def selector():
        print(X)                  # 此刻还不存在！
        X = 88                    # X 被归类为局部名字（整个函数内都是）
>>> selector()                    # 对 "import X"、"def X"... 同样会发生
UnboundLocalError: cannot access local variable 'X' where it is not associated with
a value
```

### 英文原文

> You get the name-usage error shown here, but the reason is subtle. Python reads and compiles this code when it's typed interactively or imported from a module. While compiling, Python sees the assignment to *X* and decides that *X* will be a local name everywhere in the function. But when the function is actually run, because the assignment hasn't yet happened when the *print* executes, Python says you're using an undefined name. According to its name rules, it should say this; the local *X* is used before being assigned. In fact, any assignment in a function body makes a name local. Imports, *=*, nested *def*s, nested classes, and so on are all susceptible to this behavior.
>
> The problem occurs because assigned names are treated as locals *everywhere* in a function, not just after the statements where they're assigned. Really, the previous example is ambiguous: was the *intention* to print the global *X* and create a local *X*, or is this a real programming error? Because Python treats *X* as a local everywhere, it's seen as an error; if you mean to print the global *X*, you need to declare it in a *global* statement:

### 中文翻译

> 你得到的就是这里展示的名字使用错误，但原因很微妙。Python 在交互式输入或从模块导入时读取并编译这段代码。编译期间，Python 看到对 *X* 的赋值，于是判定 *X* 在函数的所有位置都是局部名字。但当函数真正运行时，因为 *print* 执行时赋值尚未发生，Python 就说你在使用未定义的名字。按照它的名字规则，它理应这么说；局部 *X* 在使用之前未被赋值。事实上，函数体内任何赋值都会把名字变成局部。import、*=*、嵌套 *def*、嵌套类等，全都受此行为影响。
>
> 问题出在：被赋值的名字在函数中*所有*位置都被当作局部，而不只是在赋值语句之后。说真的，前面的例子是有歧义的：*意图*是打印全局 *X* 再创建局部 *X*，还是一个真正的编程错误？因为 Python 在所有位置都把 *X* 当作局部，所以它被看作错误；如果你想打印全局 *X*，就需要在 *global* 语句中声明它：

### 英文原文（REPL 演示）

```
>>> def selector():
        global X                  # Force X to be global (everywhere in function)
        print(X)
        X = 88
>>> selector()
99
```

### 中文翻译（REPL 演示）

```
>>> def selector():
        global X                  # 强制 X 是全局（函数内所有位置）
        print(X)
        X = 88
>>> selector()
99
```

### 英文原文

> Remember, though, that this means the assignment also changes the global *X*, not a local *X*. Within a function, you can't use both local and global versions of the same simple name. If you really meant to print the global and then set a local of the same name, you'd need to import the enclosing module and use module attribute notation to get to the global version:

### 中文翻译

> 不过请记住，这意味着赋值也会修改全局的 *X*，而不是某个局部的 *X*。在一个函数内部，你无法同时使用同一个简单名字的局部版本和全局版本。如果你真的想先打印全局的，再设置同名的局部，就需要导入外层模块并用模块属性记号访问全局版本：

### 英文原文（REPL 演示）

```
>>> X = 99
>>> def selector():
        import __main__           # Import enclosing module
        print(__main__.X)         # Qualify to get to global version of name
        X = 88                    # Unqualified X classified as local
        print(X)                  # Prints local version of name
>>> selector()
99
88
```

### 中文翻译（REPL 演示）

```
>>> X = 99
>>> def selector():
        import __main__           # 导入外层模块
        print(__main__.X)         # 加限定以访问名字的全局版本
        X = 88                    # 不加限定的 X 被归类为局部
        print(X)                  # 打印名字的局部版本
>>> selector()
99
88
```

### 英文原文

> Qualification (the *.X* part) fetches a value from a namespace object. The interactive namespace is a module called *__main__*, so *__main__.X* reaches the global version of *X*. If that isn't clear, review Chapter 17.
>
> In recent versions, Python has improved on this story somewhat by issuing for this case the more specific \"unbound local\" error message shown in the example listing (it used to simply raise a generic name error); this gotcha is still present in general, though.

### 中文翻译

> 限定（qualification，即 *.X* 部分）从命名空间对象取一个值。交互式命名空间是一个叫 *__main__* 的模块，所以 *__main__.X* 能访问 *X* 的全局版本。如果不清楚，请复习第 17 章。
>
> 在最近的版本中，Python 对这个故事有所改善：针对这种情形抛出了示例清单中那个更具体的 \"unbound local\" 错误消息（以前只是抛一个通用的名字错误）；不过这个陷阱总体上依然存在。

### 深度理解

- **核心概念**：**局部性判定发生在编译期，不是运行期**。函数体里任何位置出现赋值（含 `import`、嵌套 `def`、增强赋值），该名字在整个函数内就被打上\"局部\"标签，即使引用发生在赋值之前。
- **底层实现**：编译 `def` 时，编译器扫描函数体收集被赋值的名字，为每个局部名分配**固定的栈槽（slot）**，字节码用下标访问而不是字典查找——这是局部变量比全局变量快的原因。`print(X)` 编译成 `LOAD_FAST X`（局部），而函数运行时该槽还未填充，就报 UnboundLocalError；`global X` 则让访问改走 `LOAD_GLOBAL`。
- **设计原因**：\"静态局部判定\"换来的是性能（槽访问 O(1)）和确定性；代价是这种反直觉的错误。Python 选择了性能优先，用更清晰的错误消息弥补。
- **实际问题**：想\"先用全局，再建局部\"的需求，Python 明确不支持同名共存——必须用模块属性（`__main__.X`）显式绕过。这是语言设计划出的边界：简单名字在一个作用域内只能有一种身份。
- **初学者误区**：以为错误是\"运行时赋值顺序\"造成的，把赋值挪到 print 之前就完事（其实只要函数里有赋值，print 永远读局部）；或者在函数里写了 `X += 1` 这种增强赋值（它同时是读+写），忘记它也会把 X 变成局部。

## 21.26 默认参数与可变对象（Defaults and Mutable Objects）

### 英文原文

> As noted briefly in Chapters 17 and 18, mutable values for default arguments can retain state between *calls*, though this is often unexpected. In general, default argument values are evaluated and saved *once* when a *def* statement is run, not each time the resulting function is later called. Internally, Python saves one object per default argument, attached to the function itself.
>
> That's usually what you want—because defaults are evaluated at *def* time, they let you save values from the enclosing scope, if needed (functions defined within loops by factories may even depend on this behavior—see ahead). But because a default retains an object between calls, you have to be careful about changing mutable defaults. For instance, the following function uses an empty list as a default value, and then changes it in place each time the function is called:

### 中文翻译

> 正如第 17、18 章简要提到的，可变（mutable）的默认参数值可以在*调用*之间保留状态——虽然这常常出乎意料。一般来说，默认参数值在 *def* 语句运行时被求值并保存**一次**，而不是在之后每次调用生成的函数时重新求值。在内部，Python 为每个默认参数保存一个对象，挂在函数对象本身上。
>
> 这通常正是你想要的——因为默认值在 *def* 时求值，如果需要，它们让你能把外层作用域的值保存下来（工厂函数在循环里定义的函数甚至可能依赖这个行为——见后文）。但正因为默认值在调用之间保留着一个对象，修改可变默认值就必须小心。例如，下面的函数用空列表作默认值，然后每次调用时都就地修改它：

### 英文原文（REPL 演示）

```
>>> def saver(x=[]):              # Saves away a list object
        x.append(1)               # Changes same object each time!
        print(x)
>>> saver([2])                    # Default not used
[2, 1]
>>> saver()                       # Default used
[1]
>>> saver()                       # Grows on each call!
[1, 1]
>>> saver()
[1, 1, 1]
```

### 中文翻译（REPL 演示）

```
>>> def saver(x=[]):              # 保存的是一个列表对象
        x.append(1)               # 每次修改的都是同一个对象！
        print(x)
>>> saver([2])                    # 默认值未被使用
[2, 1]
>>> saver()                       # 使用了默认值
[1]
>>> saver()                       # 每次调用都会增长！
[1, 1]
>>> saver()
[1, 1, 1]
```

### 英文原文

> Some see this behavior as a feature—because mutable default arguments retain their state between function calls, they can serve some of the same roles as \"static\" local function variables in the C language. In a sense, they work much like global variables, but their names are local to the functions and so will not clash with names elsewhere in a program.
>
> To other observers, though, this seems like a gotcha—especially the first time they run into it. There are better ways to retain state between calls in Python (e.g., using the nested scope closures and function attributes we met in this part, and the classes we will study in Part VI).
>
> Moreover, mutable defaults can be overridden by real values, and are tricky to remember (and to understand at all). They depend upon the timing of default object construction. In the prior example, there is just one list object for the default value—the one created when the *def* is executed. You don't get a new list every time the function is called, so the list grows with each new append; it is not reset to empty each time.

### 中文翻译

> 有些人把这个行为当特性——因为可变默认参数在函数调用之间保留状态，它们可以扮演 C 语言里\"静态\"局部函数变量（static）的一些角色。从某种意义上说，它们非常像全局变量，但名字对函数来说是局部的，不会与程序中其他地方的名字冲突。
>
> 但在另一些人看来，这尤其像陷阱——尤其是第一次撞上它的时候。在 Python 里有更好的方式在调用之间保留状态（例如本部分见过的嵌套作用域闭包、函数属性，以及我们将在第六部分学习的类）。
>
> 而且，可变默认值可以被真实参数覆盖，又很难记住（甚至很难理解）。它们依赖于默认对象构造的时机。在前面的例子里，默认值只有一个列表对象——就是 *def* 执行时创建的那个。每次调用函数并不会得到新列表，所以列表会随着每次 append 增长；它不会每次被重置为空。

### 英文原文

> If that's not the behavior you want, simply make a copy of the default at the start of the function body, or move the default value expression into the function body. As long as the value resides in code that's actually executed each time the function is *called*, you'll get a new object each time through:

### 中文翻译

> 如果这不是你想要的行为，只需在函数体开头复制一份默认值，或者把默认值表达式挪进函数体。只要这个值位于每次调用函数时*实际执行*的代码里，每次就会得到一个新对象：

### 英文原文（REPL 演示）

```
>>> def saver(x=None):            # No argument passed?
        if x is None:
            x = []                # Run code to make a new list each time
        x.append(1)               # Changes new list object
        print(x)
>>> saver([2])
[2, 1]
>>> saver()                       # Doesn't grow here
[1]
>>> saver()
[1]
```

### 中文翻译（REPL 演示）

```
>>> def saver(x=None):            # 没有传参数？
        if x is None:
            x = []                # 运行代码，每次新建一个列表
        x.append(1)               # 修改的是新列表对象
        print(x)
>>> saver([2])
[2, 1]
>>> saver()                       # 这里不会增长
[1]
>>> saver()
[1]
```

### 英文原文

> By the way, the *if* statement in this example could *almost* be replaced by the assignment *x = x or []*, which takes advantage of the fact that Python's *or* returns one of its operand objects: if no argument was passed, *x* would default to *None*, so the *or* would return the new empty list on the right.
>
> However, this isn't exactly the same. If an empty list were passed in, the *or* expression would cause the function to extend and return a newly created list, rather than extending and returning the passed-in list like the *if* version. (The expression becomes *[] or []*, which evaluates to the new empty list on the right; see Chapter 12's \"Truth Values Revisited\" if you don't recall why.) Real program requirements may call for either behavior.

### 中文翻译

> 顺便一提，这个例子里的 *if* 语句*几乎*可以用赋值 *x = x or []* 替代——它利用的是 Python 的 *or* 返回其中一个操作数对象这一事实：如果没有传参数，*x* 默认为 *None*，于是 *or* 返回右边那个新的空列表。
>
> 然而，这并不完全相同。如果传入的是一个空列表，*or* 表达式会让函数扩展并返回一个新创建的列表，而不是像 *if* 版本那样扩展并返回传入的列表。（表达式变成 *[] or []*，求值为右边新的空列表；想不起为什么，请看第 12 章的\"真值回顾\"。）真实的程序需求可能要求其中任何一种行为。

### 英文原文

> Today, another way to achieve the value retention effect of mutable defaults in a possibly less confusing way is to use the *function attributes* we discussed in Chapter 19:

### 中文翻译

> 如今，还有一个也许更不绕的方式来实现可变默认值的\"值保留\"效果：使用我们在第 19 章讨论过的*函数属性*（function attributes）：

### 英文原文（REPL 演示）

```
>>> def saver():
        saver.x.append(1)
        print(saver.x)
>>> saver.x = []
>>> saver()
[1]
>>> saver()
[1, 1]
>>> saver()
[1, 1, 1]
```

### 中文翻译（REPL 演示）

```
>>> def saver():
        saver.x.append(1)
        print(saver.x)
>>> saver.x = []
>>> saver()
[1]
>>> saver()
[1, 1]
>>> saver()
[1, 1, 1]
```

### 英文原文

> The function name is global to the function itself, but it need not be declared because it isn't changed directly within the function. This isn't used in exactly the same way, but when coded like this, the attachment of an object to the function is much more explicit (and arguably less magical).

### 中文翻译

> 函数名对函数自身而言是全局的，但它无需声明，因为在函数内部并没有直接修改它。这种用法与默认参数不完全相同，但按这种方式编码时，对象与函数的挂接关系要显式得多（可以说也少了一些魔法）。

### 深度理解

- **核心概念**：默认值在 **def 执行时求值一次**，之后一直被函数对象持有——这是\"可变默认值累积状态\"的根源。`def` 是一句执行语句，不是声明。
- **底层实现**：函数对象内部保存着 `__defaults__` 元组（保存位置参数默认值）。`def saver(x=[])` 执行时创建的那个空列表就被存进 `__defaults__`；之后每次 `saver()` 都把**同一个**列表对象绑定给局部名 `x`，`x.append` 改的是那个共享对象。这就是\"默认值陷阱\"的全部机理。
- **设计原因**：为什么默认值在 def 时求值？一是性能（不用每次调用都求值）；二是刻意支持\"工厂函数把外层变量快照进默认值\"的用法（第 17 章闭包陷阱的正解）。可变默认值只是这个设计的副作用。
- **实际问题**：惯用修复是 `x=None` + 函数体内 `if x is None: x = []`；更现代的替代是闭包/函数属性/类（第六部分）。`x = x or []` 的简写有细微差异（传空列表时行为不同），工程上优先用显式 if 版本。
- **初学者误区**：以为\"每次调用都会新建默认列表\"；或者看到 `saver([2])` 输出 `[2, 1]` 就困惑——那是传入的真实参数，与默认对象无关。本质是**对象共享**问题：默认值对象只有一个，所有没传参的调用共享它。

## 21.27 没有 return 的函数（Functions Without returns）

### 英文原文

> In Python functions, *return* (and *yield*) statements are optional. When a function *doesn't* return a value explicitly, the function exits when control falls off the end of the function body. Technically, all functions return a value; if you don't provide a *return* statement, your function returns the *None* object automatically:

### 中文翻译

> 在 Python 函数中，*return*（以及 *yield*）语句是可选的。当函数*没有*显式返回值时，控制流掉出函数体末尾函数就退出。严格来说，所有函数都返回一个值；如果你不写 *return* 语句，函数会自动返回 *None* 对象：

### 英文原文（REPL 演示）

```
>>> def proc(x):
        print(x)                  # No return is a None return
>>> x = proc('testing 123...')
testing 123...
>>> print(x)
None
```

### 中文翻译（REPL 演示）

```
>>> def proc(x):
        print(x)                  # 没有 return 就是返回 None
>>> x = proc('testing 123...')
testing 123...
>>> print(x)
None
```

### 英文原文

> Functions such as this without a *return* are Python's equivalent of what are called \"procedures\" in some languages. They're usually invoked as statements, and the *None* results are ignored, as they do their business without computing a useful result.
>
> This is worth remembering, because Python won't tell you if you try to use the result of a function that doesn't return one. As we noted in Chapter 11, for instance, assigning the result of a list *append* method won't raise an error, but you'll get back *None*, not the modified list:

### 中文翻译

> 这种没有 *return* 的函数，是 Python 对某些语言中所谓\"过程\"（procedures）的等价物。它们通常以语句形式被调用，*None* 结果被忽略——它们干自己的活，而不计算有用结果。
>
> 这一点值得记住，因为如果你试图使用一个不返回值的函数的结果，Python 不会提醒你。例如，正如我们在第 11 章指出的：把列表 *append* 方法的结果赋值给变量不会报错，但你会拿回 *None*，而不是修改后的列表：

### 英文原文（REPL 演示）

```
>>> list = [1, 2, 3]
>>> list = list.append(4)         # append is a "procedure"
>>> print(list)                   # append changes list in place
None
```

### 中文翻译（REPL 演示）

```
>>> list = [1, 2, 3]
>>> list = list.append(4)         # append 是一个"过程"
>>> print(list)                   # append 就地修改列表
None
```

### 英文原文

> \"Common Coding Gotchas\" discusses this more broadly. In general, any functions that do their business as a side effect are usually designed to be run as statements, not expressions.

### 中文翻译

> \"常见编码陷阱\"一节更广泛地讨论了这个问题。一般来说，任何靠副作用完成工作的函数，通常都被设计成以语句方式运行，而不是以表达式方式。

### 深度理解

- **核心概念**：Python 函数一律返回一个值，没写 return 就隐式返回 `None`——\"函数\"与\"过程\"（只有副作用、无返回值）的界限在 Python 里是模糊的，靠约定而不是语法区分。
- **底层实现**：函数体末尾没有 return 时，字节码会附加一个 `RETURN_CONST None`；所以 `print(x)` 里 `x` 拿到的是那个唯一的 None 单例对象。`is None` 判断因此永远可靠。
- **设计原因**：允许省略 return 是为了简洁（很多函数只是做事的，不需要返回值）；代价是\"误用返回值\"不会报错，只能拿到 None——这是 Python 之\"宽容\"的典型例子。
- **实际问题**：`list = list.append(4)` 这种代码把列表变量覆盖成 None，是新手经典事故；链式调用（`list.sort().append(...)`）也会当场失败，因为 sort/append 都返回 None。习惯上：就地修改的方法不要赋值。
- **初学者误区**：把\"函数没 return\"当错误；或者写 `x = mylist.sort()` 期望 x 是排好序的列表。正确姿势：要么先 sort 再用原变量，要么用返回新列表的 `sorted()`。

## 21.28 其他函数陷阱（Miscellaneous Function Gotchas）

### 英文原文

> Here are two additional function-related gotchas—mostly reviews, but common enough to reiterate.
>
> **Enclosing scopes and loop variables**: We met this gotcha in Chapter 17's discussion of enclosing function scopes, but as a reminder: when coding factory functions (a.k.a. closures), be careful about relying on enclosing function scope lookup for variables that are changed by enclosing loops. When a generated function is later called, all such references will remember the value of the *last* loop iteration in the enclosing function's scope. In this case, you must use *defaults* to save loop variable values instead of relying on automatic lookup in enclosing scopes. See \"Loops Require Defaults, Not Scopes\" in Chapter 17 for more details on this topic.
>
> **Hiding built-ins by assignment**: Also in Chapter 17, we saw how it's possible to reassign built-in names in a closer local or global scope; the reassignment effectively hides (\"shadows\") and replaces that built-in's name for the remainder of the scope where the assignment occurs. This means you won't be able to use the original built-in value for the name. As long as you don't need the built-in value of the name you're assigning, this isn't an issue—many names are built in, and they may be freely reused. However, if you reassign a built-in name your code relies on, you may have problems. So don't do that, unless you really mean to. The good news is that the built-ins you commonly use will soon become second nature, and Python's error trapping will alert you early in testing if your built-in name is not what you think it is.

### 中文翻译

> 这里还有两个与函数相关的陷阱——大多是复习，但常见到值得重申。
>
> **外层作用域与循环变量**：我们在第 17 章讲外层函数作用域时遇到过这个陷阱，但提醒一下：编写工厂函数（factory functions，也叫闭包 closures）时，小心不要依赖外层函数作用域的查找来读取被外层循环改变的变量。当生成的函数稍后被调用时，所有这类引用记住的都是外层函数作用域中*最后一次*循环迭代的值。在这种情况下，你必须用*默认值*保存循环变量的值，而不是依赖外层作用域的自动查找。更多细节见第 17 章的\"循环需要默认值，而不是作用域\"。
>
> **用赋值隐藏内置名**：同样在第 17 章，我们看到了如何在更近的局部或全局作用域里重新赋值内置名；这种重新赋值会有效地隐藏（\"遮蔽\"，shadows）并替换该内置名在赋值所在作用域剩余部分中的名字。这意味着你无法再用该名字的内置值。只要你不需要所赋名字的内置值，这就不是问题——很多名字都是内置的，可以自由重用。然而，如果你重新赋值了代码依赖的内置名，就可能出问题。所以别那么做，除非你真的想。好消息是：你常用的内置名很快就会成为第二天性，而且如果你的内置名不是你想的那样，Python 的错误捕获会在测试早期就提醒你。

### 深度理解

- **核心概念**：两个陷阱都来自第 17 章的\"名字解析\"规则。闭包陷阱：闭包保存的是**单元（cell）引用**而非值——循环变量是同一个单元格，最终定格在最后一次迭代的值。遮蔽陷阱：局部赋值会让该名字在**整个**作用域内不再指向内置对象。
- **底层实现**：闭包陷阱的机理：外层循环变量 `i` 在编译时被判定为被闭包引用的\"自由变量\"，函数对象保存对同一个 cell 的引用；循环结束后 cell 里的值就是最后的迭代值，所有闭包读到相同值。修复用默认参数：`lambda i=i: ...` 让每次迭代把当前值快照进默认值。遮蔽陷阱的机理：赋值后字节码对该名字的解析从内置（LOAD_GLOBAL 链的第三级）改到局部/全局。
- **设计原因**：闭包按引用（而不是按值）捕获，是\"动态词法作用域\"的常见实现选择（Lua、JavaScript 同此）；默认参数快照是 Python 给的官方绕行方案。遮蔽则纯粹是\"名字只是字典里的键\"这一模型的自然推论。
- **实际问题**：回调列表（按钮绑定循环变量）、装饰器工厂、GUI 事件处理器里，闭包陷阱天天见；`map(lambda x: x, ...)` 里意外覆盖了内置 `map`、`list` 之类的遮蔽事故则在代码评审中高频出现。
- **初学者误区**：以为闭包会\"记住\"创建时刻的变量值（实际记住的是变量本身）；以为给 `list` 变量赋过值后还能在后续代码里用内置 list 函数——遮蔽是\"覆盖式\"的，一旦赋值，该作用域内内置名就没了。

# 本章总结

## 技术拓展（Technical Expansion）

### 实际项目中的应用场景

- **性能回归防线**：把本章的计时方法变成自动化测试（CI 里跑 `python -m timeit` 或 pyperf），防止\"改一次代码性能掉一半\"无感发生。
- **技术选型依据**：选迭代写法、选 Python 实现（CPython/PyPy）、选库之前，用本章的\"结论 + 限定条件\"模板写微型基准，代替拍脑袋。
- **剖析工具链**：微基准之外，全程序性能要用 `profile`/`cProfile`（找出真正的热点函数），两者互补——微基准回答\"哪种写法快\"，剖析回答\"该优化哪里\"。
- **第三方工具**：pyperf（Python 标准基准工具）、pytest-benchmark（把基准写进 pytest）、asv（airspeed velocity，给开源库做跨版本性能追踪）都是生产级选择。

### 与其他语言/工具的区别

| 方面 | Python | Java | C/C++ |
|---|---|---|---|
| 标准计时工具 | timeit（微基准）、cProfile（剖析） | JMH（基准框架，需要注解和单独构建） | clock()/RDTSC/chrono，自己造轮子 |
| 统计策略 | 多轮取最小值（过滤系统抖动） | JMH 输出吞吐量/均值±误差 | 取决于实现 |
| JIT 影响 | 仅 PyPy 等实现；CPython 正在路上 | HotSpot 全时 JIT，需 warm-up 处理 | 无 JIT（除非编译优化） |
| 微基准难度 | 低（内置模块） | 高（JMH 配置繁琐） | 高（编译器优化可能删掉被测代码） |

核心差别一句话：**Python 把\"测速\"做进了标准库，但测出的\"速度\"永远是\"这台机器+这个版本+这段代码\"的组合属性**——任何语言都逃不脱这个限定，Python 只是让你测起来最不费力。

### Python 发展历史背景

- **time.clock 的消亡**：Python 3.3 之前测速常用 `time.clock()`（平台相关、语义混乱），3.3 引入 `time.perf_counter`/`process_time` 后，3.8 正式移除 clock——本章 REPL 例子因此在新版本上\"全部崩掉\"，是版本演进的鲜活教材。
- **timeit 的进化**：timeit 从 Python 2.3 起就内置，历经 CLI 选项、setup 支持、`globals` 参数等增强；其\"构造 def 字符串再编译\"的策略长期稳定，是标准库长寿设计的范例。
- **性能格局的剧变**：2012 年 CPython 3.3 上 for 循环最差、生成器居中；2024 年 CPython 3.12 上排名反转，PyPy 5–20 倍碾压；CPython 3.11 引入自适应特化解释器（提速约 25%），未来 JIT 可能再度改写排名——**基准数据的\"保质期\"之短，本章历史对比就是证明**。
- **pyperf 的崛起**：PyPy 团队在 timeit 命令行里公开\"劝退\"（推荐 pyperf），反映业界对\"严谨测速（方差、统计口径）\"的追求正在成为主流。

### 高级开发者需要掌握的相关知识

- 测速时的\"干扰源\"清单：CPU 频率缩放/睿频、后台进程、垃圾回收（可对比 `gc.disable()` 前后的差别）、缓存热效应（重复执行时数据已在 L1 缓存）。
- 统计素养：为什么取 min 而非 mean（mean 对离群值敏感）、什么时候看标准差（PyPy 的平均值±标准差输出）、如何设计\"足够大\"的 number 让计时分辨率不成为误差来源。
- `timeit` 的 `globals=globals()` 参数、`Timer` 类 API、`autorange()` 自动校准次数等进阶用法。
- 装饰器计时器（第 39 章预告）：在\"函数已被业务使用\"的场景下用 `@timed` 给每次调用注入计时逻辑，与本章\"手动传函数\"模式的取舍。
- 理解 JIT/解释器差异：为何 PyPy 对纯循环友好而字符串拼接反输，为何 CPython 3.12 的 map 对内置函数是\"快车道\"——从实现细节推导性能，而非死记排名。
