## Chapter Introduction（章节导言）

### 英文原文

> Metaclasses and
> Inheritance
> In 
> Chapter 39
> , we explored decorators and studied examples of their use. In this
> final technical chapter of the book, we’re going to continue our tool-builders
> focus with an in-depth review of another advanced topic: 
> metaclasses
> , a protocol
> for managing class objects instead of their instances, introduced briefly in
> Chapter 32
> .
> On a base level, metaclasses extend the code-insertion model of decorators. As
> we learned in the prior chapter, decorators allow us to augment functions and
> classes by intercepting their creation. Metaclasses similarly allow us to intercept
> and augment 
> class creation
> —they provide a hook for inserting extra logic to be
> run at the conclusion of a 
> class
>  statement, albeit in different ways than
> decorators.
> Metaclasses can also provide behavior for classes with 
> methods
>  located in a
> separate inheritance 
> tree skipped for normal, nonclass instances. While this
> allows metaclasses to process their instance classes after creation, it also
> compounds class 
> semantics and convolutes 
> inheritance
> —whose full definition
> can finally be fleshed out here.
> Like all the subjects covered in this part of the book, this is an 
> advanced topic
> that can be studied on an as-needed basis. Metaclasses are not generally in scope
> for most application programmers but may be of interest to others seeking to
> write flexible tools. Whatever category you fall into, though, metaclasses can
> teach you more about Python’s classes and are a prerequisite to both code that
> employs them and the complete inheritance story in Python.
> As the last technical chapter of this book, this also begins to wrap up some
> threads concerning Python itself that we have met often along the way and will
> finalize in the conclusion that follows. Where you go after this book is up to you,
> but in an open source project, it’s important to keep the big picture in mind while
> hacking the small details.
> 
> To Metaclass or Not to Metaclass
> Despite the advanced status awarded to metaclasses 
> in the preceding opener,
> they have a variety of potential roles. For example, they can be used to enhance
> classes with features like tracing, object persistence, exception logging, and
> more. They can also be used to construct portions of a class at runtime based on
> configuration files, apply function decorators to every method of a class
> generically, verify conformance to expected interfaces, and so on.
> In their more grandiose incarnations, metaclasses can even be used to implement
> alternative coding patterns such as aspect-oriented programming,
> object/relational mappers (ORMs) for databases, and more. Although there are
> often alternative ways to achieve such results—as you’ll see, the roles of class
> decorators and metaclasses often intersect—metaclasses provide a formal model
> tailored to those tasks. We don’t have space to explore all such applications first-
> hand in this chapter, of course, but you can find additional use cases on the web
> after studying the basics here.
> Probably the reason for studying metaclasses most relevant to this book is that
> this topic can help demystify Python’s class mechanics in general. For instance,
> you’ll find that they are an intrinsic part of the language’s inheritance model
> formalized in full here. Although you may or may not code or reuse them in your
> work, a cursory understanding of metaclasses can impart a deeper understanding
> of Python at large.
> The Downside of “Helper” Functions
> Before we get to metaclass code, let’s get a better handle on its rationale. Like
> the decorators of 
> the prior chapter, metaclasses are optional in principle. We can
> usually achieve the same effect by passing class objects through functions—
> known interchangeably as 
> helper
>  or 
> manager
>  functions—much as we can
> achieve the goals of decorators by passing functions and classes through
> manager code. Just like decorators, though, metaclasses:
> Provide a more uniform and explicit structure
> Help ensure that application programmers won’t forget to augment their
> classes according to an API’s requirements
> 
> Avoid code redundancy and its associated maintenance costs by
> factoring class customization logic into a single location
> To illustrate, suppose we want to automatically insert a method into a set of
> classes. Of course, we could do this with simple 
> inheritance
>  if the subject
> method is known when we code the classes. In that case, we can simply code the
> method in a superclass and have all the classes in question inherit from it:
> class Extras:
>  def extra(self, args): 
> # Normal inheritance: too static
>  …
> class Client1(Extras): … 
> # Clients inherit extra methods
> class Client2(Extras): …
> X = Client1() 
> # Make an instance
> X.extra() 
> # Run the extra methods
> Sometimes, though, it’s impossible to predict such augmentation when classes
> are coded. Consider the case where classes are augmented in response to choices
> made in a user interface at runtime or loaded from an editable configuration file.
> Although we could code every class in our imaginary set to 
> manually
>  check
> these, too, it’s a lot to ask of clients (the 
> required
>  function here is abstract—it’s
> something to be filled in):
> def extra(self, arg): …
> class Client1: … 
> # Client augments: too distributed
> if required():
>  Client1.extra = extra
> class Client2: …
> if required():
>  Client2.extra = extra 
> # Add the extra method – maybe
> X = Client1()
> X.extra()
> We can add methods to a class after the 
> class
>  statement like this because, as
> we’ve learned, a class-level method is just a plain function that is associated with
> a class and has a first argument to receive a 
> self
>  instance when called through
> one. Although this works, it might become untenable for larger method sets and
> 
> puts all the burden of augmentation on each client class (and assumes they’ll
> remember to do this at all).
> It would be better from a maintenance perspective to isolate the decision logic in
> a single place. We might encapsulate some of this extra work by routing classes
> through a 
> helper function
> —a function that would extend the class as required
> and handle all the work of runtime testing and configuration:
> def extra(self, arg): …
> def extras(Class): 
> # Helper function: too manual
>  if required():
>  Class.extra = extra
> class Client1: …
> extras(Client1)
> class Client2: …
> extras(Client2)
> X = Client1()
> X.extra()
> This code runs the class through a helper function immediately after it is created.
> Although functions like this one can achieve our goal here, they still put a
> burden on class coders, who must understand the requirements and adhere to
> them in their code. It would be even better if there was a simple way to enforce
> the augmentation in the subject classes, so that they don’t need to deal with the
> augmentation 
> so explicitly
>  and would be less likely to forget to use it altogether.
> In other words, we’d like to be able to insert some code to run 
> automatically
>  at
> the end of a 
> class
>  statement to augment the class.
> This is exactly what 
> metaclasses
>  do—by declaring a metaclass, we tell Python to
> route the creation of the class object to another class we provide:
> def extra(self, arg): …
> class Extras(type):
>  def __init__(Class, classname, superclasses, attributedict):
>  if required():
>  Class.extra = extra
> class Client1(metaclass=Extras): … 
> # Metaclass declaration only
> 
> class Client2(metaclass=Extras): … 
> # Client class is instance of meta
> X = Client1() 
> # X is instance of client class
> X.extra()
> Because Python invokes the metaclass automatically at the end of the 
> class
> statement when the new class is 
> created
> , it can augment, register, wrap, or
> otherwise manage the class as needed. Moreover, the only requirement for the
> client classes is that they 
> declare
>  their metaclass; every class that does so will
> automatically acquire whatever augmentation the metaclass provides, both now
> and in the future if the metaclass changes.
> Metaclasses can also augment their class instances with inherited 
> methods
> ,
> which are akin to normal class methods but not inherited by the instances of their
> class instances—an inheritance extension and tongue twister whose true nature
> requires more info ahead (and quite possibly, sedation). Through both changes
> and methods, though, metaclasses can customize class behavior broadly.
> Of course, this is the standard rationale, which you’ll need to judge for yourself
> —in truth, clients might forget to list a metaclass just as easily as they could
> forget to call a helper function! Still, 
> the explicit nature of metaclasses may
> make this less likely. Although it may be difficult to glean from this small and
> hypothetical example, metaclasses generally handle such tasks better than more
> manual approaches.
> Metaclasses Versus Class Decorators: Round 1
> Having said that, it’s also important to 
> note that the 
> class decorators
>  described in
> the preceding chapter sometimes overlap with metaclasses—in terms of both
> utility and benefit. Like metaclasses, class decorators can be used to manage
> both classes and their later instances, and their syntax makes their usage
> similarly explicit and arguably more obvious than helper-function calls.
> For example, suppose we recoded the last section’s helper function to 
> return
>  the
> augmented class instead of simply modifying it in place. This would allow a
> greater degree of flexibility because the manager would be free to return any
> type of object that implements the class’s expected interface:
> def extra(self, arg): …
> 
> def extras(Class):
>  if required():
>  Class.extra = extra
>  return Class 
> # Return the augmented class
> class Client1: …
> Client1 = extras(Client1) 
> # Rebind to augmented class
> class Client2: …
> Client2 = extras(Client2)
> X = Client1()
> X.extra()
> If you think this is starting to look reminiscent of class decorators, you’re right.
> In the prior chapter, we emphasized class decorators’ role in augmenting
> instance
>  creation calls. Because they work by automatically rebinding a class
> name to the result of a function, though, there’s no reason that we can’t use them
> to augment the class by changing it before any instances are ever created. That
> is, class decorators can apply extra logic to 
> classes
> , not just 
> instances
> , at class
> creation time:
> def extra(self, arg): …
> def extras(Class): 
> # From helper to decorator
>  if required():
>  Class.extra = extra
>  return Class
> @extras
> class Client1: … 
> # Client1 = extras(Client1)
> @extras
> class Client2: … 
> # Rebinds class independent of instances
> X = Client1() 
> # Makes instance of augmented class
> X.extra() 
> # X is instance of original Client1
> Decorators essentially automate the prior example’s manual name rebinding
> here. Just as for metaclasses, because this decorator returns the original class,
> instances are made from that class, not from a wrapper object. In fact, instance
> creation is not intercepted at all in this example.
> 
> In this specific case—adding methods to a class when it’s created—the choice
> between metaclasses and decorators is arbitrary. Decorators can be used to
> manage both instances and classes and intersect most strongly with metaclasses
> in the second of these roles, but this discrimination is not absolute. In fact, the
> roles of each are suggested in part by their mechanics.
> As we’ll detail ahead, decorators technically correspond to metaclass 
> calls
>  used
> to make and initialize new classes. Metaclasses, though, have additional
> customization hooks beyond class creation. Their 
> methods
>  inherited by classes,
> for example, have no direct counterpart in class decorators sans extra code. This
> can make metaclasses more complex but also better suited for augmenting
> classes in some contexts.
> Conversely, because metaclasses are designed to manage classes, applying them
> to managing 
> instances
>  alone is less optimal. Because they are also responsible
> for making the class itself, metaclasses incur this as an 
> extra
>  step in instance-
> management roles and are perhaps less appropriate than decorators.
> We’ll explore some of these differences in 
> working code later in this chapter. To
> better understand how metaclasses do their work, though, we first need to get a
> clearer picture of their underlying model.
> The Metaclass Model
> To understand metaclasses, you first need to understand a bit more about both
> Python’s object model and what happens at the end of a 
> class
>  statement. As
> you’ll learn here, the two are intimately related.
> Classes Are Instances of type
> The first of these prerequisites was covered 
> previously by 
> “The Python Object
> Model”
> , which in turn assumes knowledge of the 
> MRO
>  (method resolution
> order) covered in 
> Chapter 31

> Instances are created from classes.
> 
> Classes are instances of a metaclass.
> The 
> type
>  built-in is the topmost metaclass.
> Metaclasses customize 
> type
>  with normal 
> class
>  statements.
> In short, classes are types, types are classes, and metaclasses customize types.
> Per 
> Chapter 32

> different from that between classes and their

>  instances. The latter do
> not generate more instances, and while attribute inheritance uses the same core

> type
> :
> >>>

> (<class 'type'>, <class 'type'>)

> defined classes, which are really just user-defined types—their nonclass

> type
> :
> >>> 
> class Hack: pass
>  
> # User-defined classes work the same
> >>> 
> I = Hack()

>  
> # Made from class, which is made from type
> >>> 
> type(I), type(type(I))

> Chapter 32

> type
>  class by default, most
> programmers don’t need to think about this model. However, it’s key to
> understanding the way that 
> metaclasses work—as the next section explains.
> Metaclasses Are Subclasses of type
> Why would we care that classes are instances of a 
> type
>  class? It turns out that
> this is the hook 
> that allows us to code metaclasses. Specifically, we can create
> classes from 
> subclasses
>  of 
> type
>  that customize it with normal object-oriented
> techniques and class syntax. And these 
> type
>  subclasses are known as
> metaclasses
> .
> In other words, to control the way classes are created and augment their
> behavior, all we need to do is specify that a user-defined class be created from a
> user-defined metaclass instead of the normal and default 
> type
>  class.
> Before we see how, it’s important to bear in mind that this 
> type instance
> relationship is not quite the same as normal 
> inheritance
> . User-defined classes
> may also have 
> superclasses
>  from which they and their instances inherit attributes
> as usual. As we’ve seen, inheritance superclasses are listed in parentheses in the
> class
>  statement, show up in a class’s 
> __bases__
>  tuple, and are searched for
> attributes fetched from nonclass instances.
> However, the type from which a class is created and of which it is an instance is
> a different relationship. Inheritance searches instance and class namespace
> dictionaries, but classes may also acquire behavior from their type that is not
> exposed to the normal inheritance search. In fact, metaclasses define a separate,
> secondary
>  inheritance tree available only to classes and used as a fallback when
> the normal superclass search fails.
> To lay the groundwork for understanding this distinction, the next section
> describes the procedure and syntax 
> Python uses to implement this 
> instance-of
> relationship.
> Class Statements Call a type
> 
> Subclassing the 
> type
>  class to customize it is really only half of the metaclass
> backstory. We still 
> need to somehow route a class’s creation to the metaclass
> instead of the default 
> type
> . To comprehend the way that this is arranged, we also
> need to know how 
> class
>  statements do their business.
> We’ve already learned that when Python reaches a 
> class
>  statement, it runs its
> nested block of code to create the class’s attributes—all the names assigned at
> the top level of the nested code block generate attributes in the resulting class
> object. These names are usually method functions created by nested 
> def
> s, but
> they can also be arbitrary attributes assigned to create class data shared by all
> instances.
> Technically speaking, Python follows a standard protocol to make this happen: at
> the 
> end
>  of a 
> class
>  statement, and after running all its nested code in a
> namespace dictionary corresponding to the class’s local scope, Python calls the
> type
>  object to create the new class object like this:
> class
>  = type(
> classname
> , 
> superclasses
> , 
> attributedict
> )

> type
>  object in turn defines a 
> __call__

> runs two other methods when the 
> type
>  object is called:
> type.__new__(
> typeclass
> , 
> classname
> ,

> attributedict

> , 
> classname
> , 
> superclasses
> ,

> __new__

> class
>  object, after which the
> __init__
>  method initializes the newly created object. As you’ll see in a

> type

> Hack

> type
>  class by default. To tell
> Python to create a class with a custom

> Meta

> type

> type

> classname

> superclasses
> ,

> special 
> class

> Coding Metaclasses
> So far, we’ve seen how Python routes class creation calls to a metaclass if one is
> specified and provided. How, though, do we actually 
> code
>  a metaclass that
> 
> customizes 
> type
> ?
> It turns out that you already know most of the story—metaclasses are coded with
> normal Python 
> class
>  statements and semantics. By definition, they are simply
> classes that inherit from 
> type
>  (normally, at least). Their only substantial
> distinctions 
> are that Python calls them 
> automatically
>  at the end of a 
> class
> statement and that they must generally adhere to the 
> interface
>  expected by the
> type
>  superclass if they subclass it.
> A Basic Metaclass
> Perhaps the simplest metaclass you can code is simply a subclass of 
> type
>  with a
> __new__
>  method that creates the class object by running the default method in
> type
> . A metaclass 
> __new__
>  like this is run by the 
> __call__
>  method inherited
> from 
> type
>  by virtue of normal inheritance overrides; this method 
> typically
> performs whatever augmentation is required and calls the 
> type
>  superclass’s
> __new__
>  method to create and return the new class object:
> class Meta(type):
>  def __new__(meta, classname, supers, classdict):
>

> Managing Classes with Metaclasses and Decorators
> Now that we understand the hook metaclasses use to insert code to be run at

> used to augment classes arbitrarily, and in many of the same ways as the 
> class
> decorators
>  of 
> Chapter 39
> . This doesn’t make these two tools identical—
> metaclasses also support the notion of inherited methods coming up later—but
> they are functionally redundant in some roles.
> Adding methods to classes
> To demo both this equivalence and more realistic usage,

> import time

>  result = func(*args, **kargs)
>  elapsed = time.perf_counter() - start

>  if trace:
>  funcname, alltime = func.__name__, onCall.alltime
>  print(f'{label}{funcname}: {elapsed:.5f}, {alltime:.5f}')
>  return result
>  onCall.alltime = 0
>  return onCall
>  return onDecorator

#### To Metaclass or Not to Metaclass（要不要使用元类）

> 尽管元类被称为高级主题，它们仍有许多潜在用途。例如，可以为类增加跟踪、对象持久化、异常记录等功能；也可以根据配置文件在运行时构造类的一部分，为类的每个方法统一应用函数装饰器，或检查类是否符合预期接口。
>
> 在更宏大的用法中，元类甚至可以实现面向切面编程、对象关系映射（ORM）等替代性编程模式。完成这些任务通常还有别的办法，而且类装饰器与元类的职责常常交叉；不过元类为这些工作提供了一个正式的模型。本章不可能亲自展示所有应用，掌握基础后可以再查阅其他用例。
>
> 学习元类对本书最重要的价值，可能是帮助我们消除对类机制的神秘感。元类是 Python 继承模型的内在组成部分，本章会把这个模型完整形式化。即使你从不编写或复用元类，对它有粗略认识也会加深你对 Python 的整体理解。

#### The Downside of “Helper” Functions（“辅助”函数的缺点）

> 在编写元类之前，先说明它存在的理由。原则上元类是可选的：我们通常可以把类对象传给一个函数来达到同样效果，这类函数可以叫辅助函数或管理函数，就像把函数或类传给管理代码可以实现装饰器的目标一样。
>
> 元类和这种手工方案相比，能够提供更统一、更明确的结构；能帮助保证应用程序员不会忘记按照 API 的要求增强类；还能把类定制逻辑集中到一个位置，避免重复代码和随之而来的维护成本。
>
> 假设我们想自动向一组类插入一个方法。如果在编写这些类时就知道这个方法，普通继承已经足够：把 `extra` 写在超类 `Extras` 中，`Client1` 和 `Client2` 继承它，`Client1()` 得到的实例就能调用 `X.extra()`。这种办法的问题是，它把增强方案固定在类的源代码里。
>
> 有时类被编写时根本无法预测增强内容。例如，增强可能取决于运行时用户界面的选择，或者取决于从可编辑配置文件载入的设置。我们可以让每个客户类手工检查条件，并在条件满足时执行 `Client1.extra = extra`、`Client2.extra = extra`，但这会把负担分散给所有客户类，还假定它们永远记得这样做。
>
> 类语句之后可以这样增加方法，是因为类级别的方法本质上只是一个和类关联的普通函数；通过实例调用时，Python 会把实例作为接收 `self` 的第一个参数。方法少时这仍然可行，方法集一大就难以维护，而且每个客户类都可能漏掉增强步骤。
>
> 可以把判断逻辑集中到 `extras(Class)` 辅助函数中，让它接收一个刚创建的类，按运行时配置决定是否执行 `Class.extra = extra`。这比把判断复制到每个类里好，但调用者仍然必须在每条 `class` 语句后显式写 `extras(Client1)`、`extras(Client2)`，依旧要求类作者理解并遵守这项约定。
>
> 更理想的方式，是让代码自动在 `class` 语句末尾运行，从而增强类而不要求客户显式处理。这正是元类的作用：声明元类后，Python 会把类对象的创建转交给我们提供的另一个类。示例中的 `Extras(type)` 在 `__init__` 中按条件给新类加上 `extra`，而 `Client1(metaclass=Extras)` 和 `Client2(metaclass=Extras)` 只需声明元类；`X = Client1()` 得到的普通实例就可以调用 `X.extra()`。
>
> Python 在新类创建时自动调用元类，因此元类可以按需要增强、注册、包装或管理类。客户类只须声明元类；以后修改元类时，所有声明该元类的类也会自动获得新的处理逻辑。
>
> 元类还可以通过继承的方法为自己的实例类提供行为。这些方法类似普通类方法，却不会被这些类的实例继承。这个看起来绕口的继承扩展需要后面的模型来解释，但它说明元类不仅能修改类的字典，还能广泛定制类行为。
>
> 当然，这只是使用元类的标准理由，是否值得使用仍要由工程师判断。客户同样可能忘记写元类声明，就像可能忘记调用辅助函数；元类的声明更显式，也许能降低遗漏概率。对于大型工具和库，集中、自动的定制通常比手工分散处理更容易维护。

#### Metaclasses Versus Class Decorators: Round 1（元类与类装饰器：第一回合）

> 需要注意的是，上一章介绍的类装饰器在用途和收益上有时会与元类重叠。类装饰器也能管理类以及类后来创建的实例，而且语法同样明确，比手工调用辅助函数更容易看出类被处理过。
>
> 如果让前面的辅助函数返回增强后的类，而不是只在原地修改它，就可以写出 `Client1 = extras(Client1)`。管理函数可以返回任何实现了预期接口的对象，这带来更大的灵活性。这正是类装饰器的外观：`@extras` 等价于在类语句结束后执行 `Client1 = extras(Client1)`。
>
> 类装饰器不只可以拦截实例创建，也可以在实例尚未创建时修改类。示例返回原来的类，因此实例仍由原来的 `Client1` 创建，并没有被包装对象拦截。
>
> 对于“类创建时增加方法”这一具体任务，选元类还是类装饰器可以说是任意的。两者都能管理类和实例，差别并不是绝对的；它们的典型角色更多由实现机制决定。
>
> 从技术上说，装饰器对应于创建并初始化新类之后对类对象的调用。元类则拥有超出类创建调用的定制钩子，例如元类方法可以被类继承，而类装饰器没有直接对应物，除非额外编写代码。反过来，元类既负责创建类又常被用于管理实例，因而在只想管理实例时多了一层不必要的工作，可能不如装饰器合适。

#### The Metaclass Model（元类模型）

> 要理解元类，必须先理解 Python 的对象模型，以及 `class` 语句结束时发生的事情；两者是紧密相连的。下面先看“类是 `type` 的实例”，然后再看类语句如何调用类型对象。

#### Classes Are Instances of type（类是 `type` 的实例）

> 实例由类创建；类是元类的实例；内置的 `type` 是最顶层的元类；元类用普通的 `class` 语句定制 `type`。简言之，类是类型，类型也是类，而元类定制类型。
>
> 元类与类的关系，和类与普通非类实例的关系略有不同。普通实例不会再生成更多实例；虽然两者的属性继承都使用相同的核心机制和 MRO，但类会搜索一棵普通实例不会搜索的元类树。
>
> `list` 实例由 `list` 类创建，而 `list` 类由内置 `type` 创建，所以 `type([])` 是 `list`，`type(type([]))` 是 `type`；`type(list)` 和 `type(type)` 也都显示为 `type`。用户定义的 `Hack` 同样遵循这一模型：`I = Hack()` 的类型是 `Hack`，而 `Hack` 的类型是 `type`。
>
> 类和普通实例在某种意义上都可以称为“实例”。两者的 `__class__` 都说明它们由什么创建：`[].__class__` 是 `list`，`list.__class__` 是 `type`，`I.__class__` 是 `Hack`，`Hack.__class__` 是 `type`。由于用户类默认由根元类 `type` 创建，大多数程序不必直接考虑它，但理解元类时它是基础。

#### Metaclasses Are Subclasses of type（元类是 `type` 的子类）

> 类由 `type` 创建这一点正好提供了编写元类的钩子。我们可以用普通面向对象技术和 `class` 语句编写 `type` 的子类；这些 `type` 子类就叫元类。想控制类的创建或增强类的行为，只要让目标用户类由自定义元类而不是默认的 `type` 创建即可。
>
> 但“某个类是另一个类型的实例”和“某个类继承另一个超类”不是同一关系。普通超类写在 `class` 头的括号中，出现在 `__bases__` 中，并在普通实例查找属性时被搜索；创建该类的类型则是另一条关系。普通继承查找实例和类的命名空间字典，而元类还形成一条只对类可用的次级继承树，在普通超类搜索失败时作为后备。

#### Class Statements Call a type（类语句会调用 `type`）

> Python 执行 `class` 语句时，会先运行嵌套代码块；代码块顶层赋值的名字会成为结果类对象的属性，通常包括嵌套 `def` 创建的方法，也可以包括所有实例共享的类数据。
>
> 从协议角度看，Python 在类语句末尾、完成类局部作用域对应的命名空间字典后，会调用 `type(classname, superclasses, attributedict)` 创建新类。`type` 对象的 `__call__` 又会调用 `type.__new__(typeclass, classname, superclasses, attributedict)` 创建并返回类对象，再调用 `type.__init__(class, classname, superclasses, attributedict)` 初始化已经创建的类对象。`__new__` 负责产生对象，`__init__` 负责初始化对象；元类通常就在这些钩子里定制类。
>
> 对于 `class Hack(Super)`，嵌套代码会产生 `data` 和 `meth`，Python 最终可以概念化为 `Hack = type('Hack', (Super,), {'data': 1, 'meth': meth, '__module__': '__main__'})`。也可以手工调用三参数形式的 `type` 动态创建同样的类：得到的类有 `object` 作为默认超类，实例可以访问 `data` 和 `meth`，其 `__bases__`、MRO、`dir` 和类字典都与 `class` 语句创建的类相同。
>
> 因为这个 `type` 调用会自动发生在类语句末尾，所以它是增强或处理类的理想钩子。只要把默认的 `type` 换成自定义子类，就能拦截这次调用。

#### Class Statements Can Choose a type（类语句可以选择 `type`）

> 类默认由 `type` 创建。要换用自定义元类，只需在类头使用关键字参数：`class Hack(metaclass=Meta):`。省略该参数时仍使用 `type`；写出它以后，类语句结束时的创建调用就会路由到 `Meta(classname, superclasses, attributedict)`。
>
> `metaclass` 指定的是“实例属于谁”的关系，而不是普通超类继承。普通超类仍可以写在类头中，并且由于属于主继承树，会在元类次树之前参与属性查找。例如 `class Hack(Super, metaclass=Meta)` 表示 `Hack` 正常继承 `Super`，同时是 `Meta` 的实例并由 `Meta` 创建。语法上普通超类写在 `metaclass` 关键字之前。

#### Metaclass Method Protocol（元类方法协议）

> 指定元类后，类对象创建调用从默认的 `type(...)` 变为 `Meta(...)`。如果 `Meta` 是 `type` 的子类，那么它继承的 `type.__call__` 会把新类对象的创建和初始化交给元类上的相应方法。概念上，这可能触发 `Meta.__new__(Meta, classname, superclasses, attributedict)`，随后触发 `Meta.__init__(class, classname, superclasses, attributedict)`。
>
> 对 `class Hack(Super, metaclass=Meta)`，类体执行完成后可以把过程写成 `Hack = Meta('Hack', (Super,), {'data': 1, 'meth': meth, '__module__': '__main__'})`。如果元类定义自己的 `__new__` 或 `__init__`，继承自 `type` 的 `__call__` 会在类构造流程中自动调用它们；元类方法因此成为类创建时的自动逻辑。

#### Coding Metaclasses（编写元类）

> 元类仍然使用普通 Python `class` 语句和普通语义编写。按照定义，它通常是继承 `type` 的类。真正的区别只有两点：Python 会在类语句结束时自动调用它；如果它继承 `type`，就必须遵守 `type` 超类所要求的接口。

#### A Basic Metaclass（一个基本元类）

> 最简单的元类是 `type` 的子类，只重写 `__new__`，并在其中调用默认的 `type.__new__` 来创建类。这个元类的 `__new__` 会由从 `type` 继承的 `__call__` 调用；通常先执行需要的增强，再调用超类的 `__new__` 并返回新类。
>
> 示例 `MetaOne` 在 `__new__` 中打印元类、类名、超类元组和类字典，再调用 `type.__new__`。定义 `Hack` 时先打印 `Making class`，随后元类在类语句结束时运行；定义 `Hack` 的实例 `X` 要等类已经创建完才发生，所以之后才打印 `Making instance`。输出说明元类处理类，类处理普通非类实例。
>
> 示例输出中的对象地址会因运行而变化，命名空间中的某些双下划线属性也会随 Python 版本变化；原书为简洁省略了它们。实际运行示例时，应把地址和自动加入的内建名称视为非稳定展示细节，而不是程序逻辑。

#### Customizing Construction and Initialization（定制构造与初始化）

> 元类也可以使用 `type.__call__` 所调用的 `__init__` 协议。一般来说，`__new__` 创建并返回类对象，`__init__` 接收已经创建的类并初始化它。普通非类型类也有这两个方法，但普通类中很少需要重写 `__new__`。
>
> `MetaTwo` 同时重写 `__new__` 和 `__init__`。定义 `Hack` 时，先运行 `MetaTwo.__new__` 完成类对象构造，再运行 `MetaTwo.__init__`，它可以从 `Class.__dict__` 观察到已经存在的 `__module__`、`data`、`meth` 和 `__doc__`。这一切都发生在类语句结束、任何普通实例创建之前。相反，写在 `Hack` 里的 `__init__` 会等到 `Hack()` 创建普通实例时运行，与元类的 `__init__` 不是同一个时刻。

#### Other Metaclass Coding Techniques（其他元类编写方式）

> 重定义 `type` 的 `__new__` 和 `__init__` 是最常见的插入方式，但不是唯一方式。只要对象在类语句结束时可调用、能够接收 Python 传来的参数并返回适合充当类的对象，就可以承担元类角色。

#### Using simple factory functions（使用简单工厂函数）

> 元类不一定真的是类。类语句结尾只是发起一次创建类的调用，因此任何可调用对象原则上都可以作为元类。示例 `MetaFunc(classname, supers, classdict)` 打印参数后返回 `type(classname, supers, classdict)`；`class Hack(Super, metaclass=MetaFunc)` 结束时，Python 直接调用这个函数，函数返回的类绑定到名字 `Hack`。
>
> 从技术上说，普通函数可以返回任意对象，返回值会被赋给新类的名字，不要求它必须是 `type` 实例。若返回对象不支持后续的实例创建，之后调用 `Hack()` 可能失败。这使函数元类和类装饰器在“最后把名字重新绑定到结果”这一点上变得相似。

#### Overloading class creation calls with normal classes（用普通类重载类创建调用）

> 普通非类实例也可以通过运算符重载响应调用操作，因此也能承担某些元类角色。示例用 `MetaObj()` 这个普通类实例作为元类；它的 `__call__` 接收类名、超类和类字典，调用自定义命名的 `__New__` 创建类，再调用 `__Init__` 初始化类。
>
> 这里必须使用 `__New__` 和 `__Init__` 这样的不同名字，因为若叫作 `__new__` 和 `__init__`，它们会在创建 `MetaObj()` 这个普通对象时运行，而不是在之后该对象作为元类被调用时运行。`MetaObj.__call__` 只是模拟了 `type.__call__` 的部分流程，不依赖 `type` 的元类分派语义。
>
> 还可以通过普通超类继承 `__call__`。示例中的 `SubMetaObj` 继承 `SuperMetaObj` 的 `__call__`，再提供 `__New__` 和 `__Init__`；因此普通实例仍按通常的继承规则获取调用拦截器。这种写法不常见，却揭示了“可调用对象接管类创建”这个底层模型。实践中，重写 `type` 的 `__new__`/`__init__` 通常更简单。

#### Managing Classes with Metaclasses and Decorators（用元类和装饰器管理类）

> 元类在类构造时插入的代码可以任意增强类，很多工作与类装饰器相同。不过元类还支持后面将要讨论的“元类方法继承”，所以两者并非完全相同。

#### Adding methods to classes（向类添加方法）

> `Extender` 在创建每个客户类时，把 `triple` 和 `concat` 两个函数放入传给 `type.__new__` 的类字典。函数成为类属性后，通过实例调用时会收到实例作为第一个参数，于是 `Client1` 的类体中没有写出的两个方法仍能被 `X.triple()` 和 `X.concat()` 调用，`Client2` 也获得同样的能力。
>
> 这些函数当然也可以放进超类让客户类继承，但元类可以在每次构造类时按条件选择要插入的方法。这里插入的是客户类的方法，所以 `X`、`Y` 这样的普通实例能看到；若把方法只定义在元类本身，普通实例不会继承它。
>
> 类装饰器版本 `@extender` 做的是同一件事：类先创建出来，装饰器把函数放进类并返回原类，名字被重新绑定到这个返回值。两者都在 `class` 语句末尾得到一个对象并绑定类名；元类先参与类对象的创建，装饰器则在类对象已经创建后运行。元类还可以在 `__new__`、`__init__` 或 `__call__` 中插入逻辑。

#### Automatically decorating class methods（自动装饰类方法）

> `tracer` 和 `timer` 是上一章的函数装饰器。手工使用它们时，必须在每个想跟踪或计时的方法前写装饰器；如果想处理一个类的所有方法，这会很繁琐，动态场景中甚至无法事先知道要装饰哪些方法。
>
> `decorateAll(decorator)` 返回一个元类。元类的 `__new__` 遍历类体的 `classdict`，对其中类型为 `FunctionType` 的值执行 `decorator(attrval)`，再把替换后的函数交给 `type.__new__`。因此 `Person` 的 `__init__`、`giveRaise` 和 `lastName` 都会在类创建时自动被 `tracer` 包装，运行时就会分别打印每个方法的调用次数。
>
> 把类头改成 `metaclass=decorateAll(timer())` 或 `metaclass=decorateAll(timer(label='**'))`，就能把另一种函数装饰器和参数传入元类。元类可以依据运行时条件决定是否装饰，装饰器本身也可以按类变化。
>
> 类装饰器版本遍历 `aClass.__dict__`，用 `setattr` 把包装后的函数写回类，然后返回原类。它的输出与元类版本相同，因为两者都能在类创建结束时处理方法。这个装饰器返回增强后的原类而不是代理，因此实例的类型仍是 `Person`；不过类字典里的方法已经是包装函数，而非最初定义的函数。多个装饰器也可以按 Python 的嵌套规则组合使用。

### 深度理解

- **核心概念**：要区分三种对象：普通实例由类创建，类由元类创建，元类本身通常又由 `type` 创建。`metaclass=Meta` 不等于“继承 `Meta`”，它表示目标类是 `Meta` 的实例；普通超类仍由括号列表声明。
- **底层实现**：类语句执行的是运行时协议。类体先在命名空间中执行，随后由可调用的元类接收类名、超类元组和属性字典；`type` 的默认 `__call__` 再协调 `__new__` 和 `__init__`。`__new__` 必须返回类对象，`__init__` 只能初始化已返回的对象，不能用返回值替换它。
- **设计原因**：把“构造类”本身开放出来，框架就能把注册、接口检查、字段收集或统一装饰集中到类作者不易忘记的位置。它比在每个类之后调用辅助函数更强制，比手工修改每个类更少重复。
- **实际问题**：元类会增加调试和继承成本；不同基类带有不兼容的元类时可能发生元类冲突；在 `__new__` 中原地修改传入字典、忘记调用 `type.__new__`、或错误地把实例初始化逻辑写进元类，都会造成难以诊断的行为。若类装饰器或 `__init_subclass__` 能满足需求，通常应优先考虑它们。
- **初学者误区**：元类不是“所有实例的父类”，也不会把元类方法自动传给普通实例；`Meta.__init__` 初始化的是类对象，`Hack.__init__` 初始化的是 `Hack()` 产生的普通实例。另一个常见误解是把类装饰器和元类看成完全等价：装饰器在类已创建后运行，而元类能介入创建过程并为类提供次级继承树中的行为。

### 代码分析

```python

    def __new__(mcls, name, bases, namespace):
        namespace['created_by_meta'] = True
        return super().__new__(mcls, name, bases, namespace)

class Base:
    pass

class Client(Base, metaclass=Meta):
    value = 3

obj = Client()
```

- 执行 `class Client` 时，解释器先执行类体，得到包含 `value`、`__module__` 等键的命名空间；随后调用 `Meta`。`Meta` 的 `__new__` 先把 `created_by_meta` 写入字典，再用 `super().__new__` 让 `type` 分配并初始化真正的类对象。之后如果定义了元类 `__init__`，它会接收刚创建的 `Client`。
- `Client` 的 `__class__` 是 `Meta`，而 `obj` 的 `__class__` 是 `Client`。因此 `Client` 创建时会经过 `Meta`，但 `obj.value` 和 `obj.created_by_meta` 是沿 `Client` 的普通类树查到的；元类本身的普通方法不会自动成为 `obj` 的方法。

```python

    return self.value * 3

class Extender(type):
    def __new__(mcls, name, bases, namespace):
        namespace['triple'] = triple
        return type.__new__(mcls, name, bases, namespace)

class Client(metaclass=Extender):
    def __init__(self, value):
        self.value = value

Client(4).triple()       # 12
```

- `triple` 放进客户类的命名空间后，它是普通函数描述符；从实例取出时会绑定实例作为 `self`。如果只把 `triple` 写进 `Extender`，它会成为类对象可见的元类方法，`Client()` 这个普通实例却看不到。
- **现代实践补充（Python 3）**：真实的类创建还可能经过元类的 `__prepare__`，并在类创建后触发描述符的 `__set_name__` 与基类的 `__init_subclass__`；本章用 `type(name, bases, dict)` 概括主流程，实际框架代码应遵循 `type` 的协作式调用约定。

> 元类的写法类似继承超类，所以一开始很容易混淆它们的作用范围。Python 实际上会搜索两棵类树：第一棵是一个类及其超类构成的主树；第二棵是这个类的元类及其超类构成的次树，也叫“类型树”，因为它从 `type` 延伸出来。
>
> 元类通常继承 `type`。虽然角色特殊，它们仍然用普通 `class` 语句编写，并遵循普通的面向对象模型；作为 `type` 的子类，它们可以重定义 `type` 的方法来定制类创建，最常见的是 `__new__` 和 `__init__`。元类也可以为自己的实例类定义方法，甚至可以只是返回任意对象的简单函数或其他可调用对象。
>
> 元类属性不会被类的普通实例获得。`metaclass=M` 表示类是 `M` 的实例，而不是说类的普通实例继承了 `M`。普通实例的查找只搜索实例本身、它的类和该类的超类组成的主树，从不进入元类次树；因此普通实例可以获得类和超类的行为，却获得不了元类的行为。
>
> 类对象则不同。作为元类的实例，类在主树搜索失败后，会把自己的元类及其超类组成的次树作为后备来源。如果某个名字同时存在于普通超类和元类中，普通超类的版本优先，因为主树先于次树搜索。

### 深度理解

- **核心概念**：主继承树回答“普通实例从哪个类和超类获得属性”，次级元类树回答“类对象本身在主树查找失败后从哪个元类获得属性”。两者共享 MRO 思想，但不会把次树的结果继续传递给普通实例。
- **底层实现**：普通实例的 `__class__` 链接到 `__bases__` 形成的 MRO；类对象先搜索自己的 `__mro__`，再通过 `C.__class__` 找到元类并搜索元类的 `__mro__`。方法绑定取决于找到属性的来源：类字典中的函数从类显式取出时通常是普通函数，元类字典中的函数从类取出时则绑定到该类。
- **设计原因**：把类的管理行为和实例业务行为分开，框架可以让 `Model.query()`、注册器或类级别运算只存在于类对象上，而不污染每个模型实例的 API。
- **实际问题**：同名属性的来源很容易误判；普通超类会压过元类属性，元类属性又不会出现在普通实例上。多个基类或多个元类的继承关系还可能引发元类冲突。排查时应同时检查 `C.__dict__`、`C.__mro__`、`C.__class__` 和 `C.__class__.__mro__`。
- **初学者误区**：`C.attr` 能访问到 `Meta.attr`，并不表示 `C().attr` 也能访问；`C.__class__` 是元类，`C()` 的 `__class__` 却是 `C`。另外，`Sub.meth2` 不是已经绑定到 `Sub` 的实例方法，只有经过 `Sub()` 取出才会绑定普通实例。

> 当同名属性同时存在于两种来源时，主超类树优先于次级元类树。`class M(type): attr = 1` 与 `class S: attr = 2` 一起用于 `class C(S, metaclass=M)` 时，`C.attr` 和 `I.attr` 都是 `2`；普通实例只搜索主树，而类对象也先搜索主树，只有失败后才搜索元类树。即便超类要在继承树上向上两层，主树的名字仍然胜过元类的名字。
>
> 类获得元类属性，是通过它的 `__class__` 链接实现的，类似普通实例通过 `__class__` 链接到自己的类。但普通实例的继承不会继续沿类的 `__class__` 走元类树，而是沿实例类的 `__bases__` 走主树：`I.__class__` 是 `C`，`C.__bases__` 是普通超类；对类对象而言，先沿 `C.__mro__` 查找，再沿 `C.__class__.__mro__` 查找。
>
> 因此 `C.__mro__` 是 `C` 的主树扁平化结果，`M.__mro__` 是元类次树扁平化结果。普通实例只搜索前者；类对象需要时搜索二者。下一节会说明元类之间如何用相同机制形成继承层次。

### 深度理解

- **核心概念**：`isinstance(C, M)` 的实例关系只影响 `C` 这个类对象的属性获取，不改变 `C()` 的普通继承树。判断一个属性是否能被实例看到，关键是它是否写入了 `C` 或 `C` 的普通超类，而不是它是否能通过 `C` 的元类找到。
- **底层实现**：普通实例查找可近似表示为 `[I.__dict__] + [base.__dict__ for base in I.__class__.__mro__]`；类对象查找则是 `[base.__dict__ for base in C.__mro__] + [meta.__dict__ for meta in C.__class__.__mro__]`。第二个列表只对类对象的显式属性查找追加。
- **设计原因**：如果元类的每个管理方法都自动泄漏给普通实例，框架内部的注册、验证和类级 API 会污染业务对象的命名空间。把两棵树隔离，可以让元类负责类、类负责实例。
- **实际问题**：调试 `C.attr` 时只看 `C.__dict__` 不够，因为属性可能来自超类或元类；调试 `I.attr` 时查看元类反而通常没有帮助。应分别打印 `C.__mro__`、`C.__class__.__mro__`，并按主树优先顺序定位来源。
- **初学者误区**：`C.__class__` 是元类，`C.__bases__` 才是普通超类；把二者混为一谈会错误预测 MRO。另一个误区是认为 MRO 会把两棵树拼成一条传递链，实际上普通实例不会自动获得类的元类属性。

### 代码分析

```python
class Meta(type):
    meta_value = 'from meta'

class Base:
    base_value = 'from base'

class Child(Base, metaclass=Meta):
    pass

class_instance = Child()
print(Child.meta_value)       # from meta
print(Child.base_value)       # from base
print(class_instance.base_value)  # from base
print(Child.__mro__)          # 主树
print(Child.__class__.__mro__)    # 次级元类树
```

- 访问 `Child.meta_value` 时，Python 先在 `Child` 及 `Base` 的 MRO 中查找，失败后才到 `Meta` 的 MRO；访问 `class_instance.base_value` 时只会在实例字典和 `Child.__mro__` 中查找，所以它看不到 `meta_value`。
- 如果 `Base` 也定义 `meta_value`，那么 `Child.meta_value` 会得到 `Base` 的版本，而不是 `Meta` 的版本。这体现了“主树先于次树”，与元类离 `Child` 有多近无关。

### 深度理解

- **核心概念**：元类继承不是一套完全不同的继承机制，而是把同样的 `__class__`、`__bases__` 和 MRO 关系应用到“类作为实例”这一层。区别在于查找是否继续跨越到另一棵树。
- **底层实现**：`C.__mro__` 由 `C` 的普通超类计算，`C.__class__.__mro__` 由 `C` 的元类超类计算。Python 对类属性查找最多依次使用这两组扁平 MRO；对普通实例则只使用实例类的那一组。
- **设计原因**：这种非传递边界避免了属性来源无限扩散。若 `I` 自动继承 `C` 的元类、元类的元类以及它们的超类，任何普通实例的 API 都会被类管理基础设施污染。
- **实际问题**：复杂框架中看到 `C.attr` 并不能简单断言它来自 `C`；它可能来自 `S`、`M1` 或 `M2`。元类之间不兼容时还会产生“最派生元类”选择失败的冲突，混用第三方框架基类时尤其需要留意。
- **初学者误区**：`I.__class__.attr4` 成功不等于 `I.attr4` 应成功；前者是显式先取得类再查找，后者是普通实例查找，按照规则不会跟随类的 `__class__`。

> 现在已经知道元类属性如何被类对象获得，可以把它们扩展的继承规则形式化了。继承使用两套相似但不同的查找程序；两者都以根据 `__bases__` 链计算出的 MRO 为基础，并用于显式属性获取。
>
> 查找非类实例 `I` 的名字时，先查实例 `I` 的 `__dict__`，再按从左到右查找 `I.__class__.__mro__` 中每个类的 `__dict__`。这就是从实例、它的类以及该类的所有超类查找。
>
> 查找类 `C` 的名字时，先按从左到右查找 `C.__mro__` 中每个类的 `__dict__`，也就是类自身和它的普通超类；如果还没有找到，再按从左到右查找 `C.__class__.__mro__` 中每个元类的 `__dict__`。这一步是类对象独有的元类树后备查找。

### 深度理解

- **核心概念**：MRO 是由继承树展平得到的确定搜索顺序。普通实例从实例字典开始，接着搜索实例类的 MRO；类对象先搜索自己的 MRO，再搜索元类的 MRO。

- **实际问题**：只记住“实例字典优先、再查类”会在数据描述符、内置运算和 `super` 上得到错误结论。调试属性时要先确认对象是类还是普通实例，也要确认操作是显式名字还是内置语法。

#### The descriptors deviation（描述符带来的偏离）

> 前面的规则是普通、简化的情况。之所以把例外单独列出，是因为它们在大多数代码中不常见，却会显著增加算法复杂度。第38章的属性描述符就是第一个重要例外。
>
> 数据描述符是定义了 `__set__`、能够拦截赋值的描述符。继承查找时，数据描述符的名字拥有优先权，会压过其他来源。这个规则有实际用途：它保证特殊的 `__class__` 和 `__dict__` 属性不能被实例自己的 `__dict__` 用同名键重新定义。
>
> 示例先把 `book`、`__class__` 和 `__dict__` 作为键直接写入实例字典。普通的 `I.book` 从实例字典得到 `lp6e`；但 `I.__class__` 和 `I.__dict__` 仍然得到真正的类与字典，因为类中的特殊属性描述符在实例字典之前被检查。

#### Python Inheritance Algorithm: The Less Simple Version（Python 继承算法：不那么简单的版本）

> 把数据描述符的特殊优先级和普通描述符调用加入类树、元类树后，Python 的正式属性继承算法如下。它假设读者已经理解描述符、元类和 MRO，但它仍然是属性名最终如何解析的规则。
>
> 对普通实例 `I`，先搜索 `I.__class__.__mro__` 中所有类的字典；如果找到了数据描述符，就调用它的 `__get__` 并结束。否则，检查实例 `I.__dict__`；如果实例字典有这个名字，返回实例值。若实例字典没有，再调用找到的非数据描述符，或返回类 MRO 中找到的普通值。
>
> 对类 `C`，先搜索 `C.__class__.__mro__` 中所有元类的字典；如果在那里找到数据描述符，调用它的 `__get__` 并结束。否则，在 `C.__mro__` 中搜索类和普通超类；找到任何描述符就调用它，或者返回其中的值。若两个阶段都没有结果，查找失败。
>
> 内置操作基本使用这些规则中的 MRO 来源，但 `super` 会使用自己的代理查找。每次查找按步骤顺序执行：一个 MRO 中第一次出现的名字获胜，实例最多做一次 MRO 搜索，类最多做两次。由于 MRO 已经去重并展平，既可以把它理解为一到两次树搜索，也可以理解为一到两条字典列表搜索。
>
> 隐含的 `object` 超类为每棵类树和元类树提供末端默认值。`__getattr__` 可以在属性未找到时运行，`__getattribute__` 可以拦截每一次显式获取；它们是查找模型之上的扩展。这里的算法只描述普通显式属性读取，赋值、内置方法隐式查找和 `super` 的代理查找要分别讨论。

### 深度理解

- **核心概念**：数据描述符之所以特殊，不是因为它“在实例字典里”，而是因为它出现在类 MRO 中并实现了 `__set__`（或 `__delete__`）。它可以在实例值之前拦截读写；非数据描述符则允许实例字典覆盖。
- **底层实现**：实例读取时，Python 先在类 MRO 中找到名字并判断其是否为数据描述符，再决定是否访问实例字典；普通函数、`staticmethod` 和不带写入协议的描述符会在不同绑定规则下处理。类读取时，对应的第一优先来源是元类 MRO 中的数据描述符。
- **设计原因**：描述符把字段验证、延迟计算、绑定方法和属性存取策略集中到类级对象中，避免每个实例重复实现。`property`、方法绑定和许多框架字段都是这一协议的应用。
- **实际问题**：`obj.__dict__['field'] = value` 只改变存储，不一定改变 `obj.field` 的结果；数据描述符可以继续压过它。重写 `__getattribute__` 或 `__setattr__` 时还可能递归，通常应使用 `object.__getattribute__` 或 `object.__setattr__` 访问底层实现。
- **初学者误区**：只实现 `__get__` 的描述符不是数据描述符；把它放进实例字典后可以遮蔽它。另一个误区是认为 `__get__` 总会收到普通实例，实际上从类访问描述符时 `instance` 可能是 `None`，而从元类查找时绑定对象又是类本身。

### 代码分析

```python
class DataDescriptor:
    def __get__(self, instance, owner):
        return 'value from descriptor'

    def __set__(self, instance, value):
        print('store through descriptor:', value)

class NonDataDescriptor:
    def __get__(self, instance, owner):
        return 'value from non-data descriptor'

class C:
    data = DataDescriptor()
    nondata = NonDataDescriptor()

obj = C()
obj.__dict__['data'] = 'instance data'
obj.__dict__['nondata'] = 'instance data'
print(obj.data)       # 描述符优先
print(obj.nondata)    # 实例字典遮蔽非数据描述符
obj.data = 10         # 调用 DataDescriptor.__set__
```

- 读取 `obj.data` 时，类 MRO 中先找到 `DataDescriptor`，因为它有 `__set__`，所以先调用 `__get__`，不会返回实例字典里的字符串。读取 `obj.nondata` 时，非数据描述符不能压过实例字典，于是得到 `'instance data'`。
- 下面的概念模型能表达普通实例读取的优先级，但不是可替代解释器的完整实现：

```python
def simplified_get(obj, name):
    cls = type(obj)
    found = next((base.__dict__[name] for base in cls.__mro__
                  if name in base.__dict__), None)
    if hasattr(found, '__set__') or hasattr(found, '__delete__'):
        return found.__get__(obj, cls)
    if name in obj.__dict__:
        return obj.__dict__[name]
    if hasattr(found, '__get__'):
        return found.__get__(obj, cls)
    if found is not None:
        return found
    raise AttributeError(name)
```

- 真实 CPython 会在 C 层处理特殊方法、缓存和异常路径，不能把这段 Python 函数当成等价实现；它的价值在于看清“先在类 MRO 中判定数据描述符，再看实例字典”的顺序。

#### The super supplement（`super` 补充）

> 即使只讨论属性引用，仍有两个不遵循普通继承规则的特例；这里先讨论第一个：第32章介绍的内置函数 `super`。
>
> `super` 返回的代理对象不会对自己做完整的普通继承查找。它会根据上下文，在另一个对象的 MRO 中截取一个有限的“尾部”进行扫描：从包含 `super` 调用的那个类之后开始，沿隐式实例所属类的 MRO，找到第一个包含该描述符或值的类。
>
> 这次定制扫描代替了完整继承；只有在特殊扫描失败时，才会对 `super` 代理对象本身做一般查找。`super` 在简单的协作式继承中很方便，但在复杂继承结构里会增加理解成本，成为 Python 继承规则中的又一条重要脚注。

### 深度理解

- **核心概念**：`super()` 不是“父类对象”，而是一个带有起始类和被代理对象的代理。属性查找从 MRO 中起始类的后一个位置开始，因此它支持多继承下的协作式方法链。
- **底层实现**：`super(B, obj).method` 会查看 `type(obj).__mro__`，跳过 `B` 及其之前的类，在后续类的字典中找到 `method`，并按描述符规则绑定它。零参数 `super()` 会从方法上下文获得隐含的类和实例。
- **设计原因**：让类方法调用“下一个实现”而不是硬编码某个父类，才能让同一方法在多继承 MRO 改变时仍按线性化顺序协作。
- **实际问题**：使用 `super` 的方法链必须保持兼容的参数并且各层都继续调用 `super()`；某一层直接写死 `Base.method(self)` 或不调用 `super`，就会截断链。代理还可能让调试器中显示的属性来源与直觉不同。
- **初学者误区**：`super()` 不保证调用“最近写在括号里的父类”，也不等价于 `Base.method(self)`。它遵循当前对象类的 MRO 和当前方法的起始类，静态地把某个类名写死通常会破坏多继承的合作。

### 代码分析

```python
class A:
    def run(self):
        return ['A']

class B(A):
    def run(self):
        return ['B'] + super().run()

class C(B):
    def run(self):
        return ['C'] + super().run()

print(C.__mro__)       # C, B, A, object
print(C().run())       # ['C', 'B', 'A']
```

- 在 `B.run` 中，`super()` 代理的起始点是 `B`，所以 `super().run()` 从 `C.__mro__` 中 `B` 后面的 `A` 开始；在 `C.run` 中则从 `B` 开始。每个方法只负责自己的片段，MRO 决定下一个片段。
- **现代实践补充（Python 3）**：零参数 `super()` 依赖编译器为方法保留的 `__class__` 闭包信息；脱离方法上下文、在普通嵌套函数中使用时不能假设它仍然有效。需要明确控制起点时可以写 `super(B, self)`。

### 深度理解

- **核心概念**：显式 `obj.__method__` 和内置 `operation(obj)` 不是同一条调用路径。特殊方法通常由解释器在对象的类型上查找，避免实例字典中的临时同名值改变语言语法的语义。
- **底层实现**：例如 `str(I)` 会走类型槽位对应的 `tp_str`，而 `I.__str__` 是普通属性读取；类对象的内置操作又会从其元类的槽位查找。CPython 的槽位缓存和 C 层分派让这类查找与普通 Python 字典查找不同。
- **设计原因**：如果任何实例都能通过实例字典随时改变 `+`、`len`、`str` 等语言级操作，解释器优化和类型语义都会变得不稳定。特殊方法放在类型层面可以保持操作协议一致。
- **实际问题**：给实例动态绑定 `__str__` 后，手动调用和 `str(instance)` 得到不同结果，容易导致测试和日志行为不一致。元类还可以改变类对象的 `str`、下标等行为，调试输出可能因此改变。
- **初学者误区**：以为定义了 `__getitem__` 就等于所有相关调用都会从实例字典取它；特殊方法的隐式调用通常跳过实例级属性。还要区分“显式方法调用”与“运算符/内置函数触发协议”。

### 代码分析

```python
class C:
    def __str__(self):
        return 'from class'

obj = C()
obj.__str__ = lambda: 'from instance'

print(obj.__str__())  # from instance：显式属性查找
print(str(obj))       # from class：内置操作查类型槽位
```

```python
class Meta(type):
    def __str__(cls):
        return 'from metaclass'

class C(metaclass=Meta):
    pass

print(C.__str__(C))   # 显式查找可沿 C 的主树
print(str(C))         # 内置 str 查 Meta 的类型槽位
```

- 两个例子共同说明：不要用普通显式属性查找的伪代码推断所有运算符。解释器为特殊方法准备了类型级协议，类对象还要把“对象的类型”替换成元类来考虑。
- CPython 的源码文件名是原文提到的实现线索，不应把某个版本的内部函数名当成稳定的 Python 公共 API；跨实现或跨版本时只依赖语言层面保证的行为。

#### Metaclass Methods（元类方法）

> 现在已经理解元类如何改变名字继承，可以准确讨论元类方法了。简而言之，元类中的方法会被元类的实例，也就是类对象，继承并处理；它们处理的不是这些类创建出来的普通非类实例。
>
> 因此元类方法在形式和功能上类似第32章介绍的类方法，只是它面向类的绑定行为自动发生。根据上一节的继承规则，它们只对类可见，对普通实例不可见。类装饰器没有与之直接对应的机制，不过装饰器可以返回任意对象，理论上仍能实现很多变体。
>
> 示例中，元类 `M` 定义 `z(cls)` 和 `y(cls)`，类 `C` 自己定义 `y(self)`、`x(self)`。从 `C` 取得 `C.x`、`C.y` 时，名字来自类字典，所以是普通函数；`C.z` 来自元类，因此自动绑定到类 `C`，调用 `C.z()` 时 `cls` 是 `C`。
>
> 创建普通实例 `I = C()` 后，`I.x()` 和 `I.y()` 会按普通实例方法绑定到 `I`，但 `I.z()` 失败，因为普通实例不会进入 `C` 的元类树。元类方法真正新增的两点就是：只被类继承，以及从类取得时自动绑定到该类。

### 深度理解

- **核心概念**：元类方法是“隐式类方法”：定义在元类中、通过类对象访问、自动收到类对象作为第一个参数。普通 `@classmethod` 定义在类中，通过类或实例访问，面向普通实例的类级数据。
- **底层实现**：查找 `C.z` 时，主类 MRO 找不到名字，元类 MRO 找到函数描述符；描述符把 `C` 作为绑定对象。查找 `C.x` 时名字已在 `C.__dict__` 中，取出的是类字典中的函数，不会自动把 `C` 作为参数绑定。
- **设计原因**：元类方法适合类注册、类级查询、批量改变同一元类下的类；把它们限制在类对象上，可以避免普通实例意外暴露框架管理 API。
- **实际问题**：若类自身后来定义了与元类同名的方法，主树版本优先，元类版本会被遮住。API 设计时要避免元类方法名与客户类常用方法冲突，也要明确调用者到底是类还是实例。
- **初学者误区**：看到 `C.z` 打印为 bound method 就以为所有 `C` 的方法都会自动绑定到 `C`；只有来自元类树的函数具有这种绑定，`C.x` 仍然是类字典中的普通函数。

### 代码分析

```python
class M(type):
    def z(cls):
        return f'meta method on {cls.__name__}'

class C(metaclass=M):
    def x(self):
        return f'instance method on {type(self).__name__}'

C.z()          # meta method on C

instance.x()   # instance method on C
instance.z()   # AttributeError: 普通实例不查元类树
```

- `C.z` 的绑定对象是类 `C`，而 `instance.x` 的绑定对象是 `instance`。这两个“第一个参数”都来自描述符绑定，但查找来源和可见范围完全不同。
- 若 `C` 自己定义 `z`，`C.z` 会优先使用 `C.__dict__['z']`；这正是主类树优先于元类树的规则。

- **核心概念**：Python的属性访问不是简单的字典查找，而是经过多层协议处理的复杂过程，包括__getattribute__、__getattr__、描述符和数据描述符优先级规则
- **底层实现**：Python的属性查找遵循MRO（方法解析顺序），先在实例的__dict__中查找，然后按类的MRO链查找，最后触发__getattr__。描述符协议（__get__、__set__、__delete__）在查找过程中优先于实例字典
- **设计原因**：描述符协议将属性管理的逻辑从实例中分离出来，使得属性可以跨类复用。属性装饰器property就是描述符的一个特例
- **实际问题**：__getattr__和__getattribute__的递归陷阱——在__getattribute__中访问self.xxx会再次触发__getattribute__，必须使用object.__getattribute__(self, 'xxx')来避免
- **初学者误区**：很多人认为__getattr__会在所有属性访问时触发，实际上它只在属性未找到时触发；而__getattribute__会在每次访问时触发，但需要谨慎避免无限递归
