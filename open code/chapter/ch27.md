## 27.2 类生成多个实例对象（Classes Generate Multiple Instance Objects）

### 英文原文

> To understand how the multiple objects idea works, you have to first understand
> that there are two kinds of objects in Python's OOP model: class objects and
> instance objects. Class objects provide default behavior and are used to create
> instance objects. Instance objects are the tangible objects your programs process
> —each is a namespace in its own right but inherits (i.e., has automatic access to)
> names in the class from which it was created. Class objects come from
> statements, and instances come from calls; each time you call a class, you get a
> new instance of that class.
>
> This object-generation concept is very different from most of the other program
> constructs we've seen so far in this book. In effect, classes are essentially
> factories for generating multiple instances. By contrast, only one copy of each
> module is ever imported into a single program. In fact, this is why reload works
> as it does, updating a single instance and shared object in place. With classes,
> each instance can have its own independent data, supporting multiple versions of
> the object that the class models.
>
> In this role, class instances are similar to the per-call state of the closure (a.k.a.
> factory) functions of Chapter 17, but this is a natural part of the class model, and
> state in classes is explicit attributes instead of implicit scope references.
> Moreover, this is just part of what classes do—they also support customization
> by inheritance, operator overloading, and multiple behaviors via methods.
> Hence, classes are a more complete programming tool, though OOP and
> functional programming are not mutually exclusive paradigms. We may combine
> them by using functional tools in methods, by coding methods that are
> themselves generators, by writing user-defined iterators, and so on.
>
> The following is a quick summary of the bare essentials of Python OOP in terms
> of its two object types. As you'll see, Python classes are in some ways similar to
> both defs and modules, but they may be quite different from what you're used to
> in other languages.

### 中文翻译

> 要想理解"多对象"的想法如何运作，首先必须明白 Python 的 OOP 模型中有两类对象：**类对象**（class object）和**实例对象**（instance object）。类对象提供默认行为，并用于创建实例对象。实例对象是程序所处理的具体对象——每个实例本身就是一个命名空间，但它会继承（即自动获得访问权）创建它的类中的名字。类对象来自语句（statement），实例来自调用（call）；每次调用一个类，你都会得到该类的一个新实例。
>
> 这种对象生成的概念，与我们迄今为止在本书中见到的大多数程序构造非常不同。实际上，类本质上就是生成多个实例的**工厂**（factory）。相比之下，每个模块在一个程序中只会被导入一份。事实上，这正是 reload（重新加载）之所以那样工作的原因——在原地更新单个实例和共享对象。而有了类，每个实例都可以拥有自己独立的数据，从而支持同一个类所建模对象的多个版本。
>
> 在这种角色下，类实例类似于第 17 章中闭包（closure，又称工厂）函数的"每次调用各自的状态"，但这是类模型的自然组成部分；而且在类中，状态是显式的属性（attribute），而不是隐式的作用域引用。此外，这只是类能力的一部分——类还支持通过继承定制、运算符重载，以及通过方法（method）实现多种行为。因此，类是更完整的编程工具，尽管 OOP 和函数式编程（functional programming）并不是互斥的范式。我们可以把它们结合起来：在方法中使用函数式工具、把方法本身写成生成器（generator）、编写用户自定义迭代器（iterator），等等。
>
> 下面是以这两类对象为纲，对 Python OOP 最核心要点的快速总结。你会看到，Python 类在某些方面既像 def 又像模块，但它们可能与你熟悉的其他语言中的类相当不同。

### 深度理解

- **核心概念**：OOP 模型里永远存在**两类对象**：类对象（由 `class` 语句产生）和实例对象（由"调用类"产生）。"类对象来自语句，实例来自调用"这句话是整个模型的总纲——它不是关于写法的，而是关于**运行时机**的。
- **底层实现**：在 CPython 中，"调用类" `X = MyClass()` 实际上执行的是类对象的 `__call__` 协议（由元类 `type` 实现）：分配新对象、调用 `__new__`、必要时调用 `__init__` 初始化、把新实例的 `__class__` 指针指向类对象、最后返回实例。每次调用都走完整流程，所以每次都会得到**全新的**对象。
- **设计原因**：模块天然是单例（一次 import 只有一份），所以模块无法表达"同一实体的多个版本"。类把"共享部分"（类对象里的属性）和"独立部分"（实例各自的 `__dict__`）分开存放，这正是工厂模式（factory pattern）的本质。
- **对比第 17 章的闭包**：闭包函数的"每次调用各自状态"靠的是隐式作用域引用（闭包单元），而类的"每实例状态"靠的是显式属性赋值。显式的好处是：属性可以被外部读取、修改、继承、序列化——闭包状态是"锁在函数肚子里"的。Lutz 特意点出这一点，是提醒你**类不是函数式编程的对立面**，两者可以混用。
- **初学者误区**：很多从 C++/Java 过来的人以为"类是编译期的模板"。在 Python 中类是运行时对象，`class` 只是产生它的语句——没有执行到那条语句，类就不存在。同一个 REPL 里可以随时动态改类、给类挂新属性，这在静态语言里是不可想象的。
- **生活例子**：类对象就像**奶茶店的配方本**（一套做法，共享），实例就像**按配方现做的每一杯奶茶**（每杯的甜度、温度可以不同）。模块则像一本**全员共用的值班表**——全公司永远只有这一张。

## 27.3 类对象提供默认行为（Class Objects Provide Default Behavior）

### 英文原文

> When we run a class statement, we get a class object. Here's a rundown of the
> main properties of Python classes:
>
> - **The class statement creates a class object and assigns it a name.** Just like
>   the function def statement, the Python class is an executable
>   statement. When reached and run, it generates a new class object and
>   assigns it to the first name in the class header. Also, like defs, class
>   statements typically run when the files they are coded in are first
>   imported or run as a top-level script.
> - **Assignments inside class statements make class attributes.** Just like
>   in module files, top-level assignments within a class statement (not
>   nested in a def) generate attributes in a class object. Technically, the
>   class statement defines a local scope that morphs into the attribute
>   namespace of the class object, just like a module's global scope. After
>   running a class statement, class attributes may be accessed by name
>   qualification: class.name.
> - **Class attributes provide object state and behavior.** Attributes of a
>   class object record state information and behavior to be shared by all
>   instances created from the class. Most notably and commonly, function
>   def statements nested inside a class generate methods, which process
>   instances.

### 中文翻译

> 当我们运行一个 class 语句时，就得到了一个类对象。下面是对 Python 类主要性质的梳理：
>
> - **class 语句创建类对象并给它赋予一个名字。** 就像函数 def 语句一样，Python 的 class 是一条**可执行语句**（executable statement）。当执行流到达并运行它时，它会生成一个新的类对象，并把它赋给 class 头行中的第一个名字。同样与 def 类似，class 语句通常会在其所在文件被首次导入、或以顶层脚本方式运行时执行。
> - **class 语句内部的赋值会生成类属性（class attribute）。** 就像在模块文件中一样，class 语句内部**顶层**的赋值（不嵌套在 def 中）会在类对象中生成属性。严格来说，class 语句定义了一个局部作用域，这个作用域会**蜕变**（morphs）为类对象的属性命名空间，就像模块的全局作用域那样。运行完 class 语句后，可以通过名字限定（name qualification）访问类属性：`class.name`。
> - **类属性提供对象的状态和行为。** 类对象的属性记录了状态信息和行为，供从该类创建的所有实例共享。最显著也最常见的例子是：嵌套在 class 语句内的 def 函数语句生成**方法**（method），由它们来处理实例。

### 中文翻译 2（补充说明）

> 以上三条是"类对象"的完整画像：① 类是执行产物不是声明；② 类体内的顶层赋值 = 类属性；③ 类属性是全体实例的"公共资源"。

### 深度理解

- **核心概念**：class 与 def 一样，是**可执行语句**（executable statement）而非声明。它平时躺在模块文件里，只有被 import 或作为顶层脚本执行时，才真正"跑"一遍并创建类对象。这是 Python "一切皆运行时"哲学在类上的体现。
- **底层实现**：CPython 执行 `class Foo:` 语句时，大致做三件事：(1) 创建一个新的命名空间字典（类似模块字典）；(2) 以该字典为作用域，逐条执行类体内的语句（这就是为什么 `x = 1` 这样的顶层赋值会把 `x` 放进类字典）；(3) 用 `type`（元类）把字典包装成类对象，并把名字 `Foo` 绑定到它。所谓"局部作用域 morph 成属性命名空间"，说的正是第 (1)(2) 步——作用域是编译期的概念，属性命名空间是运行期的结果，二者是同一份字典的两副面孔。
- **设计原因**：把方法用普通 `def` 写在类体内，而不是像 Java 那样用专用语法声明，是为了**保持语言最小化**——方法就是函数，函数的一切能力（默认参数、返回值、yield、装饰器）自动适用于方法，无需新语法。
- **实际问题**：理解了"class 是可执行语句"，就能理解很多怪现象：为什么类可以定义在 `if` 分支里（条件成立才创建类）；为什么同一个名字的类可以在不同函数里定义出不同版本；为什么 `class` 也可以出现在函数内部（局部类）。
- **初学者误区**：以为"类体里的变量是实例变量"——错！类体顶层赋值（`spam = 1`）创建的是**类属性**，所有实例共享同一份；要想每实例独立，必须通过方法里的 `self.spam = ...` 赋值。这是全书最常见的混淆点之一。
- **生活例子**：class 语句就像**一条流水线的开机按钮**——按下（执行）了才有机器和工人（类对象）；没按（没执行到）就什么都没有。类体里的顶层赋值则像公司墙上贴的"全体员工守则"，一份，人人可见。

## 27.4 实例对象是具体条目（Instance Objects Are Concrete Items）

### 英文原文

> When we call a class object, we get an instance object. Here's an overview of the
> key points behind class instances:
>
> - **Calling a class object like a function makes a new instance object.** Each
>   time a class is called, it creates and returns a new instance object.
>   Instances represent material items in your program's domain.
> - **Each instance object inherits class attributes and gets its own
>   namespace.** Instance objects created from classes are new namespaces;
>   they start out empty but inherit attributes that live in the class objects
>   from which they were generated.
> - **Assignments to attributes of self in methods make per-instance
>   attributes.** Inside a class's method functions, the first argument (called
>   self by convention) references the instance object being processed;
>   assignments to attributes of self create or change data in the instance,
>   not the class.
>
> The end result is that classes define common, shared data and behavior, and
> generate instances. Instances reflect palpable application entities and record per-
> instance data that may vary per object.

### 中文翻译

> 当我们像调用函数一样调用一个类对象时，就得到一个实例对象。下面是类实例的关键要点概览：
>
> - **像调用函数一样调用类对象，会生成一个新的实例对象。** 每次调用类，它都会创建并返回一个新的实例对象。实例代表了程序领域中的具体条目（material items）。
> - **每个实例对象继承类属性，并拥有自己的命名空间。** 由类创建的实例对象是新的命名空间；它们一开始是空的，但会继承生成它们的类对象中存放的属性。
> - **方法中对 self 属性的赋值，会生成每个实例各自的属性。** 在类的方法函数内部，第一个参数（按惯例称为 self）引用正在被处理的实例对象；对 self 属性赋值会创建或改变实例中的数据，而不是类中的数据。
>
> 最终结果是：类定义共同的、共享的数据与行为，并生成实例；实例反映具体的应用实体，并记录可能因对象而异的每实例数据。

### 深度理解

- **核心概念**：实例的三个要点可以浓缩成一句话——**实例 = 一个空命名空间 + 一条指向类的链接 + self 赋值入口**。实例没有自己的"说明书"，一切行为都从类那里继承；它只负责存放自己的数据。
- **底层实现**：CPython 中每个实例对象内部主要就是两个东西：`__dict__`（实例自己的属性字典，初始为空）和 `__class__`（指向类对象的指针）。属性访问 `x.attr` 的流程是：先查 `x.__dict__`，找不到就顺着 `x.__class__` 往上查。所谓"继承"就是这个自动搜索过程，不是复制粘贴。
- **设计原因**：为什么实例先空着？因为 Python 是动态语言——属性不预声明，第一次赋值才"诞生"。这让实例非常轻量、灵活，但也要求**用 `__init__` 保证属性在构造时就被创建**，否则后续方法调用可能因属性缺失而崩溃（本书后面第 28 章会展开）。
- **实际问题**：`self` 不是关键字，只是**约定俗成的第一个参数名**。Python 自动把"调用方法的实例"填进第一个参数位（`x.setdata('coding')` 实际执行 `FirstClass.setdata(x, 'coding')`）。这就是方法绑定（method binding）——函数本身还是那个函数，只是被包装后自动传入了第一个实参。
- **初学者误区**：① 以为 `self` 是特殊语法——换成 `this` 或任意名字都行（但千万别换，约定即纪律）；② 以为"实例属性要提前声明"——不需要，直接赋值即可；③ 以为给 `self` 赋值等于给所有实例赋值——恰恰相反，它只作用于当前这个实例。
- **生活例子**：实例就像**每个员工的工牌**——工牌是空白的（空命名空间），佩戴者（self）是谁，上面就填谁的名字；而"工牌应该怎么挂、什么时候戴"这些规定（方法）印在公司的《员工手册》（类）里，大家共享一份。

## 27.5 第一个示例（A First Example）

### 英文原文

> Let's turn to a real example to show how these ideas work in practice. To begin,
> let's define a class named FirstClass by running a Python class statement
> interactively in any REPL:
>
> ```python
> >>> class FirstClass:            # Define a class object
>         def setdata(self, value):    # Define class's methods
>             self.data = value        # self is the instance
>         def display(self):
>             print(self.data)         # self.data: per instance
> ```
>
> We're working interactively here, but typically, such a statement would be run
> when the module file it is coded in is imported. Like functions created with defs,
> this class won't even exist until Python reaches and runs this statement.
>
> Like all compound statements, the class starts with a header line that lists the
> class name, followed by a body of one or more nested and (usually) indented
> statements. Here, the nested statements are defs; they define functions that
> implement the behavior the class means to export.
>
> As we learned in Part IV, def is really an assignment. Here, it assigns function
> objects to the names setdata and display in the class statement's scope, and
> so generates attributes attached to the class—FirstClass.setdata and
> FirstClass.display. In fact, any name assigned at the top level of the class's
> nested block becomes an attribute of the class.
>
> Functions inside a class are usually and traditionally called methods. They're
> coded with normal defs, and they support everything we've learned about
> functions already—they can have defaults, return values, yield items on request,
> and so on. But in a method function, the first argument automatically receives an
> implied instance object when called—the subject of the call. Let's create a
> couple of instances of our class to see how this works:
>
> ```python
> >>> x = FirstClass()             # Make two instances
> >>> y = FirstClass()             # Each is a new namespace
> ```
>
> By calling the class this way (notice the parentheses), we generate instance
> objects, which are just namespaces that have access to their classes' attributes.
> Properly speaking, at this point, we have three objects: two instances and a class.
> And really, we have three linked namespaces, as sketched in Figure 27-1. In
> OOP terms, we say that x "is a" FirstClass, as is y—they both inherit names
> attached to the class.
>
> *Figure 27-1. Classes and instances: namespaces in a class tree searched by inheritance*
>
> The two instances start out empty but have links back to the class from which
> they were generated. If we qualify an instance with the name of an attribute that
> lives in the class object, Python fetches the name from the class by inheritance
> search (unless it also lives in the instance):
>
> ```python
> >>> x.setdata('coding')          # Call methods: self is x
> >>> y.setdata(3.14159)           # Runs: FirstClass.setdata(y, 3.14159)
> ```
>
> Neither x nor y has a setdata attribute of its own, so to find it, Python follows
> the link from instance to class. And that's about all there is to inheritance in
> Python: it happens at attribute qualification time, and it just involves looking up
> names in linked objects—here, by following the is-a links in Figure 27-1.
>
> In the setdata function inside FirstClass, the value passed in is assigned to
> self.data. Within a method, self—the name given to the leftmost argument
> by convention—automatically refers to the instance being processed (x or y at
> this point), so the assignments store values in the instances' namespaces, not the
> class's. That's how the data names in Figure 27-1 are created.
>
> Because classes can generate multiple instances, methods must go through the
> self argument to get to the instance to be processed. When we call the class's
> display method to print self.data, we see that it's different in each instance;
> on the other hand, the name display itself is the same in x and y, as it comes (is
> inherited) from the class:
>
> ```python
> >>> x.display()                  # Runs: FirstClass.display(x)
> coding
> >>> y.display()                  # self.data differs in each instance
> 3.14159
> ```
>
> Notice that we stored different object types in the data member in each instance
> —a string and a floating-point number. As with everything else in Python,
> instance attributes (sometimes called members) are not predeclared and have no
> type constraints; they spring into existence the first time they are assigned
> values, just like simple variables. In fact, if we were to call display on one of
> our instances before calling setdata, we would trigger an undefined name error
> —the attribute named data doesn't even exist in memory until it is assigned
> within the setdata method.
>
> As another way to appreciate how dynamic this model is, consider that we can
> change instance attributes either inside the class itself, by assigning to self in
> methods, or outside the class, by assigning to an explicit instance object:
>
> ```python
> >>> x.data = 'hacking'           # Can get/set attributes
> >>> x.display()                  # Outside the class too
> hacking
> ```
>
> Although less common, we could even generate an entirely new attribute in the
> instance's namespace by assigning to its name outside the class's method
> functions:
>
> ```python
> >>> x.anothername = 'apps'       # Can set new attributes here too!
> ```
>
> This would attach a new attribute called anothername, which may or may not be
> used by any of the class's methods, to the instance object x. Classes usually
> create all of the instance's attributes by assignment to the self argument, but
> they don't have to—programs can fetch, change, or create attributes on any
> objects to which they have references.
>
> It usually doesn't make sense to add data that the class cannot use, and it's
> possible to prevent this with extra "privacy" code based on attribute-access
> operator overloading, as we'll discuss elsewhere in this book (in Chapters 30
> and 39). Still, free attribute access translates to less syntax, and there are cases
> where it's even useful—for example, in coding data records of the sort we'll build
> later in this chapter.

>
> ```python

> ```

>

### 深度理解

- **核心概念**：这个例子第一次完整展示了三件事——① `class` 语句创建类对象，类体内的 `def` 是给类挂属性；② 调用类得到实例，实例是"空命名空间 + 指向类的链接"；③ 方法通过 `self` 读写**特定实例**的数据。这三件事合起来就是 Python OOP 的"最小可用模型"。
- **底层实现（方法绑定）**：`x.setdata('coding')` 这一行，解释器实际做了两件事。第一步是属性查找：`x` 的 `__dict__` 里没有 `setdata`，于是沿 `x.__class__` 找到类对象里的函数对象；第二步是**方法绑定**：函数对象实现了描述符协议（descriptor protocol），`__get__` 会把函数包装成一个"绑定方法"（bound method）对象，悄悄把 `x` 记为该方法的第一个实参。所以最终调用等价于 `FirstClass.setdata(x, 'coding')`。这就是"第一个参数自动收到实例"的底层机制。
- **底层实现（class 语句）**：`class FirstClass:` 执行时，CPython 创建一个空字典作为类体作用域，依次执行两个 `def`（每个 `def` 在字典里放入函数对象），最后调用 `type(...)` 创建类对象并绑定名字 `FirstClass`。类体的作用域"蜕变"成了类对象的 `__dict__`。
- **设计原因**：为什么实例属性不预声明、无类型约束？因为 Python 的属性就是字典里的键值对——字典的键是运行时才决定的。这一设计让对象像"可扩展的档案袋"，想装什么装什么，代价是读到一个从未赋过值的属性会直接报 `AttributeError`。
- **实际问题**：在类外改 `x.data`、甚至新增 `x.anothername` 都合法——这既是 Python 的灵活（少语法、适合数据记录），也是隐患（拼错属性名不会报错，只会静默创建一个新属性，产生诡异 bug）。Lutz 提前预告：第 30、39 章会讲如何用属性访问钩子做"私有性"约束。
- **初学者误区**：① 以为"每个实例会把类的方法复制一份"——没有，方法只有一份，实例通过链接共享；② 以为 `self.data = value` 是在改类——不是，它只改当前实例；③ 以为属性必须先声明——不需要，但**必须先赋值再读取**。
- **生活例子**：方法绑定就像**共享单车**——车（函数）只有一批，谁扫码（调用）就把"当前骑行者"（self）绑定到那趟行程上；扫一次绑一个人，互不干扰。

### 代码分析

```python
>>> class FirstClass:              # 定义一个类对象
        def setdata(self, value):  # 定义类的方法
            self.data = value      # self 就是实例本身，把值存入实例命名空间
        def display(self):         # 定义第二个方法
            print(self.data)       # 打印当前实例的 data 属性
```

- **解释器如何处理**：执行 `class` 头行后，解释器新建一个命名空间字典，然后逐行执行类体：两个 `def` 语句各创建了一个函数对象并存入该字典（`setdata`、`display` 两个键）。类体执行完毕，解释器用 `type()` 把字典包装成类对象，绑定到名字 `FirstClass`。此刻**函数还没有被"包成方法"**——它们只是类里的普通函数属性。

```python
>>> x = FirstClass()               # 制作两个实例
>>> y = FirstClass()               # 每个都是一个新命名空间
```

- **解释器如何处理**：调用 `FirstClass()` 触发类对象的调用协议，分配一个新实例对象（内部持有空的 `__dict__` 和指向 `FirstClass` 的 `__class__` 指针），返回后绑定给 `x`；再次调用又创建**另一个**独立实例给 `y`。所以现在内存里是三个对象：`x`、`y`（两个空实例）+ `FirstClass`（一个有方法的类）。

```python
>>> x.setdata('coding')            # 调用方法：self 是 x
>>> y.setdata(3.14159)             # 实际执行：FirstClass.setdata(y, 3.14159)
```

- **解释器如何处理**：`x.setdata('coding')` 分两步走：先在 `x.__dict__` 中找 `setdata`（没有），沿 `x.__class__` 找到类里的函数，触发绑定（把 `x` 记为第一个实参），然后以 `('coding')` 为剩余实参调用它。进入函数后 `self.data = value` 是把键 `data` 写入 **x 自己的** `__dict__`。同理，`y.setdata(3.14159)` 把键 `data` 写入 y 的字典。两个实例各有各的 `data`，互不相干——这就是"每实例数据"的诞生过程。

```python
>>> x.display()                    # 实际执行：FirstClass.display(x)
coding
>>> y.display()                    # self.data 在每个实例中不同
3.14159
```

- **解释器如何处理**：`display` 也是从类继承来的同一个函数，绑定到不同实例后读取各自的 `data` 并打印，所以输出不同。注意 `display` 这个名字本身只有一个副本，存在类里——实例里没有。

```python
>>> x.data = 'hacking'             # 可以在类外获取/设置属性
>>> x.display()                    # 在类外也一样
hacking
>>> x.anothername = 'apps'         # 也可以在类外设置全新属性！
```

- **解释器如何处理**：赋值语句 `x.data = ...` **不做继承搜索**——它只在 x 的字典里写键值（有则覆盖，无则新建）。所以类外改属性、类外加属性都是直接改字典，零限制。这也解释了 Python 数据模型里的铁律：**读取属性才搜索（继承），写入属性只落在当前对象**。这条规则在 27.11 节会有更直观的演示。

## 27.6 类通过继承进行定制（Classes Are Customized by Inheritance）

### 英文原文

> Let's move on to the second major distinction of classes. Besides serving as
> factories for generating multiple instance objects, classes also allow us to make
> changes by introducing new components (called subclasses), instead of changing
> existing components in place.
>
> As we've seen, instance objects generated from a class inherit the class's
> attributes. Python also allows classes to inherit from other classes, opening the
> door to coding hierarchies of classes that specialize behavior—by redefining
> attributes in subclasses that appear lower in the hierarchy, we override the more
> general definitions of those attributes higher in the tree. In effect, the further
> down the hierarchy we go, the more specific the software becomes. Here, too,
> there is no parallel with modules, whose attributes live in a single, flat
> namespace that is not as amenable to customization.
>
> In Python, instances inherit from classes, and classes inherit from superclasses.
> Here are the key ideas behind the machinery of attribute inheritance:
>
> - **Superclasses are listed in parentheses in a class header.** To make a
>   class inherit attributes from another class, just list the other class in
>   parentheses in the new class statement's header line. The class that
>   inherits is usually called a subclass, and the class that is inherited from
>   is its superclass.
> - **Classes inherit attributes from their superclasses.** Just as instances
>   inherit the attribute names defined in their classes, classes inherit all of
>   the attribute names defined in their superclasses. Python finds these
>   names automatically when they're accessed if they don't exist in the
>   subclasses.
> - **Instances inherit attributes from all accessible classes.** Each instance
>   gets names from the class it's generated from, as well as all of that
>   class's superclasses. When looking for a name, Python checks the
>   instance, then its class, then all superclasses above its class.
> - **Each object.attribute reference invokes a new, independent search.**
>   Python performs an independent search of the class tree for each
>   attribute fetch expression. This includes references to instances and
>   classes made outside class statements (e.g., X.attr), as well as
>   references to attributes of the self instance argument in a class's
>   method functions. That is, each self.attr expression in a method
>   invokes a new search for attr in self and above.
>
> The net effect—and the main purpose of all this searching—is that classes
> support factoring and customization of code better than any other language tool
> we've seen so far. On the one hand, they allow us to minimize code redundancy
> (and so reduce maintenance costs) by factoring operations into a single, shared
> implementation; on the other, they allow us to program by customizing what
> already exists, rather than changing it in place or starting from scratch.
>
> **NOTE — Full inheritance disclosure:** Strictly speaking, Python's inheritance
> is richer than described here, when we factor in "diamond" inheritance patterns
> and "metaclasses"—advanced topics we'll study later—but we can safely restrict
> our scope to instances and their classes, both at this point in the book and in
> most Python application code. We'll explore diamonds and the "MRO"
> inheritance search order that accommodates them in Chapter 31, but our
> definition of inheritance won't be fully complete until Chapter 40, because it
> regrettably requires metaclass info that's beyond almost all Python
> programmers' interest levels and pay grades (thankfully!).

### 中文翻译

> 接下来看类的第二个主要区别。除了作为生成多个实例对象的工厂之外，类还允许我们通过引入新的组件（称为**子类**，subclass）来做出修改，而不是原地改动已有组件。
>
> 正如我们所见，由类生成的实例对象会继承类的属性。Python 还允许**类继承其他类**，从而打开了编写"专门化行为"的类层次（hierarchy）的大门——通过在层次中较低位置的子类里**重新定义**属性，我们就能覆盖（override）树中较高位置的、更通用的定义。实际上，层次越往下，软件就越具体。在这方面，模块没有对应物：模块的属性活在单一、扁平的命名空间里，不容易定制。
>
> 在 Python 中，实例继承类，类继承超类（superclass）。以下是属性继承机制的几个关键点：
>
> - **超类列在 class 头行的括号里。** 要让一个类继承另一个类的属性，只需在新建的 class 语句头行括号中列出那个类。执行继承的类通常叫**子类**，被继承的类叫它的**超类**。
> - **类继承超类的属性。** 正如实例继承其类中定义的属性名，类也继承其超类中定义的全部属性名。当这些名字在子类中不存在而被访问时，Python 会自动找到它们。
> - **实例继承所有可到达类的属性。** 每个实例从生成它的类、以及该类的全部超类那里获得名字。查找一个名字时，Python 依次检查实例、它的类、再上溯到类之上的所有超类。
> - **每次 object.attribute 引用都会发起一次全新的、独立的搜索。** Python 对每一条属性获取表达式都独立执行一次类树搜索。这既包括在 class 语句之外对实例和类的引用（如 `X.attr`），也包括方法函数中对 self 实例参数的属性引用。也就是说，方法中的每一个 `self.attr` 表达式，都会为 `attr` 在 self 及其上层发起一次新搜索。
>
> 净效果——也是所有这些搜索的主要目的——是：类比我们目前见过的任何语言工具都更支持代码的**抽取（factoring）与定制**。一方面，它允许我们把操作抽取进单个共享实现，从而最小化代码冗余（进而降低维护成本）；另一方面，它允许我们通过"定制已有的东西"来编程，而不是原地修改或从零开始。
>
> **注意——继承的完整披露：** 严格地说，Python 的继承比这里描述的更丰富——如果把"菱形"（diamond）继承模式和"元类"（metaclass）这些高级主题考虑进来的话，我们到后面再学。但在本书目前这个阶段，以及大多数 Python 应用代码中，把范围限制在"实例及其类"是安全的。我们将在第 31 章探讨菱形继承和与之配套的 MRO（方法解析顺序）继承搜索顺序，但继承的完整定义要到第 40 章才能讲完——因为很不幸，它需要元类的知识，而这超出了几乎所有 Python 程序员的兴趣范围和职位等级（谢天谢地！）。

### 深度理解

- **核心概念**：继承不是"复制"，而是"**搜索时的优先级**"。子类定义一个同名属性，并不是把超类的属性删掉，而是让自己在搜索路径上**更靠前**，于是"盖住"了超类的同名属性——这就是覆盖（override）。
- **底层实现**：继承搜索的物理实现就是"链表"：实例 `__class__` → 类 `__bases__`（一个元组，可含多个超类）→ 超类的 `__bases__`…… 每条 `obj.attr` 表达式都从 obj 的 `__dict__` 开始，逐级向上查 `__dict__`，**第一次命中即停**。多个超类时按 MRO 顺序（菱形继承时是 C3 线性化）决定谁先谁后——本书第 31 章才展开。
- **设计原因**：为什么"每次引用都重新搜索"而不是缓存结果？因为属性可以被随时增删改（动态性），缓存会导致与运行时状态不一致。Python 宁可每次都做一次 O(深度) 的字典查找，也要保证"所见即所得"。类树通常很浅（深度 2-5 层），这个代价完全可以接受。
- **实际问题**：覆盖能力让你可以"在不触碰原代码的前提下扩展功能"——这是开放-封闭原则（open-closed principle）的语言级支持：对扩展开放（加子类），对修改封闭（不动父类）。第三方库的类也照改不误，因为继承是外部的。
- **初学者误区**：① 以为子类会"继承到"父类实例的属性——不，实例属性永远属于实例，继承只发生在类属性层面；② 以为覆盖是"替换内存里的父类方法"——父类方法原封不动，只是查找时先撞见子类的版本；③ 以为继承必须声明——在 Python 中，不写括号的类隐式继承 `object`（27.12 节会看到 `__bases__` 里的它）。
- **生活例子**：继承就像**快餐店的套餐进化**——基础套餐（父类）保持不变，新推出的套餐（子类）"继承"原套餐的配菜，只把其中一两个单品换掉（覆盖）。老顾客点原套餐，口味完全不受影响；新套餐省去了重新设计全套配菜的功夫。

> 为了说明继承的作用，下一个示例建立在前一个示例之上。首先，我们定义一个新类 `SecondClass`，它继承 FirstClass 的所有名字，并提供一个自己的名字：

>

>
> ```python
> >>> x.display()                 # x 仍然是 FirstClass 的实例（旧消息）
> hacking
> ```
>
> 我们没有**改变** FirstClass，而是**定制**了它。这当然是一个人为的示例，但作为一条规则：因为继承允许我们在外部组件（即子类）中做这类修改，类在扩展性和复用性上往往胜过函数或模块。

### 深度理解

- **核心概念**：本例演示了继承的两面性：**复用**（setdata 原样继承）+ **覆盖**（display 被替换）。`class SecondClass(FirstClass):` 括号里的 `FirstClass` 就是超类列表。
- **底层实现**：`z.display()` 的搜索路径是：`z.__dict__`（空）→ `SecondClass.__dict__`（找到 `display`，命中即停）。而 `z.setdata('LP6e')` 的路径是：`z.__dict__` → `SecondClass.__dict__`（没有 setdata）→ `FirstClass.__dict__`（命中）。两个方法一个取自已定义、一个取自父类，对调用者完全透明——调用者不知道（也不需要知道）方法定义在树的哪一层。
- **设计原因**：为什么覆盖要在"子类定义同名属性"而不是"修改父类"？因为修改父类会影响**所有**实例（包括已创建的 x），破坏性极大；而新增子类只影响新类及其实例。这就是"定制优于修改"的工程原则——最小影响面。
- **实际问题**：真实项目中，第三方库升级后你的子类照常工作，因为父类的旧行为被"盖住"而不是被改动；如果直接去改库代码，每次升级都要重打补丁。
- **初学者误区**：① 把 override 理解成"内存里替换方法"——没有替换，只是搜索次序；② 以为覆盖了 display 就必须重写 setdata——完全不用，没覆盖的照常继承；③ 忘记"同名的**任何属性**都会被覆盖"，不只是方法——数据属性同样适用。
- **生活例子**：父辈写的"通用请假流程"（父类），你在自己的部门（子类）里规定"请假必须附钉钉审批截图"（覆盖 display）——但"提前一天申请"（setdata）这条规矩照旧沿用。公司的原制度一个字没改，其他部门不受任何影响。

### 代码分析

```python
>>> class SecondClass(FirstClass):      # 括号中列出超类：继承 setdata
        def display(self):              # 重新定义 display：改变输出格式
            print(f'Current value = "{self.data}"')
```

- **解释器如何处理**：执行 class 语句时，解释器看到头行括号里有 `FirstClass`，于是把新类对象的 `__bases__` 设为 `(FirstClass,)`，并把 `display` 函数对象写入 `SecondClass` 自己的 `__dict__`。此刻类树是两层：`FirstClass` → `SecondClass`。

```python
>>> z = SecondClass()
>>> z.setdata('LP6e')           # 在 FirstClass 中找到 setdata
>>> z.display()                 # 在 SecondClass 中找到被覆盖的方法
Current value = "LP6e"
```

- **解释器如何处理**：`z.setdata('LP6e')`：查找 `setdata` 时，z 空、SecondClass 空、FirstClass 命中，于是执行 `FirstClass.setdata` 并把 `'LP6e'` 写入 z 的 `__dict__`。`z.display()`：查找 `display` 时在 SecondClass 自己的 `__dict__` 就命中了，根本不需要再往上走，所以执行的是新版本，打印 `Current value = "LP6e"`。f-string（格式化字符串）在函数执行时求值 `self.data`，取到 z 里的 `'LP6e'`。

```python
>>> x.display()                 # x 仍然是 FirstClass 的实例（旧消息）
hacking
```

- **解释器如何处理**：x 是 FirstClass 的实例，它的查找路径是 `x.__dict__` → `FirstClass.__dict__`，**根本不经过** SecondClass，所以永远用旧版本 display，打印 `hacking`。这就是"专门化完全外部于 FirstClass"的机制原因——搜索路径决定了谁影响谁。

- **生活例子**：模块是**小区**，类是**单元楼**——地址总是"小区.楼号"（`person.Person`）。你从登记册（`from ... import ...`）把某栋楼的名字抄到自己的便签上，不代表小区里又建了一栋楼。

## 27.9 类可以拦截 Python 运算符（Classes Can Intercept Python Operators）

### 英文原文

> Let's move on to the third and final major difference between classes and
> modules: operator overloading. In simple terms, operator overloading lets
> objects coded with classes intercept and respond to operations that work on
> built-in types: addition, slicing, printing, qualification, and so on. It's mostly just
> an automatic dispatch mechanism—expressions and other built-in operations
> route control to implementations in classes. Here, too, there is nothing similar in
> modules: modules can implement function calls, but not the behavior of
> expressions (apart, that is, from the odd special case added in Python 3.7 for
> module __getattr__ and __dir__ functions covered in Chapter 25, and
> bemoaned there as a confusing conflation with classes—for reasons you're about
> to see for yourself).
>
> Although we could implement all class behavior as normally named methods,
> operator overloading lets objects be more tightly integrated with Python's object
> model. Moreover, because operator overloading makes our own objects act like
> built-ins, it tends to foster object interfaces that are more consistent and easier to
> learn, and it allows class-based objects to be processed by code written to expect
> a built-in object's interface. Here is a quick rundown of the main ideas behind
> overloading operators:
>
> - **Methods named with double underscores (__X__) are special hooks.**
>   In Python classes, we implement operator overloading by providing
>   specially named methods to intercept operations. The Python language
>   defines a fixed and unchangeable mapping from each of these
>   operations to a specially named method.
> - **Such methods are called automatically when instances appear in
>   built-in operations.** For instance, if an instance object inherits an
>   __add__ method, that method is called whenever the object appears in a
>   + expression. The method's return value becomes the result of the
>   corresponding expression.
> - **Classes may override most built-in type operations.** There are dozens
>   of special operator-overloading method names for intercepting and
>   implementing nearly every operation available for built-in object types.
>   This includes expressions, but also basic operations like printing and
>   object creation.
> - **Most operator-overloading methods have no default, and none are
>   required.** If a class does not define or inherit an operator-overloading
>   method, it just means that the corresponding operation is not supported
>   for the class's instances. If there is no __add__, for example, +
>   expressions raise exceptions. As you'll learn later, a root class named
>   object that's an implicit superclass to every class does provide defaults
>   for some __X__ methods, but not for many (e.g., object has a default
>   for print strings, but not +).
>
> Importantly, operator overloading is an optional feature; it's used primarily by
> people developing tools for other Python programmers, not by application
> developers. And, candidly, you probably shouldn't use it just because it seems
> clever. Unless a class needs to mimic built-in object interfaces, it should usually
> stick to nonoperator method names whose calls are more explicit. Expressions
> like * and +, for example, may make sense for a numeric object like a matrix, but
> other code would generally serve its clients better with mnemonically named
> methods.
>
> Because of this, we won't go into details on every operator-overloading method
> available in Python in this learner's book. Still, as previewed in the prior chapter,
> there is one operator-overloading method you are likely to see in almost every
> Python class: the __init__ method, which is known as the constructor method
> and is used to initialize instance objects' state. Pay special attention to this
> method, because __init__, along with the self argument and inheritance
> search, turns out to be a core requirement for reading and understanding most
> OOP code in Python.

### 中文翻译

> 接下来看类与模块的第三个也是最后一个主要区别：**运算符重载**（operator overloading）。简单来说，运算符重载让用类编写的对象能够拦截并响应那些作用于内建类型（built-in type）的操作：加法、切片、打印、属性限定等等。它基本上就是一个自动分派（dispatch）机制——表达式和其他内建操作会把控制权路由到类中的实现。在这里，模块也没有对应物：模块可以实现函数调用，但无法实现表达式的行为（唯一例外是 Python 3.7 为模块 `__getattr__` 和 `__dir__` 函数添加的奇怪特例，在第 25 章讲过，并在那里被吐槽为与类的令人困惑的混淆——原因你马上就会亲眼看到）。
>
> 虽然我们可以把所有类行为实现为普通命名的方法，但运算符重载让对象与 Python 的对象模型结合得更紧密。此外，因为运算符重载让自定义对象表现得像内建对象，它倾向于催生更一致、更容易学习的对象接口，也允许基于类的对象被那些"期望内建对象接口"的代码处理。下面是重载运算符的主要思想概览：
>
> - **用双下划线命名的方法（__X__）是特殊的钩子（hook）。** 在 Python 类中，我们通过提供特殊命名的方法来拦截操作，从而实现运算符重载。Python 语言定义了一个固定的、不可改变的映射，把每个操作对应到特定命名的方法。
> - **当实例出现在内建操作中时，这些方法会被自动调用。** 例如，如果一个实例对象继承了 `__add__` 方法，那么每当该对象出现在 `+` 表达式中，这个方法就会被调用。方法的返回值成为对应表达式的结果。
> - **类可以覆盖大多数内建类型操作。** 有几十个特殊的运算符重载方法名，用于拦截和实现内建对象类型可用的几乎所有操作。这包括表达式，也包括打印和对象创建等基础操作。
> - **大多数运算符重载方法没有默认实现，也都不强制要求。** 如果某个类没有定义或继承某个运算符重载方法，那只是意味着该操作对这类实例不受支持。比如没有 `__add__`，`+` 表达式就会抛出异常。你以后会学到：名为 `object` 的根类是所有类的隐式超类，它为少数 `__X__` 方法提供了默认实现，但大多数都没有（例如 `object` 有打印字符串的默认实现，但没有 `+`）。
>
> 重要的是：运算符重载是一个**可选**特性，主要被那些"为其他 Python 程序员开发工具"的人使用，而不是应用开发者。而且坦率地说，你不应该仅仅因为它看起来很酷就使用它。除非一个类需要模仿内建对象的接口，否则通常应该坚持使用调用更显式的、非运算符的方法名。比如 `*` 和 `+` 这样的表达式对矩阵这样的数值对象可能有意义，但其他代码通常用有助记名字的方法，对使用者更友好。
>
> 正因如此，在这本入门书里，我们不会逐一讲解 Python 中所有可用的运算符重载方法。不过，正如上一章预告的那样，有一个运算符重载方法几乎会在每个 Python 类里出现：`__init__` 方法——它被称为**构造函数**（constructor）方法，用来初始化实例对象的状态。请特别关注这个方法，因为 `__init__` 连同 `self` 参数和继承搜索，正是阅读和理解大多数 Python OOP 代码的核心要件。

### 深度理解

- **核心概念**：运算符重载 = **表达式分派**。`a + b` 在 Python 中不是"符号上的魔法"，而是被翻译成 `type(a).__add__(a, b)` 之类的方法调用。类只要定义了对应名字的钩子方法，就能接管该操作。
- **底层实现**：CPython 的求值循环（评估栈）遇到 `+` 操作码 `BINARY_OP` 时，会查找左操作数的类型（及其基类链）里的 `__add__` 特殊方法；如果左操作数不支持，还会尝试右操作数的 `__radd__`（反向运算）。这个查找用的是**类型**而非实例本身（特殊方法查找在类型层级上进行，不经过实例字典——这是与普通属性查找的重要差异）。
- **为什么这样设计**：让 `+`、`print()`、`len()`、`for` 循环这些"语言级操作"统一走方法分派，意味着自定义对象可以无缝融入语言生态——任何为内建对象写的代码（排序、拼接、格式化）都能直接处理你的对象。这就是"协议"（protocol）思想：不需要继承某个具体基类，只要实现接口（duck typing 的运算符版）。
- **实际问题**：`__init__` 是唯一几乎必须用的重载方法——它不是为"炫技"，而是为"构造时初始化状态"，属于工程必需品。判断一个类是否该重载运算符的标准是：**这个操作符对你的对象是否有直觉意义**（矩阵用 `+` 合理，用户对象用 `+` 就莫名其妙）。
- **初学者误区**：① 以为 `__X__` 是保留字——不是，它们是普通名字，只是约定；② 以为不定义 `__add__` 时 `+` 会"自动做点什么"——不会，直接 `TypeError`；③ 以为 `__init__` 是"分配内存"的构造器——不是！分配内存由 `__new__` 负责，`__init__` 只做**初始化**，此时对象已经存在。本书第 30 章会细讲。
- **生活例子**：运算符重载像**电话分机**——语言只认"总机号码"（`+` 这个符号），总机把电话自动转给分机（`__add__` 方法）。没有分机的部门（没定义方法的类），来电（表达式）就无人接听（抛异常）。

## 27.10 第三个示例（A Third Example）

### 英文原文

> On to another example. This time, we'll define a subclass of the prior section's
> SecondClass that implements three specially named attributes that Python will
> call automatically:
>
> - __init__ is run when a new instance object is created: self is the new
>   ThirdClass object.¹
> - __add__ is run when a ThirdClass instance appears in a + expression.
> - __str__ is run when an object is printed (technically, when it's
>   converted to its print string by the str built-in function or its Python-
>   internals equivalent).
>
> Our new subclass also defines a normally named method called mul, which
> changes the instance object in place. Here's the new subclass (copy-and-pasters:
> in REPLs, you may need to omit blank lines added here for clarity):
>
> ```python
> >>> class ThirdClass(SecondClass):      # Inherit from SecondClass
>         def __init__(self, value):      # On "ThirdClass(value)"
>             self.data = value
>         def __add__(self, other):       # On "self + other"
>             return ThirdClass(self.data + other)
>         def __str__(self):              # On "print(self)", "str()"
>             return f'[ThirdClass: {self.data}]'
>         def mul(self, other):           # In-place change: named
>             self.data *= other
> ```
>
> ThirdClass "is a" SecondClass, so its instances inherit the customized display
> method from SecondClass of the preceding section. This time, though, ThirdClass
> creation calls pass an object to the value argument in the __init__
> constructor, where it is assigned to self.data. The net effect is that ThirdClass
> arranges to set the data attribute automatically at construction time, instead of
> requiring later setdata calls:
>

> >>> a = ThirdClass(3)           # __init__ called
> >>> a.display()                 # Inherited method called
> Current value = "3"
> ```
>
> ThirdClass objects can also now show up in + expressions and print calls. For
> +, Python passes the instance object on the left to the self argument in __add__
> and the value on the right to other, as illustrated in Figure 27-3; whatever
> __add__ returns becomes the result of the + expression (more on its result in a
> moment):
>
> ```python
> >>> b = a + 3                   # __add__: makes a new instance
> >>> b.display()                 # b has all ThirdClass methods
> Current value = "6"
> ```
>

> ```

> superclasses, as usual. As for all attributes, the lowest (most specific) version is
> used.
>
> Operator-overloading method names are also not built-in or reserved words; they
> are just attributes that Python looks for when objects appear in various contexts.
> Python usually calls them automatically, but they may occasionally be called by
> your code as well. For example, the __init__ method is often called manually
> to trigger required initialization steps in a superclass constructor, as you'll see in
> the next chapter.

#### 返回结果——或者不（Returning results—or not）

> Some operator-overloading methods like __str__ require results, but others are
> more flexible. For example, notice how the __add__ method makes and returns a

> which in turn triggers __init__ to initialize the result. This is a common

> ThirdClass object too, because that's what + returns for this class's objects.

>

> 相比之下，mul 通过重新赋值 self 的属性来**原地**修改当前实例。我们可以用 `__mul__` 重载 `*` 表达式来做同样的事，但这与内建类型（如数字和字符串）的 `*` 行为差异太大——内建类型总是制造新对象。按惯例，重载的运算符应当与内建操作的语义一致。不过，因为运算符重载本质上只是"表达式到方法"的分派机制，在自己的类里，你完全可以按自己喜欢的方式解释运算符。另外，敬请期待第 30 章关于就地运算符（in-place operator）方法的相关内容（预告：`__imul__` 处理 `*=`）。

#### 其他运算符重载方法（Other operator-overloading methods）

### 深度理解

- **核心概念**：第三个示例把"运算符重载"三件套凑齐了：`__init__`（构造时初始化）、`__add__`（`+` 表达式）、`__str__`（打印）。注意它们的共同点——**都是普通属性**，与其他方法无异，只是名字碰巧被语言"约定"了。
- **底层实现（`__init__` 的调用链）**：`ThirdClass(3)` 的完整流程是：① 调用类对象 → 元类 `type.__call__`；② 调用 `ThirdClass.__new__`（默认从 `object` 继承）分配并返回一个**空的**实例；③ 若返回的是 ThirdClass 的实例，自动调用 `__init__(实例, 3)`；④ 返回实例。所以 `__init__` 里 `self.data = value` 是在"对象已存在、只是状态未初始化"时写入初始状态。
- **底层实现（`+` 的分派）**：`a + 3` 在求值栈上执行 `BINARY_OP` 指令，按类型层级查找 `__add__`；找到后调用 `ThirdClass.__add__(a, 3)`，返回值 `ThirdClass(6)` 成为表达式结果。注意 `__add__` 内部又调用了 `ThirdClass(...)`，于是递归触发了一次完整的构造流程——`b` 是一个全新的、data=6 的 ThirdClass 实例。
- **设计原因**：为什么 `__add__` 返回**新对象**而 `mul` 原地修改？因为语言内建语义如此：`3 + 5` 产生新整数，`a + b`（字符串）也产生新字符串——"加法不破坏操作数"是用户心智预期；而 `mul` 是普通方法，行为由你定义。遵循内建语义，你的类才不会吓到使用者。
- **实际问题**：`print(b)` 能打出 `[ThirdClass: 6]`，靠的是 `__str__` 返回字符串。没有 `__str__` 时 print 会退而使用 `object` 的默认实现，输出 `<__main__.ThirdClass object at 0x...>`——这就是为什么日志和调试输出里"类都该有 `__repr__`/`__str__`"是工程常识。
- **初学者误区**：① 以为 `__init__` 是"分配内存"——不是，那是 `__new__` 的活，初学者完全不用碰 `__new__`；② 以为特殊方法"不能手动调用"——可以，只是不常见；③ 以为 `a + 3` 会修改 a——不会，`__add__` 返回新对象，a 保持原样；④ 把 `__str__`（给人看的打印）和 `__repr__`（给调试者的、无歧义表示）混为一谈——本书下一章会区分。
- **生活例子**：`__init__` 像**新员工入职登记**——人已经来了（对象已分配），填表建档（初始化属性）；`__add__` 像**称重台**——把两筐苹果放上去，得到一个新的总重数字，两筐原苹果分毫未动；`__str__` 像**商品标签**——顾客（print）看到的就是你贴上去的那行字。

### 代码分析

```python
>>> class ThirdClass(SecondClass):      # 继承 SecondClass
        def __init__(self, value):      # 在 "ThirdClass(value)" 时运行
            self.data = value           # 构造时就把数据写进新实例
        def __add__(self, other):       # 在 "self + other" 时运行
            return ThirdClass(self.data + other)   # 返回一个新实例
        def __str__(self):              # 在 "print(self)"、"str()" 时运行
            return f'[ThirdClass: {self.data}]'    # 返回打印用的字符串
        def mul(self, other):           # 原地修改：命名方法
            self.data *= other          # 直接改变当前实例的数据
```

- **解释器如何处理**：`ThirdClass(3)` 执行时：元类协议分配空实例 → 自动调用 `__init__(新实例, 3)` → `self.data = 3` 写入实例字典。`a.display()` 的搜索路径：a 空 → ThirdClass 无 display → SecondClass 命中（继承生效），打印 `Current value = "3"`。`a + 3`：求值栈对 `+` 执行特殊方法查找，命中 ThirdClass 的 `__add__`，调用 `__add__(a, 3)`，内部 `self.data + other` 得到整数 6，再 `ThirdClass(6)` 递归构造新实例（触发又一次 `__init__`），返回它作为表达式结果，绑定给 b。`print(b)`：print 会调用 `str(b)`，解释器在类型层级找 `__str__`，用其返回值作为打印内容。`a.mul(3)`：普通方法调用，`self.data *= other` 等价于 `self.data = self.data * other`，直接改写 a 实例字典中的 data（3→9）。

```python
>>> b = a + 3                   # __add__：生成一个新实例
>>> b.display()                 # b 拥有 ThirdClass 的全部方法
Current value = "6"
```

- **解释器如何处理**：注意 `b` 与 `a` 是**两个不同的对象**——`+` 没有改动 a（a.data 仍是 3），而是把新实例交给 b。这是"加法不破坏操作数"语义的直接体现。`b.display()` 同样沿继承链找到 SecondClass 的 display。

```python
>>> a.mul(3)                    # mul：原地修改实例
>>> print(a)                    # 打印该实例的数据
[ThirdClass: 9]
```

- **解释器如何处理**：`mul` 与方法调用毫无特殊之处：绑定 a 到 self，`self.data *= 3` 把 a 自己的 data 从 3 改成 9。随后 `print(a)` 经 `__str__` 输出 `[ThirdClass: 9]`。对比 `+` 与 `mul`：一个"新生"，一个"原地"——这正是重载运算符时应遵循内建语义的直观教材。

## 27.11 世界上最简单的 Python 类（The World's Simplest Python Class）

### 英文原文

> Despite the details of the class statement that we've begun to uncover in this
> chapter, you should keep in mind that the basic inheritance model behind classes
> is very simple—all it really involves is searching for attributes in trees of linked
> objects. In fact, we can create a class with nothing in it at all. The following
> statement makes a class with no attributes attached, an empty namespace object:
>
> ```python
> >>> class rec: pass             # Empty namespace object
> ```
>
> We need the no-operation pass placeholder statement (discussed in Chapter 13)
> here because we don't have any methods to code. After we make the class by
> running this statement interactively, we can start attaching attributes to the class
> by assigning names to it completely outside of the original class statement:
>
> ```python
> >>> rec.name = 'Pat'            # Just objects with attributes
> >>> rec.age = 40
> ```
>
> And, after we've created these attributes by assignment, we can fetch them with
> the usual syntax. When used this way, a class is roughly similar to a "struct" in
> C, or a "record" in Pascal. It's basically an object with field names attached to it,

>
> ```python
> >>> print(rec.name)             # Like a C struct or a record
> Pat
> ```
>
> Notice that this works even though there are no instances of the class yet; classes
> are objects in their own right, even without instances. In fact, they are just self-
> contained namespaces; as long as we have a reference to a class, we can set or
> change its attributes anytime we wish. Watch what happens when we do create
> two instances, though:
>
> ```python
> >>> x = rec()                   # Instances inherit class names
> >>> y = rec()
> ```
>
> These instances begin their lives as completely empty namespace objects.
> Because they remember the class from which they were made, though, they will
> obtain the attributes we attached to the class by inheritance:
>
> ```python
> >>> x.name, y.name              # name is stored on the class only
> ('Pat', 'Pat')
> ```
>
> Really, these instances have no attributes of their own; they simply fetch the
> name attribute from the class object where it is stored. If we do assign an
> attribute to an instance, though, it creates (or changes) the attribute in that object,
> and no other—crucially, attribute references kick off inheritance searches, but
> attribute assignments affect only the objects in which the assignments are made.
> Here, this means that x gets its own name, but y still inherits the name attached to
> the class above it:
>
> ```python
> >>> x.name = 'Sue'              # But assignment changes x only

### 中文翻译

> 尽管本章已经揭示了不少 class 语句的细节，但请记住：类背后的基本继承模型非常简单——它实际上只涉及在链接对象的树中搜索属性。事实上，我们可以创建一个什么都没有的类。下面这条语句会创建一个不带任何属性的类，即一个空的命名空间对象：
>
> ```python
> >>> class rec: pass             # 空的命名空间对象
> ```
>
> 这里需要用到空操作占位语句 pass（第 13 章讨论过），因为我们没有任何方法要写。交互式运行这条语句创建类之后，我们可以完全在原始的 class 语句之外，通过给类赋值来开始挂接属性：
>
> ```python
> >>> rec.name = 'Pat'            # 只是带属性的对象
> >>> rec.age = 40
> ```
>
> 用赋值创建好这些属性后，我们就可以用通常的语法获取它们。这样使用时，类大致类似于 C 语言的 "struct"（结构体）或 Pascal 语言的 "record"（记录）——本质上就是一个挂着字段名（field name）的对象，而且可能比字典之类的替代品更容易编写：
>
> ```python
> >>> print(rec.name)             # 像 C 的 struct 或记录
> Pat
> ```
>
> 注意：即使这个类还没有任何实例，这一切也能工作——即使没有实例，类本身也是合法的对象。事实上，它们就是自包含的命名空间；只要持有某个类的引用，我们就可以随时设置或修改它的属性。不过，看看当我们真的创建两个实例时会发生什么：
>
> ```python
> >>> x = rec()                   # 实例继承类的名字
> >>> y = rec()
> ```
>
> 这两个实例以完全空的命名空间对象开始它们的生命。但正因为它们记得"自己由哪个类生成"，它们会通过继承获得我们挂在类上的属性：
>
> ```python
> >>> x.name, y.name              # name 只存储在类上
> ('Pat', 'Pat')
> ```
>
> 实际上，这些实例自己没有属性；它们只是从存储 name 的类对象那里取回它。不过，如果我们真的给某个实例赋值一个属性，它只会在**那个对象**中创建（或改变）属性，而不会影响其他对象——关键在于：**属性引用会触发继承搜索，但属性赋值只影响被赋值的对象本身**。在这里，这意味着 x 得到了自己的 name，而 y 仍然继承挂在类上的 name：
>
> ```python
> >>> x.name = 'Sue'              # 但赋值只改变 x
> >>> rec.name, x.name, y.name
> ('Pat', 'Sue', 'Pat')
> ```

### 深度理解

- **核心概念**：本章最重要的规则浓缩在这句话里——**读取走继承，写入不传播**（references search, assignments don't）。`x.name = 'Sue'` 不会修改类上的 `name`，而是把 `'Sue'` 写进 x 自己的字典，从此 x 的读取路径在实例这一层就命中了，不再向上。y 与 rec 的 `name` 原封不动。
- **底层实现**：`class rec: pass` 执行后，`rec.__dict__` 是 `{}`（只有 dunder 内建键）；`rec.name = 'Pat'` 直接往类字典里加键。`x = rec()` 创建实例，`x.__dict__` 为空，`__class__` 指向 rec。`x.name` 的查找：x 字典没有 → 沿链接到 rec 字典 → 命中 `'Pat'`。`x.name = 'Sue'` 则只写 x 字典（新增键）。一次赋值、两个查找路径，机制就这么简单。
- **设计原因**：为什么赋值不继承？如果赋值也"继承"（写进类），那么改一个实例的数据会污染所有实例，多实例的独立性就荡然无存——那与共享全局变量无异。Python 选择"读时向上查、写时就地写"，在共享与独立之间画了一条干净的分界线。
- **实际问题**：这个"空类当 struct 用"的技巧正是 27.13 节数据记录的基础；而"赋值不继承"这条规则则解释了所有"以为改了实例属性、结果所有实例都变了"的经典 bug——其实根源往往是写到了**类属性**（在类体顶层赋值）而不是实例属性。
- **初学者误区**：① 以为 `pass` 可有可无——类体必须至少一条语句，空类体语法不合法；② 以为"类必须有实例才有用"——类本身就是对象，可独立存取属性；③ 把"给类挂属性"和"给实例挂属性"搞混——`rec.name = ...` 是类属性，所有实例共享；④ 以为 `x.name = 'Sue'` 会"顺带"改掉 y——不会，只有 x 受影响。
- **生活例子**：类像**公司的公开邮箱**（`rec.name`），每个员工（实例）都默认看这封公告；某员工在公告下贴了张自己的便签（`x.name = 'Sue'`），从此他只看自己的便签——但公告还是那份公告，其他员工看到的还是它。

### 代码分析

```python
>>> class rec: pass             # 空的命名空间对象
>>> rec.name = 'Pat'            # 只是带属性的对象
>>> rec.age = 40
>>> print(rec.name)             # 像 C 的 struct 或记录
Pat
```

- **解释器如何处理**：`class rec: pass` 创建类对象（字典近乎为空）。`rec.name = 'Pat'` 与 `rec.age = 40` 是两条普通赋值语句，把键值写入类对象的 `__dict__`。`print(rec.name)` 则是"读类对象的属性"——先查 rec 自己的字典，命中即返回。整个过程没有创建任何实例，类对象独立完成存取——证明"类即对象"。

```python
>>> x = rec()                   # 实例继承类的名字
>>> y = rec()
>>> x.name, y.name              # name 只存储在类上
('Pat', 'Pat')
```

- **解释器如何处理**：两个实例的字典都是空的，但 `__class__` 都指向 rec。读 `x.name`：x 空 → 沿链接查 rec → 命中 `'Pat'`。y 同理。所以两个实例"共享"同一个值——严格说不是共享，而是**各自沿链接取到同一份**。

```python
>>> x.name = 'Sue'              # 但赋值只改变 x
>>> rec.name, x.name, y.name
('Pat', 'Sue', 'Pat')
```

- **解释器如何处理**：`x.name = 'Sue'` 只往 x 的字典里写键 `name`。之后读取：`rec.name` 直接命中类字典（`'Pat'`）；`x.name` 命中 x 字典（`'Sue'`，无需向上）；`y.name` 沿链接命中类字典（`'Pat'`）。同一个名字、三条不同的查找路径、三个不同的结果——这就是"命名空间树 + 逐层查找"模型最直观的演示。

> >>> list(key for key in rec.__dict__ if not key.startswith('__'))

> >>> list(x.__dict__)

> []
> ```

> >>> x.name, x.__dict__['name']  # 这里的属性就是字典键
> ('Sue', 'Sue')
> >>> x.age                       # 但属性获取还会检查类
> 40
> >>> x.__dict__['age']           # 索引字典不做继承
> KeyError: 'age'
> >>> x.__dict__                  # 对象命名空间对比继承
> {'name': 'Sue'}

> ['age', 'name']
> ```

### 深度理解

- **核心概念**：本章的"引擎盖时刻"——类的所有机制可以浓缩成三样东西：`__dict__`（每个对象的属性字典）、`__class__`（实例→类的链接）、`__bases__`（类→超类的链接元组）。**继承树 = 字典 + 链接**，再无其他。
- **底层实现**：`x.name` 的解释器流程：查 `x.__dict__` → 未命中则沿 `x.__class__` 找到类 → 查类字典 → 未命中再沿类 `__bases__` 逐个查超类字典 → 全未命中抛 `AttributeError`。而 `x.__dict__['name']` 是纯字典索引，**不做任何向上查找**——所以 `x.__dict__['age']` 会 `KeyError`，尽管 `x.age` 能拿到 40。`dir(x)` 则是"类字典 + 所有基类字典的键"的并集，所以能看到继承来的 `age`。
- **为什么这样设计**：把命名空间做成字典，让"属性"与"字典键"统一——属性系统零专用机制，赋值/读取就是字典读写。这种"数据结构的复用"让整个对象模型可以用一句话向任何人讲清楚，也让内省（introspection）变得免费：`vars(x)`、`x.__dict__` 直接可看。
- **实际问题**：`uppername` 变方法的例子揭示了一个深刻的真相：**"方法"这个身份不是函数自带的，而是"函数被挂在类上"这个位置赋予的**。绑定机制（方法对象自动把实例作为第一实参）由描述符协议触发，与函数是否"生来就是方法"无关。这为"把任意函数变成方法"（monkey-patching、装饰器包装）铺平了道路。也解释了为什么 `self` 必须显式——Python 无法在函数定义时知道它将来会不会变成方法，干脆统一显式。
- **初学者误区**：① 以为 `__dict__` 是给高级用户用的内部细节——它恰恰是理解本模型的钥匙；② 以为"属性记法"和"字典索引"完全等价——只有对象**自己**有的键才等价，继承来的不行；③ 以为方法有特殊存储——方法只是类字典里的普通函数，绑定发生在调用瞬间；④ 以为 `dir` 只列自己定义的属性——它列的是整条继承链的并集。
- **生活例子**：`__dict__` 是**个人档案袋**，`__class__` 是"入职公司名"，`__bases__` 是"公司归属的总部"。查 `x.age` 像人事流程：先翻本人档案（没有）→ 问公司制度（有，40 岁退休年龄）→ 查到即答；而 `x.__dict__['age']` 是只翻本人档案，翻不到就说"档案里没有"。

### 代码分析

```python
>>> list(key for key in rec.__dict__ if not key.startswith('__'))
['name', 'age']
```

- **解释器如何处理**：生成器表达式遍历 `rec.__dict__`（类对象的字典），过滤掉以 `__` 开头的内建键，剩下的就是我们手工赋的 `name` 和 `age`。这证明"类属性"物理上就是类字典里的键值对。

```python
>>> x.name, x.__dict__['name']  # 这里的属性就是字典键
('Sue', 'Sue')
>>> x.age                       # 但属性获取还会检查类
40
>>> x.__dict__['age']           # 索引字典不做继承
KeyError: 'age'
>>> [attr for attr in dir(x) if attr[:2] != '__']
['age', 'name']
```

- **解释器如何处理**：`x.__dict__['name']` 与 `x.name` 结果相同，因为 name 就在 x 自己的字典里。`x.age` 能取到 40，是因为属性记法沿 `__class__` 链接找到了类字典里的 age；而 `x.__dict__['age']` 是纯索引，x 字典里没有 age，直接 `KeyError`——**同样的属性，两种取法，结果一成一败**。`dir(x)` 走的是类型层级，把类里的 `age` 和实例里的 `name` 合并返回。

```python
>>> def uppername(obj):
        return obj.name.upper() # 仍然需要一个 self 参数（obj）
>>> rec.method = uppername      # 现在它是类的方法了！
>>> x.method()                  # 运行方法来处理 x
'SUE'
>>> rec.method(x)               # 可以通过实例或类调用
'SUE'
```

- **解释器如何处理**：`uppername` 本是模块里的普通函数。`rec.method = uppername` 把它存入类字典——从这一刻起，通过实例访问 `x.method` 时，描述符协议看到"类字典里存的是函数"，自动把它包装成绑定方法（记住 x 作为第一实参），所以 `x.method()` 等价于 `uppername(x)`。而 `rec.method(x)` 走的是"类本身取属性"的路径（函数没有被绑定），需要手动传实例。同一个函数对象，两种调用姿势——绑定与否，只看访问它时经过了谁。

## 27.13 回顾记录：类对比字典（Records Revisited: Classes Versus Dictionaries）

### 英文原文

> Although the simple classes of the prior section are meant to illustrate class
> model basics, the techniques they employ can also be used for real work. For
> example, Chapters 8 and 9 showed how to use dictionaries, tuples, and lists to
> record properties of entities in our programs, generically called records. It turns
> out that classes can often serve better in this role—they package information like
> dictionaries, but can also bundle processing logic in the form of methods. For
> reference, here is an example for tuple- and dictionary-based records we used
> earlier in the book (using one of many dictionary coding techniques):
>
> ```python
> >>> rec = ('Pat', 40.5, ['dev', 'mgr'])  # Tuple-based record
> >>> print(rec[0])
> Pat
> >>> rec = {}
> >>> rec['name'] = 'Pat'              # Dictionary-based record
> >>> rec['age'] = 40.5                # Or {...}, dict(n=v), etc.
> >>> rec['jobs'] = ['dev', 'mgr']
> >>> print(rec['name'])
> Pat
> ```
>
> As we just saw, though, there are also multiple ways to do the same with classes.
> Perhaps the simplest is this—trading keys for attributes:
>
> ```python
> >>> class rec: pass
> >>> rec.name = 'Pat'                 # Class-based record
> >>> rec.age = 40.5
> >>> rec.jobs = ['dev', 'mgr']
> >>> print(rec.name)
> Pat
> ```
>
> This code has substantially less syntax than the dictionary equivalent. It uses an
> empty class statement to generate an empty namespace object, which we then
> fill out by assigning class attributes over time, as before. This works, but a new
> class statement will be required for each distinct record we will need. Perhaps
> more typically, we can instead generate instances of an empty class to represent
> each distinct entity:
>
> ```python
> >>> class rec: pass
> >>> pers1 = rec()                    # Instance-based records
> >>> pers1.name = 'Bob'
> >>> pers1.jobs = ['dev', 'mgr']
> >>> pers1.age = 40.5
> >>> pers2 = rec()
> >>> pers2.name = 'Sue'
> >>> pers2.jobs = ['dev', 'cto']
> >>> pers1.name, pers2.name
> ('Bob', 'Sue')
> ```
>
> Here, we make two records from the same class. Instances start out life empty,
> just like classes. We then fill in the records by assigning to attributes. This time,
> though, there are two separate objects, and hence two separate name attributes.
> In fact, instances of the same class don't even have to have the same set of
> attribute names; in this example, one has a unique age name. Instances really are
> distinct namespaces, so each has a distinct attribute dictionary. Although they are
> normally filled out consistently by a class's methods, they are more flexible than
> you might expect.
>
> Finally, we might instead code a more full-blown class to implement the record
> and its processing—something that data-oriented dictionaries do not directly
> support:
>
> ```python
> >>> class Person:
>         def __init__(self, name, jobs, age=None):   # class = data + logic
>             self.name = name
>             self.jobs = jobs
>             self.age = age
>         def info(self):
>             return (self.name, self.jobs)
> >>> rec1 = Person('Bob', ['dev', 'mgr'], 40.5)      # Construction calls
> >>> rec2 = Person('Sue', ['dev', 'cto'])
> >>> rec1.jobs, rec2.info()                          # Attributes + methods
> (['dev', 'mgr'], ('Sue', ['dev', 'cto']))
> ```
>
> This scheme also makes multiple instances, but the class is not empty this time:
> we've added logic (methods) to initialize instances at construction time and
> collect attributes into a tuple on request. The constructor imposes some
> consistency on instances here by always setting the name, job, and age
> attributes, even though the latter can be omitted when an object is made.
> Together, the class's methods and instance attributes create a package, which
> combines both data and logic.
>
> We could further extend this code by adding logic to compute salaries, parse
> names, and so on. Ultimately, we might link the class into a larger hierarchy to
> inherit and customize an existing set of methods via the automatic attribute
> search of classes, or perhaps even store instances of the class in a file with
> Python object pickling to make them persistent. In fact, we will—in the next
> chapter, we'll expand on this analogy between classes and records with a more
> realistic running example that demonstrates class basics in action.
>
> To be fair to other tools, in this form, the two preceding class construction calls
> more closely resemble dictionaries made all at once, but still seem less cluttered
> and provide extra processing methods. In fact, the class's construction calls more
> closely resemble Chapter 9's named tuples—which makes sense, given that
> named tuples really are classes with extra logic to map attributes to tuple offsets:
>
> ```python
> >>> rec = dict(name='Pat', jobs=['dev', 'mgr'], age=40.5)    # Dictionaries
> >>> rec = {'name': 'Pat', 'jobs': ['dev', 'mgr'], 'age': 40.5}   # Ditto
> >>> ... setup code ...
> >>> rec = Rec('Pat', ['dev', 'mgr'], 40.5)                    # Named tuples
> ```
>
> In the end, although types like dictionaries and tuples are flexible, classes allow
> us to add behavior to objects in ways that built-in types and simple functions do
> not directly support. Although we can store functions in dictionaries too (e.g.,
> under key info to mimic the class's method), using them to process implied
> instances is nowhere near as natural and structured as it is in classes, and key
> lookup has no notion of inheritance to enable customization.
>
> But to vet the purported benefits of classes firsthand, you'll have to move ahead
> to the next chapter.

### 中文翻译

> 虽然上一节的简单类是用来演示类模型基础的，但它们采用的技术也可以用于真实工作。例如，第 8 章和第 9 章展示了如何使用字典、元组和列表来记录程序中实体的属性，统称为**记录**（record）。事实证明，类在这个角色上往往更胜一筹——它们像字典一样打包信息，还能以方法的形式捆绑处理逻辑。作为参考，这里给出我们早先在书中用过的元组版和字典版记录示例（使用众多字典编码技巧之一）：
>
> ```python
> >>> rec = ('Pat', 40.5, ['dev', 'mgr'])  # 基于元组的记录
> >>> print(rec[0])
> Pat
> >>> rec = {}
> >>> rec['name'] = 'Pat'              # 基于字典的记录

> Pat
> ```

> >>> class rec: pass

>
> 这段代码比字典版少了很多语法。它用一个空的 class 语句生成一个空的命名空间对象，然后像之前一样，通过随时间给类属性赋值来填充它。这能工作，但每需要一个不同的记录，就得写一条新的 class 语句。更典型的做法或许是：生成一个空类的**实例**来表示每个不同的实体：

> >>> class rec: pass
> >>> pers1 = rec()                    # 基于实例的记录
> >>> pers1.name = 'Bob'
> >>> pers1.jobs = ['dev', 'mgr']
> >>> pers1.age = 40.5
> >>> pers2 = rec()

> >>> pers2.jobs = ['dev', 'cto']

> >>> class Person:
>         def __init__(self, name, jobs, age=None):   # 类 = 数据 + 逻辑
>             self.name = name
>             self.jobs = jobs
>             self.age = age

>

>
> 归根结底，虽然字典和元组这类类型很灵活，但类允许我们以内建类型和简单函数无法直接支持的方式为对象**添加行为**。虽然我们也可以把函数存进字典（比如放在 info 键下模仿类的方法），但用它们去处理隐含的实例，远不如在类中来得自然和结构化；而且字典键查找没有继承的概念，无法实现定制。

### 深度理解

- **核心概念**：本节把前几节的技术"实战化"：类可以当**记录（record）**用，且有一个字典永远给不了的东西——**行为**。三种方案递进：类属性当字段（共享版）→ 实例属性当字段（每实体独立）→ 完整类（字段 + 方法，构造时统一初始化）。
- **底层实现**：三种方案在内存中的差异一目了然：方案一数据全在类字典；方案二数据分散在各自实例的 `__dict__`（pers1 有 name/jobs/age，pers2 只有 name/jobs——**属性集合都可以不一样**，因为实例字典互不相关）；方案三实例字典在 `__init__` 执行后一次性被写满，且 `info` 方法留在类里共享。
- **设计原因**：为什么"空类当 struct"能行？因为 Python 的属性赋值无门槛——字典能加键，对象就能加属性。这比 C 的 struct 更自由（字段无须预声明），比 Pascal 的 record 更自由。而给记录配方法，则实现了"数据内聚行为"——调用方拿到对象就知道能对它做什么。
- **实际问题**：现实工程中这类模式的演进路径是：裸字典（手滑键名易错）→ 类记录（属性自动补全、可加方法）→ `dataclass`/namedtuple（现代 Python 的标准答案，自动生成 `__init__`/`__repr__`）。Lutz 此处埋的"记录=类"的类比，正是后续学习数据类（dataclass）的思想起点。
- **初学者误区**：① 以为"类的实例必须由类的 `__init__` 统一初始化"——不一定，先建空实例再逐属性赋值完全合法（动态性）；② 以为同一类的实例"结构必须相同"——上例 pers1 有 age 而 pers2 没有，照样运行；③ 以为字典能完全替代类——字典存不了行为与继承，键拼错还不报错（`rec['nam']` 静默 KeyError 也罢了，赋值时 `rec['nam'] = ...` 直接造出新键，bug 更难找）。
- **生活例子**：字典版记录是**一张手写信息卡**（只能看字）；实例版记录是**带贴纸的文件夹**（每人的贴纸可以不同）；完整类记录是**标准简历表 + 填表规则**（`__init__` 规定必填项，`info` 是"一键导出摘要"的按钮）。面试官（调用方）只看到表就能知道能做什么——这就是"数据+逻辑打包"的价值。

### 代码分析

```python
>>> class rec: pass
>>> pers1 = rec()                    # 基于实例的记录
>>> pers1.name = 'Bob'
>>> pers1.jobs = ['dev', 'mgr']
>>> pers1.age = 40.5
>>> pers2 = rec()
>>> pers2.name = 'Sue'
>>> pers2.jobs = ['dev', 'cto']
>>> pers1.name, pers2.name
('Bob', 'Sue')
```

- **解释器如何处理**：`pers1 = rec()` 与 `pers2 = rec()` 创建两个互不相关的实例（各自 `__dict__` 为空，`__class__` 都指向 rec）。随后的属性赋值分别写入各自的字典。注意 pers1 多了一个 `age` 键而 pers2 没有——**解释器对此毫无意见**，实例字典本来就可以形态各异。最后读取 `pers1.name`、`pers2.name` 各自命中自己的字典，返回 `('Bob', 'Sue')`。

```python
>>> class Person:
        def __init__(self, name, jobs, age=None):   # 类 = 数据 + 逻辑
            self.name = name
            self.jobs = jobs
            self.age = age
        def info(self):
            return (self.name, self.jobs)
>>> rec1 = Person('Bob', ['dev', 'mgr'], 40.5)      # 构造调用
>>> rec2 = Person('Sue', ['dev', 'cto'])
>>> rec1.jobs, rec2.info()                          # 属性 + 方法
(['dev', 'mgr'], ('Sue', ['dev', 'cto']))
```

- **解释器如何处理**：`Person('Bob', ['dev', 'mgr'], 40.5)` 触发构造流程：分配空实例 → 自动调用 `__init__(实例, 'Bob', [...], 40.5)` → 三个 `self.x = ...` 把实例字典写满 → 返回。`rec2` 只传了两个位置参数，`age` 用默认值 `None`——默认参数机制照常生效。`rec1.jobs` 是实例字典直接命中；`rec2.info()` 则沿 `__class__` 找到类里的 `info` 函数并绑定 rec2，函数内部用 `self.name`、`self.jobs` 组装元组返回。数据（属性）+ 逻辑（方法）在此合体为"包"。

>    corresponds to an entire file of code.
>
>    类总是嵌套在模块内部；它们是模块对象的属性。类和模块都是命名空间，但类对应的是语句（而不是整个文件），并支持 OOP 的多个实例、继承和运算符重载等概念（模块大多不支持）。在某种意义上，模块就像一个没有继承的"单实例类"，对应着整个代码文件。
>
> 2. Classes are made by running class statements; instances are created by
>    calling a class as though it were a function.
>
>    类通过运行 class 语句创建；实例通过像调用函数一样调用类来创建。
>
> 3. Class attributes are created by assigning attributes to a class object. They
>    are normally generated by top-level assignments nested in a class
>    statement—each name assigned in the class statement block becomes an
>    attribute of the class object (technically, the class statement's local scope
>    morphs into the class object's attribute namespace, much like a module).
>    Class attributes can also be created, though, by assigning attributes to the
>    class anywhere a reference to the class object exists—even outside the class
>    statement.
>
>    类属性通过对类对象赋值属性来创建。它们通常由嵌套在 class 语句中的顶层赋值生成——class 语句块中赋值的每个名字都会成为类对象的属性（严格说，class 语句的局部作用域会蜕变为类对象的属性命名空间，很像模块）。不过，类属性也可以在任何持有类对象引用的地方通过赋值创建——甚至可以在 class 语句之外。
>
> 4. Instance attributes are created by assigning attributes to an instance object.
>    They are normally created within a class's method functions coded inside the
>    class statement, by assigning attributes to the self argument (which is
>    always the implied instance). Again, though, they may be created by
>    assignment anywhere a reference to the instance appears, even outside the
>    class statement. Usually, all instance attributes are initialized in the __init__
>    constructor method; that way, later method calls can assume the attributes
>    already exist.
>
>    实例属性通过对实例对象赋值属性来创建。它们通常在 class 语句内部编写的方法函数中，通过给 self 参数（它始终是隐含的实例）赋值来创建。但同样，它们也可以在出现实例引用的任何地方通过赋值创建，甚至在 class 语句之外。通常，所有实例属性都在 `__init__` 构造函数方法中初始化；这样，后续的方法调用就可以假定这些属性已经存在。
>
> 5. self is the name commonly given to the first (leftmost) argument in a class's
>    method function; Python automatically fills it in with the instance object that
>    is the implied subject of the method call. This argument need not be called
>    self (though this is a very strong convention); its position is what is
>    significant. (Ex-C++ or Java programmers might prefer to call it this because
>    in those languages that name reflects the same idea; in Python, though, this
>    argument must always be explicit in method headers and code.)
>
>    self 是类的方法函数中第一个（最左边）参数常用的名字；Python 会自动用作为方法调用隐含主语的那个实例对象来填充它。这个参数不一定非得叫 self（虽然这是非常强的约定）；重要的是它的位置。（前 C++ 或 Java 程序员可能更喜欢叫它 this，因为在那些语言里这个名字反映同样的概念；但在 Python 中，这个参数在方法头和方法代码里必须始终显式写出。）
>
> 6. Operator overloading is coded in a Python class with specially named
>    methods; they all begin and end with double underscores to make them
>    unique. These are not built-in or reserved names; Python just runs them
>    automatically when an instance appears in the corresponding operation.
>    Python itself defines the mappings from operations to special method names.
>
>    运算符重载在 Python 类中通过特殊命名的方法编写；这些方法都以双下划线开头和结尾，以保证唯一。它们不是内建或保留名字；当实例出现在对应操作中时，Python 只是自动运行它们。从操作到特殊方法名的映射由 Python 自己定义。
>
> 7. Operator overloading is useful to implement objects that resemble built-in
>    types (e.g., sequences or numeric objects such as matrixes), and to mimic the
>    built-in type interface expected by a piece of code. Mimicking built-in type
>    interfaces enables you to pass in class instances that also have state
>    information (i.e., attributes that remember data between operation calls).
>    You generally shouldn't use operator overloading when a simple named
>    method will suffice, though.
>
>    运算符重载对实现"类似内建类型"的对象（如序列或矩阵之类的数值对象）很有用，也可以用来模仿某段代码所期望的内建类型接口。模仿内建类型接口，使你可以传入还带有状态信息（即在操作调用之间记住数据的属性）的类实例。不过，当简单的命名方法足够用时，一般不应该使用运算符重载。
>
> 8. The __init__ constructor method is the most commonly used; almost every
>    class uses this method to set initial values for instance attributes and
>    perform other startup tasks. The __str__ method (and its __repr__ sibling) is
>    not uncommon, but not as much of a fixture as __init__.
>
>    `__init__` 构造函数方法最常用；几乎每个类都用它来为实例属性设置初始值并执行其他启动任务。`__str__` 方法（及其孪生 `__repr__`）并不罕见，但不像 `__init__` 那样是标配。
>
> 9. The special self argument in method functions, the inheritance search for
>    attributes, and the __init__ constructor method are the cornerstones of OOP
>    code in Python. If you get these, you should be able to read the text of most
>    OOP Python code—apart from these, it's largely just packages of functions.
>    In classes, self represents the automatic object argument, and __init__ is
>    commonly used to initialize instances.
>
>    方法函数中特殊的 self 参数、属性的继承搜索、以及 `__init__` 构造函数方法，是 Python OOP 代码的三大基石。掌握了它们，你就能读懂大多数 Python OOP 代码的正文——除此之外，它们大体上只是函数的包（packages of functions）。在类中，self 代表自动传入的对象参数，`__init__` 常用于初始化实例。

#### 原书脚注

> 1. Not to be confused with the __init__.py files in module packages! The method
>    here is a class constructor function used to initialize the newly created
>    instance, not a namespace for a module-package folder. See Chapter 24 for
>    more details.
>
>    不要与模块包中的 `__init__.py` 文件混淆！这里的方法是用作类构造函数、初始化新建实例的函数，而不是模块包文件夹的命名空间。更多细节见第 24 章。
>
> 2. In fact, this is one of the reasons the self argument must always be explicit in
>    Python methods—because methods can be created as simple functions
>    independent of a class, they need to include the implied instance argument
>    explicitly. They can be called as either functions or methods, and Python can
>    neither guess nor assume that a simple function might eventually become a
>    class's method. The main reason for the explicit self argument, though, is to
>    make the meanings of names more apparent: names not referenced through
>    self are simple variables mapped to scopes, while names referenced through
>    self with attribute notation are obviously instance attributes.
>
>    事实上，这正是 self 参数在 Python 方法中必须始终显式的原因之一——因为方法可以独立于类、作为简单函数创建，它们需要显式地包含这个隐含的实例参数。它们既可以作为函数调用，也可以作为方法调用，而 Python 既无法猜测、也无法假设一个简单函数最终可能成为类的方法。不过，显式 self 参数的主要原因是让名字的含义更清楚：不通过 self 引用的名字是映射到作用域的普通变量，而通过 self 用属性记法引用的名字显然就是实例属性。

# 本章总结

## 技术拓展（Technical Expansion）

### 1. 实际项目中的应用场景

- **领域模型（Domain Model）**：本章的"记录"类比直接通向现代工程实践——员工、订单、商品等实体用类建模（或更现代的 `dataclass`），属性存状态，方法存行为。所有 Web 框架（Django 的 Model、SQLAlchemy 的 Declarative Base）都是"类=数据库表"模式的体现。
- **方法绑定与回调**：理解"方法=挂到类上的函数 + 绑定机制"，你才能看懂装饰器（decorator）、`functools.partial`、以及 pytest fixtures、Flask 路由等框架魔法——它们大量利用"函数被包装后改变调用签名"的技术。
- **运算符重载的真实舞台**：应用代码中你很少自己写 `__add__`，但你**天天消费**别人写的——NumPy 数组的 `a + b`、pandas 的 Series、pathlib 的 `Path / "sub"`。学会本章的分派机制，读框架源码不再神秘。
- **`__init__` 作为"属性清单"**：作者说"看 `__init__` 就知道实例有什么属性"——这是真实工程中的实用技巧：读陌生类时先看 `__init__`，几秒钟就能建立对象的字段画像。

### 2. 与其他语言的区别（Java/C++）

| 维度 | Python | Java | C++ |
|---|---|---|---|
| 类的创建 | `class` 是运行时可执行语句 | 编译期声明 + 字节码类文件 | 编译期声明 |
| 类的本质 | 带 `__dict__`/`__class__`/`__bases__` 的运行时对象 | 元数据对象（java.lang.Class） | 无运行时实体（除 RTTI 表） |
| 实例属性声明 | 无需声明，运行时赋值即创建 | 必须预声明字段 | 必须预声明成员 |
| self/this | 显式 `self`，位置即语义 | 隐式 `this` 指针 | 隐式 `this` |
| 方法定义 | 类体内的普通 `def`（本质是函数赋值） | 专用方法语法 + 可见性修饰符 | 专用成员函数语法 |
| 继承搜索 | 运行期逐层字典查找 | 编译期解析 + 虚表（vtable）分派 | 编译期解析 + 虚表分派 |
| 运算符重载 | 通过特殊命名方法（`__add__` 等），可选 | 不支持 | 通过 `operator+` 成员/友元函数 |
| 对象唯一性控制 | 无（多继承默认允许，菱形用 MRO 解） | 单继承（类）+ 多接口 | 多继承（菱形需虚继承） |

**核心洞察**：Python 把"类"彻底降格为普通数据对象（字典+链接），因此动态性（运行时加属性、函数变方法、运行时改类）是免费的；Java/C++ 为了编译期类型安全，付出了类系统僵硬、运行期不可改的代价。这也是为什么 Python 框架能玩出"动态注册方法"等魔术而 Java 需要依赖反射框架。

### 3. Python 发展历史背景

- **Python 1.0（1994）**：Guido 借鉴 Smalltalk 与 C++ 设计出 Python 的类模型，但坚持两条自己的原则：**一切属性可动态添加**（Smalltalk 的做法），**self 显式**（独此一家，理由是"名字意义更明显、函数可独立于类存在"）。
- **classic classes → new-style classes（2000-2008）**：Python 2.2 引入"新式类"（继承 `object`），统一了类型与类的模型；Python 3 中只有新式类——本章 `rec.__bases__` 显示 `<class 'object'>` 正是这个历史演进的遗迹。
- **为什么 `__init__` 不叫 `constructor`**：Python 的设计者刻意区分"构造"（`__new__`，分配）与"初始化"（`__init__`，填充状态）——这是为了支持不可变对象等高级用法，也解释了为什么语言文档从不说 `__init__` 分配内存。
- **现代演进**：`dataclasses`（3.7）、`typing` 的 `NamedTuple` 等工具把本章"手工填属性"的模式自动化，但底层机制一字未变——理解本章，你就理解了现代 Python 框架的砖石。

### 4. 高级开发者需要掌握的相关知识

- **描述符协议（descriptor protocol）**：方法绑定只是描述符 `__get__` 的一个应用；`property`、`classmethod`、`staticmethod`、`slots` 全是描述符。第 38 章详细展开，这是从"会用"到"懂 Python 对象模型"的必经之路。
- **元类（metaclass）**：`type` 是类的类——"class 语句执行时发生了什么"的最终答案。第 40 章才讲，但知道"类对象由 `type` 创建"已足以解释本章所有现象。
- **MRO 与 C3 线性化**：多继承时 `__bases__` 不再只有一个元素，查找顺序由 `type(obj).mro()` 决定。第 31 章内容，遇到"菱形继承"前先了解概念即可。
- **特殊方法查找的"类型层"特性**：`__add__`、`__str__` 等特殊方法是通过**类型**查找的（不走实例字典）——这意味着 `x.__add__ = ...` 这样给实例挂特殊方法无效。这是高级调试中常踩的暗坑。
- **`__slots__`**：用固定属性名换取内存与访问速度，但会改变对象的动态性。第 32 章覆盖。
- **序列化与持久化**：`pickle` 能存类实例，靠的正是"实例 = `__dict__` + `__class__`"这个结构——本章 27.12 节的引擎盖视角是理解它的直接前提。
