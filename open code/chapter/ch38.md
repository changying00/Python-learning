> 不过，对于工具构建者来说，管理属性访问可能是设计灵活 API 的重要组成部分。此外，理解本章的 descriptor（描述符）模型，会让 `__slots__` 和 `property` 等相关工具变得更具体；如果你正在使用的代码中出现了描述符，这些内容甚至可能是必读内容。

#### Why Manage Attributes?（为什么管理属性？）

> 对大多数 Python 程序来说，对象属性是核心组成部分；我们经常把脚本正在处理的实体信息存放在属性中。通常，属性只是对象的名字。例如，一个人的 `name` 属性可能只是一个字符串，可以用普通的属性语法读取和设置：`person.name` 用于读取属性值，`person.name = value` 用于修改属性值。
>
> 多数情况下，属性要么直接存放在对象中，要么从对象所属的类继承而来。这个基本模型足以应付 Python 生涯中编写的大多数程序。
>
> 但有时需要更大的灵活性。假设程序原本直接使用 `name` 属性，后来需求改变了：读取名字时要校验，或者要通过程序逻辑转换名字。我们当然可以编写方法来管理访问，例如用 `getName` 读取、用 `setName` 设置；这里的 `valid` 和 `transform` 只是抽象的假设函数。问题是，程序中所有使用名字的地方都必须改写，这可能是一项不小的工作。调用者还必须知道数据究竟以普通属性还是方法的形式导出。
>
> 这种问题比想象中更常见。类似电子表格的程序中，一个单元格的值可能最初只是离散数据，后来变成任意计算。如果对象接口要支持这种演进而不破坏现有代码，那么事后再把属性改成方法并不理想。

#### Inserting Code to Run on Attribute Access（在属性访问时插入代码）

> 更好的方案是：在需要时，让读取属性自动运行代码。这正是 managed attribute（受管属性）的主要作用之一，它允许我们在接口已经存在之后再加入属性访问器逻辑。更一般地说，它支持超出简单数据存储的各种属性使用方式。
>
> 本章集中讨论四种属性访问技术：
>
> 1. 内置的 `property`，为某个特定属性指定访问方法。
> 2. 描述符的 `__get__` 和 `__set__` 方法，处理某个特定属性的访问，也是 `property`、`__slots__` 等工具的基础。
> 3. `__getattr__` 和 `__setattr__` 方法，处理未定义属性的读取和所有属性赋值。
> 4. `__getattribute__` 方法，处理所有属性读取。
>
> 前面章节已经简要介绍过这些工具。本章会比较它们的共同目标和重要差异。后两种技术可以用于 delegation（委托）式 proxy（代理）类，把任意属性转发给被包装对象；前两种通常针对某一个明确的属性。四种方案在复杂度、表达方式和美观性上也不同，需要通过实际代码来判断取舍。
>
> 本章还会使用比前面更大的程序示例。结尾的 `CardHolder` 案例可以作为研究较大类的自学例子。下一章还会使用这里介绍的一些技术来编写 decorators（装饰器），因此在继续学习前，至少应对本章主题有总体认识。

### 深度理解

- **核心概念**：属性语法是稳定的对象接口。受管属性把“读取、赋值、删除时是否执行额外逻辑”从调用者代码中移到类的实现中，因此可以在不改变 `person.name` 这种调用形式的情况下加入校验、转换或计算。
- **底层实现**：`obj.attr` 最终会进入对象的属性查找协议，而不只是无条件读取 `obj.__dict__`。类属性、实例属性、描述符以及 `__getattribute__` 等机制都可能参与这个过程；`__getattr__` 只是在普通查找失败后作为后备入口运行。
- **设计原因**：Python 允许同一种点号语法既表示普通存储又表示动态计算，目的是让实现可以演进而不迫使所有客户端改成方法调用。这是“接口保持简单、实现可以替换”的封装方式。
- **实际问题**：数据校验、格式规范化、延迟计算、访问日志、代理对象和兼容旧 API 都会遇到属性管理需求。但拦截逻辑会增加调用路径和调试难度，应该只管理真正需要管理的属性。
- **初学者误区**：不要把四种技术当成同义词，也不要一开始就用 `__getattribute__` 拦截整个对象。单个属性通常优先考虑 `property`；需要复用协议或保存描述符状态时再考虑 descriptor；通用代理才适合 `__getattr__` 等全局拦截器。

### 代码分析

```python
# 这是原文用来说明接口变化问题的概念性代码；valid 和 transform 是假设函数。
class Person:
    def getName(self):
        if not valid():
            raise TypeError('cannot fetch name')
        return self.name.transform()

    def setName(self, value):
        if not valid(value):
            raise TypeError('cannot change name')
        self.name = transform(value)


person = Person()
person.getName()       # 方法式读取
person.setName('value')  # 方法式写入
```

- 解释器执行 `person.getName()` 时，先查找 `getName`，再把 `person` 作为隐式的第一个参数传给函数；这会把原本简单的 `person.name` 接口变成调用者必须了解的方法接口。
- 受管属性的目标是保留 `person.name` 和 `person.name = value` 的外部形式，把校验和转换放在类内部。后文的 `property` 和 descriptor 都是对这一目标的不同实现。
- 这段代码不是可直接运行的完整程序，`valid`、`transform` 和示例中的 `name` 行为是原文为了说明接口问题而使用的假设内容，不能把它当成最终实现。

### 中文翻译

#### Properties（属性）

> `property` 协议允许我们把某个具体属性的读取、赋值和删除操作路由到自己提供的函数或方法中，因此可以在属性访问时自动运行代码、拦截属性删除，并在需要时为属性提供文档。
>
> `property` 是内置函数，返回的 property object（属性对象）像方法函数一样被赋给类属性，所以它会像其他类属性一样被子类和实例继承。访问器会接收被访问实例作为 `self`，因此可以读取该实例的状态和类属性。
>
> 一个 property 只管理一个明确的属性，不能通用地捕获所有属性访问；但它可以同时控制读取和赋值，让属性从简单数据变成动态计算，而不改变调用者的代码形式。property 与 descriptor 密切相关，实际上它是受限的描述符。

#### The Basics（基础）

> property 通过把内置函数的结果赋给类属性来创建：`attribute = property(fget, fset, fdel, doc)`。四个参数都可以省略，默认值都是 `None`。前三个参数为 `None` 时，对应的读取、赋值或删除操作不受支持，尝试执行会自动引发 `AttributeError`。
>
> `fget` 用于拦截读取，`fset` 用于拦截赋值，`fdel` 用于拦截删除。它们可以是任何可调用对象，包括类方法，并且第一个参数要接收被访问的实例。调用时，`fget` 返回计算出的属性值，`fset` 和 `fdel` 通常返回 `None`；三者都可以通过抛出异常拒绝访问。`doc` 是属性的文档字符串；如果省略，property 会复制 `fget` 的文档字符串。
>
> `property(...)` 返回的对象被放在定义该属性的类命名空间中，并由所有实例继承。无论使用显式赋值还是装饰器语法，之后对该属性的访问都会自动调用相应处理函数。

#### A First Example（第一个示例）

> `prop-person.py` 使用 property 跟踪名为 `name` 的属性访问。真正存放数据的名字是 `_name`，这样不会与 property 本身冲突。读取 `sue.name` 会运行 getter，赋值会运行 setter，删除会运行 deleter；另一个 `bob` 实例以及 `Person` 的子类也会继承同一个 property。
>
> 示例输出依次显示 `fetch...`、`change...`、`remove...`，并打印两个实例的名字和 `name property docs`。把 property 放到父类 `Super` 中、让 `Person(Super)` 继承它时，输出不变。property 和普通方法一样遵循继承规则，同时因为访问器收到 `self`，可以访问不同继承深度实例的状态。

#### Computed Attributes（计算属性）

> property 不只是记录访问，还可以在每次读取时动态计算属性值。`PropSquare` 把基础值存放在实例的 `value` 中，把 `X` 定义为 property；读取 `P.X` 会返回 `P.value ** 2`，写入 `P.X` 则修改 `P.value`。因此 `P` 从 3 改为 4 后得到 9、16，而另一个实例 `Q` 仍依据自己的 32 计算出 1024。
>
> property 访问器会自动收到 `self`，所以 getter 能使用发起访问的那个实例的状态。外部看起来像读取数据，内部实际上隐含了一次方法调用。

#### Coding Properties with Decorators（用装饰器编写属性）

> 装饰器语法 `@decorator` 等价于先定义函数、再执行 `func = decorator(func)` 并把名字重新绑定到返回值。因此 `@property` 等价于先定义 `name`，再执行 `name = property(name)`。这只是创建 property 的另一种写法。

#### Setter and deleter decorators（setter 和 deleter 装饰器）

> property 对象还提供 `getter`、`setter` 和 `deleter` 方法。它们会把相应访问器添加到 property，并返回 property 的一个副本。通常 getter 和文档在创建 property 时已经填写，随后可以用 `@name.setter` 和 `@name.deleter` 为同一个属性补充赋值、删除逻辑。
>
> `prop-person-deco.py` 与显式调用 `property(getName, setName, delName, ...)` 的版本行为相同：读取运行 getter，赋值运行 setter，删除运行 deleter，类和实例都能继承 property。两种写法的选择主要是风格问题；装饰器形式通常把同名的三种访问逻辑放在一起，更容易看出它们属于同一个属性。

### 深度理解

- **核心概念**：`property` 是类级别的属性对象，用访问器把点号读取、赋值和删除分别映射到函数。外部看到的是 `obj.name`，内部可以是存储、校验、格式化或实时计算。
- **底层实现**：类体执行结束时，`property(...)` 的结果被放进类的命名空间。读取 `obj.name` 时，属性查找发现这个对象实现了描述符协议并调用它的 `__get__`；赋值和删除分别进入 `__set__`、`__delete__`。访问器的 `self` 是客户端实例，而不是 property 对象本身。
- **设计原因**：property 让类可以先以公开数据属性发布 API，后来再加入校验或计算，而不要求调用方从 `obj.name` 改成 `obj.get_name()`。它把常见的单属性需求封装成标准库对象，使用成本低于手写描述符。
- **实际问题**：setter 应该验证输入并保持对象不变量，getter 不宜隐藏昂贵的网络或数据库副作用；存储字段通常使用 `_name` 等不同名字，否则 getter 读取 `self.name` 会再次触发自身。只提供 getter 时可以形成只读属性，尝试赋值会抛出 `AttributeError`。
- **初学者误区**：`@property` 不会把值缓存到属性名本身；它仍然是每次读取都可能执行的代码。`@name.setter` 中再次写 `def name` 不是覆盖 getter，而是返回一个包含原 getter 和新 setter 的 property 副本并重新绑定名字。装饰器的重点是 property 的重绑定，不是 `functools.wraps`（后者属于通用函数装饰器的另一个问题）。

### 代码分析

```python
class Person:
    def __init__(self, name):
        self._name = name  # 真实数据放在不同的实例属性中

    @property
    def name(self):
        print('fetch...')
        return self._name

    @name.setter
    def name(self, value):
        print('change...')
        self._name = value

    @name.deleter
    def name(self):
        print('remove...')
        del self._name


sue = Person('Sue Jones')
print(sue.name)          # 调用 property 的 getter
sue.name = 'Susan Jones'  # 调用 setter
del sue.name             # 调用 deleter
```

- 创建 `Person` 类时，类体先创建三个函数。执行 `@property` 后，第一次 `name` 被绑定为 property 对象；`@name.setter` 取出这个对象，生成带 setter 的副本并再次绑定 `name`；`@name.deleter` 做同样的事情。因此类创建结束时，`Person.__dict__['name']` 是 property，而不是最后一个普通函数。
- `sue.name` 的读取由属性查找协议调用 property 的 getter，并传入 `sue`。`sue.name = ...` 不会把名为 `name` 的键直接写入 `sue.__dict__`，而是进入 property 的 setter；setter 再把值写入 `_name`，从而避免递归。
- property 的访问器可以是普通函数、静态可调用对象或方法，但它们必须符合相应的参数约定。类级访问 `Person.name` 会返回 property 对象本身，这也是查看 `__doc__` 的原因。

> operator-overloading

> self

> generic

> narrowly focused

> The Basics

> These methods are generally

> self

> all

> object
>  class is always a superclass to every class,

>  def __getattribute__(self, name):

> self
>  attribute assignments 
> anywhere
>  in a class defining this method

> __setattr__

> __setattr__
>  itself. To work around this problem, you
> can assign the attribute as a key in the instance’s 
> __dict__
>  namespace

>  def __setattr__(self, name, value):

> __setattr__

> higher superclass to avoid looping, just like 
> __getattribute__

> scheme is sometimes preferred when wrapped classes use 
> slots

> __dict__

>  def __setattr__(self, name, value):

### 中文翻译

#### Descriptors（描述符）

> `descriptor（描述符）` 提供了另一种拦截属性访问的方式，并且和上一节的 `property` 紧密相关。严格说，`property` 本身就是一种描述符。`property` 只是描述符的一种简化写法，它把方法函数绑定到属性访问上；而描述符是 Python 中许多类工具的底层实现机制，包括 `property` 和 `__slots__`。
>
> 从功能上说，描述符协议允许我们把某个属性的读取、赋值和删除操作路由到一个单独类的实例方法中。因此，我们可以在属性读取和赋值时自动插入代码，拦截删除操作，并在需要时提供属性文档。
>
> 描述符是独立的类，并像方法函数一样被赋给类属性。它们同样会被子类和实例继承。描述符的访问方法会同时收到描述符实例自身的 `self`，以及持有这个描述符的客户端类实例。因为这样，描述符既可以保存自己的状态，也可以使用被管理对象的状态；它既能调用客户端类中的方法，也能调用自己定义的专用方法。
>
> 和 `property` 一样，描述符也只管理某一个具体属性；它不能通吃所有属性访问，但能对某个属性的读取和赋值进行完整控制，并允许我们把一个属性从简单数据自由改造成计算结果，而不破坏已有代码。区别在于，描述符更一般：它本身就是一个类，因此可以保存状态、参与继承层次、通过组合聚合对象，还可以自然地定义内部方法和文档字符串。

#### The Basics（基础）

> 描述符通常写成独立类，并为自己希望拦截的属性访问操作提供特定名字的方法。描述符类中的 `__get__`、`__set__` 和 `__delete__` 会在相应的属性访问发生时自动运行。
>
> 如果这些方法中的某个缺失，通常就表示这种访问不受支持。和 `property` 不同的是，描述符如果省略 `__set__`，它的名字仍然可能在实例中被赋值并重新定义，从而把描述符“遮住”；所以要做成真正只读，必须显式定义 `__set__` 并在里面抛出异常。
>
> 带有 `__set__` 的描述符在继承方面还有特殊语义，本章先不展开，后面在元类和完整继承模型中再讨论。简单说，带 `__set__` 的描述符称为 data descriptor（数据描述符），它的优先级高于通常的名字查找结果。比如，`__class__` 这个继承来的描述符会覆盖实例命名空间中的同名键；这也意味着你自己写的数据描述符同样会优先于实例字典中的同名属性。

### 代码分析

```python
class Descriptor:
    "文档字符串写在这里"

    def __get__(self, instance, owner):
        ...

    def __set__(self, instance, value):
        ...

    def __delete__(self, instance):
        ...
```

- 解释器在类体执行结束后才真正把 `Descriptor()` 放进另一个类的类属性里。只要这个实例对象出现在类命名空间中，属性查找就会识别出它是描述符，并在读取、写入、删除时分别调用对应方法。
- `__get__` 的两个参数里，`instance` 是通过哪个实例访问的，`owner` 是这个描述符挂在哪个类上。`instance is None` 时，说明是通过类本身访问，比如 `Class.attr`。
- `__set__` 和 `__delete__` 只负责拦截，不负责存储策略本身；真正的存储位置可以是描述符自己，也可以是客户端实例。

#### Descriptor method arguments（描述符方法参数）

> 三个描述符方法都接收描述符实例本身 `self`，以及被挂载到的客户端类实例 `instance`。`__get__` 还额外接收 `owner`，也就是描述符所附着的类。
>
> `instance` 要么是通过实例访问属性的那个对象，要么在通过类访问时是 `None`。前者通常返回计算结果，后者通常在支持类级访问时返回描述符对象本身。
>
> 下面这个 REPL 例子说明了这一点：当 `X.attr` 被读取时，Python 自动运行 `Subject.attr` 上的描述符实例的 `__get__`，并把描述符对象、`X` 实例和 `Subject` 类传进去。

### 代码分析

```python
class Descriptor:
    def __get__(self, instance, owner):
        print(self, instance, owner, sep='\n')


class Subject:
    attr = Descriptor()  # 描述符实例作为类属性


X = Subject()
X.attr
Subject.attr
```

- `X.attr` 会触发 `Descriptor.__get__(Subject.attr, X, Subject)` 这一类的调用路径，虽然这里的 `Subject.attr` 在展示时已经是“取出的描述符对象”，不会再次递归进入同一个协议。
- 通过实例访问时，`instance` 是 `X`；通过类访问时，`instance` 变成 `None`。这就是为什么很多描述符会在 `instance is None` 时返回自己，方便查看文档或调试。

#### Read-only descriptors（只读描述符）

> 只省略 `__set__` 并不足以让描述符真正只读，因为实例仍然可以直接在自己的命名空间里放入同名键，从而把类属性中的描述符遮住。下面例子里，`X.a = 99` 并不是修改描述符，而是在 `X` 上创建了实例属性 `a`。
>
> 如果要让描述符属性真正不可写，就必须在描述符类里定义 `__set__`，在赋值时主动抛出异常。这样，当属性名本身是描述符时，Python 会把赋值请求路由到描述符对象，而不是写进实例字典。

### 代码分析

```python
class D:
    def __get__(*args):
        print('get')


class C:
    a = D()  # a 是一个描述符实例


X = C()
X.a
C.a
X.a = 99
X.a
list(X.__dict__.keys())
```

- 先读取 `X.a` 时，查找结果命中类属性 `a` 上的描述符，因此执行 `D.__get__`。但一旦执行 `X.a = 99`，普通实例赋值规则会在 `X.__dict__` 里写入键 `a`，从而把类上的描述符遮住。
- 这说明“没有 `__set__`”不等于“只读”。真正只读要靠 `__set__` 拦截并抛错，否则实例可以自由覆盖同名属性。

#### NOTE：The deletion trio（删除三件套）

> 不要把描述符的 `__delete__` 和一般对象的 `__del__` 混淆。前者在尝试删除受管属性名时调用，后者是对象即将被垃圾回收时运行的实例析构方法。`__delete__` 更接近我们后面要讲的 `__delattr__`，而不是 `__del__`。

#### A First Example（第一个示例）

> 这里沿用 `property` 一节的第一个例子，不过改成用描述符来拦截名为 `name` 的属性访问。`Name` 类的 `__get__`、`__set__` 和 `__delete__` 都把实际数据放在客户端实例的 `_name` 中。
>
> 关键点有两个：第一，描述符对象必须作为客户端类的类属性来赋值，放到实例属性里不会按描述符协议工作；第二，`__get__` 会收到 `self`、`instance` 和 `owner` 三个对象，分别代表描述符实例、`Person` 实例和 `Person` 类。
>
> 示例输出和 `property` 版本完全一致，因此描述符在语义上可以替代 property，只是写法更通用。

### 代码分析

```python
class Name:
    'name descriptor docs'

    def __get__(self, instance, owner):
        print('fetch...')
        return instance._name

    def __set__(self, instance, value):
        print('change...')
        instance._name = value

    def __delete__(self, instance):
        print('remove...')
        del instance._name


class Person:
    def __init__(self, name):
        self._name = name
    name = Name()  # 把描述符实例放进类属性
```

- `sue.name` 读取时走 `Name.__get__`，而不是直接读 `sue.__dict__['name']`。赋值和删除也是一样，都会回到描述符方法。
- 因为 `_name` 真正保存在实例里，所以每个 `Person` 实例有自己的状态；描述符只是一个共享的访问入口。

#### Computed Attributes（计算属性）

> 描述符同样可以在读取时动态计算值。`DescSquare` 把基础数据放在描述符对象自己的 `value` 中，每次读取时返回平方值；写入时则修改这个描述符状态。`Client1` 和 `Client2` 的 `X` 看起来像普通属性，实际上都由描述符对象接管。
>
> 这和 `property` 的计算属性行为一致，但底层对象不是 property，而是一个完整的类实例。

### 代码分析

```python
class DescSquare:
    def __init__(self, start):
        self.value = start  # 每个描述符实例保存自己的状态

    def __get__(self, instance, owner):
        return self.value ** 2

    def __set__(self, instance, value):
        self.value = value


class Client1:
    X = DescSquare(3)


class Client2:
    X = DescSquare(32)
```

- 这里的状态存在描述符对象里，所以 `Client1.X` 和 `Client2.X` 各自对应不同的描述符实例，彼此互不影响。
- 读取 `c1.X` 时，解释器先在类中找到 `X`，再调用 `DescSquare.__get__`。写入 `c1.X = 4` 会调用 `__set__`，改的是描述符内部的 `value`。

#### Using State Information in Descriptors（在描述符中使用状态信息）

> 前两个例子把信息放在不同位置：`name` 示例依赖客户端实例上的数据，而平方示例依赖描述符对象自身的数据。实际上，描述符可以同时使用这两种状态中的任意一种，或者混合使用。
>
> 描述符状态是“每个描述符一份”的数据，适合存放描述符内部实现细节，或者需要被同一类所有实例共享的信息。客户端实例状态则是“每个对象一份”的数据，适合存放业务数据。选错位置就会出问题：员工姓名这类字段应该放在实例上，而不该放在描述符上；描述符实现细节也不应该散落到每个实例里。
>
> `DescState` 例子把 `value` 存在描述符对象里，因此两个客户端实例会共享同一个值。`InstState` 则把 `_X` 放在客户端实例里，因此每个对象的 `X` 都可以不同。最后的 `DescBoth` 同时用到了两种状态：描述符自己的 `data` 和实例自己的 `data`。
>
> 这里还顺带提醒了 `dir()` 和 `getattr()` 的区别：`managed` 这样的属性名虽然没有出现在实例字典里，仍然能通过 `dir()` 看到，因为它是类属性上的描述符。`__getattr__` 和 `__getattribute__` 这类更通用的拦截器没有类级属性名可注册，所以默认不会出现在 `dir()` 结果中。

### 代码分析

```python
class DescState:
    def __init__(self, value):
        self.value = value

    def __get__(self, instance, owner):
        print('DescState get')
        return self.value * 10

    def __set__(self, instance, value):
        print('DescState set')
        self.value = value
```

- 这个版本的关键点是“共享”：`self.value` 属于描述符对象，所以所有使用同一个 `DescState()` 的客户端实例都会读写同一份值。
- 这在需要全局状态、缓存或者类级计数时有用，但如果想给每个对象保存独立数据，就会把不同实例互相污染。

```python
class InstState:
    def __get__(self, instance, owner):
        print('InstState get')
        return instance._X * 10

    def __set__(self, instance, value):
        print('InstState set')
        instance._X = value
```

- 这里的状态放在客户端实例里，所以每个对象的 `X` 可以独立变化。解释器每次访问 `obj.X` 时，都会把当前实例传给 `__get__`。
- 这也是描述符比 property 更灵活的地方：描述符既可以做共享状态，也可以做每实例状态。

#### How Properties and Descriptors Relate（property 与描述符的关系）

> `property` 本质上就是一个简化版描述符。`Property` 类示例说明了这一点：它把 `fget`、`fset` 和 `fdel` 存在描述符状态中，再在 `__get__`、`__set__`、`__delete__` 中转发给这些函数。
>
> 这段实现只覆盖了基本的 property 用法，但已经足够说明 Python 的 `property()` 为什么只是语法和封装上的便利，而不是一种全新的底层机制。若要支持 `@x.setter` 和 `@x.deleter`，还需要给 `Property` 补上返回副本的 `setter` 和 `deleter` 方法；标准库里的 `property` 已经做了这件事。

### 代码分析

```python
class Property:
    def __init__(self, fget=None, fset=None, fdel=None, doc=None):
        self.fget = fget
        self.fset = fset
        self.fdel = fdel
        self.__doc__ = doc

    def __get__(self, instance, instancetype=None):
        if instance is None:
            return self
        if self.fget is None:
            raise AttributeError("can't get attribute")
        return self.fget(instance)
```

- `property` 之所以能像函数装饰器一样工作，本质上是因为它也是一个描述符对象。读取时把实例传给 `fget`，赋值和删除时分别调用 `fset` 和 `fdel`。
- `instance is None` 时返回自身，方便通过类访问文档和对象本体。这也是 `Person.name.__doc__` 能工作的原因。

#### Descriptors and slots and more（描述符与 slots 等）

> 现在应该可以大致理解 `__slots__` 的实现思路了：它通过创建类级描述符，把槽名访问映射到实例内部的顺序存储空间，而不是把属性放进实例字典。与显式调用 `property()` 不同，`__slots__` 的大部分魔法是在类创建阶段自动完成的。
>
> `slots` 本章不建议日常使用，除非是极端场景。描述符还会被 Python 用在其他类工具中，这里不展开内部实现，想深入可看官方文档和开源源码。

#### NOTE：Descriptor cliff-hangers（描述符伏笔）

> 下一章会用描述符实现同时适用于函数和方法的装饰器，也会用描述符拦截内置操作的方法查找。再下一章会把数据描述符的优先级放进完整继承模型里讨论。这里先记住一点：带 `__set__` 的描述符很“强势”，它不能被实例字典里的同名键轻易遮住。

### 深度理解

- **核心概念**：描述符是“对象上的对象”。它把属性访问变成了一个可编程协议，所以同一个属性名可以既像数据，又像计算入口，还能保存自己的状态。
- **底层实现**：属性查找时，Python 会先检查类层面的描述符协议，再决定是否读取实例字典。带 `__set__` 的数据描述符优先级高，普通描述符则可能被实例同名属性遮住。
- **设计原因**：把属性行为抽成协议，而不是硬编码成 `property` 这种单一形式，可以让框架复用同一套机制实现字段验证、ORM 列映射、延迟加载和 `slots`。
- **实际问题**：最常见的错误是把共享状态和每实例状态放错位置，结果出现“一个对象改动，另一个对象跟着变”的问题。另一个常见坑是误以为省略 `__set__` 就等于只读，实际上实例还能自己覆盖同名键。
- **初学者误区**：不要把描述符看成“更高级的 property”，它们是同一协议的不同层次。真正的差别不只是语法，而是状态位置、继承语义和复用能力。

### 中文翻译

#### __getattr__ and __getattribute__（属性读取拦截器）

> `__getattr__` 和 `__getattribute__` 是拦截实例属性读取的另外两种方式。`__getattr__` 只在普通查找找不到属性时运行；`__getattribute__` 则在每次显式读取属性时运行。后者覆盖范围更大，但必须通过父类实现来避免递归。
>
> 这两个方法通常和 `__setattr__`、`__delattr__` 一起讨论。它们都属于 Python 的 operator-overloading（运算符重载）协议，是类中的特殊方法，会在实例执行对应操作时自动调用。它们能访问宿主类的实例状态和其他方法。
>
> 与 property 和描述符相比，这些方法更通用：它们可以处理任意名字，特别适合 delegation（委托）和 proxy（代理）对象，把属性访问转发给内部对象。但它们默认只拦截读取；要拦截赋值必须额外实现 `__setattr__`，要拦截删除则实现 `__delattr__`。

#### The Basics（基础）

> 四个方法的基本形式如下：`__getattr__(self, name)` 处理未定义属性读取，`__getattribute__(self, name)` 处理所有属性读取，`__setattr__(self, name, value)` 处理所有赋值，`__delattr__(self, name)` 处理所有删除。两个读取方法通常返回属性值，另两个通常返回 `None`；所有方法都可以通过抛出异常拒绝操作。
>
> `Catcher` 示例用 `__getattr__` 打印未定义属性名，用 `__setattr__` 打印每次赋值。将 `__getattr__` 换成 `__getattribute__` 在这个小例子里输出相似，但后者会捕获更多读取，并且更容易出现自递归。

### 代码分析

```python
class Catcher:
    def __getattr__(self, name):
        print('Get:', name)  # 只在普通查找失败后运行

    def __setattr__(self, name, value):
        print('Set:', name, value)  # 每次实例赋值都运行


X = Catcher()
X.job
X.pay
X.pay = 'bread'
```

- `X.job` 先经过正常实例、类和继承链查找；查找失败后才调用 `__getattr__`。因此一个已经存在的 `job` 不会进入这个方法。
- `X.pay = 'bread'` 没有“先查找再赋值”的后备阶段，而是直接调用 `__setattr__`。如果方法不把值写进实例字典，赋值实际上就不会保存。

#### Delegation with `__getattr__`（用 `__getattr__` 实现委托）

> `Wrapper` 示例把一个列表保存为 `wrapped`，并在 `__getattr__` 中调用 `getattr(self.wrapped, attrname)`。当代理自身没有 `append` 属性时，读取被转发给内部列表，所以 `X.append(4)` 能修改被包装的列表。
>
> 这种通用转发不需要为内部对象的每个属性编写一个 property 或描述符；代价是拦截器会增加调用路径，而且某些内置操作不会走这条路径，后文会专门说明。

### 代码分析

```python
class Wrapper:
    def __init__(self, obj):
        self.wrapped = obj  # 保存被包装对象

    def __getattr__(self, attrname):
        print('Trace:', attrname)
        return getattr(self.wrapped, attrname)  # 转发未定义属性


X = Wrapper([1, 2, 3])
X.append(4)
```

- 访问 `X.append` 时，`Wrapper` 的实例字典和类中都没有 `append`，于是才调用 `__getattr__`。
- `getattr(self.wrapped, 'append')` 对列表执行正常的属性查找，返回绑定方法；随后 `X.append(4)` 实际调用的是列表的 `append`。
- `wrapped` 本身已经存在，因此在 `__getattr__` 中读取它不会触发同一个 `__getattr__`；如果代理把内部对象也写成一个不存在的属性，就可能再次进入拦截器。

#### Avoiding loops in attribute interception methods（避免属性拦截方法递归）

> 这些方法最复杂的地方是递归。`__getattr__` 只处理未定义属性，所以在里面读取已经存在的属性通常没有问题；但 `__getattribute__` 和 `__setattr__` 处理所有操作，在它们内部直接访问或赋值 `self.xxx` 会再次调用自己。
>
> 为避免 `__getattribute__` 递归，应通过更高的父类实现读取，例如 `object.__getattribute__(self, 'other')`。为避免 `__setattr__` 递归，可以直接操作 `self.__dict__['other']`，或者调用 `object.__setattr__(self, 'other', value)`。如果类使用 `__slots__`，可能没有 `__dict__`，这时应使用父类方法。
>
> `__getattribute__` 中不能用 `self.__dict__` 作为绕过手段，因为读取 `self.__dict__` 本身也会再次进入 `__getattribute__`。`__delattr__` 虽然较少使用，但删除属性时同样要采用字典操作或父类方法来避免循环。

### 代码分析

```python
class Broken:
    def __getattribute__(self, name):
        return self.other  # 再次触发 __getattribute__，形成递归


class Safe:
    def __getattribute__(self, name):
        return object.__getattribute__(self, name)  # 绕过当前实现

    def __setattr__(self, name, value):
        object.__setattr__(self, name, value)  # 绕过当前实现
```

- `object.__getattribute__` 和 `object.__setattr__` 不是魔法变量，而是直接调用基类的默认实现；它们让属性操作跳过当前类覆写的特殊方法。
- 直接写 `self.__dict__` 只适用于确实有实例字典且不需要触发描述符的简单场景。调用 `object.__setattr__` 能保留 slots、property 和其他类级虚拟属性的处理能力。

#### A First Example（第一个示例）

> `getattr-person.py` 用三个通用方法实现和 property、描述符相同的 `name` 管理。`__getattr__` 只在读取未定义的 `name` 时返回 `_name`；`__setattr__` 把写入 `name` 映射到 `_name`；`__delattr__` 对删除操作做同样映射。
>
> 构造函数中的 `self._name = name` 也会触发 `__setattr__`，因为它捕获所有实例赋值。这个例子没有 property 或描述符那样独立的文档对象，受管属性的规则只存在于拦截方法的代码中。

### 代码分析

```python
class Person:
    def __init__(self, name):
        self._name = name  # 这里也会进入 __setattr__

    def __getattr__(self, attr):
        if attr == 'name':
            return self._name  # _name 已存在，不会再次进入 __getattr__
        raise AttributeError(attr)

    def __setattr__(self, attr, value):
        if attr == 'name':
            attr = '_name'
        self.__dict__[attr] = value  # 直接写字典，避免递归
```

- 读取 `person.name` 时，正常查找看不到 `name`，所以进入 `__getattr__`；读取 `_name` 是普通的已定义属性，不会再触发 `__getattr__`。
- 赋值和删除永远先进入 `__setattr__`、`__delattr__`，所以方法必须明确决定最终的存储名字和存储位置。

#### Using `__getattribute__`（使用 `__getattribute__`）

> 把前例中的 `__getattr__` 换成 `__getattribute__` 后，所有读取都会被捕获。示例把 `name` 映射到 `_name`，并用 `object.__getattribute__` 完成真正读取。由于 `__setattr__` 内部通过 `self.__dict__` 写值，读取 `__dict__` 本身还会多触发一次 `__getattribute__`，输出中因此会出现额外的 `get: __dict__`。
>
> 这种实现和 property、描述符版本能得到相同结果，但对只管理一个属性来说有些过度；通用拦截器更适合代理和批量路由，单个属性通常用 property 或描述符更清晰，也少拦截不相关的访问。

#### Computed Attributes（计算属性）

> `AttrSquare` 在实例中保存 `value`，但不保存名为 `X` 的属性。读取 `A.X` 时，因为 `X` 未定义，`__getattr__` 返回 `value ** 2`；赋值 `A.X = 4` 则由 `__setattr__` 把名字改成 `value` 并写入实例字典。两个实例分别使用自己的状态，因此输出是 9、16、1024。

### 代码分析

```python
class AttrSquare:
    def __init__(self, start):
        self.value = start  # 触发 __setattr__

    def __getattr__(self, attr):
        if attr == 'X':
            return self.value ** 2
        raise AttributeError(attr)

    def __setattr__(self, attr, value):
        if attr == 'X':
            attr = 'value'
        self.__dict__[attr] = value
```

- `__getattr__` 版本读取 `self.value` 时不会再进入 `__getattr__`，因为 `value` 已经存在；这也是它比 `__getattribute__` 简单的原因。
- `__getattribute__` 版本如果在 `if attr == 'X'` 分支里直接写 `self.value`，会再次调用 `__getattribute__`。虽然可以这样写，但会多一次拦截；用 `object.__getattribute__(self, 'value')` 能避免额外递归。

#### Using `__getattribute__`（使用 `__getattribute__`）

> `getattribute-computed.py` 用 `__getattribute__` 代替前一个示例中的 `__getattr__`，并用 `object.__setattr__` 代替直接写 `__dict__`。因为 `__getattribute__` 捕获所有读取，分支中的 `self.value` 会再次触发它；如果改成通过父类读取 `value`，仍然需要一次标准实现调用，但不会再产生额外的递归入口。

### 代码分析

```python
class AttrSquare:
    def __getattribute__(self, attr):
        if attr == 'X':
            return object.__getattribute__(self, 'value') ** 2
        return object.__getattribute__(self, attr)

    def __setattr__(self, attr, value):
        if attr == 'X':
            attr = 'value'
        object.__setattr__(self, attr, value)
```

- 解释器读取 `X` 时先进入 `__getattribute__`；通过 `object.__getattribute__` 读取 `value` 后直接得到实例状态，不会再次回到当前覆写方法。
- 这说明“调用父类实现”并不是完全没有成本，而是用一次明确的标准查找替代了不受控的重复拦截。

#### `__getattr__` and `__getattribute__` Compared（两者比较）

> `GetAttr` 同时展示了三种来源的属性：`attr1` 来自类，`attr2` 来自实例，`attr3` 是动态计算的虚拟属性。因为 `attr1` 和 `attr2` 已经被普通查找找到，`__getattr__` 只会为 `attr3` 打印日志。
>
> `GetAttribute` 则对三个读取都打印日志，再把未管理的名字交给 `object.__getattribute__`。因此它能捕获更多访问，但必须承担父类转发和递归规避的成本。若属性本来就没有物理存储，两种方式可以实现相近效果。

### 代码分析

```python
class GetAttribute:
    attr1 = 1

    def __init__(self):
        self.attr2 = 2

    def __getattribute__(self, attr):
        print('get:', attr)
        if attr == 'attr3':
            return 3
        return object.__getattribute__(self, attr)
```

- `object.__getattribute__` 会继续执行标准的描述符、实例字典和类继承链查找，所以未管理的属性仍保持正常语义。
- 对 `GetAttr` 来说，只有标准查找失败后才调用 `__getattr__`；对 `GetAttribute` 来说，每个显式点号读取都先经过覆写方法。

#### Management Techniques Compared（四种管理技术比较）

> 原文随后用四个 `Powers` 实现比较同一个任务：property、描述符、`__getattr__` 和 `__getattribute__` 都把 `square` 和 `cube` 计算出来，并允许修改 `square` 的基础值。property 版本最直接；描述符版本把行为抽成可复用类；`__getattr__` 版本依靠未定义属性触发并配合 `__setattr__`；`__getattribute__` 版本则必须把所有未管理读取转给父类。
>
> REPL 测试通过 `importlib.import_module` 按名字加载四个模块，然后统一创建 `Powers(3, 4)`、读取 `square` 和 `cube`、再把 `square` 改为 5。四个实现都得到 9、64、25，说明相同外部行为可以由不同协议实现。

### 代码分析

```python
class Powers:
    def __getattribute__(self, name):
        if name == 'square':
            return object.__getattribute__(self, '_square') ** 2
        if name == 'cube':
            return object.__getattribute__(self, '_cube') ** 3
        return object.__getattribute__(self, name)

    def __setattr__(self, name, value):
        if name == 'square':
            object.__setattr__(self, '_square', value)
        else:
            object.__setattr__(self, name, value)
```

- 这四种方案的共同模式是“公开名”和“基础状态”分离。区别在于公开名由谁拦截：property 或描述符挂在类属性上，`__getattr__` 等则在实例操作流程中决定路由。
- 选择方案时不能只比较代码行数，还要比较是否需要批量委托、是否需要出现在 `dir()` 中、是否要管理赋值和删除，以及额外拦截的性能和递归风险。

### 深度理解

- **核心概念**：`__getattr__` 是查找失败后的后备钩子，`__getattribute__` 是所有显式属性读取的总入口；`__setattr__` 和 `__delattr__` 分别覆盖所有赋值和删除。
- **底层实现**：点号读取通常先进入 `__getattribute__`，标准实现负责描述符、实例字典和 MRO 查找；只有标准查找抛出未找到错误时，外层机制才会尝试调用 `__getattr__`。父类方法调用是跳过当前覆写的直接路径。
- **设计原因**：通用拦截器让代理对象不必为被包装对象的每个名字生成一个属性访问器，也能按名字实现日志、权限和路由。它牺牲了一部分静态可见性和局部性，换取了通用性。
- **实际问题**：递归、额外调用、缺少 `__dict__`、异常类型不正确和未处理的赋值是最常见的故障。代理类还要考虑特殊方法的隐式查找不会自动走这些拦截器。
- **初学者误区**：`__getattr__` 不是“每次读取都调用”；在 `__getattribute__` 中使用 `self.xxx` 或 `self.__dict__` 不是安全的绕过方式；`__setattr__` 不会自动替你保存值，方法必须显式调用父类或写入命名空间。

#### Intercepting Built-in Operation Attributes（拦截内置操作属性）

> 前文说过，`__getattr__` 会拦截未定义属性，`__getattribute__` 会拦截所有显式属性读取，因此它们很适合实现委托。但这里必须补充一个重要限制：由内置操作隐式触发的特殊方法名，不会自动路由到这两个实例拦截器。
>
> 例如，打印、`+` 表达式和索引操作会隐式查找 `__str__`、`__add__` 和 `__getitem__`。这些名字会直接在类上查找，跳过实例及其实例属性拦截器。因此，代理类不能只依赖 `__getattr__` 或 `__getattribute__` 来通用地转发这些内置操作；如果要支持它们，必须在代理类中自己重定义对应的特殊方法。
>
> 显式读取和隐式操作因此表现不同：`X.__add__` 会通过实例拦截器，但 `X + Y` 使用的特殊方法查找不会通过同一条路径。原文把这看成 Python 3 中与元类和内置操作优化相关的分叉。无论历史原因如何，代理类都必须把这种差异当成接口设计的一部分。

### 代码分析

```python
class GetAttr:
    def __getattr__(self, name):
        print('getattr:', name)
        return lambda *args: None  # 为显式读取提供一个占位可调用对象

    def __len__(self):
        print('__len__: 66')
        return 66


class GetAttribute:
    def __getattribute__(self, name):
        print('getattribute:', name)
        return lambda *args: None

    def __len__(self):
        print('__len__: 66')
        return 66
```

- `len(X)` 会寻找类上的 `__len__`，不会先执行 `X.__getattribute__('__len__')`。因此显式定义的 `__len__` 会直接运行，而没有 `__getitem__`、`__add__` 或 `__call__` 时，相应的内置操作会失败。
- 显式调用 `X.__getitem__(0)` 是普通的点号读取，才会进入 `__getattr__` 或 `__getattribute__` 并取得返回的 lambda；`X[0]` 走的是解释器对特殊方法的隐式查找，不能依赖这个 lambda。
- `object` 提供默认的 `__str__` 和 `__repr__`，所以 `print(X)` 还会受到继承来的默认方法影响。若代理要把打印转给内部对象，必须显式实现 `__str__` 或 `__repr__`。

> 现在可以解释第28章 `Manager` 类为什么必须定义 `__repr__` 来把打印请求路由给包装对象。`object` 默认提供 `__repr__`，而内置的 `print` 会绕过 `__getattr__` 和 `__getattribute__`，所以只写通用属性委托不足以改变打印行为。

#### Example: Attribute Validations（示例：属性验证）

> 结尾的 `CardHolder` 案例用四种管理方案实现同一个对象。它有四个属性，其中三个要在读取或保存时验证、转换或隐藏数据：账号、姓名和年龄；`addr` 保持直接访问；`remain` 是按需计算且只读的虚拟属性。四个版本使用相同的测试代码，并得到相同的外部结果，但内部实现完全不同。
>
> 这个案例的重点不是把所有代码背下来，而是观察同一个对象接口如何分别映射到 property、描述符、`__getattr__` 和 `__getattribute__`，以及状态究竟存在哪里。

#### Using Properties to Validate（使用 property 验证）

> property 版本管理 `name`、`age` 和 `acct`，同时让 `addr` 直接存在于实例中。构造函数里的 `self.acct`、`self.name` 和 `self.age` 赋值也会触发 property setter，所以初始化过程本身就会执行格式转换和校验。
>
> `name` 经过小写化并把空格替换成下划线；`age` 必须在 0 到 150 之间；`acct` 会去掉连字符并检查长度，读取时隐藏最后三位。数据放在 `__name`、`__age` 和 `__acct` 中，避免与 property 名字冲突。双下划线会触发 name mangling（名称改写），例如在 `CardHolder` 方法中会变成包含类名的实例键。
>
> `remain` 没有存储数据，读取时计算 `retireage - age`；只提供 getter，因此尝试赋值会自动引发 `AttributeError`。测试输出显示账号遮罩、姓名规范化、剩余年限计算和三种非法操作的错误信息。

### 代码分析

```python
class CardHolder:
    acctlen = 8
    retireage = 62.5

    def __init__(self, acct, name, age, addr):
        self.acct = acct  # 进入 acct setter
        self.name = name  # 进入 name setter
        self.age = age    # 进入 age setter
        self.addr = addr  # 普通实例属性

    def getName(self):
        return self.__name

    def setName(self, value):
        self.__name = value.lower().replace(' ', '_')

    name = property(getName, setName)

    def remainGet(self):
        return self.retireage - self.age

    remain = property(remainGet)  # 没有 setter，因此只读
```

- 类体执行时，`name` 和 `remain` 被绑定为 property 对象；初始化时对 `self.name` 的赋值进入 setter，而不是在实例字典中直接创建 `name` 键。
- `remainGet` 中的 `self.age` 还会触发 `age` property getter，因此计算属性可以组合其他受管属性，而不是必须直接读其私有存储字段。
- 双下划线只提供名称改写，不是安全边界。它主要避免子类或其他名字意外冲突，不能阻止有意访问者通过改写后的名字读取数据。

#### Using Descriptors to Validate（使用描述符验证）

> 描述符和 property 在功能上相似，都适合管理特定属性；区别是描述符可以保存自己的状态，也可以把一套访问逻辑复用于多个类。

##### Option 1: Validating with shared descriptor-instance state（方案一：使用共享的描述符实例状态）

> 第一个描述符版本把姓名、年龄和账号的实际值保存在 `Name`、`Age` 和 `Acct` 描述符实例自身。这样不必在客户端实例中使用双下划线字段，但这些值实际上是类级共享状态。
>
> `remain` 的描述符必须定义 `__set__` 并抛出异常；否则给 `instance.remain` 赋值时，普通赋值可能在实例字典中创建同名键，遮住类级描述符。这个版本故意展示共享状态的后果，而不是推荐这种业务数据存储方式。

### 代码分析

```python
class Name:
    def __get__(self, instance, owner):
        return self.name  # 状态属于描述符实例

    def __set__(self, instance, value):
        self.name = value.lower().replace(' ', '_')


class CardHolder:
    name = Name()  # 所有 CardHolder 实例共享这一对象
```

- `bob = CardHolder(...)` 和 `sue = CardHolder(...)` 都会调用同一个 `Name` 对象的 `__set__`，第二次写入会覆盖第一次写入。
- `addr` 仍然是客户端实例属性，所以 `bob.addr` 和 `sue.addr` 不会互相覆盖；这正好体现了描述符状态和实例状态的作用域差异。

##### Option 2: Validating with per-client-instance state（方案二：使用每个客户端实例的状态）

> 第二个描述符版本把数据改存到客户端实例上，例如 `instance.__name`、`instance.__age` 和 `instance.__acct`。描述符对象只保留访问逻辑，因此 `bob` 和 `sue` 的受管数据能够独立存在。
>
> 这个版本仍然使用名称改写来避免描述符公开名字和真实存储字段冲突。通过类访问描述符时，`instance` 是 `None`；如果 `__get__` 直接访问 `instance.__name`，就会出现 `NoneType` 错误。原文指出，这种实现本来就依赖客户端实例，单独通过类访问它没有业务意义。
>
> `validate_tester_plus.py` 在创建 `sue` 后再次读取 `bob`，用来确认 `bob` 不会变成 `sue`。这正是方案一和方案二最直观的差别。

### 代码分析

```python
class Name:
    def __get__(self, instance, owner):
        return instance.__name  # 数据属于当前客户端实例

    def __set__(self, instance, value):
        instance.__name = value.lower().replace(' ', '_')


class CardHolder:
    name = Name()
```

- 这里 `Name` 类体中的 `__name` 会被改写为 `_Name__name`，而不是 `_CardHolder__name`。因此通过类访问时，`instance is None` 会导致错误；通过实例访问时，描述符方法能拿到正确对象。
- 描述符本身在所有 `CardHolder` 实例之间共享，但它不保存业务值，所以共享访问逻辑不会造成业务数据共享。

#### Using `__getattr__` to Validate（使用 `__getattr__` 验证）

> `__getattr__` 版本更通用，但需要在运行时检查名字。`name` 和 `age` 经过 `__setattr__` 转换后直接存进实例，因此以后读取它们不会触发 `__getattr__`；`acct` 存成 `_acct`，所以读取公开的 `acct` 时仍会触发 `__getattr__` 并返回遮罩值；`remain` 完全是虚拟属性。
>
> 原文用 `match` 语句按属性名分派逻辑，并在未知名字上抛出 `AttributeError`。`__setattr__` 负责格式化姓名、验证年龄、清理账号、拒绝设置 `remain`，最后通过 `self.__dict__` 保存，避免递归。

### 代码分析

```python
class CardHolder:
    def __getattr__(self, name):
        match name:
            case 'acct':
                return self._acct[:-3] + '***'
            case 'remain':
                return self.retireage - self.age
            case _:
                raise AttributeError(name)

    def __setattr__(self, name, value):
        if name == 'acct':
            name = '_acct'
        self.__dict__[name] = value  # 避免再次调用 __setattr__
```

- 公开的 `acct` 没有实际存储，因此读取时先失败，再进入 `__getattr__`；内部的 `_acct` 已存在，所以不会递归。
- `remain` 的读取也没有实例字典键，进入 `__getattr__` 后再读取 `self.age`。因为 `age` 是已定义实例属性，这个读取不会触发 `__getattr__`。
- 这种方案在设置所有属性时都有一次 `__setattr__` 调用，即使设置的是未管理的 `addr`；它通常比全量 `__getattribute__` 少一些读取成本。

#### Using `__getattribute__` to Validate（使用 `__getattribute__` 验证）

> 最后一个版本让 `__getattribute__` 拦截所有读取，按名字识别 `acct` 和 `remain`，其他名字交给 `object.__getattribute__`。由于所有读取都能被捕获，`acct` 可以直接存成 `acct`，不需要把真实字段改成 `_acct`。
>
> 这个版本沿用前一版本的 `__setattr__`。它对未管理属性的读取和赋值都增加额外调用，因此如果性能是首要目标，可能是四个版本中最重的；但当确实需要全量读取拦截时，它能提供最直接的统一入口。

### 代码分析

```python
class CardHolder:
    def __getattribute__(self, name):
        superget = object.__getattribute__
        if name == 'acct':
            return superget(self, 'acct')[:-3] + '***'
        if name == 'remain':
            return superget(self, 'retireage') - superget(self, 'age')
        return superget(self, name)  # 非受管属性走标准查找

    def __setattr__(self, name, value):
        object.__setattr__(self, name, value)  # 绕过当前类的递归入口
```

- `superget` 保存的是父类实现本身，而不是通过 `self` 再读取一个方法属性；这样不会重新进入当前类的 `__getattribute__`。
- 读取 `remain` 时，`superget(self, 'age')` 仍然会执行标准属性查找和可能存在的描述符，但不会再次进入这个覆写方法。
- 四个版本都能通过测试，是因为它们都实现了相同的外部规则；真正的工程选择取决于属性数量、是否需要复用、状态作用域、可见性和性能。

### 深度理解

- **核心概念**：显式属性读取和内置操作的特殊方法查找是两条不同路径；同一个代理对象可能能转发 `obj.method()`，却不能自动转发 `len(obj)`、`obj + other` 或 `print(obj)`。
- **底层实现**：普通点号访问进入实例属性协议，而 `len`、算术、索引和调用等操作通常直接从对象类型上查找特殊方法。这样可以使用类型级特殊方法槽并保持运算语义稳定，但也绕过了实例级的通用拦截器。
- **设计原因**：特殊方法的类型级查找有利于解释器优化，也避免每次运算都先构造一个实例属性访问流程。代理类若要透明地支持这些操作，只能显式定义或批量生成对应的特殊方法。
- **实际问题**：验证类要保证 setter、descriptor `__set__` 和 `__setattr__` 的异常行为一致；描述符状态放错位置会让不同用户对象互相污染；名称改写只解决命名冲突，不提供真正的安全性。
- **初学者误区**：不要因为 `X.__add__` 能被拦截就以为 `X + Y` 也会被拦截；不要把类级描述符状态当成实例字段；不要用裸 `except` 掩盖验证错误，实际 API 应抛出明确的 `TypeError`、`ValueError` 或 `AttributeError`。

- **设计原因**：property、描述符和通用拦截器彼此有重叠但并不互相取代；不同工具保留不同的可见性、复用性和性能特征。
- **实际问题**：实际排查代理、验证类或 ORM 字段时，先判断访问是显式点号还是内置操作，再判断状态是在实例、类还是描述符上。
- **初学者误区**：不要把 `__getattr__` 当成 `__getattribute__` 的简写，也不要把 property 装饰器和普通函数装饰器的执行时机混为一谈。

### 深度理解

- **核心概念**：答案把四个问题归结为三条轴线：触发范围（未定义或全部）、管理对象（单个属性或任意名字）以及状态归属（实例或描述符）。
- **底层实现**：`property` 是一种具体描述符；描述符通过 `__get__`、`__set__`、`__delete__` 接收访问；`__getattr__` 和 `__getattribute__` 则是类的特殊方法。
- **设计原因**：这些机制共存，是因为 Python 需要同时支持局部字段封装、可复用字段协议和通用代理，而任何一种方案都无法在所有维度上取代其他方案。
- **实际问题**：选型时应先写清楚读、写、删、类访问、实例隔离和特殊方法行为，再选择最小的协议；这比根据“代码最短”决定更可靠。
- **初学者误区**：property 的 getter、setter 和 deleter 不是三个独立公开属性；装饰器语法最终仍然是名称重绑定，理解这一点才能看懂 `@name.setter` 的执行结果。

# 本章总结

## 技术扩展（Technical Expansion）
- **实际项目中的应用场景**：ORM 字段映射、配置对象、数据验证模型、延迟加载、缓存属性、权限检查、审计日志和代理对象都可能使用属性管理。框架代码中常见的是可复用描述符；业务类中更常见的是 `property`。
- **与其他语言的区别**：

| 维度 | Python | Java | C++ |
|---|---|---|---|
| 单属性访问器 | `property` 或描述符，仍使用点号语法 | 通常显式写 getter/setter 方法 | 常用 getter/setter，也可重载运算符 |
| 通用属性拦截 | `__getattribute__`、`__getattr__` | 通常依靠代理、反射或字节码工具 | 通常依靠代理、模板或宏，语言本身没有同等实例协议 |
| 字段协议复用 | 描述符实例可挂到多个类属性 | 常用注解、反射框架或组合 | 常用模板、继承和成员函数 |
| 特殊操作查找 | 内置操作按类型查找特殊方法 | 运算符和方法调用遵循静态类型规则 | 运算符重载在编译期参与类型解析 |
- **Python 发展历史背景**：描述符协议在 Python 2.2 的新式类体系中成为核心对象模型能力，`property` 随后提供了更易用的封装方式；装饰器语法在 Python 2.4 引入，之后被广泛用于 `@property`、`@classmethod` 等工具。Python 3 继续保留并强化这些协议，同时对特殊方法采用类型级查找以支持稳定的内置运算语义。
- **高级开发者需要掌握的相关知识**：继续学习完整的 MRO 和数据描述符优先级、`__slots__`、元类、函数绑定、装饰器、`__set_name__`、`dataclasses`、属性缓存、`inspect.getattr_static` 以及 ORM 和验证框架中的字段描述符实现。

## 学习建议（Learning Advice）
- **重要程度：4/5**：日常业务代码不必频繁手写描述符，但阅读框架源码、调试代理对象和理解 Python 对象模型时非常重要。
- **应该掌握到什么程度**：能够准确说出四种拦截技术的触发时机，能写出不会递归的 `__getattribute__` 和 `__setattr__`，能判断描述符状态应放在描述符还是客户端实例，并能解释类访问时 `instance is None` 的含义。
- **建议练习**：分别用 `property`、描述符、`__getattr__` 和 `__getattribute__` 实现一个带校验、格式化和只读计算字段的类，再创建两个实例验证状态是否隔离；随后给代理类补上 `__len__`、`__repr__` 和 `__add__`，观察内置操作的特殊方法查找。
- **后续应该学习哪些相关内容**：继续学习第39章装饰器，随后结合元类和完整 MRO 理解数据描述符优先级；在实践中阅读 `dataclasses`、SQLAlchemy 或 Pydantic 的字段实现，比较它们如何利用同一协议。
