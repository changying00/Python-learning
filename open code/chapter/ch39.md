>
> **什么是装饰器？** 简单地说，装饰（decoration）是为函数和类指定管理或增强代码的一种方式。装饰器本身是可调用对象，例如函数，它们处理其他可调用对象。Python 装饰器有两种相关形式：function decorator（函数装饰器）在函数定义时重绑定名字，可以管理函数、方法或它们之后的调用；class decorator（类装饰器）在类定义时重绑定名字，可以管理类或之后通过类名创建的实例。
>
> 换句话说，装饰器让代码在函数或类定义语句结束时自动运行：函数装饰器在 `def` 结束时运行，类装饰器在 `class` 结束时运行。它们可以安装 wrapper（包装器，也叫 proxy（代理））。函数装饰器的包装器拦截之后的函数调用，通常再把调用转给原函数；类装饰器的包装器拦截之后的实例创建，通常再把创建请求转给原类。
>
> 装饰器也不一定要拦截调用。函数装饰器可以在函数对象创建后把它注册到 API，类装饰器也可以直接给类增加方法或数据。若装饰器返回原对象而不是包装器，它就只是一个明确的创建后处理步骤。
>
> 根据需要，装饰器可以用于日志、调用跟踪、缓存结果、参数检查和计时，也可以用于代理对象、单例类以及整个对象接口的增强。函数装饰器更适合一个具体函数或方法的调用，类装饰器更适合实例创建和完整对象接口的管理。
>
> 装饰器不是技术上不可替代的工具；手写名字重绑定或调用辅助函数也能实现同样效果。但它有明显、统一的语法，定义时只应用一次，不必在每个调用点重复书写，也更不容易让 API 使用者忘记必须的增强逻辑。它还把增强代码封装起来，减少重复并便于维护。代价是包装器可能改变对象的类型，并为每次调用增加额外层次；任何包装技术都会有类似代价。
>
> **装饰器与宏的区别。** 装饰器有点像其他语言中的面向切面编程，也像 Java 的注解，但把它称作宏容易误导。C 的 `#define` 宏是文本替换和展开，用来生成代码；Python 装饰器是在运行时基于名字重绑定、可调用对象和代理对象工作的。它们有时用途相交，却不是同一种机制，就像 Python 的 `import` 不是 C 的 `#include` 一样。装饰器是可调用对象管理可调用对象，而不是文本展开。
>
> **基础模型。** 装饰器的大部分“魔法”都可还原为一次自动重绑定：函数或类创建后，把它传给装饰器，再把返回值放回原来的名字。理解这个映射，是后面读实际代码的基础。

### 代码分析

```python
def manage(obj):
    # 创建后处理对象，也可以返回一个包装器
    return obj

@manage
def task():
    return 'ok'

# 装饰语法等价于：task = manage(task)
```

`def task` 执行完函数体后先创建函数对象，然后立即调用 `manage(task)`，最后把结果绑定到名字 `task`。真正执行 `task()` 时，名字查找到的是返回值，而不是必然是最初的函数对象。类装饰器只是把同样的步骤放到 `class` 语句结束处。原书讨论的是运行时重绑定，不是预处理器宏。

**现代 Python 补充：** 如果返回的是嵌套包装函数，通常用 `functools.wraps` 复制 `__name__`、`__qualname__`、`__doc__` 和 `__wrapped__` 等元数据；这不会改变装饰器的重绑定时机，只改善调试、文档和反射。

### 深度理解

- **核心概念**：装饰器协议只有一个关键动作：把刚创建的函数或类交给一个可调用对象，并把返回值重新绑定到原名字。返回原对象时是注册或初始化，返回包装器时才会改变后续调用路径。
- **底层实现**：解释器执行 `def` 或 `class` 后先得到对象，再按装饰器表达式的结果调用装饰器；随后执行名字存储。后续调用先解析这个名字，因此会进入包装器的 `__call__` 或嵌套函数，而不是再次执行装饰器。
- **设计原因**：显式的 `@` 位置把“这个对象被增强了”放在定义处，避免把横切逻辑分散在许多调用点。它也让库作者可以把注册、跟踪、校验等政策封装为可复用工具。
- **实际问题**：包装层会引入额外调用、改变 `type()`/`isinstance()` 的观察结果，函数元数据也可能变成包装器自己的名字。需要保留原函数身份时，应在包装函数上使用 `functools.wraps`；这属于现代实践补充。
- **初学者误区**：`@decorator` 不是文本替换，也不是每次调用都重新执行装饰器；它在定义完成时执行一次。装饰器返回的对象可以不是函数，只有它可调用时，原名字才仍能以调用语法使用。

> **函数装饰器基础。** 正如前面预览过的那样，函数装饰器主要是一种语法糖：在 `def` 语句结束时，让一个函数经过另一个可调用对象处理，并把原函数名重新绑定到处理结果。
>
> **用法。** 函数装饰器是关于后面函数定义的运行时声明。它写在定义函数或方法的 `def` 前一行，由 `@` 和一个 metafunction（元函数，即管理另一个函数的函数或其他可调用对象）组成。从 Python 3.9 起，`@` 后面可以是任何能返回元函数的表达式，虽然通常只是一个名字。
>
> `@decorator` 后面的 `def F(arg)` 和调用 `F(99)`，等价于先定义 `F`，再执行 `F = decorator(F)`，最后调用新的 `F(99)`，也就是 `decorator(F)(99)`。装饰器只在定义时运行一次；后续调用运行的是它返回的可调用对象。
>
> 这条自动重绑定规则对普通函数和类中的方法都成立。装饰器可以返回另一个实现包装逻辑的对象，也可以直接返回原函数。`staticmethod` 和 `property` 的写法就是同一规则的内置版本：`meth = staticmethod(meth)`，以及 `name = property(name)`。前者返回静态方法路由器，后者返回属性描述符。
>
> **实现。** 装饰器是“接受一个可调用对象并返回一个可调用对象”的协议，但调用者和返回者不必都是函数，也可以是类或可调用类实例。返回原函数时，装饰器只做创建后处理，例如注册函数或初始化属性；返回不同对象时，返回值就是之后接收调用的代理。
>
> 常见包装器是装饰器内部定义的嵌套函数。它通过闭包保留原函数 `F`，在后续收到 `*args` 时执行 `F(*args)`。另一种写法是让装饰器类实现 `__init__` 和 `__call__`，把原函数存到实例属性 `self.func` 中。每次装饰都会产生一个独立闭包或独立装饰器实例，因此可以保存各自的状态。
>
> 但可调用类实例装饰方法时有一个陷阱。方法名被绑定到装饰器类实例后，Python 会把装饰器实例放进 `__call__` 的 `self`，而不会把被调用对象的类实例自动放进 `*args`。原方法所需的 `C` 实例因此丢失，调用转发会缺少参数。
>
> 用嵌套函数作为包装器可以同时支持普通函数和方法。因为包装器本身仍是普通函数，属性被实例访问时会形成 bound method（绑定方法），Python 会把 `C` 实例作为第一个参数传进 `wrapper(*args)`，然后包装器把它转发给原方法。描述符也能同时拿到装饰器实例和主题类实例，但实现更复杂。

### 代码分析

```python
from functools import wraps

def decorator(func):
    @wraps(func)                 # 现代 Python 补充：复制函数元数据
    def wrapper(*args, **kwargs):
        # 这里在真正调用时运行，而不是在 @ 行运行
        return func(*args, **kwargs)
    return wrapper

@decorator
def F(arg):
    return arg

# 定义阶段发生：F = decorator(F)
result = F(99)                   # 调用 wrapper，再由 wrapper 调用原 F

class C:
    @decorator
    def method(self, value):
        return value
```

函数体建立后，`decorator(F)` 只执行一次；`wrapper` 的 `func` 是闭包单元，所以即使外层 `decorator` 返回，原函数仍被引用。`method` 被保存为普通函数 `wrapper` 时，描述符协议会在 `C().method` 的取属性阶段产生绑定方法，于是 `self` 会进入 `args[0]`。若改成 `class Decorator` 的实例，取到的是装饰器实例本身，必须显式实现 `__get__` 才能补回主题实例。

### 深度理解

- **核心概念**：`@decorator` 只是 `F = decorator(F)` 的简写；真正决定行为的是装饰器返回什么。嵌套函数返回函数，装饰器类返回带 `__call__` 的实例，两者都能成为调用代理。
- **底层实现**：嵌套 `wrapper` 通过 `co_freevars`/闭包单元保存 `F`；可调用类则把 `F` 存在实例字典中。方法绑定只会自动发生在普通函数描述符上，不会自动把主题实例传给可调用类实例的 `__call__`。
- **设计原因**：`*args, **kwargs` 让一个包装器可以转发不同签名的函数；返回原对象则允许装饰器只做注册或属性初始化，不必为每次调用增加代理层。
- **实际问题**：不转发返回值会让被装饰函数“凭空”变成返回 `None`；不接收 `**kwargs` 会拒绝关键字调用；不使用 `wraps` 会让调试器、文档工具和 `inspect` 看到包装器的元数据。
- **初学者误区**：方法的 `self` 不是装饰器自动提供的神奇参数。它来自普通函数的绑定过程；一旦原方法名被换成可调用实例，装饰器实例就占据了 `__call__` 的 `self`。

> **类装饰器基础。** 函数装饰器很有用，因此同一模型后来扩展到了类。它起初因为和下一章的元类有职责重叠而受到抵制，但最终被采用，因为它能用更简单的方式完成许多相同目标。
>
> 类装饰器与函数装饰器关系紧密，语法和编写模式也很相似。区别在于，它不只是包住单个函数或方法，而是管理类本身，或者包住实例创建调用，对由该类创建的实例增加逻辑。作为后者，它可以管理完整对象接口，而不只是一个可调用对象。
>
> **用法。** 类装饰器写在 `class` 语句前。`@decorator class C: ...` 等价于先创建类，再执行 `C = decorator(C)`。之后写 `C(99)` 时，调用的是装饰器返回的可调用对象；它可以调用原类，也可以完全决定返回什么。
>
> **实现。** 类装饰器和函数装饰器一样，既可以在类刚创建后处理它并返回原类，也可以返回另一个函数、嵌套类或带 `__call__` 的对象。一个常见模式是在装饰器函数内定义 `Wrapper`，让 `Wrapper.__init__` 创建原类实例，让 `Wrapper.__getattr__` 把未定义的属性请求转给原实例。
>
> 这样，类名会被重新绑定到 `Wrapper` 类。调用类名其实创建的是 `Wrapper` 实例；每个包装器实例内部再保存一个原类实例。每个被装饰的类都有自己的闭包作用域，记住原类；每次实例创建又有自己的包装器对象，因此不同实例不会互相覆盖。
>
> 类装饰器通常使用闭包工厂、实现 `__init__`/`__call__` 的类，或两者的组合。闭包把状态放在外层作用域，类把状态放在属性里。必须选择正确的组合：若装饰器类的 `__call__` 每次都把新实例存到同一个 `self.wrapped`，后一个实例就会覆盖前一个；让 `__call__` 每次返回新的 `Wrapper` 实例，或让嵌套函数每次创建新的包装器，才能支持同一类的多个实例。

### 代码分析

```python
def decorator(cls):
    class Wrapper:
        def __init__(self, *args, **kwargs):
            self.wrapped = cls(*args, **kwargs)

        def __getattr__(self, name):
            return getattr(self.wrapped, name)

    return Wrapper

@decorator
class C:
    def __init__(self, value):
        self.value = value

# 定义阶段：C = decorator(C)，C 现在指向 Wrapper
x = C(99)                         # 实际调用 Wrapper(99)
```

这里 `cls` 由装饰器闭包保留，`x.wrapped` 则保存每一次实际构造的原类实例。`__getattr__` 只在 `Wrapper` 自己找不到属性时触发，因此可以把普通属性和方法委托给 `C`。若错误地在装饰器类的单个实例上反复写 `self.wrapped`，`x` 和 `y` 会引用同一个最后创建的状态。

### 深度理解

- **核心概念**：类装饰器重绑定的是类名，所以它可以改变“类名调用时会创建什么”，也可以在类对象本身上追加属性。实例接口代理只是其中一种用途。
- **底层实现**：`class C` 完成后，装饰器调用发生在类体执行和类对象创建之后。返回 `Wrapper` 类时，后续 `C(...)` 是 `Wrapper(...)`，`Wrapper.__init__` 再显式调用闭包中的原类。
- **设计原因**：用类装饰器包住实例创建，可以让所有构造点自动获得同一增强逻辑，而不用把 `Wrapper(Original(...))` 写在每个调用点。
- **实际问题**：代理对象的 `type` 不再是原类；未代理的特殊方法可能不经 `__getattr__`；错误的状态保存策略还会把多个实例合并为一个。需要按“每个装饰类”和“每个生成实例”分别设计状态。
- **初学者误区**：`@decorator` 不会把类继承关系、类体代码搬进包装类；它只是把已经创建好的类对象传给装饰器。返回嵌套 `Wrapper` 后，原类仍在闭包中，类名本身已经不是原类。

> **装饰器嵌套。** 一个装饰器不够时，可以把多个装饰器叠加到同一个函数、方法或类上。每个装饰器必须独占一行。`@A @B @C` 放在 `def f` 上，等价于 `f = A(B(C(f)))`。

### 代码分析

```python
def d1(func):
    return lambda: 'X' + func()

    return lambda: 'Y' + func()

    return lambda: 'Z' + func()

@d3

    return 'hack'
```

### 深度理解

- **核心概念**：嵌套装饰器是函数复合，不是并行列表；书写顺序从上到下，应用顺序从下到上，调用顺序再从外到内。
- **底层实现**：每个装饰器接收上一层的返回对象并产生新的绑定值。闭包包装器把上一层保存在自由变量中，调用链因此形成一串嵌套的 Python call。
- **设计原因**：把横切功能拆成小装饰器，可以按需组合而不修改业务函数；显式的顺序也把依赖关系留在定义点。
- **实际问题**：层数越多，异常堆栈、签名和性能越难读；某一层没有返回结果或没有转发关键字参数，就会破坏后续层。缓存、权限和事务等装饰器的顺序必须经过测试。
- **初学者误区**：最上面的装饰器不是最先包原函数的；`@A @B` 不是 `A(B)` 的调用语句，而是定义结束后的 `A(B(f))`。装饰器参数的求值顺序也不能和包装器的调用顺序混为一谈。

### 中文翻译

> **装饰器参数。** 函数和类装饰器看起来可以直接带参数，但实际过程是：参数先传给一个可调用对象，这个对象返回真正的装饰器，而真正的装饰器再返回最后处理函数或类调用的可调用对象。因此通常有三层：接收配置的外层工厂、接收被装饰对象的装饰器、拦截后续调用的包装器。
>
> `@decorator(A, B)` 应理解为 `F = decorator(A, B)(F)`，而调用 `F(99)` 才是最后的包装器调用。`decorator(A, B)` 在装饰发生前就求值，所以 `A`、`B` 通常被保存在外层闭包中，供真正的装饰器和后续包装器使用。
>
> 这些参数可以是初始化值、跟踪标签、待验证的属性名或其他配置。每一层可以是函数、类或可调用类实例，也可以用闭包变量或实例属性保存状态。
>
> 装饰器协议不局限于包装后续调用。装饰器若直接返回传入的函数或类，就可以在创建后注册对象、初始化对象属性，或执行其他一次性处理。这种场景不需要代理层，但仍然享受 `@` 语法把意图写在定义处的优点。

### 代码分析

```python
def configured(label):
    # 第一层：先接收装饰器配置
    def decorator(func):
        # 第二层：接收刚创建的函数
        def wrapper(*args, **kwargs):
            # 第三层：接收真正调用的参数
            print(label, func.__name__)
            return func(*args, **kwargs)
        return wrapper
    return decorator

@configured('trace')
def work(value):
    return value * 2

# work = configured('trace')(work)
```

解释器先执行 `configured('trace')`，得到 `decorator`；函数定义完成后再执行 `decorator(work)`，得到 `wrapper` 并重绑定 `work`。`label` 和 `func` 分别由两层闭包保存，调用 `work(3)` 时才进入 `wrapper`。如果希望包装器在 `inspect`、日志和文档中显示原函数身份，现代 Python 可以在最内层使用 `@functools.wraps(func)`，但这是元数据补充，不改变三层调用关系。

### 深度理解

- **核心概念**：带参数装饰器不是“给包装器传参数”的单层函数，而是一个返回装饰器的工厂；配置和被装饰函数是两个不同阶段进入闭包的状态。
- **底层实现**：外层调用产生新的作用域，内层 `decorator` 捕获配置，`wrapper` 再捕获原函数。每次写一次 `@configured(...)` 都会产生一套独立的作用域链。
- **设计原因**：把配置放在定义处，可让同一个通用工具服务于多个函数，同时避免把标签、范围等策略写进业务函数体。
- **实际问题**：参数工厂会在模块导入或类体执行期间运行，配置表达式的副作用会提前发生；三层函数也会增加阅读和调试成本。包装器仍需正确转发返回值、异常、位置参数和关键字参数。
- **初学者误区**：`@configured('trace')` 不是把字符串传给 `work`；它先调用外层工厂。装饰器参数在定义时确定，调用 `work(3)` 时只传业务参数，不会重新生成装饰器。

### 代码分析

```python
from functools import wraps
import time

def tracer(func):
    calls = 0

    @wraps(func)                 # 现代 Python 补充：保留 func 的元数据
    def wrapper(*args, **kwargs):
        nonlocal calls
        calls += 1
        wrapper.calls = calls
        print(f'call {calls} to {func.__name__}')
        return func(*args, **kwargs)

    wrapper.calls = 0            # 把同一状态镜像到函数对象，便于外部读取
    return wrapper

def timer(func):
    alltime = 0.0

    @wraps(func)
    def wrapper(*args, **kwargs):
        nonlocal alltime
        start = time.perf_counter()
        result = func(*args, **kwargs)
        alltime += time.perf_counter() - start
        wrapper.alltime = alltime
        return result

    wrapper.alltime = 0.0
    return wrapper
```

`@tracer` 发生在函数定义阶段，调用阶段只进入 `wrapper`。`func` 和 `calls` 是闭包单元，每次执行外层 `tracer` 都得到一套新状态。若用原书的可调用类，状态在 `self.func`/`self.calls` 中；若装饰方法，普通嵌套函数能触发绑定方法机制，而可调用类需要额外的 `__get__`。`perf_counter()` 是计时器逻辑，不是装饰器机制本身；装饰器只负责把计时逻辑安装到每次调用路径上。

### 深度理解

- **核心概念**：函数装饰器可以把“调用前、调用后、异常处理和状态累计”集中到包装层；状态策略决定计数器是每个函数独有、全模块共享，还是能被外部观察。
- **底层实现**：类包装器依靠 `__call__`，嵌套函数依靠闭包，方法支持依靠普通函数的描述符绑定，描述符版本依靠 `__get__` 保存主题实例。每多一层包装，调用栈就多一次 Python 层调用。
- **设计原因**：跟踪、计时、参数检查等横切逻辑与业务函数分离，函数本身保持原来的调用形式；定义处的一次重绑定还能保证后续普通调用不会意外绕过增强逻辑。
- **实际问题**：包装器必须转发 `*args`、`**kwargs`、返回值和异常；还要考虑线程并发下计数器的共享语义、计时本身的管理开销，以及包装后对象类型/签名发生变化。`functools.wraps` 只能修复常用元数据，不能让可调用类实例重新变成原函数类型。
- **初学者误区**：`self` 在可调用装饰器类中首先表示装饰器实例，不是被装饰方法的主题对象；全局计数器也不是“每个函数一个”。此外，计时结果不能直接比较不同机器，装饰器引入的额外调用也可能影响微基准。

### 代码分析

```python
def timer(label='', trace=True):
    class Timer:
        def __init__(self, func):
            self.func = func
            self.alltime = 0.0

        def __call__(self, *args, **kwargs):
            # 省略计时细节：调用原函数并按配置输出
            return self.func(*args, **kwargs)

    return Timer

@timer(label='[CCC]==>')
def listcomp(n):
    return [x * 2 for x in range(n)]

def singleton(cls):
    instance = None

    def on_call(*args, **kwargs):
        nonlocal instance
        if instance is None:
            instance = cls(*args, **kwargs)
        return instance

    return on_call
```

`timer(...)` 在定义 `listcomp` 前先运行并返回 `Timer`；随后类装饰协议把 `listcomp` 传给 `Timer(...)`，名字重绑定为一个 `Timer` 实例。`singleton` 则为每个 `cls` 调用产生自己的闭包，`nonlocal instance` 修改的是该类对应的外层变量。若把 `instance` 放在装饰器函数外部，就会错误地让所有被装饰类共享单例。

### 深度理解

- **核心概念**：参数化装饰器是“工厂返回装饰器”，类装饰器则是“类对象经过处理后重新绑定”。两者都依靠定义阶段建立的闭包或实例状态，后续调用只是使用已建立的状态。
- **底层实现**：标签和开关位于外层函数的自由变量中，函数对象位于 `Timer` 实例或中层闭包中，累计时间位于每个部署的实例属性中。单例工厂则把唯一实例放在每个部署自己的闭包里。
- **设计原因**：配置与业务函数分离后，一个计时器可以按函数定制输出；类装饰器把实例创建政策集中到类定义处，单例和接口代理不必修改所有构造点。
- **实际问题**：单例会忽略后续构造参数，可能导致调用者误以为得到了新对象；全局字典会延长类和实例的生命周期。嵌套 `Timer` 类用于函数时方便保存状态，却会再次触发方法绑定陷阱。
- **初学者误区**：`@timer(label=...)` 的标签不是在每次调用时解析；`@singleton` 也不会让原类本身只能被实例化一次，而是把类名改成一个返回缓存实例的可调用对象。状态究竟按模块、按装饰部署还是按生成实例隔离，必须先明确。

> This code is nontrivial, and you’re probably best off tracing through it on your
> own to see how it works. To help you study, though, here are a few highlights
> worth mentioning.
> Inheritance versus delegation
> The initial and limited privacy example 
> shown in 
> Chapter 30
>  used 
> inheritance
>  to
> mix in a 
> __setattr__
>  to catch accesses. Inheritance makes this difficult,
> however, because differentiating between accesses from inside or outside the
> class is not straightforward (inside access should be allowed to run normally, and
> outside access should be restricted). To work around this, the 
> Chapter 30
> example requires inheriting classes to use 
> __dict__
>  assignments to set attributes
> —an incomplete solution at best.
> The version here uses 
> delegation
>  (embedding one object inside another) instead
> of inheritance; this pattern is better suited to our task as it makes it much easier
> to distinguish between accesses inside and outside of the subject class. Attribute
> accesses from outside the subject class are intercepted by the wrapper layer’s
> overloading methods and delegated to the class if valid. Accesses inside the class
> itself (i.e., through 
> self
>  within its methods’ code) are not intercepted and are
> allowed to run normally without checks because privacy is not inherited in this
> version.
> Decorator arguments
> 
> The class decorator used here 
> accepts any number of arguments to name private
> attributes. Again, though, this simply means that the arguments are passed to the
> Private
>  function, and 
> Private
>  returns the decorator function to be applied to
> the subject class. That is, the arguments are used before decoration ever occurs;
> Private
>  returns the decorator, which in turn “remembers” the privates list as an
> enclosing-scope reference.
> State retention and enclosing scopes
> Speaking of enclosing scopes, there are 
> actually 
> three levels
>  of state retention at
> work in this code:
> The arguments to 
> Private
>  are used before decoration occurs and are
> retained as an enclosing-scope reference for use in both 
> onDecorator
> and 
> onInstance
> .
> The class argument to 
> onDecorator
>  is used at decoration time and is
> retained as an enclosing-scope reference for use at instance-creation
> time.
> The wrapped instance object is retained as an instance attribute in the
> onInstance
>  proxy object for use when attributes are later accessed
> from outside the class.
> This all works fairly naturally, given Python’s scope and namespace rules.
> Using __dict__ and __slots__ (and other virtuals)
> The 
> __setattr__
>  method in this code relies on an instance object’s 
> __dict__
> attribute namespace dictionary in order to set 
> onInstance
> ’s own 
> wrapped
> attribute. As we learned in the prior chapter, this method cannot assign an
> attribute directly without looping. However, it uses the 
> setattr
>  built-in instead
> of 
> __dict__
>  to set attributes in the 
> wrapped
>  object itself. Moreover, 
> getattr
>  is
> used to fetch attributes in the 
> wrapped
>  object since they may be stored in the
> object itself or inherited by it.
> Because of that, this code will work for most classes—including those with
> “virtual” class-level attributes based on 
> slots
> , 
> properties
> , 
> descriptors
> , and even
> __getattr__
>  and its ilk. By assuming a namespace dictionary for itself only and
> 
> using storage-neutral tools for the wrapped object, the wrapper class avoids
> limitations imposed by other tools.
> For example, you may recall from 
> Chapter 32
>  that classes with 
> __slots__
>  may
> not store attributes in a 
> __dict__
> , and in fact, may not even have one of these at
> all. However, because we rely on a 
> __dict__
>  only at the 
> onInstance
>  level here
> and not in the wrapped instance, this concern does not apply. Class 
> onInstance
> will have a 
> __dict__
>  itself because it does not use slots. In addition, because
> setattr
>  and 
> getattr

> __dict__
>  and

> delegated names will be looked up anew in the wrapped instance, irrespective of
> attributes of the 
> decorator proxy object itself.

### 中文翻译

> **类装饰器方式。** 类装饰器可以把手动的 `__getattr__` 委托包装改成“定义类时安装，创建实例时自动包装”。例39-14的 `Tracer(aClass)` 在内部定义 `Wrapper`：`Wrapper.__init__` 接收任意位置和关键字参数，创建 `aClass` 的实例并保存到 `wrapped`；`__getattr__` 打印属性名、增加 `fetches` 计数，再用 `getattr` 把请求转给原实例。`Tracer` 返回 `Wrapper`，所以 `Hack` 和 `Person` 的类名都被重绑定到这个包装类。
>
> `work = Hack()`、`bob = Person(...)` 和 `sue = Person(...)` 创建的都是 `Wrapper` 实例。访问 `work.display`、`bob.name`、`bob.pay` 等外部属性时会产生跟踪输出；`pay` 方法体内部通过自己的 `self.hours` 和 `self.rate` 访问原对象，不会再经过外层包装，这正是示例想要的边界。`bob` 和 `sue` 各有自己的 `fetches`，输出最后为 `[4, 2]`。这与前面跟踪单个函数调用的装饰器不同：这里拦截的是整个对象接口。
>
> `__getattr__` 仍然不能捕获内建操作隐式发起的特殊方法查找。普通显式属性如 `x.append` 会进入包装器，但 `x + 1` 或 `print(x)` 可能直接在包装类上查找 `__add__`、`__str__`，这一点稍后会专门处理。
>
> 用户定义类之外，也可以包装内置类型。因为 `@` 语法要求后面跟 `class` 语句，可以先写 `class MyList(list): pass` 再装饰，或者直接手动执行 `MyList = Tracer(list)`。两种写法都会让 `MyList([1, 2, 3])` 返回 `Wrapper`，`append` 经过 `__getattr__` 委托给真正的列表。装饰器把实例创建放到类定义层，保留普通的构造调用形式；手动包装则需要在每个构造点写 `Wrapper(...)`。
>
> **保留多个实例的陷阱。** 例39-15把 `Tracer` 几乎原样改成装饰器类：`__init__` 在 `@Tracer` 应用时保存原类，`__call__` 在每次构造时创建原实例并写入 `self.wrapped`，然后返回 `self`。它能处理多个被装饰的类，却不能处理同一个类的多个实例：`bob = Person('Bob')` 后再执行 `sue = Person('Sue')` 会覆盖同一个 `Tracer` 对象里的 `wrapped`，于是再次读取 `bob.name` 得到 `Sue`。前面的函数式 `Tracer` 返回一个 `Wrapper` 类，每次调用都会新建 `Wrapper` 实例，因此可以正确隔离状态。
>
> **案例：Private 和 Public 属性。** 例39-17的类装饰器 `Private('data', 'size')` 返回装饰器，再返回嵌套的 `onInstance` 代理。代理把原 `Doubler` 实例保存到 `wrapped`；外部读取属性时进入 `__getattr__`，若名字在 `privates` 中就抛出 `TypeError`，否则委托给原对象；外部赋值进入 `__setattr__`，代理自己的 `wrapped` 允许直接写入，私有名字拒绝，其他名字转发给原对象。`Doubler` 自己的方法内部通过原类实例的 `self` 访问 `data` 和 `size`，不会被代理拦截，因此类内部可以正常使用这些名字。
>
> 自测试输出显示，创建代理时会记录两次 `set: wrapped`；外部读取 `label`、调用 `display` 和 `double` 会被跟踪，改变公开属性 `Y.label` 也会被委托。注释掉的测试会分别因为读取私有 `size`、读取私有 `data`、写入 `data` 而抛出异常。这个模型使用 delegation（委托/嵌入）而不是 inheritance（继承），所以更容易区分“从代理外部发起的访问”和“原类方法内部通过 `self` 发起的访问”。
>
> 例39-18把规则推广为 `Private` 和 `Public` 两种互斥声明。使用 `Private` 时，列出的名字不能从类外读取或赋值，未列出的名字默认公开；使用 `Public` 时，列出的名字公开，未列出的名字默认私有。因此 `Private('age')` 和 `Public('name')` 的交互示例都允许改写 `name`，但读取或写入 `age` 会抛出 `TypeError`。
>
> 这个实现有多层状态：`Private`/`Public` 的属性名或检查函数在最外层闭包中；被装饰的类由 `onDecorator` 捕获，供之后每次实例化使用；每个 `onInstance` 再把实际原实例保存为属性。代理自身用 `__dict__` 保存管理属性，而对原对象使用 `getattr`/`setattr`，因此能兼容普通实例属性、继承属性、`__slots__`、property、descriptor 以及原对象自己的 `__getattr__`。
>
> 这里的私有化只是示例性质，并不等同于 C++ 或 Java 的强制 private。原书明确指出，Python 更重视赋能而不是控制；这类访问检查适合开发期减少误操作，但不能作为严格的安全边界。

### 代码分析

```python
def Tracer(cls):
    class Wrapper:
        def __init__(self, *args, **kwargs):
            self.fetches = 0
            self.wrapped = cls(*args, **kwargs)

        def __getattr__(self, name):
            self.fetches += 1
            print('Trace:', name)
            return getattr(self.wrapped, name)

    return Wrapper

@Tracer
class Person:
    def __init__(self, name):
        self.name = name

bob = Person('Bob')               # 实际创建 Wrapper，再由它创建原 Person
print(bob.name)                   # Wrapper.__getattr__ 委托属性
```

类定义完成后发生 `Person = Tracer(Person)`，闭包中的 `cls` 仍指向原始 `Person`。之后 `Person('Bob')` 查找到的是 `Wrapper` 类，因此每次调用都会新建一个包装器和一个原实例。`__getattr__` 只在包装器自身属性查找失败时触发，`fetches` 不会被自己的读取递归计数。

```python
def accessControl(fail_if):
    def onDecorator(cls):
        class onInstance:
            def __init__(self, *args, **kwargs):
                self.__wrapped = cls(*args, **kwargs)

            def __getattr__(self, name):
                if fail_if(name):
                    raise TypeError('private attribute fetch, ' + name)
                return getattr(self.__wrapped, name)

            def __setattr__(self, name, value):
                if name == '_onInstance__wrapped':
                    self.__dict__[name] = value
                elif fail_if(name):
                    raise TypeError('private attribute change, ' + name)
                else:
                    setattr(self.__wrapped, name, value)

        return onInstance
    return onDecorator
```

`__setattr__` 对代理自己的 `__wrapped` 必须走 `__dict__`，否则给它赋值会再次进入 `__setattr__` 形成递归；原实例则使用 `setattr`，让属性、描述符和 `__slots__` 的规则继续生效。`functools.wraps` 主要服务于函数包装器，不能自动解决类代理的 `isinstance` 身份问题。

### 深度理解

- **核心概念**：接口代理把实例创建重定向到包装类，再把显式属性访问委托给内部原对象；`Private`/`Public` 只是把委托前的名字检查加入这条路径。
- **底层实现**：闭包保存原类和声明集合，`Wrapper`/`onInstance` 的实例属性保存具体原实例。`__getattr__` 只处理普通显式查找，`__setattr__` 负责把写入分流到代理自身或被包装对象。
- **设计原因**：委托比继承更容易观察访问来自哪里：原类方法内部继续直接操作原实例，外部访问则必须经过代理。把包装逻辑放到类装饰器上，还能让所有构造出来的实例自动获得同样接口。
- **实际问题**：包装实例的类型不是原类，特殊方法可能绕过 `__getattr__`，私有名可以通过名称改写后的 `_onInstance__wrapped` 绕过，且每次属性访问都会增加代理成本。代理状态必须按“装饰部署”和“生成实例”分开保存。
- **初学者误区**：`__getattr__` 不是所有属性访问的总入口；只在普通查找失败时才调用。类内部的 `self.data` 也不是在访问代理，而是在访问原类实例，所以不会触发外部私有检查。

```python
        return f'Tally: {self.sum}'

        self.sum += value
```

### 深度理解

- **核心概念**：名称改写解决的是代理内部命名冲突，不是安全隔离；内置操作问题则揭示了普通属性协议和特殊方法协议的分离。
- **底层实现**：类体中的 `__wrapped` 会被编译器改成带类名的名称；`__getattr__` 是实例普通查找失败的后备机制，而二元运算和字符串转换会直接检查类型的特殊方法。
- **设计原因**：特殊方法放在类上可以让所有实例共享稳定的运算协议，也避免每次运算都依赖动态属性查找。代理要参与这些协议，就必须显式实现入口。
- **实际问题**：遗漏一个特殊方法就会让代理在索引、迭代、上下文管理或运算时失败；名称改写会影响调试和序列化，绕过改写名也意味着私有检查不能被当作安全边界。
- **初学者误区**：能拦截 `obj.attr` 不等于能拦截 `obj + other`；`print(obj)` 也不是简单地先调用普通 `getattr`。代理设计必须逐项列出要支持的特殊方法。

> **直接在代理中重定义。** 最直接的办法是在代理类中为可能出现的内置操作重新定义 `__add__`、`__str__`、`__getitem__`、`__call__` 等方法，再把调用直接转给被包装对象。代码有重复，但容易理解，也可以由工具或公共超类生成。例39-19选择直接调用 `self.__wrapped + other`、`str(self.__wrapped)` 等方式，因此这些特殊方法绕过了 `__getattr__` 的访问验证；这是否符合 Private/Public 策略要由设计者决定。
>
> **放进混入超类。** 例39-20把同一组特殊方法集中到 `BuiltinsMixin`，代理类继承它，并约定使用 `_wrapped` 保存原对象。这样所有代理都能复用一份方法定义，但会带来属性命名冲突和对该超类的继承依赖。例39-21的混入版本不直接访问 `_wrapped`，而是调用子类的 `__getattr__('__add__')`、`__getattr__('__str__')` 等入口，于是内置操作也经过 Private/Public 验证；代价是多一层委托调用，而且特殊方法仍需逐个列出。
>

### 代码分析

```python
class BuiltinsMixin:
    def __add__(self, other):
        # 内置运算先在代理类上找到这个方法
        return self.__getattr__('__add__')(other)

    def __str__(self):
        return self.__getattr__('__str__')()

    def __getitem__(self, index):
        return self.__getattr__('__getitem__')(index)

class ProxyDesc:
    def __init__(self, name):
        self.name = name

    def __get__(self, instance, owner):
        # 描述符把特殊方法获取导向普通验证路径
        return instance.__getattr__(self.name)

class Builtins:
    __add__ = ProxyDesc('__add__')
    __str__ = ProxyDesc('__str__')
```

`exec(f'__{attr}__ = ProxyDesc("__{attr}__")')` 的作用只是自动生成上面这些类属性，不会改变特殊方法查找发生在类上的事实。操作表达式先找到代理类上的入口，入口再决定是否通过 `__getattr__` 验证和委托。若直接写 `return self._wrapped + other`，就跳过验证；若写 `return self.__getattr__('__add__')(other)`，则会把 `__add__` 当作显式名字处理。

### 深度理解

- **核心概念**：代理要支持特殊方法，必须把入口放进代理类的类型层；直接实现、混入继承和描述符生成只是组织这些入口的三种方式。
- **底层实现**：内置操作先做类型级特殊方法查找，找到代理方法后才进入方法体。描述符方案在这之前增加一次 `__get__`，由描述符保存名字并返回经过 `__getattr__` 的绑定结果。
- **设计原因**：把特殊方法集中在混入或描述符中可以减少每个代理类的重复代码，并能选择“直接委托”或“走访问验证”两种政策。
- **实际问题**：`exec` 生成代码难以静态检查，特殊方法列表不完整时仍会漏功能；混入会引入命名冲突和继承依赖；每层委托都会增加调用成本。
- **初学者误区**：描述符不是把所有内置运算自动转成普通属性访问；它仍需被安装在代理类上，并且 `__get__` 返回的对象必须能接受运算所需参数。直接重定义特殊方法也不等于自动保留原对象的全部协议。

### 代码分析

```python
def rangetest(**argchecks):
    def onDecorator(func):
        if not __debug__:
            return func                 # python -O：直接重绑定原函数

        funcargs = func.__code__.co_varnames[:func.__code__.co_argcount]

        def onCall(*pargs, **kargs):
            positionals = funcargs[:len(pargs)]
            for name, (low, high) in argchecks.items():
                if name in kargs:
                    value = kargs[name]
                elif name in positionals:
                    value = pargs[positionals.index(name)]
                else:
                    continue                    # 调用时省略，使用默认值
                if value < low or value > high:
                    raise TypeError(f'{name} not in {low}..{high}')
            return func(*pargs, **kargs)

        return onCall
    return onDecorator
```

`@rangetest(...)` 先建立配置闭包，函数定义完成后再建立 `onCall` 并重绑定函数名。方法调用时 `pargs[0]` 是 `self`，所以 `funcargs` 中的 `self` 自然占据第一个位置；检查 `percent` 时可按名字定位到第二个位置。`__debug__` 的判断发生在装饰阶段，不是每次业务调用都重新决定是否包装。

**现代 Python 3.12 补充：** 原文在早期的内联示意中出现了 `raise TypeError, 'percent invalid'` 的旧式写法；Python 3.12 应写成 `raise TypeError('percent invalid')`。原书的装饰器核心算法仍然可以用，但生产代码通常会使用 `inspect.signature(...).bind()` 或 `bind_partial()` 处理更复杂的签名，而不是把这里的简化算法误当成完整调用绑定器。

### 深度理解

- **核心概念**：范围检查装饰器把参数验证从函数体移到定义阶段安装的调用代理；真正的业务函数仍负责业务，代理负责按声明检查值。
- **底层实现**：配置通过外层闭包保存，原函数的参数名来自 `__code__.co_varnames` 和 `co_argcount`，调用参数由 `*pargs/**kargs` 收集后按 Python 的位置/关键字规则映射。
- **设计原因**：统一工具可以避免在每个方法中复制校验代码，也可以在 `-O` 下通过定义阶段返回原函数来去掉开发期检查层。
- **实际问题**：简化映射不验证所有非法调用，不处理无名额外位置参数，也会让包装器改变签名；`-O` 关闭检查意味着生产环境不再得到这些运行时保证，不能把它当作安全校验。
- **初学者误区**：方法参数索引不是从业务参数开始，`self` 已占用位置0；`__debug__` 不是可在运行时随意修改的开关；装饰器参数中的范围元组不会自动进行类型转换或处理 `None` 等非数值输入。

- **底层实现**：函数签名中的明确参数来自代码对象，包装器的星号参数只收集运行时值；代理嵌套会改变外层可观察的参数名，导致位置映射信息丢失。

- **实际问题**：额外位置参数无法命名检查，嵌套时外层可能漏检位置值，错误报告可能延迟到原函数调用；对边界输入需要补充测试，不能只测正常调用。
- **初学者误区**：`*args` 在包装器里看到的是一个元组，不代表原函数就有一个叫 `args` 的业务参数；`functools.wraps` 也不会自动修复所有签名映射。装饰器“能调用”不等于“能准确自省”。

### 中文翻译

> **装饰器参数与函数注解。** 第19章介绍的 annotation（注解）也可以替代本案例中用于指定范围测试的装饰器参数。注解把表达式写在 `def` 头部的参数或返回值位置，Python 会把它们收集到字典并附加到函数对象上。
>
> 因此可以把 `@rangetest(a=(1, 5), c=(0.0, 1.0))` 改成 `@rangetest` 配合 `def func(a:(1, 5), b, c:(0.0, 1.0))`。两种方式仍然需要函数装饰器拦截后续调用；区别只是范围信息的保存位置：装饰器参数放在外层作用域，注解放在原函数的 `__annotations__` 属性中。注解版本少一层状态保留。
>
> 例39-27给出了两种不完整的骨架。装饰器参数版本由外层 `rangetest(**argchecks)` 保存字典，`onCall` 调用时读取它；注解版本直接在 `onCall` 中读取 `func.__annotations__`。两种版本运行都打印 `{'a': (1, 5), 'c': (0.0, 1.0)}` 并得到 `6`，所以它们提供的是不同的用户接口，仍然需要相同的参数名与位置匹配算法。
>
> 使用注解会把函数定义绑定到一种用途：每个参数只有一个注解表达式，范围测试就占用了这个位置，也不便同时承担第6章所说的可选类型提示等其他含义。装饰器参数写在函数外，更容易删除、更通用，也能把多个带参数装饰器叠加到同一个函数上，并让函数保持普通的签名外观。如果只有一个明确用途，两者更多是风格和取舍问题。

### 代码分析

```python
def rangetest(func):
    def on_call(*args, **kwargs):
        checks = func.__annotations__
        # 真实实现还要按参数名映射并执行范围检查
        print(checks)
        return func(*args, **kwargs)
    return on_call

@rangetest
def add(a: (1, 5), b, c: (0.0, 1.0)):
    return a + b + c

result = add(1, 2, c=3)
```

函数定义时注解表达式被收集到函数对象上；`@rangetest` 随后把原函数传给装饰器并把名字改绑到 `on_call`。调用时 `on_call` 读取的是闭包里的原函数注解。注解本身不会自动验证范围，仍需装饰器或其他运行时代码解释这些值。

**现代 Python 3.12 补充：** 实际项目中的类型注解主要供类型检查器、IDE 和文档工具使用，不能默认当成运行时校验器；本书此处把注解表达式当作范围配置，是一个特定工具接口。

### 深度理解

- **核心概念**：装饰器参数和注解都能提供配置数据，但前者是外部策略，后者是函数对象元数据；两者都仍需要包装器解释并执行检查。
- **底层实现**：注解在函数创建时写入 `__annotations__` 字典，参数化装饰器则通过外层闭包保存 `argchecks`。两种方案最终都在调用代理中读取配置。
- **设计原因**：把策略放在装饰器外能保持函数通用并支持多个增强层；把策略放进函数签名则能让接口信息与函数定义靠得更近。
- **实际问题**：注解槽位只有一个，把范围约束放进去会和类型提示、文档语义竞争；参数化装饰器则可能产生多层闭包和元数据处理问题。注解不会自动执行校验。
- **初学者误区**：看到 `a: (1, 5)` 不代表 Python 会自动限制 `a` 的范围；它只是一个注解值。`@rangetest` 仍然负责拦截调用，且包装器若不使用 `wraps`，外部看到的函数元数据可能来自 `on_call`。

# 本章总结

## 技术扩展（Technical Expansion）

本章的直接应用是把日志、计时、缓存、权限检查、参数验证、注册和接口代理等横切逻辑集中到定义处。设计装饰器时应先决定它管理的是函数对象、函数调用、类对象、实例创建，还是实例接口，再决定状态按装饰部署还是按生成实例隔离。

| 对比项 | Python 装饰器 | Java 注解 | C/C++ 宏 |
|---|---|---|---|
| 主要机制 | 运行时可调用对象和名字重绑定 | 元数据/框架处理，具体行为依赖工具链 | 预处理阶段的文本替换或展开 |
| 典型作用时机 | `def`/`class` 创建完成后 | 编译或运行时由框架读取 | 编译前 |
| 是否天然产生包装调用 | 可以返回 wrapper 或代理 | 不由注解本身保证 | 不适用，宏生成或替换文本 |
| 主要风险 | 类型、签名、元数据和性能变化 | 注解本身可能没有运行时行为 | 展开结果难以调试、缺少对象语义 |

### 现代 Python 3.12 补充

- `functools.wraps`/`update_wrapper` 用于复制包装函数的常见元数据；它不能修复方法绑定、代理类型或特殊方法查找。
- `functools.lru_cache` 是标准库中的参数化装饰器案例；使用它时要确认参数可哈希、缓存生命周期和并发语义。
- `contextlib.contextmanager` 使用生成器函数构造上下文管理器，展示了装饰器把函数对象转换成另一种协议对象的思路。
- Web 路由、测试标记、重试和权限装饰器都属于本章的应用模式；实际框架可能还依赖 `inspect`、描述符或元类，不能只凭 `@` 判断行为。
- Python 的函数装饰器语法来自 PEP 318，类装饰器规范来自 PEP 3129；这些是历史背景补充，不改变本章的运行时模型。

高级开发者还应掌握包装器的异常和返回值传播、签名与 `inspect.signature`、`__wrapped__` 链、描述符绑定、特殊方法代理、线程安全状态，以及何时用简单函数调用、`__init_subclass__` 或元类替代装饰器。

## 学习建议（Learning Advice）

- 重要程度：5/5。框架使用者至少要能展开 `@d` 的重绑定过程；库作者还要能设计状态、签名和元数据策略。
- 应掌握到的程度：能写普通函数装饰器、参数化装饰器和类装饰器，能解释闭包与 `__call__` 的区别，能识别方法绑定陷阱，能为包装器保留返回值、异常和元数据。
- 实践要求：分别测试普通函数、方法、多个被装饰对象、多个生成实例、关键字参数、默认参数和内置特殊方法；不要只看一次成功输出。
- 后续学习：阅读第40章的 metaclass（元类），并把本章的名字重绑定与类创建流程、描述符、函数自省和标准库 `functools` 联系起来。
