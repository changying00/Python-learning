>
> 因为模块和类（class）其实不过是"华丽版"的命名空间，所以这一部分也把命名空间的概念正式化。

- **核心概念**：模块是 Python 程序的最高级组织单元。想象一栋写字楼——语句是砖，函数是房间，模块就是整层楼，而命名空间是层与层之间"谁也看不见谁"的隔断墙。本章就是这张"楼层平面图"。
- **底层实现**：模块对象本质上是一个带有 `__dict__` 字典的对象，所有顶层名字都被存进这个字典里，作为模块的属性。所谓"模块就是命名空间"，在 CPython 里体现为模块对象 + 属性字典。

## 22.2 Module Essentials（模块要点）

### 英文原文

> In simple and concrete terms, modules typically correspond to Python source code files. Each file of code is a module automatically, and modules import other modules to use the names they define. Modules might also correspond to extensions coded in external languages such as C, Java, or C#, and even to entire directories in package imports, which extend the model for nested files. In all their forms, modules are processed with two statements and one tool:
>
> **import** — Lets a client (importer) fetch a module as a whole
>
> **from** — Allows clients to fetch particular names from a module
>
> **importlib.reload** — Provides a way to reload a module's code without stopping Python
>
> We've used imports in prior examples to load both Python standard-library modules, as well as code files that reside in the current directory—the one we are in when launching the REPL or a script file. While straightforward on the surface, these tools imply an underlying model that's richer than you might think. Before we delve into its details, though, let's begin by getting a handle on the purpose of modules in our Python programs.

### 中文翻译

> 用简单具体的话说，模块通常对应 Python 源代码文件。每个代码文件自动就是一个模块，模块之间通过导入（import）彼此，以使用对方定义的名字。模块也可能对应以 C、Java、C# 等外部语言编写的扩展（extension），甚至对应包导入（package import）中的整个目录——这扩展了模型，使其支持嵌套文件。无论何种形式，模块都由两个语句和一件工具来处理：
>
> **import（导入）**——让客户端（导入方）把整个模块作为一个整体取走
>
> **from（从…导入）**——允许客户端从模块中取出特定名字
>
> **importlib.reload（重载）**——提供一种不必停止 Python 就能重新加载模块代码的方式
>
> 我们在前面的例子中已经用导入加载过 Python 标准库模块，以及位于当前目录的代码文件——即我们启动 REPL 或脚本文件时所在的那个目录。虽然表面上很简单，但这些工具背后的底层模型比你想的要丰富得多。在深入细节之前，让我们先弄清楚模块在我们 Python 程序中的用途。

### 深度理解

- **核心概念**：处理模块的核心工具只有三样：`import`（取整个模块）、`from`（取模块里的特定名字）、`importlib.reload`（不重启 Python 重新执行模块代码）。本书后续所有关于模块的内容都围绕这三者展开。
- **底层实现**：`import b` 在字节码层面是一条 `IMPORT_NAME` 指令；`from b import x` 在 `IMPORT_NAME` 之后还会执行 `IMPORT_FROM` 指令。`importlib.reload` 则是重新运行模块文件的字节码并更新 `sys.modules` 中的模块对象内容。
- **设计原因**：只给两个语句一个工具，是因为模块的绝大部分需求就这两种：要整包，还是要单件。这种"最小接口"设计让导入系统简单易学，复杂的文件解析全部隐藏在语句背后。
- **解决什么实际问题**：加载标准库（`import sys`）、加载自己写的代码文件、以及运行时更新模块代码（reload 用于动态定制，如热更新配置）。
- **初学者误区**：把 `import` 理解为"把另一文件的文本粘贴进来"，或以为 reload 是"再 import 一次"。前者是 C 语言 `#include` 的思维方式，后者会惊讶地发现"重复 import 根本不重新执行代码"——这正是 `sys.modules` 缓存导致的（见 22.6 节）。

## 22.3 Why Use Modules?（为什么使用模块？）

### 英文原文

> In short, modules provide an easy way to organize components into a system, by serving as self-contained packages of variables known as namespaces. All the names defined at the top level of a module file become attributes of the imported module object, but a file's names can't be seen without imports, and don't clash with names in other files.
>
> This model is related to the scopes we studied in the last part of this book. As we learned in Chapter 17, imports give access to names in a module's global scope. The file surrounding a function is always that function's own global scope, but imports allow one file to see the global names of another file as attributes. That is, the module file's global scope morphs into the module object's attribute namespace when it is imported.
>
> Ultimately, this allows us to link individual files into a larger program system, with three primary benefits:
>
> **Code reuse** — Modules make code permanent. Because a module's code is saved in a file, you can both run it multiple times and use it in multiple programs. As you've learned, code you type at a Python REPL goes away when you exit Python, but code in module files can be rerun as many times as you wish. Moreover, the tools you define in modules may be reused by any number of external clients, and in programs coded both now and in the future.
>
> **Minimizing redundancy** — Module reuse naturally enables shared copies of common code. If more than one file uses the same or similar code, you can write it once in a module that can then be imported by many clients. For example, in the prior chapter's benchmarking examples, test scripts imported common timer and test-runner functions, instead of repeating them. In other words, modules—like functions—help us factor code to avoid the redundancy that results from copy-and-paste programming. As for functions, this minimizes work when common code must be changed.
>
> **Namespace partitioning** — Modules are also the highest-level namespace structure in a Python program. Although they are fundamentally just packages of names, these packages are also self-contained—you can never see a name in another file unless you explicitly import that file. Much like the local scopes of functions, this helps avoid name clashes across your programs. In fact, you can't avoid this feature—everything "lives" in a module. Because both the code you run and the objects you create are always implicitly enclosed in modules, modules group components by nature.
>
> At least that's the abstract story. To truly understand the role of modules in a Python system, we need to digress for a moment and explore the general structure of a Python program.

### 中文翻译

> 简而言之，模块提供了一种把组件组织成系统的简便方式：它作为自包含的变量包（称为命名空间）来服务。模块文件顶层定义的所有名字都会成为被导入模块对象的属性（attribute），但一个文件里的名字，未经导入就不可见，也不会与其他文件中的名字冲突。
>
> 这个模型与我们上一部分研究的作用域（scope）密切相关。如第 17 章所学，导入让我们能够访问模块全局作用域中的名字。包围函数的那个文件永远是函数自身的全局作用域，但导入允许一个文件把另一个文件的全局名字当作属性来看待。也就是说，模块文件的全局作用域在被导入时"变身"（morph）为模块对象的属性命名空间。
>
> 归根结底，这让我们能够把一个个独立文件链接成更大的程序系统，带来三大主要好处：
>
> **代码复用（Code reuse）**——模块让代码"永生"。因为模块代码保存在文件中，你既可以多次运行它，也可以把它用在多个程序中。如你所知，在 Python REPL 里敲的代码在你退出 Python 时就消失了，但模块文件里的代码可以想运行多少次就运行多少次。此外，你在模块中定义的工具可以被任意多的外部客户端复用，也可以用在你现在和将来编写的程序里。
>
> **最小化冗余（Minimizing redundancy）**——模块复用自然带来了公共代码的共享副本。如果不止一个文件使用相同或相似的代码，你可以在一个模块里写一次，再被许多客户端导入。例如，上一章的基准测试（benchmarking）例子中，测试脚本导入了公共的计时器和测试运行器函数，而不是重复编写它们。换句话说，模块——和函数一样——帮助我们分解代码，避免"复制粘贴式编程"造成的冗余。和函数一样，当公共代码需要修改时，这也把工作量降到了最低。
>
> **命名空间划分（Namespace partitioning）**——模块还是 Python 程序中最高层的命名空间结构。虽然它们本质上只是名字的包，但这些包也是自包含的——除非你显式导入某个文件，否则你永远看不到另一个文件里的名字。这与函数的局部作用域非常相似，有助于避免程序间的名字冲突。事实上，你根本躲不开这个特性——一切都"活"在某个模块里。因为你运行的代码和你创建的对象总是被隐式地包裹在模块中，模块天然地对组件进行了分组。
>
> 至少这是抽象层面的说法。要真正理解模块在 Python 系统中的作用，我们需要暂时离题，探究一下 Python 程序的总体结构。

### 深度理解

- **核心概念**：用模块的三大好处——代码复用、消除冗余、命名空间划分——解释"为什么要用模块"。其中命名空间划分是最本质的一条：模块的全局作用域在导入时"变身"为模块对象的属性命名空间。
- **底层实现**："变身"的过程在 CPython 里真实存在：`import b` 会创建 `ModuleType` 对象，然后逐条执行 `b.py` 的字节码，顶层每条赋值语句都会执行 `STORE_ATTR`，把名字存进模块对象的 `__dict__`。全局作用域和模块属性字典，本质是同一个字典的两种视角。
- **设计原因**：为什么 Python 不像 C 那样"文本包含"（`#include`）而是"对象属性"？因为文本包含会造成同名覆盖和编译依赖混乱，而运行时属性访问让"谁导入谁"完全显式、可按需动态进行。
- **解决什么实际问题**：三个场景——同一份代码想在多个程序里用（复用）、同一段逻辑被多处复制导致改一处漏三处（冗余）、两个模块都定义了 `max` 却互不干扰（冲突）。
- **初学者误区**：以为"所有文件共享一套全局名字"（那是 C 预处理器的世界观）；或者反过来，以为模块命名空间必须"手动创建"。实际上一切都是自动的：任何 `.py` 文件天然就是模块，顶层名字天然就是属性。

## 22.4 Python Program Architecture（Python 程序架构）

### 英文原文

> So far in this book, many examples have sugarcoated the complexity of Python programs. In practice, programs usually involve more than just one file. For all but the simplest scripts, your programs will take the form of multifile systems—as the code-benchmarking programs of the preceding chapter illustrated. Even if you can get by with coding a single file yourself, you will almost certainly wind up using external files that someone else has already written.
>
> This section reviews the general architecture of Python programs—the way you divide a program into a collection of source code files (a.k.a. modules) and link the parts into a whole. As you'll see, Python fosters a modular program structure that groups functionality into coherent and reusable units, in ways that are almost automatic. Along the way, this section also explores the central concepts of Python modules, imports, and object attributes.

### 中文翻译

> 到目前为止，本书中的许多例子都把 Python 程序的复杂性"糖衣化"了。实际上，程序通常不止一个文件。除了最简单的脚本之外，你的程序都会采用多文件（multifile）系统的形式——上一章的代码基准测试程序就说明了这一点。即使你自己只写一个文件就能搞定，你几乎也必然会用到别人已经写好的外部文件。
>
> 本节回顾 Python 程序的总体架构——也就是你如何把程序划分成一组源代码文件（也就是模块），并把各个部分链接成一个整体。你将会看到，Python 培育了一种模块化的程序结构，以几乎自动化的方式把功能组织成内聚、可复用的单元。与此同时，本节也会探讨 Python 模块、导入和对象属性的核心概念。

### 深度理解

- **核心概念**：现实世界的 Python 程序是多文件系统：一个顶层脚本（script）+ 零个或多个模块库。架构 = 怎么拆 + 怎么连。
- **底层实现**："连"靠的是 import 语句在运行时把模块对象绑定到变量上；"拆"没有任何强制规定，纯靠约定和组织。
- **设计原因**：单文件脚本能跑，但无法分工、无法复用。多文件是规模化的必然。Python 之所以让"文件即模块"自动成立，是为了让拆分几乎零成本——你不需要像 Java 那样声明包名才能拆文件。
- **解决什么实际问题**：一个项目多人协作时怎么切分代码、代码怎么跨文件引用、程序入口和工具库怎么区分。
- **初学者误区**：分不清"脚本文件"和"模块文件"的职责——脚本负责"做事情"（顶层代码会立即执行），模块负责"定义工具"（顶层代码只是把名字准备好）。同一个文件在一种场景是脚本，在另一种场景可能被当作模块导入。

## 22.4.1 How to Structure a Program（如何组织一个程序）

### 英文原文

> At a base level, a Python program consists of text files containing Python statements, with one main top-level file, and zero or more supplemental files known as modules.
>
> Here's how this works. The top-level (a.k.a. script) file contains the main flow of control of your program—this is the file you run to launch your application. The module files are libraries of tools, used to group components used by the top-level file, and possibly elsewhere. Top-level files use tools defined in module files, and modules use tools defined in other modules.
>
> Although they are files of code too, module files generally don't do anything when run directly; rather, they define tools intended for use in other files. A file imports a module to gain access to the tools it defines, which are known as its attributes—variable names attached to objects such as functions. Ultimately, we import modules and access their attributes to use their tools.

### 中文翻译

> 在最基本的层面上，一个 Python 程序由包含 Python 语句的文本文件组成：一个主要的顶层（top-level）文件，外加零个或多个称为模块的补充文件。
>
> 它是这样运作的：顶层文件（又称脚本，script）包含程序的主控制流——这是你运行以启动应用程序的文件。模块文件是工具库，用来组织顶层文件以及其他地方要用的组件。顶层文件使用模块文件中定义的工具，模块也使用其他模块中定义的工具。
>
> 虽然模块文件本身也是代码文件，但它们通常不会在直接运行时"做什么事"；相反，它们定义供其他文件使用的工具。一个文件导入某个模块，是为了访问它定义的工具——这些工具被称为模块的属性（attribute），即挂在函数等对象上的变量名。归根结底，我们导入模块并访问其属性，来使用它们的工具。

### 深度理解

- **核心概念**：程序结构 = 一个"总指挥"（顶层脚本，跑起来的文件）+ 若干"工具库"（模块）。工具用属性（attribute）的形式向外暴露。
- **底层实现**：顶层脚本由 `python a.py` 命令以 `__main__` 模块的身份运行；被导入的模块则按名字创建各自独立的模块对象。两者执行的字节码完全相同，差别只在于"谁被当作主程序"。
- **设计原因**：把"控制流"和"工具定义"分开，是程序架构中最古老也最有效的组织原则。脚本负责流程编排（像导演），模块负责功能实现（像演员）。
- **解决什么实际问题**：入口文件该放什么、工具文件该放什么；如何让多个脚本共享同一套底层实现。
- **初学者误区**：直接运行模块文件时"什么都没发生"就以为代码写错了——其实模块被直接运行时，顶层 `def` 只是定义了函数，没有任何调用，所以看起来"没动静"，这是正常的设计意图。

## 22.4.2 Imports and Attributes（导入与属性）

### 英文原文

> To make this a bit more concrete, Figure 22-1 sketches the structure of a Python program composed of three files: `a.py`, `b.py`, and `c.py`. The file `a.py` is chosen to be the top-level script file; it will be a simple text file of statements, which is executed from top to bottom when launched. The files `b.py` and `c.py` are modules; they are simple text files of statements as well, but they are not usually launched directly. Instead, as explained previously, modules are normally imported by other files that wish to use the tools the modules define.
>
> **Figure 22-1.** Program architecture in Python
>
> For instance, suppose the file `b.py` in Figure 22-1 defines a function called `job` for external use, per Example 22-1 (and ignoring `c.py` for the moment). As you learned when studying functions in Part IV, `b.py` will contain a Python `def` statement to generate the function, which you can later run by passing values in parentheses after the function's name.
>
> **Example 22-1.** b.py (module)
>
> ```python
> def job(tool):
>     print(tool, 'coder')
> ```
>
> This function probably seems trivial at this point in this book, but we're keeping it simple to focus on module basics. Now, suppose `a.py` wants to use `job`. To this end, it might contain Python statements like those in Example 22-2.
>
> **Example 22-2.** a.py (script)
>
> ```python
> import b
> b.job('Python')
> ```
>
> The first of these, a Python `import` statement, gives the file `a.py` access to everything defined by top-level code—that is, code not nested inside a function or class—within the file `b.py`. The code `import b` roughly means: *Load the file `b.py` (unless it's already loaded), and give me access to all its attributes through the name `b`*.
>
> To satisfy such goals, `import` (and, as you'll see later, `from`) statements execute and load other files on request. More formally, in Python, cross-file module linking is not resolved until such `import` statements are executed at runtime; their net effect is to assign module names—simple variables like `b`—to loaded module objects. In fact, the module name used in an `import` statement serves two purposes: it identifies the external file to be loaded (by base name `b` here), but it also becomes a variable assigned to the loaded module.
>
> Similarly, objects defined by a module's code are also created at runtime, while the import is executing: `import` literally runs statements in the target file one at a time to create its contents. Along the way, every name assigned at the top level of the file becomes an attribute of the module, accessible to importers. For example, the second of the statements in `a.py` calls the function `job` defined in the module `b`—and created by running its `def` statement during the import—using object attribute notation. The code `b.job` means: *Fetch the value of the name `job` that lives within the object `b`*.
>
> This happens to be a callable function in our example, so we pass a string in parentheses (`'Python'`). If you run `a.py`, the words "Python coder" will be printed—hardly a shocker if you've read prior chapters, but illustrative.
>
> As we've seen, the `object.attribute` notation is general and pervasive in Python code because most objects have useful attributes that are fetched with the "." operator. Some attributes reference callable objects like functions that take action (e.g., a salary computer), while others are simple values that denote data (e.g., a person's name).
>
> Imports are similarly general because any file can import tools from any other file. For instance, the file `a.py` in Figure 22-1 may import `b.py` to call its function, but `b.py` might also import `c.py` to leverage different tools defined there. In fact, import chains can go as deep as you like: in this example, module `a` can import `b`, which can import `c`, which can import `b` again, and so on. More realistically, in the benchmarking code of the prior chapter, test scripts imported runner modules, which imported timer modules.
>
> The main point behind all this is that modules (and module packages, described in Chapter 24) are the topmost level of code reuse in Python. Components coded in module files can be used both in your original program and in any other programs you may write later. For instance, if we later discover that the function `b.job` in Example 22-1 is widely useful, we can deploy it in completely different programs; all we have to do is import `b` again from the other programs. While unlikely in this simple demo, modules by nature create packages of reusable tools.

### 深度理解

- **核心概念**：顶层脚本 + 模块 + 导入 + 属性，四者构成 Python 程序架构的全部要素。`import b` 的名字 `b` 一石二鸟：既是文件名，又是变量名。
- **底层实现**：执行 `import b` 时，CPython 完成三步（查找→编译→运行）后，把模块对象绑定到局部命名空间的 `b` 上（执行 `STORE_NAME` 指令）。`b.job` 是属性访问：先取出 `b` 模块对象，再到其 `__dict__` 里查 `job`（LOAD_ATTR 指令）。运行 `a.py` 时，顶层 `import` 和 `b.job('Python')` 都是立即执行的语句。
- **设计原因**：把"文件定位"和"名字绑定"合成一个语句，省去了 C 语言里"头文件 + 链接器"两套机制。对象属性表示法让跨文件访问与对象内部访问语法完全统一——`b.job` 和 `person.name` 没有任何机制上的区别。
- **解决什么实际问题**：程序入口文件想用工具库里的函数；一个工具模块想调用另一个工具模块（导入链）；写完的工具想被未来的其他项目复用。
- **初学者误区**：以为 `import b` 之后文件里所有名字都"自动可见"——错，必须通过 `b.xxx` 取；以为 `import` 是"把文件内容粘进来"——错，它只创建对象并绑定变量；以为函数被"搬运"进了 `a.py`——错，函数对象活在 `b` 模块里，`a.py` 只是拿到了引用。

### 代码分析

```python
# b.py（模块）
def job(tool):
    print(tool, 'coder')   # 打印传入的工具名 + 'coder'

# a.py（脚本）
import b                   # 加载 b.py 并绑定为变量 b
b.job('Python')            # 取 b 的属性 job 并调用，传入 'Python'
```

**解释器如何处理**：

1. 运行 `a.py` 时，解释器先把它编译成字节码，然后逐条执行顶层语句。
2. 执行到 `import b`：解释器检查 `sys.modules` 中是否有 `b`，没有则走三步流程——在 `sys.path` 里找到 `b.py`、编译成字节码、执行其代码。`b.py` 里的 `def job(...)` 被执行，创建函数对象，并作为属性 `job` 存进模块对象 `b` 的 `__dict__` 中。最后把模块对象赋给 `a.py` 顶层命名空间里的名字 `b`。
3. 执行到 `b.job('Python')`：先取模块对象 `b`，再取它的 `job` 属性（一个函数对象），然后传入字符串 `'Python'` 调用它。
4. 函数体执行 `print('Python', 'coder')`，终端输出 `Python coder`。

**设计思想**：`import` 的名字承担"文件标识 + 变量绑定"双重职责，既免去了写文件路径的麻烦，又让导入方拥有一个显式的前缀（`b.`），天然形成命名空间隔离。
