### 深度理解

- **核心概念**：装饰器（decorator）是一种"**在函数/类定义语句收尾的瞬间自动运行一段代码**"的机制。它不是某个只能在函数前面加一个 `@` 的小记号，而是一整套"由 callable 管理 callable"的协议。本章是散落在前文各处 `@` 用法的总中枢。
- **底层实现**：装饰器的本质是**名字重绑定（name rebinding）**——`@dec` 写在 `def f` 之前，等价于函数定义结束后自动执行 `f = dec(f)`。理解了这一条，装饰器机制就已经理解了一半。
- **设计原因**：Lutz 点破了它的现实意义——装饰器正在流行的 Python 框架中普及（如 Flask 的 `@app.route`、Django 的 `@login_required`、PyTorch 的 `@autocast`）。框架的使用者即使不会自己写装饰器，也必须看得懂它们。
- **解决什么实际问题**：把"横切关注点"（日志、计时、校验、注册、权限）从业务代码中剥离出来，做到**一次声明、处处生效、显式可见**。这些逻辑若不用装饰器，就得散落在每个调用点，极易遗漏。
- **初学者误区**：以为装饰器是"魔法语法"。其实它毫不新奇——它只是把 `f = dec(f)` 写成 `@dec` 的等价形式。真正的难点不在于 `@` 本身，而在于**如何编写那个要返回 callable 的 `dec`**。

## 39.2 What's a Decorator?（什么是装饰器？）

### 英文原文

> Simply put, **decoration** is a way to specify management or augmentation code for functions and classes. Decorators themselves take the form of callable objects (e.g., functions) that process other callable objects. As suggested earlier in this book, Python decorators come in two related flavors:
>
> **Function decorators**, added first, do name rebinding at function definition time, providing a layer of logic that can manage functions and methods or later calls to them.
>
> **Class decorators**, added later, do name rebinding at class definition time, providing a layer of logic that can manage classes or the instances created by later calls to them.
>
> In short, decorators provide a way to insert **automatically run code** at the close of function and class definition statements—at the end of a `def` for function decorators and at the end of a `class` for class decorators. Such code can play a variety of roles, as described in the following sections.

### 中文翻译

> 简单来说，**装饰（decoration）**是一种为函数和类指定"管理代码或增强代码"的方式。装饰器本身采用"可调用对象（callable objects，例如函数）"的形式，去处理其他可调用对象。正如本书前文所暗示的，Python 装饰器分两个相关门类：
>
> **函数装饰器（function decorators）**，最先加入，在函数定义时执行名字重绑定，提供一层逻辑去管理函数与方法（methods），或管理对它们的后续调用。
>
> **类装饰器（class decorators）**，后来加入，在类定义时执行名字重绑定，提供一层逻辑去管理类，或管理由后续对其的调用所创建的实例。
>
> 总之，装饰器提供了一种方式，能在函数和类定义语句收尾时**插入自动运行的代码**——函数装饰器插在 `def` 语句的末尾，类装饰器插在 `class` 语句的末尾。这样的代码可以扮演多种角色，正如以下各节所述。

### 深度理解

- **核心概念**：装饰器提供的钩子是"**定义语句结束时自动运行**"。这与普通赋值语句一样平凡：`def` 与 `class` 语句本来就是在运行时执行的，装饰器只不过是在这一语句末尾追加了一次重赋值。
- **底层实现**：CPython 编译 `@dec` 时，会把它编译成"定义函数/类 → 调用 `dec` → 把结果赋回原名字"的字节码序列。装饰器在模块被 import 时执行一次，而不是在每次调用时执行。
- **设计原因**：函数先加入，社区先在函数上趟平了路，后来才把同样的模型推广到类。两类装饰器共享同一套语法，降低了学习迁移成本。
- **解决什么实际问题**：让"给函数加日志、缓存、鉴权"这类横切逻辑从每个调用点收拢到一处静态声明；类装饰器则把"每次创建实例都要手动包一层代理（proxy）"的苦役压缩成一条 `@` 行。
- **初学者误区**：以为"装饰器装饰的是函数本身"。准确的说法是——**装饰器的返回值**（可能还是原函数，也可能是别的任意可调用对象）被绑定到原名字上。

### 代码分析

本章开篇是概念介绍，其"代码"其实是一幅映射图：

```python
# 装饰器语法：
@decorator          # 装饰函数
def F(arg): ...
F(99)               # 调用函数

# 等价形式：
def F(arg): ...
F = decorator(F)    # 重绑定：把函数名绑定到装饰器的返回结果
F(99)               # 本质上调用 decorator(F)(99)
```

Python 解释器看到 `@decorator` 时，会先编译 `def F` 创建函数对象 `F`，紧接着立刻把 `F` 作为参数调入 `decorator`，最后把返回结果重新绑定到 `F` 这个名字上。因此之后 `F(99)` 不再调用原来的函数体，而是调用 `decorator(F)` 的返回值——可能是原始函数，也可能是一个包装器（wrapper）。**设计思想**：把"事后追加行为"变成定义时刻的确定性动作，让增强逻辑与函数本体解耦。

## 39.3 Managing Calls and Instances（管理调用与实例）

### 英文原文

> In typical use, this automatically run code may be used to augment calls to functions and classes. It arranges this by installing **wrapper** (a.k.a. **proxy**) objects to be invoked later:
>
> **Call proxies**: Function decorators install wrapper objects to intercept later **function calls** and process them as needed, usually passing the call on to the original function to run the managed action.
>
> **Interface proxies**: Class decorators install wrapper objects to intercept later **instance-creation calls** and process them as required, usually passing the call on to the original class to create a managed instance.
>
> Decorators achieve these effects by automatically rebinding function and class names to other callables at the end of `def` and `class` statements. When later invoked, these callables can perform tasks such as tracing and timing function calls, managing access to class instance attributes, and so on.

### 中文翻译

> 在典型使用中，这段自动运行的代码可以用来增强对函数和类的调用。它的实现方式是：安装**包装器（wrapper）**（又名**代理（proxy）**）对象，留待之后被调用：
>
> **调用代理（call proxies）**：函数装饰器安装包装器对象，以拦截后续的**函数调用**并按需处理——通常把调用转发给原函数，去执行被管理的动作。
>
> **接口代理（interface proxies）**：类装饰器安装包装器对象，以拦截后续的**实例创建调用（instance-creation calls）**并按需处理——通常把调用转发给原类，从而创建被管理的实例。
>
> 装饰器通过在 `def` 和 `class` 语句的末尾自动把函数名、类名重绑定到其他可调用对象，来实现这些效果。当这些可调用对象后来被调用时，就可以执行诸如跟踪（tracing）与计时（timing）函数调用、管理类实例属性的访问等任务。

### 深度理解

- **核心概念**："调用代理"与"接口代理"是把所有装饰器角色一分为二的两个原型。函数装饰器拦截"对函数的调用"；类装饰器拦截"对类的实例化调用"；而拦截实例的接口访问，靠的是包装器实例上的 `__getattr__`。
- **底层实现**：安装代理的本质，是把名字从"原来的可调用对象"改成"另一个可调用对象（wrapper）"。调用发生时，解释器只认识新的代理对象，原对象被埋藏在代理内部。
- **设计原因**："拦截 → 处理 → 放行给原对象"是代理模式的普适优点；装饰器把"安装代理"这个动作自动化了，让使用者无需手工改写调用点。
- **解决什么实际问题**：想给所有调用加密、鉴权、缓存、记录、计时，又不想去每个调用点改写——代理是标准解法，装饰器让安装代理只需要一行 `@`。
- **初学者误区**：以为包装器必须返回"函数"。实际上包装器只须是"可调用"即可；返回 lambda、类实例（带 `__call__`）都完全可以。

## 39.4 Managing Functions and Classes（管理函数与类）

### 英文原文

> Although most examples in this chapter deal with using wrappers to intercept later calls to functions and classes, this is not the only way decorators can be used:
>
> **Function managers**: Function decorators can also be used to **manage function objects** instead of or in addition to later calls to them—to register a function to an API, for instance. Our primary focus here, though, will be on their more commonly used call-wrapper application.
>
> **Class managers**: Class decorators can also be used to **manage class objects** directly, instead of or in addition to instance-creation calls—to augment a class with new methods or data, for example. Because this role intersects strongly with that of **metaclasses**, we'll explore additional decorator use cases in the next chapter.
>
> As detailed there, both tools run at the end of the class creation process, but class decorators often offer a lighter-weight solution.
>
> In other words, function decorators can be used to manage both function calls and function objects, and class decorators can be used to manage both class instances and classes themselves. By returning the decorated object itself instead of a wrapper, decorators become a simple post-creation step for functions and classes.
>
> Regardless of the role they play, decorators provide a convenient and explicit way to code tools useful both during program development and in live production systems.

### 中文翻译

> 虽然本章的大多数示例都是利用包装器去拦截对函数和类的后续调用，但这并不是装饰器唯一的使用方式：
>
> **函数管理器（function managers）**：函数装饰器也可以用来**管理函数对象本身**，而不是（或不限于）对它们的后续调用——例如把函数注册到一个 API。不过我们这里的重点，仍然是装饰器更常见的"调用包装器"应用。
>
> **类管理器（class managers）**：类装饰器也可以直接**管理类对象本身**，而不是（或不仅是）处理实例创建调用——例如为类扩充新方法或新数据。因为这个角色与**元类（metaclasses）**的角色高度重叠，我们将在下一章中探讨更多的装饰器用例。正如那里将详述的，两种工具都在类创建过程的末尾运行，但类装饰器通常提供更轻量级的解决方案。
>
> 换言之，函数装饰器既能管理函数调用，也能管理函数对象；类装饰器既能管理类实例，也能管理类本身。如果装饰器不加包装器、而是直接返回被装饰对象本身，那么它就为函数和类提供了简单的"创建后处理步骤（post-creation step）"。
>
> 无论扮演哪种角色，装饰器都提供了一种便捷而显式的方式去编写工具——这些工具在程序开发期和真实生产系统中都大有用途。

### 深度理解

- **核心概念**：装饰器的能力光谱有两大极端——管理"原函数/原类**本身**"（管理器）vs. 管理"**对它们的后续调用**"（包装器）。
- **底层行为**：当作管理器时，装饰器 `dec` 拿到 `O`，处理完 `O` 后 `return O`（返回原对象）；当作包装器时，`dec` 返回别的可调用对象。
- **设计原因**：注册到 API、初始化属性这类"一次性"需求不需要代理，只需要"创建结束时顺手跑一段代码"——这正好是装饰器的定位。
- **解决什么实际问题**：例如把一组函数注册进路由表、给函数附加元数据、把类登记到框架的清单中。若没有装饰器，你得在定义之后到处显式调用注册函数。
- **初学者误区**：以为 `@dec` 一定会产生"代理"并带来额外调用开销。其实装饰器完全可以零开销（直接返回原对象）——是否包装，取决于你写不写 wrapper。

## 39.5 Using and Defining Decorators（使用与定义装饰器）

### 英文原文

> Depending on your job description, you might encounter decorators as a user or a provider. As we've seen, Python itself comes with built-in decorators that have specialized roles—static and class method declaration, property creation, and more. In addition, many popular Python toolkits include decorators to perform tasks such as managing database or user-interface logic. In such cases, we can get by without knowing how the decorators are coded.
>
> For more general tasks, programmers can code arbitrary decorators of their own. For example, function decorators may be used to augment functions with code that adds call tracing or logging, caches call results, performs argument validity testing during debugging, times calls made to functions for optimization, and so on.
>
> Any behavior you can imagine adding to—really, wrapping around—a function call is a candidate for custom function decorators.
>
> On the other hand, function decorators are designed to augment only a specific function or method call, not an entire **object interface**. Class decorators fill the latter role better—because they can intercept instance-creation calls, they can be used to implement arbitrary object interface augmentation or management tasks.
>
> For example, custom class decorators can trace, validate, or otherwise augment every attribute reference made for an object. They can also be used to implement proxy objects, singleton classes, and other common coding patterns.
>
> In fact, you'll find that many class decorators are a prime application of the delegation coding pattern we met in Chapter 31.

### 中文翻译

> 取决于你的职位描述，你可能以"使用者"或"提供者"的身份遇到装饰器。正如我们所看到的，Python 自带一些具有专门角色的内建装饰器——静态方法（staticmethod）与类方法（classmethod）声明、property 创建等等。此外，许多流行的 Python 工具包也包含装饰器，用来执行诸如管理数据库或用户界面逻辑之类的任务。在这些情况下，我们即使不知道装饰器是怎么编码的，也能顺利使用。
>
> 对于更一般的任务，程序员可以编写属于自己的任意装饰器。例如，函数装饰器可以用来增强函数：添加调用跟踪或日志记录代码、缓存调用结果、在调试期间执行参数有效性测试、为优化目的而给函数调用计时等等。任何你能想象到可以附加在——准确说是"包裹在"——函数调用周围的行为，都是自定义函数装饰器的候选。
>
> 另一方面，函数装饰器设计上只能增强某一个具体的函数或方法调用，而不是整个**对象接口（object interface）**。类装饰器更适合填补后者的角色——因为类装饰器能拦截实例创建调用，所以它们可以用来实现任意的对象接口增强或管理任务。例如，自定义类装饰器可以跟踪、校验或以其他方式增强对对象所做的每一次属性引用。它们还可以用来实现代理对象、单例类（singleton classes）以及其他常见编码模式。事实上，你会发现许多类装饰器正是我们在第 31 章遇到的**委托（delegation）**编码模式的典型应用。

### 深度理解

- **核心概念**：本节界定了装饰器的两大适用半径——函数装饰器管"单点调用"，类装饰器管"整体接口"。
- **底层实现**：管整体接口靠的是 `__getattr__` 钩子：包装器实例上任何未定义属性的访问都会落入 `__getattr__`，从而被转交给被包裹对象。
- **设计原因**：函数调用只是一次执行，而对象接口是无数次属性访问。拦截调用只需一次重绑定；拦截接口需要持续的代理层，因此用类装饰器更顺手。
- **解决什么实际问题**：单例、代理对象、接口跟踪、数据库 ORM 中"一个类对应一张表"的声明、UI 框架的事件绑定——这些都是类装饰器的主场。
- **初学者误区**：以为类装饰器只能"装饰用户自定义类"。其实只要包装器足够通用，连 list、dict 等内置类型也能被装饰（第 31 章的委托模式已示范）。

## 39.6 Why Decorators?（为什么使用装饰器？）

### 英文原文

> Like many advanced Python tools, decorators are never required from a purely technical perspective: we can often implement their functionality instead using simple helper function calls or other techniques. And at a base level, we can always manually code the name rebinding that decorators perform automatically.
>
> That said, decorators provide an explicit syntax for such tasks, which makes intent clearer, can minimize augmentation code redundancy, and may help ensure correct API usage:
>
> Decorators have a very **explicit** syntax, which makes them easier to spot than helper function calls that may be arbitrarily far removed from the subject functions or classes.
>
> Decorators are applied **once** when the subject function or class is defined; it's not necessary to add extra code at every call to the class or function, which may have to be changed in the future.
>
> Because of both of the prior points, decorators make it less likely that a user of an API will **forget** to augment a function or class according to API requirements.
>
> In other words, beyond their technical model, decorators offer some advantages in terms of both code maintenance and consistency. Moreover, as structuring tools, decorators naturally foster **encapsulation** of code, which reduces redundancy and makes future changes easier.
>
> Like most tools, decorators have some potential **drawbacks**, too—when they insert wrapper logic, they can alter the types of the decorated objects, and they may incur extra calls when used as call or interface proxies. On the other hand, the same considerations apply to any technique that adds wrapping logic to objects.
>
> We'll explore these trade-offs in the context of real code later in this chapter. Although the choice to use decorators is ultimately subjective, their advantages are compelling enough to have escalated them to common practice in the Python world. To help you decide for yourself, let's turn to the details.

### 中文翻译

> 与许多高级 Python 工具一样，从纯粹的技术角度看，装饰器从来不是必需的：我们常常可以用简单的辅助函数调用或其他技巧来实现相同的功能。在最底层，我们也总能手动写出装饰器自动执行的那些名字重绑定。话虽如此，装饰器为这类任务提供了**显式的语法**，这让意图更清晰、能减少增强代码的**冗余（code redundancy）**，并有助于**确保 API 的正确使用**：
>
> 装饰器拥有非常**显式（explicit）**的语法，比那些可能离被装饰函数或类任意遥远的辅助函数调用更容易被发现。
>
> 装饰器在被装饰的函数或类**定义时只应用一次**；不需要在被装饰类或函数的每一次调用处添加额外代码——那些调用点将来可能还要修改。
>
> 由于以上两点，装饰器使得 API 的使用者不太可能**忘记**按照 API 的要求去增强某个函数或类。
>
> 换言之，除了技术模型之外，装饰器在代码维护性与一致性上都带来一些好处。此外，作为结构化工具，装饰器还自然而然地促成了代码的**封装（encapsulation）**，这减少了冗余，也让将来的修改更容易。
>
> 与大多数工具一样，装饰器也有一些潜在的**弊端（drawbacks）**——当它们插入包装器逻辑时，会改变被装饰对象的类型；当它们用作调用代理或接口代理时，可能带来额外的调用开销。另一方面，任何为对象添加包装逻辑的技术都有同样的考量。
>
> 我们将在本章稍后的真实代码中审视这些权衡（trade-offs）。虽然是否使用装饰器最终是主观选择，但它们的优势已强大到足以让它们升级为 Python 世界中的常见实践。为了帮你做出自己的判断，让我们进入细节。

### 深度理解

- **核心概念**：本节回答"为什么不直接写 `f = dec(f)` 或封装辅助函数"——答案是**显式性（explicitness）**与**一次应用**。装饰器把行为声明放在定义旁，读者无需在代码中四处追查调用点。
- **底层实现**：语法层面，`@dec` 与手动 `f = dec(f)` 的字节码几乎完全一样；区别在于语法强调了"声明位置"和"单次应用"。
- **设计思想**：这是 Python 哲学"显式优于隐式"（Explicit is better than implicit）的直接落地，同时兼顾"最小冗余"——一次定义、处处生效。
- **解决的实际问题**：框架 API 的完整性——让"忘记增强"成为小概率事件；也让"把某个函数注册到某条路由"成为一种声明式表达。
- **初学者误区**：把"类型改变"的弊端想得过重。确实 `isinstance(f, types.FunctionType)` 在装饰后可能为 False，但在绝大多数"以调用来使用"的场景里无碍。本节特意预告了这个权衡，后面还会用 `__class__`、`isinstance` 演示它。

## 39.7 DECORATORS VERSUS MACROS（装饰器对比宏）

### 英文原文

> Python's decorators bear similarities to what some call aspect-oriented programming in other languages—code inserted to run automatically before or after a function call runs. Their syntax also very closely resembles (and is likely borrowed from) Java's annotations, though Python's model may be considered more flexible and general.
>
> Some liken decorators to macros too, but this isn't entirely apt and can be misleading. Macros, like C's `#define` preprocessor directive, are associated with textual replacement and expansion and designed for generating code.
>
> By contrast, Python's decorators are a runtime operation based upon name rebinding, callable objects, and often, proxies. While the two may have use cases that sometimes overlap, decorators and macros are fundamentally different in scope, implementation, and coding patterns.
>
> Comparing the two seems akin to comparing Python's `import` with a C `#include`, which similarly confuses a runtime object-based operation with text insertion.
>
> Of course, the term macro has also been diluted over time—to some, it now can also refer to any canned series of steps or procedure—and users of other languages might find the analogy to decorators useful anyhow. But they should also keep in mind that decorators are about callable objects managing callable objects, not text expansion. Python tends to be best understood and used in terms of Python idioms.

### 中文翻译

> Python 的装饰器与某些语言中所谓的**面向切面编程（aspect-oriented programming）**有相似之处——即在函数调用运行之前或之后自动插入执行的代码。它们的语法与 Java 的**注解（annotations）**也非常相似（很可能是借鉴而来），不过 Python 的模型可以被认为更灵活、更通用。
>
> 也有人把装饰器比作**宏（macros）**，但这个比喻并不完全恰当，还可能产生误导。宏，如 C 语言的 `#define` 预处理器指令，与文本替换（textual replacement）和展开（expansion）相关，其设计目的是生成代码。相比之下，Python 装饰器是**运行时（runtime）**操作——基于名字重绑定、可调用对象，并且往往基于代理。虽然两者的用例有时重叠，但装饰器与宏在范围、实现和编码模式上有着根本性的不同。把两者相提并论，就像把 Python 的 `import` 与 C 的 `#include` 相比——这同样混淆了"基于对象的运行时操作"与"文本插入"。
>
> 当然，"宏"这个术语随着时间推移已被稀释——对某些人来说，它现在也可以指任何成套的固定步骤或流程——而且其他语言的用户也许仍会发现把它类比于装饰器有些用处。但他们也应记住：装饰器是"可调用对象管理可调用对象"，而不是文本展开。Python 最好用 Python 自己的习语来理解和运用。

### 深度理解

- **核心概念**：装饰器是**运行时基于对象的操作**（运行期发生的名字重绑定），而宏是**编译前基于文本的操作**（字符串替换）。二者分属两个世界。
- **底层实现**：C 的 `#define` 在预处理阶段就完成了文本替换，编译器看到的已是替换后的代码；Python 的 `@dec` 则在程序运行、模块导入时以普通函数调用方式执行。
- **设计原因**：Lutz 指出，若把装饰器当宏理解，容易误以为装饰器"展开成代码文本"。实际它只是调用了 callable，这与 Python 一贯的"一切皆对象"哲学一致。
- **解决什么实际问题**：这个区分帮助开发者选型——需要"生成代码"用宏（或代码生成器），需要"运行时包装行为"用装饰器。Java 注解与 Python 装饰器也类似，但 Python 模型更通用（注解常只是元数据，装饰器则真正包裹行为）。
- **初学者误区**：把 `@decorator` 想象成"在被装饰函数里粘贴了一段代码"。其实装饰器运行时包装与文本插入完全不同；用 Python 习语思考 Python，而不是用 C 的思维套用。

### 英文原文

> Let's get started with a first-pass look at decoration behavior from an abstract perspective. We'll write real and more substantial code soon, but since most of the magic of decorators boils down to an automatic rebinding operation, it's important to understand this mapping first—for both functions and classes.

### 中文翻译

> 让我们先从抽象视角第一次粗略打量装饰行为。我们很快就会写出真实而更充实的代码，但由于装饰器的大部分"魔法"归根到底是一次自动重绑定（automatic rebinding）操作，先弄清这层映射很重要——对函数和类都是如此。

### 深度理解

- **解决什么实际问题**：为后面所有示例提供一个统一的思维模型——无论装饰器多花哨，最终都能还原成一次赋值。
- **初学者误区**：急于写装饰器代码，却忽略了"这只是一次重绑定"这一根本心智模型，导致遇到额外参数、嵌套时就迷路。

## 39.9 Function Decorator Basics（函数装饰器基础）

### 英文原文

> As previewed earlier in this book, function decorators are largely just syntactic "sugar" that runs one function through another at the end of a `def` statement and rebinds the original function name to the result.

### 中文翻译

> 正如本书此前预览过的，函数装饰器在很大程度上只是语法"糖"——在 `def` 语句末尾把一个函数送入另一个函数处理，并把原函数名字重绑定到结果上。

### 深度理解

- **核心概念**：函数装饰器 = 在 `def` 末尾执行 `func = decorator(func)` 的语法糖。
- **底层实现**：`decorator` 必须是一元可调用对象（只收一个参数：被装饰函数），其返回值必须是可调用对象，且参数个数要能匹配之后的调用。
- **设计原因**：语法糖的目的不是增加能力，而是提高可读性与一致性，让"增强"意图直接写在定义旁边。
- **解决什么实际问题**：让"计时、日志、缓存"等增强逻辑不需要改函数体，也不需要每处调用点额外包函数。
- **初学者误区**：以为装饰器能任意改变函数的参数签名。其实 `decorator` 返回的 callable 要与之后调用时的参数形态匹配，否则调用会失败。

### 代码分析

```python
# 用法（Usage）：
@decorator          # 装饰函数
def F(arg): ...
F(99)               # 调用函数

# 等价映射为：
def F(arg): ...
F = decorator(F)    # 重绑定：把函数名绑定到装饰器的返回结果
F(99)               # 本质上调用 decorator(F)(99)
```

解释器处理顺序：编译 `def F` 生成函数对象 → 调用 `decorator(F)` → 把返回值赋回 `F`。此后每次 `F(99)` 调用的都是装饰器返回的对象，可能是 wrapper，也可能是原函数本身。书里还给出关键一行注释语句：

```python
func(6, 7)              # @decorator func → 之后逻辑等价
decorator(func)(6, 7)   # 真正的调用形态
```

**设计思想**：装饰只执行一次（定义时），之后每次调用都走包装层；若装饰器返回原函数，则调用等价于没装饰。

### 中文翻译

> 装饰器本身是一个"**返回可调用对象的可调用对象（callable that returns a callable）**"。也就是说，它返回的是"当被装饰函数经由原名调用时，之后要调用的那个对象"——可以是一个拦截后续调用的包装器对象，也可以是以某种方式增强后的原函数。事实上，装饰器可以是任意类型的可调用对象，也可以返回任意类型的可调用对象：函数与类的任何组合皆可，只是某些组合更适合特定场景。
>
> 例如，为了接入装饰协议、在函数刚创建后就管理它，我们可以编写这样形式的装饰器：
>
> > ```python
> > def decorator(F):
> >     # 在这里对函数 F 进行处理
> >     return F          # 返回原函数
> > @decorator
> > def func(): ...       # func = decorator(func)
> > ```
>
> 正是因此，它只是给函数定义添了一个"创建后处理步骤"：被装饰的原函数被赋回它自己的名字。这样的结构可以用来把函数注册到一个 API、初始化函数属性等等。
>
> 在更典型的使用中，为了插入拦截后续调用的逻辑，我们可以让装饰器返回一个与原函数不同的对象——一个针对后续调用的代理：
>
> (default)
> ```python
> def decorator(F):
>     # 保存或使用函数 F
>     # 返回一个不同的可调用对象：嵌套 def、带 __call__ 的类实例等
> @decorator
> def func(): ...       # func = decorator(func)
> ```
>
> 这个装饰器在"装饰时刻"被调用，它返回的可调用对象则在"原函数名字被后续调用"时被调用。装饰器本身收到被装饰的函数；返回的可调用对象收到之后传给被装饰函数名字的各种参数。只要编码得当，这对类层次的方法（methods）同样成立——隐藏的实例对象会自然地出现在返回可调用对象的第一个参数中。
>
> 用骨架代码来说，这里有一个抓住该要点的常用编码模式——装饰器返回一个保留原函数于闭包作用域的包装器：
>
> ```python
> def decorator(F):            # 在 @ 装饰时执行
>     def wrapper(*args):      # 在包装函数被调用时执行
>         # 使用 F 与 args
>         return F(*args)      # F 调用原函数
>     return wrapper
>
> @decorator                    # func = decorator(func)
> def func(x, y): ...           # func 被传入装饰器的 F
> func(6, 7)                    # 6, 7 被传入 wrapper 的 *args
> ```
>
> 当名字 `func` 之后被调用时，它实际调用的是 `decorator` 返回的 `wrapper` 函数；由于原函数 `func` 还在**外层作用域（enclosing scope）**里，`wrapper` 可以运行它。按这种方式编码，每个被装饰的函数都会产生一个新的作用域来保留状态。
>
> 若想用类达到同样的效果，我们可以重载调用操作（`__call__`），用实例属性代替外层作用域：
>
> ```python
> class decorator:
>     def __init__(self, func):    # 在 @ 装饰时执行
>         self.func = func         # 保存原函数到实例属性
>     def __call__(self, *args):    # 在包装函数被调用时执行
>         # 使用 self.func 与 args
>         return self.func(*args)  # 调用原函数
>
> @decorator                        # func = decorator(func)
> def func(x, y): ...               # func 被传入 __init__
> func(6, 7)                        # 6, 7 被传入 __call__ 的 *args
> ```
>
> 现在，当名字 `func` 之后被调用时，它实际调用的是 `decorator` 类实例的 `__call__` 运算符重载方法；由于原函数 `func` 还能在**实例属性（instance attribute）** `self.func` 里取到,`__call__` 就能运行它。按这种方式编码，每个被装饰的函数都会产生一个新实例来保留状态。

### 深度理解

- **核心概念**：装饰器是"返回可调用对象的可调用对象"。最核心的编码选择是：**用什么外壳包住原函数**——嵌套函数的闭包作用域，还是类的实例属性。
- **底层实现**：闭包方案依赖"自由变量 + 单元格（cell）"来保留 `F`；类方案依赖实例的 `__dict__` 保存 `self.func`。二者都是状态保存的手段。
- **设计原因**：闭包代码量少、写法直观；类则把状态显式挂在属性上、便于从外部访问。书里两种都示范，正是让读者权衡。
- **解决什么实际问题**：装饰器内部需要"记住原函数"——闭包与实例属性是两个主流记忆载体。
- **初学者误区**：以为 `__call__` 里的 `self` 是指被装饰类实例。不——它指的是装饰器类自己的实例；这一点在装饰方法时会引发著名的"方法陷阱"（Class Pitfall）。

### 代码分析

上面两幅代码骨架，配合解释器执行路径讲解：

```python
def decorator(F):            # ① 装饰时刻：@ 触发，F 是被装饰函数
    def wrapper(*args):      # ② 创建内层函数对象（此时只是定义，未执行）
        return F(*args)      # ④ 调用时，通过闭包 cell 拿到 F 并转发
    return wrapper           # ③ 把 wrapper 返回，赋给 func 名字
func(6, 7)                   # ⑤ 真正执行 wrapper(6, 7)
```

类的版本把 ② 拆成 `__init__`（保存 `self.func`）与 `__call__`（转发调用），状态从"闭包 cell"变成了"实例属性"。

**设计思想**：装饰器不直接处理业务逻辑，它只做"接管名字＋转发原函数"，从而把增强逻辑与业务逻辑解耦。

> 按这种方式编码时，`wrapper` 能在第一个参数里收到 class C 的实例，因此它可以派发到原方法并访问其状态信息。
>
> 从技术上讲，嵌套函数版本之所以可行，是因为 Python 只有在一个方法属性引用的是简单函数时，才会创建**绑定方法（bound method）**对象并把主题实例传给 `self`；当一个方法属性引用的是可调用类的实例时，传给 `self` 的反而是这个可调用类自己的实例。所以你必须确保你的装饰器编码得当。
>
> 还要注意：嵌套函数大概是支持"同时装饰函数和方法"最直接的方式，但不一定是唯一方式。例如，前一章的**描述符（descriptors）**在调用时能同时收到描述符类实例和主题实例。虽然更复杂，但本章稍后你会看到如何借助这个工具去装饰函数与方法。

### 深度理解

- **核心概念**：class-based 装饰器只适合装饰"裸函数"；一旦装饰类里的方法，`self` 就会被装饰器实例霸占，主题类 C 的实例彻底丢失。
- **底层实现**：Python 把"方法调用"实现为两步——第一步对 `C.method` 做属性解析（attribute lookup）。如果属性是简单函数，就包装成绑定了实例的 bound method；如果属性是可调用类的实例，则不绑定，直接把该实例当可调用对象调用。
- **设计原因**：这个差异是 Python 属性协议的内建行为，不是 bug；理解它才能解释为什么"类封装装饰器"会踩坑。
- **解决的实际问题**：写装饰器时如果希望"函数和方法通用"，优先用嵌套函数（把 `self` 留在 `*args` 里），而不是用带 `__call__` 的可调用类。
- **初学者误区**：看到 `tracer.__call__(self, *args)` 就以为 `self` 是被装饰的对象——实则 `self` 是装饰器（tracer）实例本身。

最终，本章前段那句"不必担心"的总结在这里被打脸：类方案并不是万能答案。后面"Class Pitfall: Decorating Methods"整节将展开演示其崩溃过程，这里先记住方向。

## 39.11 Class Decorator Basics（类装饰器基础）

### 英文原文

> Function decorators proved so useful that the model was extended to allow class decoration. They were initially resisted because of role overlap with the next chapter's metaclasses; in the end, though, they were adopted because they provide a simpler way to achieve many of the same goals.
>
> Class decorators are strongly related to function decorators; in fact, they use the same syntax and very similar coding patterns. Rather than wrapping individual functions or methods, though, class decorators are a way to manage classes or wrap up instance-creation calls with extra logic that manages or augments instances created from a class. In the latter role, they may manage full object interfaces instead of a single callable object.

### 中文翻译

> 函数装饰器实在太有用了，于是该模型被扩展到了类上。类装饰器最初还因为与下一章的**元类（metaclasses）**角色重叠而遭到抵制；不过最终它们还是被采纳了，因为它们为实现许多同样的目标提供了更简单的方式。
>
> 类装饰器与函数装饰器关系密切；事实上，它们使用同样的语法和非常相似的编码模式。不过，类装饰器不是去包装单个函数或方法，而是一种管理类的方式，或者说是用一种额外的逻辑把"实例创建调用"包装起来，去管理或增强由某类创建出来的实例。在后一种角色里，它们管理的是完整的对象接口，而不只是一个可调用对象。

### 深度理解

- **核心概念**：类装饰器 = 在 `class` 语句末尾执行 `C = decorator(C)` 的语法糖。它管理的对象是"类"及"类的实例"。
- **底层实现**：与元类在"类创建过程结尾"运行类似，类装饰器也在类创建后立即运行；但类装饰器不需要 `type` 介入创建过程，因此更轻量。
- **设计原因**：Lutz 提到历史——类装饰器因与元类职责重叠曾被抗拒。最终因其"轻量、简单"而被纳入：能做元类 80% 的事，却不需要理解 metaclass 机制。
- **解决什么实际问题**：单例、代理、接口跟踪、属性隐私校验——这些需要"管住整个类"的需求，用类装饰器一行 `@` 即可。
- **初学者误区**：以为类装饰器只能"装饰"，在实例化时失效。实际恰恰相反——`C()` 会触发装饰器返回的 callable，实例化自己也已被接管。

### 代码分析

```python
# 用法（Usage）：
@decorator          # 装饰类
class C: ...
x = C(99)           # 创建实例

# 等价映射为：
class C: ...
C = decorator(C)    # 重绑定：把类名字绑定到装饰器返回结果
x = C(99)           # 本质上调用 decorator(C)(99)
```

解释器处理顺序：编译 `class C` 生成类对象 → 调用 `decorator(C)` → 把返回结果赋回 `C`。此后 `C(...)` 触发的实际是装饰器返回的可调用对象，它"可能调用也可能不调用"原类。**设计思想**：把"实例创建"纳入增强链条——一次装饰、所有实例统一接管。

### 英文原文

> New class decorators are coded with many of the same techniques used for function decorators, though some may involve two levels of augmentation—to manage both instance-construction calls as well as instance-interface access.
>
> Because a class decorator is also a callable that returns a callable, most combinations of functions and classes suffice. However it's coded, the decorator's result is what runs when an instance is later created. For example, to simply manage a class just after it is created, return the original class itself.
>
> To instead insert a wrapper layer that intercepts later instance-creation calls, return a different callable object.
>
> To see how this works at the interface level, consider the following example, which inserts an object that intercepts undefined attributes of a class instance:
>
> In this example, the decorator rebinds the class name to another class, which retains the original class in an enclosing scope and creates and embeds an instance of the original class when it's called. When an attribute is later fetched from the instance, it is intercepted by the wrapper's `__getattr__` and delegated to the embedded instance of the original class.
>
> Moreover, each decorated class creates a new scope, which remembers the original class. We'll flesh out this example into some more useful code later in this chapter.
>
> Like function decorators, class decorators are commonly coded as either closure (a.k.a. "factory") functions that create and return callables, classes that use `__init__` or `__call__` methods to intercept call operations, or some combination thereof. Closure functions typically retain state in enclosing-scope references, and classes retain state in attributes.

### 中文翻译

> 新的类装饰器用很多与函数装饰器相同的技巧来编写，尽管有些可能涉及**两级增强（two levels of augmentation）**——既要管理"实例构造调用"，又要管理"实例的接口访问"。
>
> 因为类装饰器同样是一个"返回可调用对象的可调用对象"，所以函数与类的大多数组合都够用。无论怎么编码，装饰器的返回结果就是"之后创建实例时运行的东西"。例如，若只是想在被创建的类刚完成时管理它，直接返回原类本身即可。
>
> 若想插入一层拦截后续实例创建调用的包装器，则返回另一个不同的可调用对象。
>
> 为了看看它在接口层次上是如何工作的，考虑下面这个例子——它插入一个对象来拦截类实例的（未定义）属性：
>
> (Code: `def decorator(cls)` 返回内部 `class Wrapper`，用 `__getattr__` 委托)
>
> 在这个例子中，装饰器把类名字重绑定到另一个类上，这类把原类保留在外层作用域里，并在自己被调用时创建、嵌入一个原类的实例。之后当从实例上抓取某个属性时，该访问会被包装器的 `__getattr__` 拦截，并委托（delegate）给被嵌入的原类实例。此外，每个被装饰的类都会产生一个新作用域，记住的正是原类。我们稍后会把此例充实成更有用的代码。
>
> 与函数装饰器一样，类装饰器通常写成闭包（closure，也就是"工厂 factory"）函数——创建并返回可调用对象，或使用 `__init__`/`__call__` 方法拦截调用操作的类，或是二者的组合。闭包函数通常在外层作用域引用中保留状态，类则在属性中保留状态。

### 深度理解

- **核心概念**：类装饰器可能涉及**两级增强**——"实例构造"与"实例接口访问"分别被管理，对应两个不同的钩子时刻。
- **底层实现**：用 `class Wrapper` 的方案里，`Wrapper.__init__` 负责创建并嵌入原类实例；`Wrapper.__getattr__` 负责把外部属性访问委托给嵌入实例。原类保存在 `Tracer`/`decorator` 函数的外层作用域里。
- **设计原因**：用函数工厂 + 嵌套类，能让"每个被装饰类"各有一个独立的 `Wrapper` 类与独立作用域，从而支持多实例、多类互不干扰。
- **解决什么实际问题**：属性级代理、接口跟踪、单例、访问校验都需要"在实例化的同时接管接口"，本节给出了最小可行示范。
- **初学者误区**：把"被装饰的类"与"装饰器返回的类"混为一谈。被装饰的类被嵌入到了返回类的实例内部，`x` 前端其实是 Wrapper 实例。

### 代码分析

```python
def decorator(cls):                 # 在 @ 装饰时执行
    class Wrapper:
        def __init__(self, *args):    # 在实例创建时执行
            self.wrapped = cls(*args)  # 用外层作用域里的原类构造真实实例
        def __getattr__(self, name):   # 在属性抓取时执行
            return getattr(self.wrapped, name)  # 委托给被包装的实例
    return Wrapper                    # 返回的是类，而非实例

@decorator
class C: 
    def __init__(self, x, y):
        self.attr = 'hack'          # 由 Wrapper.__init__ 里的 cls(...) 运行

x = C(6, 7)      # 实际调用 Wrapper(6, 7)，其 __init__ 内部再调 cls(6, 7)
print(x.attr)    # 触发 Wrapper.__getattr__，打印 "hack"
```

解释器执行链：`x = C(...)` → 名字 `C` 已指向 `Wrapper` 类 → `Wrapper.__init__` → 内部 `cls(*args)` 调用真正的原类创建实例 → 嵌入 `self.wrapped`。之后每次 `x.attr` 都会先落在 `Wrapper.__getattr__`（因为 `attr` 不是 Wrapper 自己的属性名），而后被 `getattr` 委托给 `self.wrapped`。**设计思想**：接口代理 = 拦截属性访问钩子（`__getattr__`）＋ 转发（`getattr`），这两者的结合是可复制的**委托**模式。

### 深度理解

- **核心概念**："**每类一个装饰器实例，还是每类实例一个 wrapper？**"——状态保存在哪里，决定了能否支持多实例。
- **底层实现**：`class Decorator` 方案里 `self.wrapped` 是装饰器实例的**单个**属性，每次 `__call__` 都会覆盖它；`def decorator` + `class Wrapper` 方案每次调用都 `new` 一个 wrapper 实例，各自持有独立 `self.wrapped`。
- **设计原因**：这是"状态保存策略"的经典教训：想把状态按"实例"粒度存储，状态就必须属于被创建的 wrapper 实例而非共享的装饰器对象。
- **解决什么实际问题**：写通用类装饰器时，务必弄清"你的状态是 per-class 还是 per-instance"，否则会出现莫名其妙的数据串扰。
- **初学者误区**：只要代码能跑就以为正确——本例中 `bob` 与 `sue` 共享同一 `wrapped`，第二个实例悄悄覆盖第一个，这种 bug 极其隐蔽。

### 代码分析

```python
# 错误：每类一个 Decorator 实例，每次 __call__ 覆盖 self.wrapped
class Decorator:
    def __init__(self, C):            # 在 @ 装饰时执行
        self.C = C
    def __call__(self, *args):       # 在实例创建时执行
        self.wrapped = self.C(*args) # 每次都覆盖同一个属性！
        return self
    def __getattr__(self, attrname):
        return getattr(self.wrapped, attrname)

@Decorator
class C: ...
x = C()   # self.wrapped = 实例1
y = C()   # self.wrapped = 实例2，x 被覆盖！

# 正确：工厂返回 Wrapper 类，每次创建都 new 一个 Wrapper
def decorator(C):
    class Wrapper:
        def __init__(self, *args):
            self.wrapped = C(*args)   # 每实例独立 wrapped
    return Wrapper

# 或：包装函数每次新建 Wrapper 实例
def decorator(C):
    def onCall(*args):
        return Wrapper(C(*args))
    return onCall
```

**设计思想**：状态粒度的选择直接决定行为正确性。这是本章反复出现的"状态保存（state retention）"主线的第一次爆雷，后文还会多次遇见。

## 39.13 Decorator Nesting（装饰器嵌套）

### 英文原文

> Sometimes, one decorator isn't enough. For instance, suppose you've coded two function decorators to be used during development—one to test argument types before function calls and another to test return value types after function calls.
>
> You can use either independently, but what to do if you want to employ both on a single function? What you really need is a way to nest the two, such that the result of one decorator is the function decorated by the other.
>
> It's irrelevant which is nested, as long as both steps run on later calls.
>
> To support multiple nested steps of augmentation this way, decorator syntax allows you to add multiple layers of wrapper logic to a decorated function or method. When this feature is used, each decorator must appear on a line of its own. Decorator syntax of this form:
>
> `@A` / `@B` / `@C` / `def f(...)`
>
> runs the same as the following: `def f(...)`, then `f = A(B(C(f)))`.
>
> Here, the original function is passed through three different decorators, and the resulting callable object is assigned back to the original name. Each decorator processes the result of the prior, which may be the original function or an inserted wrapper.
>
> If all the decorators insert wrappers, the net effect stacks them: when the original function name is called, three different layers of wrapping object logic will be invoked to augment the original function in three different ways. The last decorator listed is the first applied and, thus, the most deeply nested when the original function name is later called.
>
> Just as for functions, multiple class decorators result in multiple nested function calls and possibly multiple levels and steps of wrapper logic around instance-creation calls.
>
> With wrappers, when an instance of the original C class is finally requested, the call is redirected to the wrapping layer objects, which may have arbitrarily different roles—they might trace and validate attribute access for example, and both steps would be run in turn on later requests.

### 中文翻译

> 有时候一个装饰器不够用。比如你编写了两个开发期函数装饰器——一个在函数调用前测试参数类型，另一个在函数调用后测试返回值类型。你可以单独用其中任意一个，但如果你想把两者同时作用在一个函数上该怎么办呢？你真正需要的是一种**嵌套（nest）**两者的方式：让上一个装饰器的结果，成为下一个装饰器要装饰的函数。谁在外谁在内无所谓，只要两次增强都能在后续调用上运行即可。
>
> 为了以这种方式支持多步嵌套增强，装饰器语法允许你给同一函数或方法叠加多层包装逻辑。使用这一特性时，每个装饰器都必须独占一行。这种形式的装饰器语法：`@A` / `@B` / `@C` / 其下 `def f(...)`，与下面等价：先写 `def f(...)`，再 `f = A(B(C(f)))`。
>
> 在这里，原函数被依次穿过三个不同的装饰器，最终得到的可调用对象被赋回原名。每个装饰器处理的是前一个装饰器的结果——可能是原函数，也可能是插入的包装器。
>
> 如果所有装饰器都插入了包装器，净效果就是把它们**叠加（stack）**起来：当原函数名字被调用时，会依次触发三层包装对象逻辑，从三个不同方面增强原函数。**列在最下方的装饰器最先被应用，因此在后续调用时嵌套得最深**。
>
> 与函数类似，多个类装饰器也会产生多重嵌套的函数调用，在实例创建调用周围可能有多层多级的包装逻辑。当真正需要原 C 类的实例时，调用会被改道到各装饰器提供的包装层对象——它们的角色可以千差万别（比如跟踪与校验属性访问），每一次后续请求都会依次走完各层。

### 深度理解

- **核心概念**：装饰器嵌套 = 多个装饰器叠加。映射规则 `f = A(B(C(f)))`：**自下而上应用**（C 先应用、最深），调用时**自上而下包装**（A 最外层先被触发）。
- **底层实现**：这就是嵌套函数调用的普通求值顺序：先求 `C(f)`、再以结果为参求 `B(...)”、最后 `A(...)` 赋回 `f`。
- **设计原因**：单一装饰器只能注入一种增强；叠加允许"参数校验＋返回值校验＋日志"这类多横切关注点同时存在。
- **解决什么实际问题**：把正交的增强逻辑拆成多个装饰器分别复用，而不是写一个巨型装饰器而边界复杂。
- **初学者误区**：记反应用顺序。记住"**先贴先内、后贴先触**"——`@A` 在最上，调用时 A 的包装最先执行、最晚交给下一层。

### 代码分析

```python
# 两个"干实事"的装饰器示例：
def d1(F): return lambda: 'X' + F()   # 在结果前拼接 'X'
def d2(F): return lambda: 'Y' + F()
def d3(F): return lambda: 'Z' + F()

@d1
@d2
@d3
def func(): return 'hack'      # func = d1(d2(d3(func)))
print(func())                  # 打印 "XYZhack"
```

执行链：`d3` 先包，产生 `lambda: 'Z'+'hack'`；`d2(d3(func))` 再包出 `'Y'+(...)`；最终 `d1` 最外层。调用 `func()` 时从外向内：`lambda: 'X' + (lambda: 'Y' + (lambda: 'Z' + 'hack')() )()`，即最外层的 `d1` 包装先运行，最内层 `d3` 的包装最后运行、最先返回。**设计思想**：每个包装器借助闭包记住被包装者 F，可无限叠加；同语法同样适用于类。

## 39.14 Decorator Arguments（装饰器参数）

### 英文原文

> Both function and class decorators can also seem to take arguments. Really, though, the role of these arguments is simpler than it may seem: decorator arguments are passed to a callable that returns the decorator—which in turn returns a callable. By nature, this usually sets up multiple levels of state retention. The following, for instance:
>
> @decorator(A, B) / def F(arg) / F(99)
>
> is automatically mapped into this equivalent form, where `decorator` is a callable that **returns** the actual decorator. The returned decorator in turn returns the callable that handles later calls to the original function name:
>
> `def F(arg): ...` / `F = decorator(A, B)(F)` (Rebind F to result of decorator's return value) / `F(99)` (Essentially calls decorator(A, B)(F)(99))
>
> Decorator arguments are resolved before decoration ever occurs, and they are usually used to retain state information for use in later calls.
>
> In other words, decorator arguments often imply **three levels of callables**: a callable to accept the decorator arguments, which returns a callable to serve as the decorator, which returns a callable to handle calls to the original function or class. Each of the three levels may be a function or class, and may retain state in the form of scopes or class attributes.
>
> Decorator arguments can be used to provide attribute initialization values, call-trace message labels, attribute names to be validated, and much more—any sort of configuration parameter. A decorator with arguments is sometimes called a "decorator factory," since it creates a decorator that in turn creates a wrapper.

### 中文翻译

> 函数装饰器和类装饰器看起来也都能"带参数"。但其实这些参数的角色比看起来更简单：装饰器参数是被传给一个"返回装饰器的可调用对象"的，而这个返回的装饰器又返回一个可调用对象。这样的结构天然会展开多级状态保存。例如下面这段：
>
> `@decorator(A, B)` / `def F(arg): ...` / `F(99)`
>
> 自动映射成如下等价形式，其中 `decorator` 是一个**返回真正装饰器**的可调用对象；返回的装饰器再返回一个可调用，供后续对原函数名的调用使用：
>
> `def F(arg): ...`；`F = decorator(A, B)(F)`（把 F 重绑定为 decorator 返回值的调用结果）；`F(99)`（本质上调用 `decorator(A, B)(F)(99)`）
>
> 装饰器参数在装饰发生之前就已解析完成，通常用来保留状态信息供后续调用使用。
>
> 某种角度看，装饰器**参数天生隐含三级可调用对象（three levels of callables）**：第一级接受装饰器参数并返回一个"作为装饰器"的可调用，第二级返回一个"处理对原函数或类调用"的可调用。三级中的每一级都可是函数或类，也都可以用作用域或类属性保存状态。
>
> 装饰器参数可以用来提供属性初始化值、调用跟踪消息的标签（label）、需要校验的属性名等等——任何这类"配置参数"都行。带参数的装饰器有时也被叫作"装饰器工厂（decorator factory）"。

### 深度理解

- **核心概念**：`@decorator(A, B)` 并不是"装饰器带了参数"，而是"工厂函数 `decorator(A, B)` 返回一个真正的装饰器，后者再返回 wrapper"。**三级嵌套**是理解钥匙。
- **底层实现**：第一级 `decorator(A, B)` 在 `@` 之前就求值（参数先解析）；返回的 `actualDecorator(F)` 在 `def` 结束时应用；`actualDecorator` 返回的 wrapper 在每次调用时执行。
- **设计原因**：配置信息（标签、上下界、姓名）必须在装饰时刻就固定下来，所以要"先接受配置、再接受函数、最后应付调用"。
- **解决什么实际问题**：让同一个装饰器模板能被不同函数以不同配置复用，比如 `@timer(label='fast')` 与 `@timer(label='slow')` 两套计时配置并行存在。
- **初学者误区**：写嵌套时层数混乱。可以把每层想象成"参数收搜集器 → 装饰器 → 包装器"三个尽责员，各自只负责一级调用。

### 代码分析

```python
def decorator(A, B):
    # 第 1 层：在 @ 之前执行，保存 A、B
    def actualDecorator(F):
        # 第 2 层：在 @ 时刻执行，保存函数 F
        def wrapper(*args):        # 第 3 层：每次调用执行
            ...                     # 用 A、B、F
        return wrapper
    return actualDecorator

@decorator(A, B)                   # 先算 decorator(A, B)，得到 actualDecorator
def F(arg): ...
F(99)                              # 即 wrapper(99)
```

**设计思想**：三级结构把"配置"、"被装饰对象"、"运行期参数"三个不同生命周期分装进三处作用域，互不污染。

## 39.15 Decorators Manage Functions and Classes, Too（装饰器也能管理函数和类）

### 英文原文

> To wrap up, although much of the rest of this chapter focuses on wrapping later calls to functions and classes, it's important to remember that the decorator mechanism is more general than this—it is simply a protocol for passing functions and classes through any callable immediately after they are created. As such, it can also be used to invoke arbitrary post-creation processing:
>
> def decorator(O): / # Augment function or class O processes / return O
> @decorator / def F(): ...  # F = decorator(F)
> @decorator / class C: ...  # C = decorator(C)
>
> If we return the original decorated object this way instead of a proxy, we are not intercepting later calls—instead we'd run a one-time processed action at definition time. Such decorators might be used to register callable objects to an API, initialize attributes in functions or classes when they are created, and so on. Decorator roles are limited only by your imagination.

### 中文翻译

> 小结一下（To wrap up）:虽然本章后面的主体内容都聚焦于"包装对函数与类的调用"，但要记住：装饰器机制比这更通用——它其实只是一个"在对象创建后立刻把函数或类交给任意可调用对象处理一次"的协议。因此它也能用来执行任意的创建后处理：
>
> def decorator(O)：# 增强函数或类 O / return O
> @decorator 修饰 def F、@decorator 修饰 class C → F = decorator(F)、C = decorator(C)

> 如果我们这样返回原装饰对象而不是代理，就并没有拦截后续调用——而是在定义时刻运行一次"一次性处理"。这种装饰器可以用注册可调用对象到 API、在函数或类创建时初始化属性等等。装饰器的角色只受你的想象力限制。

### 深度理解

- **核心概念**：装饰器协议 = "创建后把对象交给某个 callable 处理一次"。包装调用只是它最常见的用途，不是全部。

- **设计原因**：把"注册回调、附加元数据、登记路由"这类创建侧动作也统一到 `@` 语法下，代码更集中、意图更清晰。
- **解决实际问题**：ORM 模型注册、事件处理器登记、函数属性初始化——"定义时跑一次"的需求，装饰器顺手就能办。
- **初学者误区**：以为装饰器必须返回"别的东西"。返回原对象完全合法，且是"零开销增强"的范本。

        self.func = func

        print(f'call {self.calls} to {self.func.__name__}')
        self.func(*args)

## 39.18 Decorator State Retention Options（装饰器状态保存选项）

### 英文原文

> The preceding example raises an important point. Decorators have a variety of options for retaining state information provided at decoration time to be used during later calls to decorated objects.
>
> They generally need to support multiple decorated objects and multiple later calls, but there are several ways to implement these goals: instance attributes, global variables, nonlocal closure variables, and function attributes can all be used for retaining state.
>
> This topic parallels the initial state coverage in Chapter 17 but can be fleshed out here with class details, and it is so endemic to decorators that it qualifies as a prerequisite. This topic also applies to both function and class decorators, but let's explore it in the narrower function-decorator realm.

### 中文翻译

> 前面的例子引出一个重要问题。对于"装饰时刻提供、后续调用时使用"的状态信息，装饰器有各种各样的保存选项。它们通常需要支持多个被装饰对象、多次后续调用，但实现目标有几种途径：实例属性（instance attributes）、全局变量（global variables）、nonlocal 闭包变量（nonlocal closure variables）、函数属性（function attributes）都可以用来保存状态。
>
> 这个主题与第 17 章的状态保存入门讲解平行，但这里可以用类的细节把问题讲得更饱满；它如此贯穿装饰器始终，几乎算是一个先修知识点。这对函数装饰器和类装饰器都成立，不过本节先在较窄的函数装饰器范围内探索它。

### 深度理解

- **核心概念**：**状态保存（state retention）**是装饰器的主线难题——"装饰时刻的信息如何活到后续调用"，四大载体：实例属性、全局、nonlocal、函数属性。
- **底层实现**：四种载体分别是"对象 `__dict__`"、"模块命名空间"、"闭包单元格（cell）"、"函数对象的命名空间"。各自的可见性与每函数隔离性不同。
- **设计原因**：没有唯一解——要"每函数独立"还是"全局共享"、要"外部可见"还是"内部私密"，决定了选哪种载体。
- **解决什么实际问题**：计数器、累计时间、配置标签、缓存——所有需要在多次调用之间保持可变的量，都得先想清楚存哪。
- **初学者误区**：在嵌套函数里直接 `+=` 外层变量而报 `UnboundLocalError`，或是用了全局变量导致所有装饰函数共享一个计数器。

### State with class-instance attributes（用类实例属性保存状态）

### 英文原文

> As an opening act in the state-retention show, Example 39-2 codes an augmented version of the prior example, which adds support for keyword arguments with ** syntax and returns the wrapped function's result to support more use cases (for nonlinear readers, we first studied keyword arguments in Chapter 18).

### 中文翻译

> 作为状态保存这场大戏的开场，示例 39-2 编写了前一示例的增强版：为关键字参数加上了 `**` 语法支持，并返回"被包装函数的结果"以支持更多用例（对非线性读者说明：关键字参数我们最早在第 18 章学过）。
>
> 与原型一样，它用**类实例属性**显式保存状态。被包装函数与计数都是"每实例（per-instance）"的信息——每次装饰都得到自己的一份。以脚本运行时可以看到，`hack` 与 `code` 两个函数各有自己的计数，因为每次装饰都创建了新的类实例。
>
> 虽然这个方案装饰函数很实用，但当它应用到**方法**上时仍有问题——这个短板我们在后面的修订中解决。

（书里这里还讨论了运行输出：`call 1 to hack / 6 / call 2 to hack / 15 / call 1 to code / 16 / call 2 to code / 65536`。）

### 代码分析
```python
# 示例 39-2：decorator_state_classes.py
class tracer:                # 状态通过实例属性保存
    def __init__(self, func):    # 在 @ 装饰时执行
        self.calls = 0           # 保存 func 供日后调用
        self.func = func
    def __call__(self, *args, **kwargs):   # 在调用原函数时执行
        self.calls += 1
        print(f'call {self.calls} to {self.func.__name__}')
        return self.func(*args, **kwargs)  # 返回结果以支持更多用例

@tracer
def hack(a, b, c):            # 同 hack = tracer(hack)
    print(a + b + c)          # 触发 tracer.__init__

@tracer
def code(x, y):               # 同 code = tracer(code)
    print(x ** y)             # 把 code 包进 tracer 对象

if __name__ == '__main__':
    hack(1, 2, 3)             # 实际调用 tracer 实例，运行 tracer.__call__
    hack(a=4, b=5, c=6)       # hack 是实例属性
    code(4, 2)                # 实际调用 tracer 实例，self.func 是 code
    code(2, y=16)             # 这里的 self.calls 是 per-decoration 的
```

**改进点**：多了 `**kwargs`（支持关键字参数）与 `return`（返回原函数结果）。**设计思想**：装饰器要"透明代理"，就应把原名该收到的参数与返回值都原样转发——加返回值是通用工具的基本修养。

## 39.19 State with global variables（以全局变量保存状态）

### 英文原文

>
> As we saw in Chapters 17 and 19, we can attach arbitrary attributes to functions by assignment, with `func.attr = value`. Because a factory function makes a new function on each call, its attributes become per-call state. Moreover, you need to use this technique only for state that must change; enclosing-scope references are still retained and work normally. To demo, Example 39-5 simply uses `wrapper.calls` for state.
>
> It works the same as the preceding nonlocal version because the counter is again per-decorated-function. As we learned in Chapter 17, this works only because the name `wrapper` is retained in the enclosing `tracer` function's scope. When we later increment `wrapper.calls`, we are not changing the name `wrapper` itself, so no `nonlocal` declaration is required.
>
> This scheme was almost relegated to a footnote because it is perhaps more obscure than nonlocal and might be probably saved for cases where other schemes don't help.
>
> However, function attributes have a substantial advantage: like class instances, they allow access to the saved state from outside the decorator's code; nonlocals can only be seen inside the nested function itself, but function attributes have wider visibility. We will employ them again in an answer to one of the end-of-chapter questions, where their visibility outside callables becomes an asset.
>
> As changeable state associated with a context of use, they're equivalent to nonlocals. As usual, choosing from multiple tools is an inherent part of the programming task. Because decorators often imply multiple levels of callables, you can combine functions with enclosing scopes, classes with attributes, and function attributes to achieve a variety of coding structures.
>
> As you'll see later, this sometimes will be subtler than you expect—each decorated function should have its own state, and each decorated class may require state both for itself and for each generated instance.

        return func(*args, **kwargs)

## 39.20 Class Pitfall: Decorating Methods（类陷阱：装饰方法）

### 英文原文

> When the preceding section's class-based tracer function decorator, Example 39-2, was initially coded, it was assumed that it could also be applied to any method—decorated methods should work the same, but the automatic self instance argument would simply be included at the front of *args. The only real downside to this assumption is that it is completely wrong, though the reasons for the failure are far from obvious.
>
> In short, when applied to a class's method, this version of the tracer fails because self is the instance of the decorator class and the instance of the decorated subject class is not included in *args at all.
>
> This phenomenon was introduced abstractly earlier in this chapter, but now we can see it in the context of working code. Example 39-2's class-based decorator works as advertised for plain functions (copy/pasters: don't copy the initial "..." REPL prompts included in this chapter).
>
> However, decoration of class-level methods fails (more lucid sequential readers might recognize this as an adaptation of our Person class resurrected from the object-oriented tutorial in Chapter 28):
>
> The root of the problem here is in the self argument of the tracer class's __call__ method—is it a tracer instance or a Person instance? We ultimately need both as it's coded: the tracer for decorator state, and the Person for routing on to the original method. Really, self must be the tracer object to provide access to tracer's state information (its calls and func); this is true whether decorating a simple function or a method.
>
> Unfortunately, when our decorated method name is rebound to a class instance object with a __call__, Python passes only the tracer instance to self; it doesn't pass along the Person subject in the arguments list at all. Moreover, because the tracer knows nothing about the Person instance we are trying to process with method calls, there's no way to create a bound method with an instance, and thus, no way to correctly dispatch the call.
>
> This isn't a bug, but it's wildly subtle.
>
> In the end, the prior listing winds up passing too few arguments to the decorated method, and results in an error. Add a line to the decorator's __call__ to print all its arguments to verify this—as you can see, self is the tracer instance, and the Person instance is entirely absent:
>
> `<__main__.tracer object at 0x108a02c00> (0.10,) {}`
>
> As mentioned earlier, this happens because Python passes the implied subject instance to self only when a method name is bound to a simple function; when it is an instance of a callable class, that class's instance is passed instead.

### 中文翻译

> 前面一节的基于类的 `tracer` 函数装饰器（示例 39-2）最初编写时，假设它也可以应用到任何**方法（method）**上——被装饰的方法应该同样工作，隐藏的 `self` 实例参数会自然出现在 `*args` 的前端。这个假设唯一的"真实缺点"是：它**完全错误**——不过失败的原因远非显而易见。
>
> 简言之，当它应用到类的方法上时，这个版本的 `tracer` 会失败：因为 `self` 是装饰器类的实例，而被装饰主题类的实例根本没进 `*args`。
>
> 这个现象在本章前文已经抽象地介绍过，现在我们能在具体代码中看到它。示例 39-2 的基于类的装饰器对普通函数一切正常（复制粘贴党注意：不要连本章 REPL 里开头的 "..." 提示符一起复制，以免破坏缩进）。
>
> 但对类级别的方法做装饰却失败了（细心的顺序读者可能会认出，这是第 28 章面向对象教程里 `Person` 类的改编版）：
>
> `pat.giveRaise(.10)` 会报错 `TypeError: Person.giveRaise() missing 1 required positional argument: 'percent'`
>
> 问题根源在 `tracer` 类的 `__call__` 方法的 `self` 参数上——它到底是 `tracer` 实例还是 `Person` 实例？按现在的写法我们其实两者都要：`tracer` 用来取装饰器状态，`Person` 用来把调用路由到原方法。事实上，`self` **必须**是 `tracer` 对象，以提供对 `tracer` 状态信息（`calls` 与 `func`）的访问——无论装饰的是普通函数还是方法都是如此。
>
> 不幸的是，当我们的被装饰方法名被重绑定为"带 `__call__` 的类实例"时，Python 只会把 `tracer` 实例传给 `self`；`Person` 主题根本不在参数列表里。而且，因为 `tracer` 对我们要处理的 `Person` 实例一无所知，就没有办法造出一个带实例的绑定方法，因此也就无法正确派发调用。这不是 bug，但它极其微妙。
>
> 最终，前面的清单给被装饰方法传的参数不足，于是报错。往装饰器的 `__call__` 里加一行打印全部参数即可验证——如你所见，`self` 是 tracer 实例，而 Person 实例完全缺席：
>
> `<__main__.tracer object at 0x108a02c00> (0.10,) {}`
>
> 如前所述，这之所以发生，是因为 Python 只有当方法名绑定到简单函数时，才会把隐藏的主题实例传给 `self`；当方法名绑定到可调用类的实例时，传给 `self` 的取而代之的是那个类自己的实例。

### 深度理解

- **核心概念**：**"类实例装饰器 ≠ 方法装饰器"**。`@tracer` 装饰 `giveRaise` 后，`giveRaise` 变成 `tracer` 实例；`pat.giveRaise(...)` 触发的是 `tracer.__call__(self=tracer实例, *args)`，`Person` 实例没有位置可站。
- **底层实现**：属性解析规则——`pat.giveRaise` 找到的属性是"可调用类实例"时，Python **不**做 bound-method 包装；只有属性是简单函数时才把实例绑进去。所以 `Person` 永远进不了参数。
- **设计原因**：这是语言协议的自洽结果，非缺陷；理解它必须放弃"self 一定是被装饰对象"的直觉。
- **解决什么实际问题**：凡是"要同时装饰函数与方法"的通用装饰器，都必须绕开"单个 self 实例兼任两职"的陷阱——嵌套函数方案是正解。
- **初学者误区**：报错信息里说 `missing 1 required positional argument: 'percent'`，初学者常去检查 `Person`，却不知是装饰器的 `__call__` 参数形态出了问题。

### 代码分析

```python
class Person:
    def __init__(self, name, pay):
        self.name = name
        self.pay = pay

    @tracer
    def giveRaise(self, percent):    # giveRaise = tracer(giveRaise)
        self.pay *= (1.0 + percent)

pat = Person('Pat Jones', 50_000)
pat.giveRaise(.10)                   # 实际是 tracer.__call__(tracer实例, .10)
# → call 1 to giveRaise
# → TypeError: Person.giveRaise() missing 1 required positional argument: 'percent'
```

调用链：`pat.giveRaise` 属性解析得到 `tracer` 实例 → 调用它 `(...)` 触发 `__call__`，参数只有 `(0.10,)`；`__call__` 内部 `self.func(*args)` = `giveRaise(0.10)`，原方法需要 `self` 与 `percent` 两个参数，于是缺参报错。**设计思想**：装饰器若要用可调用类实现，必须意识到"它接管了方法调用协议"，而方法协议里的 `self` 已被它自己占用。

### Using nested functions to decorate methods（用嵌套函数装饰方法）

### 英文原文

> If you want your function decorators to work on both simple functions and class-level methods, the most straightforward solution lies in using one of the other state retention solutions described earlier—code your function decorator as nested def statements so that you don't depend on a single self instance argument to be both the wrapper class instance and the subject class instance.
>
> In fact, we already have—both Examples 39-4 and 39-5 work for both functions and class methods by using nested functions along with nonlocal variables or function attributes.
>
> Because decorated methods here are rebound to simple functions instead of instance objects, Python correctly passes the Person object as the first argument, and the decorator propagates it on in the first item of *args to the self argument of the real, decorated methods.
>
> Trace through these results and decorators to make sure you have a handle on this model; the next section provides an alternative to it that supports classes but is also substantially more complex.

### 中文翻译

> 如果你希望函数装饰器既能用于普通函数也能用于类级别的方法，最直接的解决方案在于使用前面讲过的其他状态保存方案之一——把函数装饰器写成**嵌套的 `def` 语句**，从而不再依赖"单个 `self` 实例参数兼任包装类实例与主题类实例两职"。
>
> 事实上我们早就在这么做了——示例 39-4 与 39-5 通过"嵌套函数＋nonlocal 变量或函数属性"，对函数与类方法都能正常工作。
>
> 因为这里被装饰的方法被重绑定为简单函数而非实例对象，Python 会正确地把 `Person` 对象作为第一个参数传入，装饰器再把它原样放在 `*args` 的第一项，传播给真正被装饰方法的 `self`。请亲手追踪一遍这些结果与装饰器，确保你完全掌握了这个模型；下一节将提供一个支持类但复杂得多的替代方案。

### 深度理解

- **核心概念**：嵌套函数方案里，`wrapper` 是**普通函数**，`pat.giveRaise` 是简单函数属性 → Python 会按绑定方法协议把 `pat` 塞进第一个参数 → `wrapper` 的 `*args` 第一个元素就是 `Person` 实例。
- **底层实现**：属性解析找到简单函数 → 创建 bound method（绑定 `pat`）→ 调用时 `args = (pat, 0.10)` → `wrapper` 转发 `func(*args)` 即 `giveRaise(pat, 0.10)`，完美。
- **设计原因**：把"自我状态"放进闭包而不是 `self` 字段，是解除"self 冲突"的关键一步——一石二鸟。
- **解决什么实际问题**：**编写"函数与方法通用"装饰器的唯一推荐姿势**，后续的 `rangetest`、计时器修订版都照此办理。
- **初学者误区**：觉得"反正报错也能看"，不追踪参数流。建议在 `wrapper` 里打印 `args` 亲自看一遍 `(person实例, 0.1)`，这个模型才真正扎根。

### 代码分析

from decorator_state_nonlocals import tracer

@tracer
def hack(a, b, c):             # 对函数有效
    print(a + b + c)

        self.name = name

### Using descriptors to decorate methods（用描述符装饰方法）

### 英文原文

> Although the nested function solution illustrated in the prior section is the most straightforward way to support decorators that apply to both functions and class-level methods, other schemes are possible. The descriptor feature we explored in the prior chapter, for example, can help here as well.
>
> Recall from our discussion in the prior chapter that a descriptor is normally a class attribute assigned to an object with a __get__ method run automatically whenever that attribute is referenced and fetched. Descriptors may also have __set__ and __del__ access methods, but we don't need them here.
>
> More relevant to this chapter's topic: because the descriptor's __get__ method receives both the descriptor class instance and subject class instance when invoked, it's well suited to decorating methods when we need both the decorator's state and the original class instance for dispatching calls. Consider the alternative tracing decorator in Example 39-6, which also happens to be a descriptor when used for a class-level method.
>
> This works the same as the preceding nested function coding. Its operation varies by usage context:
> - Decorated functions invoke only its __call__, and never invoke its __get__.
> - Decorated methods invoke its __get__ first to resolve the method name fetch; the object returned by __get__ retains the subject class instance and is then invoked to complete the call expression, thereby triggering the decorator's __call__.
>
> For example, given the same testing code, the call pat.giveRaise(.10) runs tracer.__get__ first because the giveRaise attribute in the Person class has been rebound to a descriptor by the method function decorator. The call expression then triggers the __call__ method of the returned wrapper object, which in turn invokes tracer.__call__.
>
> In other words, decorated method calls trigger a five-step process: tracer.__get__, which invokes wrapper.__init__, followed by three call operations—wrapper.__call__, tracer.__call__, and finally the original wrapped method.
>
> The wrapper object retains both descriptor and subject instances, so it can route control back to the original decorator/descriptor class instance. In effect, the wrapper object saves the subject class instance available during method attribute fetch and adds it to the later call's arguments list, which is passed to the decorator __call__.

### 中文翻译

>
> 回忆前一章的讨论：描述符通常是"一个带有 `__get__` 方法的对象"，被赋给类属性，每当该属性被引用、抓取时 `__get__` 就自动运行。描述符也可以有 `__set__` 与 `__del__` 访问方法，但我们这里用不到。
>

> - 装饰**函数**时只触发它的 `__call__`，永远不会触发 `__get__`。
> - 装饰**方法**时，先触发 `__get__` 解析方法名的抓取；`__get__` 返回的对象保留了主题类实例，随后该对象被调用来完成调用表达式，从而触发装饰器的 `__call__`。

>
> `wrapper` 对象同时保留了描述符实例与主题实例，因此它能把控制权路由回原装饰器/描述符类实例。实际上，`wrapper` 对象保存了"方法属性抓取时可得"的主题类实例，并把它加入后续调用的参数列表，传入装饰器 `__call__`。

### 深度理解

- **核心概念**：描述符方案的本质——利用 `__get__(instance, owner)` **一次性同时拿到描述符与主题实例**，再用 wrapper 把它们粘合成后续调用。
- **底层实现**：方法被装饰后，`giveRaise` 是 `tracer` 实例（同时也是描述符）；`pat.giveRaise` 触发 `__get__(tracer实例, Person)`；返回的 `wrapper` 记录 `(desc, subj)`，调用它时构造 `desc(subj, *args)` 完成路由。
- **设计原因**：当"装饰器状态"与"主题实例"都要时，描述符是 Python 提供的唯一"一箭双雕"钩子——比闭包更重，但展示另一种可能。
- **解决什么实际问题**：提供比嵌套函数更结构化的备选；其代价是复杂度与每方法多步调用的性能损耗，作者明确劝退："如果复杂度没让你崩溃，性能开销也该让你崩溃了"。
- **初学者误区**：忘了描述符协议只在"类属性"上生效——`@tracer` 装饰普通函数时 `__get__` 根本不触发，所以"函数走 `__call__`、方法走 `__get__`+`__call__`"两条路径必须同时维护。

### 代码分析

```python
# 示例 39-6：calltracer_desc_class.py（节选）
class tracer(object):              # 一个"装饰器 + 描述符"
    def __init__(self, func):      # 在 @ 装饰时执行
        self.calls = 0             # 保存 func 供日后调用
        self.func = func
    def __call__(self, *args, **kwargs):   # 在调用原函数/方法时执行
        self.calls += 1
        print(f'call {self.calls} to {self.func.__name__}')
        return self.func(*args, **kwargs)
    def __get__(self, instance, owner):    # 在方法属性抓取时执行
        return wrapper(self, instance)     # 返回粘合两者的代理

class wrapper:
    def __init__(self, desc, subj):        # 同时保存两个实例
        self.desc = desc                   # 路由回装饰器/描述符
        self.subj = subj
    def __call__(self, *args, **kwargs):
        return self.desc(self.subj, *args, **kwargs)   # 运行 tracer.__call__

@tracer
def hack(a, b, c): ...          # hack = tracer(hack)，只用 __call__
class Person:
    @tracer
    def giveRaise(self, percent): ...   # giveRaise 变成了描述符
```

**五步执行链**（方法调用）：`pat.giveRaise(.10)` → ① `tracer.__get__(pat)` → ② `wrapper.__init__(desc=pat实例, subj=pat)` → ③ `wrapper.__call__(.10)` → ④ `tracer.__call__(pat, .10)` → ⑤ 原方法体。**设计思想**：把"属性抓取"与"调用"两个时刻之间的信息（主题实例）暂存于 wrapper，从而在不依赖绑定方法的情况下正确路由。示例 39-7 用嵌套函数代替 wrapper 类得到等价的更短版本，示例 39-8 则演示了"只有 `__get__` 没有 `__call__`"的版本——它只能装饰方法、装饰函数就崩（属性访问不会触发 `__get__`）。

### 深度理解

- **核心概念**：计时装饰器 = 在 `__call__` 里"掐秒表、跑函数、再掐表"，累计进 `self.alltime`。定时工具与业务解耦。
- **底层实现**：`time.perf_counter()` 取高精度单调时钟；`self.alltime += elapsed` 把每次耗时累加到实例属性中。
- **设计原因**：把基准测试（benchmark）变成"声明式"工具——用 `@timer` 装饰即可对比两种写法的快慢，不改任何业务代码。
- **解决问题**：性能对比、热点定位；`allTime` 作为属性可被外部读取，`**map/comp` 比率直观量化差距。
- **初学者误区**：用装饰器做精细基准时忘了它本身有包装开销；书里特意用第 21 章非装饰器方案（`timer`、`timeit`）对照，提醒两种手段并存互补。

### 代码分析

```python
# 示例 39-9：timerdeco1.py
"Caveat: timer won't work on methods as coded (see quiz solution)"
import time, sys
class timer:
    def __init__(self, func):
        self.func = func
        self.alltime = 0
    def __call__(self, *args, **kargs):
        start = time.perf_counter()                      # 记录起始时间
        result = self.func(*args, **kargs)               # 调原函数
        elapsed = time.perf_counter() - start            # 结算本次耗时
        self.alltime += elapsed                          # 累加总耗时
        print(f'{self.func.__name__}: {elapsed:.5f}, {self.alltime:.5f}')
        return result

@timer
def listcomp(N):
    return [x * 2 for x in range(N)]
@timer
def mapcall(N):
    return list(map((lambda x: x * 2), range(N)))

if __name__ == '__main__':
    for func in (listcomp, mapcall):
        result = func(5)              # 本次调用耗时、返回值
        func(50_000); func(500_000); func(1_000_000)
        print(result)
        print(f'allTime = {func.alltime}\n')   # 该函数所有调用的总耗时
    print('**map/comp =', round(mapcall.alltime / listcomp.alltime, 3))
```

**解释器执行链**：`@timer` 时 `timer.__init__` 建实例；每次 `listcomp(...)` → `timer.__call__` → 计时并转发。`func.alltime` 以实例属性暴露累计耗时。**设计思想**：计时、对比、累计，全部内聚到装饰器；业务函数保持纯净。注意本版是"类装饰器"，不能直接用类方法——提示语已写"quiz solution"，正是章末测验题 1。

## 39.22 Adding Decorator Arguments（添加装饰器参数）

### 英文原文

> The timer timer decorator of the prior section works, but it would be nice if it were more configurable—providing an output label and turning trace messages on and off, for instance, might be useful in a general-purpose tool. Decorator arguments come in handy here: when they're coded properly, we can use them to specify configuration options that can vary for each decorated function. A label, for instance, might be added as abstractly follows.
>
> This code adds an enclosing scope to retain a decorator argument for use on a later actual call. The structure of a decorator-factory is:
>
> def timer(label=''): -> def decorator(func): -> def onCall(*args): -> func(*args); print(label,...)
>
> When the listcomp function is defined, Python really invokes decorator—the result of timer, run before decoration actually occurs—with the label value available in its enclosing scope. That is, timer returns the decorator, which remembers the decorator argument and the original function, and returns the callable onCall, which ultimately stops the original function on later calls.
>
> Because this structure creates new decorator and onCall functions, their enclosing scopes are per-decoration state retention.
>
> We can put this structure to use in our timer to allow a label and a range computer flag to be passed in at decoration time. Example 39-10 does just that, coded in a module file so it can be imported as a general tool; it uses a class for the second state retention level.

### 中文翻译

> 上一节的计时装饰器能工作，但要是它能更可配置就更好了——比如提供输出标签（label）、开关跟踪消息，这对通用工具可能很关键。此刻**装饰器参数**就派上用场了：只要编码得当，我们就可以用它们来指定随每个被装饰函数而变化的配置选项。比如，标签可以如下抽象地添加。
>
> 这段代码新增一层外层作用域，用来把装饰器参数保留给后续实际调用使用。装饰器工厂的结构是：外层 `def timer(label='')` → 中层 `def decorator(func)` → 内层 `def onCall(*args)`（内部 `func(*args)` 且打印 `label` 等）→ 依次返回。
>
> 当 `listcomp` 被定义时，Python 实际上是在装饰尚未发生之前就调用 `timer`（其结果 `decorator` 以标签作为参数），外层已经携带着 `label` 的值。也就是说，`timer` 返回装饰器；装饰器记住装饰器参数与原函数，返回可调用 `onCall`；`onCall` 才是以后调用时执行的。由于这个结构创建了新的 `decorator` 与 `onCall` 函数，它们的外层作用域就是"每装饰一份"的状态保存。
>
> 我们可以把这个结构用进计时器，让"标签"和"跟踪开关"在装饰时刻传入。示例 39-10 正是这样做的——它把计时器编成模块文件，便于作为通用工具被 import；它用**类**（而非嵌套函数）来实现第二层状态保存，但净效果相似。

### 深度理解

- **核心概念**：**装饰器工厂**三级结构：`timer(label)`（读配置）→ `Timer`/`decorator`（接收函数）→ `__call__`/`onCall`（处理调用）。
- **底层实现**：`label`、`trace` 存活在 `timer` 函数帧的闭包里；`Timer` 类实例在 `@` 时刻创建并保存 `self.func`。
- **设计原因**：配置参数必须在"装饰时刻"固定，不能每次调用再变；外层闭包正是为长期保存配置而生。
- **实际问题**：同一套计时器在不同函数上输出不同标签（`[CCC]==>` 与 `[MMM]==>`），大程序输出里能一眼分辨；`trace=False` 可无人值守关闭。
- **初学者误区**：把 `@timer(label='x')` 当作"调用 timer 后再装饰"的两步，理解对了三步的一半——务必看到 `timer(...)` 已经先执行了（参数已解析完）。

### 代码分析

```python
# 示例 39-10：timerdeco2.py
import time
def timer(label='', trace=True):   # 第一层：在装饰参数处保存参数
    class Timer:
        def __init__(self, func):      # 第二层：在 @ 时保存被装饰函数
            self.func = func
            self.alltime = 0
        def __call__(self, *args, **kargs):   # 第三层：在调用时执行
            start = time.perf_counter()
            result = self.func(*args, **kargs)
            elapsed = time.perf_counter() - start
            self.alltime += elapsed
            if trace:                       # 开/关跟踪输出
                if label: print(label, end=' ')
                print(f'{self.func.__name__}: {elapsed:.5f}, {self.alltime:.5f}')
            return result
    return Timer

# 示例 39-11：testseqs.py（客户端）
from timerdeco2 import timer
@timer(label='[CCC]==>')
def listcomp(N):                    # listcomp = timer(...)(listcomp)
    return [x * 2 for x in range(N)]

@timer(trace=True, label='[MMM]==>')
def mapcall(N):
    return list(map((lambda x: x * 2), range(N)))
```

**执行时序**：`@timer(label='[CCC]==>')` 求值时：① `timer('[CCC]==>')` 立即返回 `Timer` 类 → ② 类 body 被装饰 `Timer(listcomp)` 建实例、保存 `func`、`alltime=0` → ③ `listcomp(...)` 调用 `Timer.__call__`。**注意**：单实例保存于"第二层类的实例"，而标签保存在第一层闭包中。`**`设计思想**：用"每层一个生命周期"隔开配置、函数、调用三类信息，让同一装饰器能以不同标签复用。（书中还强调：此计时器仍不能用于类方法——这正留作章末测验第 1 题。）

> 要使用它，就对想实施"单实例模型"的类加上装饰，如示例 39-13 所示。装饰 `Person` 与 `Hack` 两个类。
>
> 现在，当 `Person` 或 `Hack` 类之后被用来创建实例时，装饰器提供的包装逻辑层会把实例创建调用路由给 `onCall`，`onCall` 保证"每类只有一个实例"——不管创建调用发生多少次。本书随之给出运行输出：`Sue 1000` / `Sue 1000` / `42 42`。
>
> （解读：第二次 `Person('Bob',...)` 实际返回的还是 `Sue` 那个对象，`bob.name` 仍打印 `Sue`；`X` 与 `Y` 两个 `Hack` 实例也是同一个，故两个 `attr` 都是 `42`。）

### 深度理解

- **核心概念**：单例模式 = "每个类只允许一个实例"。类装饰器通过"拦截创建调用 → 查表/复用"实现。
- **底层实现**：`instances` 全局字典以"类对象"为键、以实例为值；`onCall` 每次创建时先查 `if aClass not in instances`，存在则直接返回旧实例。
- **设计原因**：类装饰器版的单例把"曾否创建"的表格逻辑从类本身拿出，附在装饰层，类保持纯粹。
- **最实用的动机**：配置中心、连接池、全局状态存储——"全程序唯一实例"需求广泛。
- **初学者误区**：以为 `Person`、`Hack` 各实例是不同的。实际上 `bob` 与 `sue` 指向同一个对象（都打印 `Sue 1000`）——这是验证单例最直观的方式。也注意用**全局字典**（每个类一个条目）与用 **nonlocal**（每类一个作用域）两种实现殊途同归。

### 代码分析

```python
# 示例 39-12：singletons.py
instances = {}                          # 模块级全局表：类 → 实例
def singleton(aClass):                  # 在 @ 装饰时执行
    def onCall(*args, **kwargs):        # 在实例创建时执行
        if aClass not in instances:     # 每个类一个条目
            instances[aClass] = aClass(*args, **kwargs)   # 首次创建才真的构造
        return instances[aClass]        # 之后一律复用第一次的实例
    return onCall
# 示例 39-13：使用（节选）
@singleton      # Person = singleton(Person)，Person 被重绑定为 onCall
class Person:
    def __init__(self, name, hours, rate): ...
sue = Person('Sue', 50, 20)      # 真正执行的是 onCall('Sue', 50, 20)
bob = Person('Bob', 40, 10)     # 再次调用 onCall——返回 sue 对象！
print(sue.name, sue.pay())      # Sue 1000
print(bob.name, bob.pay())      # Sue 1000  ← 与 sue 相同！
```

**执行细节**：`Person` 经 `@singleton` 重绑定为各 `onCall`；两次实例化都走进 `onCall`；首次将真实例存入 `instances[Person]`，第二次直接返回同一对象。**设计思想**：把"唯一性保证"从类内部移到装饰层——类保持普通，句法外统一管控。非 local 版用每类一个 `instance=None` 的闭包变量代替全局字典，二者等价。

### Singleton coding alternatives（单例的其他实现）

### 英文原文

> Interestingly, you can also code a more self-contained solution where the enclosing-scope changes via nonlocal. The following alternative achieves an identical effect, by using one enclosing scope per class, instead of one global table entry per class.
>
> You can also code a self-contained solution with either function attributes or a class instead. The first option leverages the fact that there is one onCall function per decoration — the function object's namespace serves the same role as an enclosing scope.
>
> The second uses one instance per decoration, relying on the same coding pattern that we'll later label a common decorator class pitfall — here we want just one instance, but that's not often the case.

### 中文翻译

> 有意思的是，你也可以用 nonlocal 修改外层作用域名的方式来写一个更自包含的版本。下面的替代方案效果完全相同：每个类用一个外层作用域，而不是每个类一个全局表条目。它不依赖装饰器之外的全局作用域里的名字（这里 `None` 检查也可用 `==` 或 `is`，都无所谓）。
>
> 此外，你还可以用函数属性或类实现同样自包含的版本。第一个法子利用"每次装饰产生一个 onCall 函数"这个事实——函数对象的命名空间可以充当外层作用域；第二个法子每装饰用一个实例——它依赖的正是我们稍后要称之为"装饰器类陷阱"的那种编码模式：这里我们恰好**想要**一个实例，但通常我们并不想要。

### 深度理解

- **核心概念**：单例的三种自包含变体：nonlocal 闭包变量、函数对象属性、装饰器类属性——状态容器的选择决定实现形态。
- **底层实现**：nonlocal 版把 `instance` 藏进闭包；函数属性版把 `instance` 挂在 `onCall` 函数对象上；类版存在 `self.instance`。
- **设计原因**：体现"多工具殊途同归"——作者有意展示同一种行为有多种编码姿态，训练读者在状态容器间自如切换。
- **实际问题**：模块化封装时，尽量"自包含"（不依赖外部全局字典），便于复用、移植。
- **初学者误区**（重要预告）：类版单例"刻意"用了一个类是"单实例"的巧合工作；同样代码换到别处（如 Tracer 接口跟踪）就会因"每类一个实例、每实例只有一个 wrapped"而翻车。这正是"类陷阱"的前奏。

### 代码分析
```python
# 变体 1：用 nonlocal（每类一个闭包作用域）
def singleton(aClass):            # 在 @ 装饰时执行
    instance = None
    def onCall(*args, **kwargs):      # 在实例创建时执行
        nonlocal instance
        if instance == None:
            instance = aClass(*args, **kwargs)   # 每类一个作用域
        return instance
    return onCall

# 变体 2：函数属性（每装饰一个 onCall 函数对象即自带命名空间）
def singleton(aClass):
    def onCall(*args, **kwargs):
        if onCall.instance == None:
            onCall.instance = aClass(*args, **kwargs)
        return onCall.instance
    onCall.instance = None
    return onCall

# 变体 3：装饰器类（每类一个装饰器实例，状态在 self.instance）
class singleton:
    def __init__(self, aClass):     # 在 @ 装饰时执行
        self.aClass = aClass
        self.instance = None
    def __call__(self, *args, **kwargs):   # 在实例创建时执行
        if self.instance == None:
            self.instance = self.aClass(*args, **kwargs)
        return self.instance
```

三种方案行为相同。**设计思想**（作者的建议)：挑一版写进 importable 模块即可；类版"显式、有结构"，便于将来演化，但 OOP 不必处处用。

## 39.25 Tracing Object Interfaces（跟踪对象接口）

### 英文原文

> The singleton example of the prior section illustrated using class decorators to manage all the instances of a class. Another common use case for class decorators augments the interface of each generated instance. Class decorators can essentially install a wrapper or "proxy" logic layer atop instances that manages access to their interfaces.
>
> For example, in Chapter 31, the __getattr__ operator-overloading method was shown as a way to wrap up entire object interfaces of embedded instances in order to implement the delegation coding pattern. Recall that __getattr__ is run when an undefined attribute name is fetched; we can use this hook to intercept method calls in a controller class and propagate them to an embedded object.

### 中文翻译

> 上一节的单例示例演示了用类装饰器管理"一个类的所有实例"。类装饰器另一常见用法是增强**每个生成实例的接口**。从根本上说，类装饰器可以在实例之上安装一层包装器或"代理（proxy）"逻辑层，拦截对实例属性的访问。
>
> 比如第 31 章曾展示，`__getattr__` 运算符重载方法可以包裹"被嵌入实例的整个对象"接口，从而实现委托编码模式。回忆一下：一个未定义的属性名被抓取时，`__getattr__` 会运行；我们可以用这个钩子在控制器类里拦截方法调用，并把它们转发给被嵌入的对象。

### 深度理解

- **核心概念**：两种"全量管理"的差异——单例管"类**的所有实例**"，接口跟踪管"**每个**实例的全部接口"。
- **底层实现**：`Wrapper.__getattr__` 拦截一切未定义属性访问；已定义的（Wrapper 自己的）属性不受影响，因此 `fetches` 等计数属性不被跟踪。
- **设计原因**：委托模式的价值——不需要知道被包装对象的完整接口，`__getattr__ + getattr` 就能"原样转发"。
- **实际问题**：调试时观察"外部到底碰了哪些属性"，或做访问审计、权限前置。
- **初学者误区**：以为 `__getattr__` 能拦截一切属性。它只拦截"未定义"属性；内置运算（如 `+`、`[]`）的隐式访问它接不住——这个洞尾段专门修补。

### The nondecorator approach（非装饰器方案）

### 英文原文

> For reference and review, here's the original nondecorator delegation example:
>
> class Wrapper:
>   def __init__(self, object):
>     self.wrapped = object      # Save object
>   def __getattr__(self, attrname):
>     print('Trace:', attrname)  # Trace fetch
>     return getattr(self.wrapped, attrname)   # Delegate fetch
>
> x = Wrapper([1,2,3])          # Wrap a list object
> x.append(4)                    # Delegate to list method
>
> In this code, the Wrapper class intercepts access to the wrapped object's explicitly named attributes, prints a trace message, and uses the getattr built-in to pass off the request to the wrapped object. This whole-interface model differs from the behavior of function decorators, which wrap up one specific method.

### 中文翻译

> 作为参考与复习，这里给出最初的非装饰器委托示例：
>
> class Wrapper:
>   def __init__(self, object):
>       self.wrapped = object      # 保存对象
>   def __getattr__(self, attrname):
>     print('Trace', attrname)   # 打印跟踪信息
>     return getattr(self.wrapped, attrname)   # 委托属性
>
> x = Wrapper([1,2,3])          # 包装一个列表对象
> x.append(4)                    # 委托给列表方法
>
> 在这段代码里，`Wrapper` 类拦截对被包装对象的显式属性的访问，打印一条跟踪消息，并用 `getattr` 内建函数把请求转给被包装对象。这个"**整体界面（whole-interface）**"模型与函数装饰器（只包装一个具体方法）的行为不同。

### 深度理解

- **核心概念**：委托（delegation）模式的三件套：构造时嵌入对象、`__getattr__` 拦截、`getattr` 转发。
- **底层实现**：`x.append` 里 `append` 不是 `Wrapper` 实例的属性 → 落入 `__getattr__` → 打印、转发。已定义属性（如 `wrapped`）不触发。
- **设计原因**：委托是不知接口细节时的万能转发——不做方法清单，只管"你有就转"。
- **实际问题**：跟踪"外部对对象属性的每次触碰"，为接口监控工具奠基。
- **初学者误区**：委托后还指望 `x` 是 `list` 类型；`isinstance(x, list)` 为 False——类型不再是原类型，这是代理的固有代价。

### 代码分析
```python
class Wrapper:
    def __init__(self, object):
        self.wrapped = object      # 保存对象
    def __getattr__(self, attrname):
        print('Trace:', attrname)  # 跟踪抓取
        return getattr(self.wrapped, attrname)   # 转发抓取

x = Wrapper([1, 2, 3])   # 包装一个列表对象
x.append(4)              # 委托到列表方法，输出 Trace: append，列表变 [1,2,3,4]
```

**执行链**：`x.append` 属性查找，`Wrapper` 类无该方法、实例 `__dict__` 也没有 → 落入 `__getattr__('append')` → 打印、`getattr(被包装列表, 'append')` 取出真实方法 → 调用它（即 `[1,2,3].append(4)`）。**设计思想**：属性钩子＋内建转发＝极简但完整的接口代理。

## 39.26 The class-decorator approach（类装饰器方案）

### 英文原文

> Class decorators provide an alternative and convenient way to code this __getattr__ technique and wrap an entire interface. The preceding code, for example, can be coded as a class decorator that triggers wrapped instance creation instead of passing premade instances into the wrapper's constructor. Example 39-14 codes this mod, supports keyword arguments with **kargs, and counts the number of accesses to illustrate changeable state.
>
> It is important to note that this is very different from the tracer decorator we met earlier (despite the name!) earlier. There, decorators traced and timed calls to a given function or method. By intercepting instance-creation calls, the class decorator here allows us to trace an entire object interface—accesses to any of the instance's attributes.
>
> It's also important to note that this decorator's __getattr__ won't catch the implicit attribute fetches of built-in operations per the prior chapter, but we'll defer more on this until we code attribute privacy ahead.

### 中文翻译

> 类装饰器提供了一种替代且便捷的方式来编码这种 `__getattr__` 技术并包装整个接口。例如，上面的代码可以改写成"类装饰器触发被包装实例的创建"而不是"把预制实例传进包装器构造函数"。示例 39-14 做了这种改动，用 `**kargs` 支持关键字参数，并计数访问次数以演示可变状态。
>
> 必须注意：这与我们早先遇到的跟踪装饰器（尽管同名！）完全不同。在那里，装饰器跟踪的是"对给定函数或方法的**调用**"。而这里，通过拦截实例创建调用，这个类装饰器让我们能跟踪**整个对象接口**——即对实例任何属性的访问。
>
> 还需要注意：这个装饰器的 `__getattr__` 捕获不了内置运算隐式触发的属性抓取（照上一章所述），这个问题我们要到实现属性隐私时再详细讨论。

### 深度理解

- **核心概念**：**"接口跟踪" ≠ "调用跟踪"**——前者管"实例上的每次属性访问"，后者管"某函数被调用了几次"。
- **底层实现**：`Tracer(aClass)` 工厂每次创建返回内部 `Wrapper` 类；每次 `C()` 实例化都新建一个 `Wrapper` 实例，`self.wrapped` 与 `self.fetches` 各自独立。
- **设计原因**：把"包装接口"的需求推到装饰层，客户端照常写 `Person('Bob', 40, 50)`，一切管理外挂自动生效。
- **实际问题**：对每个实例的每属性访问做跟踪、校验、计数的通用基础设施——这正是后面"属性隐私"装饰器的直接前身。
- **初学者误区**：误以为 `work.fetches` 也会被跟踪；不会——`fetches` 是 `Wrapper` 自身已定义属性，`__getattr__` 只拦截未定义的。

### 代码分析

```python
# 示例 39-14：interfacetracer.py（节选）
def Tracer(aClass):          # 在 @ 装饰时执行
    class Wrapper:
        def __init__(self, *args, **kargs):   # 在实例创建时执行
            self.fetches = 0
            self.wrapped = aClass(*args, **kargs)   # 用外层作用域名字构造真实例
        def __getattr__(self, attrname):      # 捕获除自身属性外的所有访问
            print('Trace:', attrname)
            self.fetches += 1
            return getattr(self.wrapped, attrname)   # 委托给被包装对象
    return Wrapper

if __name__ == '__main__':
    @Tracer
    class Hack:
        def display(self): print('Hack!' * 3)
    @Tracer
    class Person:
        def __init__(self, name, hours, rate): ...
        def pay(self):
            return self.hours * self.rate   # 方法内部访问不跟踪

    work = Hack(); work.display()    # 触发 __getattr__，输出 'Hack!Hack!Hack!'
    print([work.fetches])           # [1]
    bob = Person('Bob', 40, 50); print(bob.name)   # Trace: name → Bob
    print(bob.pay())                # 2000
    sue = Person('Sue', rate=100, hours=60)  # 不同 Wrapper、不同 Person
    print('calls:', [bob.fetches, sue.fetches])   # calls: [4, 2]
```

**执行链**：`@Tracer` 使 `Person` 指向 `Wrapper` 类；`bob = Person('Bob',...)` → `Wrapper.__init__` 内 `aClass(...)` 构造真 Person，嵌入 `self.wrapped`；之后 `bob.name` 触发 `__getattr__`。`sue` 是另一个独立的 `Wrapper` 实例，故 `fetches` 计数互不干扰。**设计思想**：工厂每次返回"新 Wrapper 类"，每实例 `Wrapper` 各带状态——为 **多实例安全**与 **每类作用域** 的双保障。

### Applying class decorators to built-in types（应用于内置类型）

### 英文原文

> Also note that the preceding one decorates a user-defined class. Just like in the original example in Chapter 31, we could also use the decorator to wrap up built-in objects such as lists, as long as we either subclass to allow decoration syntax or perform the decoration rebinding manually—decorator syntax requires a class statement for the @ line. As displayed, there are two ways to wrap a built-in.
>
> The decorator approach allows us to move instance creation into the decorator itself instead of a premade object. Although this makes little difference in these simple demos, in general it lets us retain normal instance-creation syntax and limits augmentation syntax to class definition. Rather than requiring all instance-creation calls to route objects through a wrapper manually, we need only augment class definitions with decorator syntax.
>
> Assuming you will make more than one instance of a class and want to apply the augmentation to every instance of a class, decorators will generally be a net win in terms of both code size and code maintenance.

### 中文翻译

> 还需要注意：上文装饰的是用户自定义类。不过正如第 31 章最初示例那样，我们也可以让这个装饰器去包裹内置对象类型（如 list）——只要要么用**子类**配合装饰语法（`@` 行必须配 `class` 语句），要么**手工**执行装饰重绑定。有两种方式包裹内置类型。
>
> 装饰器方案让我们把实例创建移进装饰器本身，而不是要求传入预制对象。尽管这在简单演示里差别不大，但一般来说它让我们保留正常的实例创建语法，并把增强语法限制在类定义处。这不需要让所有实例创建调用都手工把对象塞进包装器，而只需在类定义上用装饰语法。
>
> 假设你要为一个类创建多个实例，并希望增强应用到该类的每个实例，那么从代码量与代码维护两个角度来看，装饰器通常都是净胜的。

### 深度理解

- **核心概念**：给 `list` 等内置类型加外衣，有"子类 + `@Tracer`"与"手工重绑定 `MyList = Tracer(list)`"两条路。
- **底层实现**：`class MyList(list): pass` 让 `@Tracer` 语法可落在 class 行；`MyList = Tracer(list)` 则绕过语法约束直接调工厂。
- **设计原因**：装饰器把"创建与包装"合并成一步，调用方仍写 `MyList([1,2,3])`——零负担。
- **实际问题**：对任何（含第三方内置）类加接口管理，通常只需加一行 `@`，不必改写实例创建处。
- **初学者误区**：对内置类型强行写 `@Tracer` 到没有 class 语句的地方；正确姿势要么子类化，要么手工重绑定。

### 代码分析
```python
from interfacetracer import Tracer

@Tracer
class MyList(list): pass      # MyList = Tracer(MyList)
x = MyList([1, 2, 3])         # 触发 Wrapper()，包住真实列表
x.append(4)                   # 触发 __getattr__ → 委托给 list.append
x.wrapped                     # [1, 2, 3, 4]

MyList = Tracer(list)         # 或者手工执行装饰重绑定
x = MyList([4, 5, 6])
x.append(7)                   # Trace: append → [4,5,6,7]
```

对比非装饰器写法 `bob = Wrapper(Person('Bob', 40, 50))`——装饰式 `bob = Person(...) ` 更干净。**设计思想**：把"对象构造过程"纳入装饰层管理，外部代码零变化。

## 39.27 Class Pitfall: Retaining Multiple Instances（类陷阱：保留多个实例）

### 英文原文

> Curiously, the decorator function can be coded instead, almost, as a class with set. Example 39-15 alternative is coded as a class with __init__, __call__, and __getattr__ to provide identical logic to the previous version—the __init__ triggers on @ decorator, the __call__ on instance creation, __getattr__ on attribute fetch.
>
> As we saw in the abstract earlier, though, this class-only alternative handles multiple classes as before, but it won't quite work for multiple instances of a given class: each instance-creation call triggers __call__, which overwrites the previous instance. The net effect is that the tracer saves just one—the last wrapped.
>
> Example 39-16 extends this file to demo the problem. This code's output follows—the second overwrites the first.
>
> The problem here is bad state retention—we make one decorator instance per class but not per class instance, such that only the last instance is retained. The solution, as in our prior class pitfall for decorating methods, lies in abandoning an example adapted to a class-based decorator.
>
> The earlier function-based Tracer version does work for multiple instances. Because it returns a class instead of an instance of that class, each instance-creation makes a new Wrapper instance instead of overwriting the state of a single shared Tracer instance.
>
> The moral here: decorators are not only arguably magical, they can also be incredibly subtle!

### 中文翻译

> 有趣的是，前一个例子的装饰器本身几乎也可以"用封装成类"的方式实现——用恰当的运算符重载协议。示例 39-15 的替代编码就把 `Tracer` 写成一个类：`@` 装饰类时触发它的 `__init__`，创建主题类实例时触发 `__call__`，访问属性时触发 `__getattr__`。
>
> 正如我们前面抽象地讨论过的，这种纯类替代能像以前一样处理多个**类**，但对"同一个类的多个实例"却有问题：每次实例创建调用都会触发 `__call__`，而 `__call__` 覆盖了上一个实例。净效果是 `Tracer` 只保存一个——最后创建的那个。
>
> 示例 39-16 把这段扩展一下以演示问题。其输出结果如下：第二个覆盖第一个——`bob` 名字打印出 `Sue`！
>
> 问题在于**糟糕的状态保存**：我们每类造了一个装饰器实例，但没有"每实例"一个，结果只有最后一个被保留。解决方案与我们前面处理"方法装饰类陷阱"时一样——放弃基于类的装饰器。
>
> 前面基于函数的 `Tracer`（示例 39-14）是能处理多实例的。因为它返回的是一个**类**（`Wrapper`），而非那个类的实例，每次实例创建都会新建 `Wrapper` 实例，而不是覆盖一个共享 `Tracer` 实例的状态。
>
> 结论：装饰器不光可以说得神乎其神——它们还能**极其微妙地出错**！

### 深度理解

- **核心概念**：同一个 Tracer 类方案，作为"类装饰器"会在多实例场景翻车——状态粒度错了。
- **底层机制**：`__call__` 的 `self.wrapped = self.aClass(...)` 每次都写同一个 `self.wrapped` 属性；第二个 `Person('Sue')` 直接把第一个 `Person('Bob')` 顶掉了。
- **设计原因**：这是"状态该放在哪个对象上"的经典对照：函数版返回类→状态的载体是每个实例；类版返回实例→状态全堆在同一个装饰器实例上。
- **实际问题**：任何"要为某类包装多实例"的装饰器，都不要把 per-instance 状态放在装饰器实例身上。
- **初学者误区**：这种 bug 的先导症状是：明明实例化两次，却返回（打印）同一个值。看到了这个现象，就该想到"每实例状态被覆盖"。

### 代码分析

```python
# 示例 39-15/16：interfacetracer-fail.py
class Tracer:
    def __init__(self, aClass):        # 在 @ 装饰器时执行
        self.aClass = aClass           # 用实例属性保存类
    def __call__(self, *args):         # 在实例创建时执行
        self.wrapped = self.aClass(*args)   # ONE（LAST）INSTANCE PER CLASS！
        return self
    def __getattr__(self, attrname):
        print('Trace:', attrname)
        return getattr(self.wrapped, attrname)

@Tracer                       # 触发 __init__
class Hack:
    def display(self): print('Hack!' * 3)
work = Hack(); work.display()      # 触发 __call__、__getattr__

@Tracer
class Person:
    def __init__(self, name): self.name = name

bob = Person('Bob'); print(bob.name)   # Trace: name → Bob
sue = Person('Sue'); print(sue.name)   # Trace: name → Sue
print(bob.name)                        # OOPS: bob 的名字变成了 'Sue'！
```

**执行细节**：每次 `Person('...')` 都调用同一个 `Tracer` 实例的 `__call__`（同一 self），`self.wrapped` 被覆盖；`bob` 与 `sue` 其实都是同一个 `Tracer` 实例（`self` 相同），故 `bob.name` 一变都被改写。**对照**：函数版返回 `Wrapper` **类**，于是 `Person()` 每次生成不同的 `Wrapper` 实例，`wrapped` 与 `fetches` 各自独立。

## 39.29 Implementing Private Attributes（实现私有属性）

### 英文原文

> First up, the class decorator in Example 39-17 implements a Private declaration and access checks for class instance attributes—attributes stored on each instance, or inherited from its classes.
>
> This decorator disallows fetch and change access to the attributes from outside the decorated class but still allows the class to access those names within its own methods. It's not quite the same as "private" in C++ or Java, but it provides similar access validations as an option for cases where this might be useful during development.
>
> We saw an initial and incomplete implementation for instance attribute privacy in Chapter 30; this version extends it to validate fetches, too, and it uses delegation instead of inheritance to implement the model.
>
> Although it implements attribute privacy through the sugar of class decorators, attribute interception is still based upon the __getattr__ and __setattr__ operator-overloading methods we met in prior chapters. When a private access is detected, it raises an exception.
>
> Example 39-17 lists the decorator's first-cut code, along with a self-test. As coded, it catches all explicit attribute fetches, but not the implicit fetches of built-in operations.
>

### 中文翻译

> 首先登场的是类装饰器（示例 39-17），它实现了带访问校验的 **Private 声明**：操作用于"存储在实例上、或从所属类继承来的类实例属性"。 该装饰器禁止从被装饰类的**外部**对这些属性做抓取与修改访问，但允许类自身在自己的方法中自由使用这些名字。它并不完全等于 C++ 或 Java 的 "private"，但提供类似的访问校验，作为开发期特定场景下的一种可选方案。 我们在第 30 章见过一个针对"只改不改读"的实例属性隐私的初始且不完整实现；本示例把它扩展到**抓取**也要校验，并且用**委托（delegation）**而非**继承**来实现模型。 尽管它是借助类装饰器语法糖来实现属性隐私的，其属性拦截最终还是基于 `__getattr__` 与 `__setattr__` 运算符重载方法。一旦检测到私有属性访问，就引发一个带错误消息的异常，可用 `try` 捕获，也可任其终止脚本。 示例 39-17 列出装饰器的初稿代码与模块底部的自测。如所写，它能守住显式属性抓取，但抓不住内置运算的**隐式抓取**（稍后详谈）。

### 深度理解

- **核心概念**：私有属性 = 用**代理**包装类实例＋" 名单制"访问校验：`privates` 列表里的名字禁止外部 get/set。
- **底层实现**：`Private(*privates)` 工厂 → `onDecorator(aClass)` → `onInstance`（proxy 类）；`__getattr__` 里 `attr in privates` 则 `raise TypeError`，否则委托；`__setattr__` 里对 `wrapped` 特殊放行、对非私有名转发到 `wrapped`。
- **设计原因**：用"白名单"式模拟 OO 语言的访问控制；Python 哲学是"人人自觉"，Lutz 明说"sparingly（少用）"。
- **解决问题**：开发期防止误改关键属性；异常把违规访问变成**立即暴露**的崩溃，胜过静默错误。
- **初学者误区**：以为拦截了"类内"访问——委托模式只拦截**外部**访问，类内方法里 `self.data` 走正常路径、零校验（隐私不继承）。
- **提示**：`trace` 辅助函数用 3.12 的嵌套 f-string（`f'[{...}]'`）打印调试。

### 代码分析

```python
# 示例 39-17：access1.py（节选·含中文注释）
traceMe = False
def trace(*args):
    if traceMe: print(f'[{' '.join(map(str, args))}]')   # Python 3.12+ 嵌套 f-string

def Private(*privates):            # privates 保存在外层作用域
    def onDecorator(aClass):       # aClass 保存在外层作用域
        class onInstance:               # 被包装在实例属性中
            def __init__(self, *args, **kargs):
                self.wrapped = aClass(*args, **kargs)
            def __getattr__(self, attr):    # 自身属性不会触发 getattr
                trace('get:', attr)          # 其它名字都假设在 wrapped 上
                if attr in privates:
                    raise TypeError('private attribute fetch, ' + attr)
                else:
                    return getattr(self.wrapped, attr)
            def __setattr__(self, attr, value):   # 外部访问
                trace('set:', attr, value)          # 其它正常运行
                if attr == 'wrapped':               # 允许自己的属性
                    self.__dict__[attr] = value     # 避免死循环
                elif attr in privates:
                    raise TypeError('private attribute change, ' + attr)
                else:
                    setattr(self.wrapped, attr, value)  # 转发给被包装对象
        return onInstance
    return onDecorator

if __name__ == '__main__':
    traceMe = True
    @Private('data', 'size')                 # Doubler = Private(...)(Doubler)
    class Doubler:
        def __init__(self, label, start):
            self.label = label        # 类内部的访问
            self.data = start         # 不被拦截，正常运行
        def size(self):
            return len(self.data)     # 方法体内访问无校验
        def double(self):             # 因为隐私不继承
            for i in range(self.size()):
                self.data[i] = self.data[i] * 2
        def display(self):
            print(f'{self.label} => {self.data}')
```

**执行链**：`@Private('data','size')` → 先 `Private('data','size')` 返回 `onDecorator` → 调 `onDecorator(Doubler)` 返回 `onInstance` 类并赋给 `Doubler`。之后每次 `Doubler(...)` 创建 `onInstance` 代理，内部嵌入真实例。外部访问 `X.label` 合法转发；`X.data` 或 `X.size` 因在 `privates` 名单中被 `raise` 拦截。**设计要点**：`__setattr__` 设置自己 `wrapped` 时**必须**走 `self.__dict__[attr]=value` 绕开递归，这一反直觉技巧正是阅读关键。

## 39.30 Implementation Details（实现细节）

### 英文原文

> This code is nontrivial, and you're probably best off tracing through it on your own to see how it works. To help you study, though, here are a few highlights worth mentioning: **Inheritance versus delegation**: The initial privacy example used inheritance to mix in a __setattr__ to catch accesses; inheritance makes this difficult because distinguishing accesses inside from outside the class is not straightforward.
>
> The version here uses delegation (embedding) instead, which is better suited to this task. Attributes accessed from outside the class are intercepted by the wrapper's overloading methods and delegated back if allowed; accesses from inside the class's methods are not intercepted and run normally.
>
> **Decorator arguments**: The class decorator accepts any number to name the private attributes; this really means the arguments are passed to Private, which returns the decorator, which remembers privates in outer scope.
>
> **State retention and enclosing scopes**: There are actually there are three levels of state retention in play here: - Private's arguments are retained in outer scope for use in both onDecorator and onInstance. - onDecorator's class argument is retained in outer scope for use at instance-creation time. - The wrapped instance is retained as an instance attribute in the onInstance proxy.
>
> **Using __dict__ and __slots__**: __setattr__ relies on __dict__ to set the proxy's own wrapped attribute (it cannot assign directly without looping). It uses setattr to set attributes in the wrapped object, and getattr to fetch (since those may be inherited or in slots).
>
> As such, this works for virtual attributes, slots, properties, descriptors, and even classes with __getattr__. The wrapped class may use slots or properties; the proxy always has a __dict__.
>

### 中文翻译

> （标题节对应书中的"实现细节"几个小节，下面逐节展开。） **继承与委托**：最初的隐私示例在第 30 章，用**继承**混入一个 `__setattr__` 来捕获访问。继承让这件事变得困难，因为区分"从类内部访问"与"从类外部访问"并不直接。于是这里改用**委托（embedding）**替代继承：外部访问由代理的运算符重载方法拦截并委托回类本身（验证通过时）；类内部的方法体（通过 `self`）访问正常执行——因为隐私在此版本中不被继承。 **装饰器参数**：类装饰器接受任意数量的参数以指定私有属性名。同样地，这意味着参数传给 `Private`，`Private` 返回装饰器，装饰器把 `privates` 表格以外层作用域引用"记住"。 **状态保存与外层作用域**：这段代码里实际有**三级**状态保存： - `Private` 的参数（在装饰发生前用到）→保留为外层作用域引用，供 `onDecorator` 与 `onInstance` 一同使用。 - `onDecorator` 的类参数（在装饰时用到）→保留为外层作用域引用，供"创建实例时刻"使用。 - 被包装的实例 →作为 `onInstance` 代理对象的实例属性保留。 **`__dict__` 与 `__slots__` 及虚拟属性**：`__setattr__` 依赖实例属性命名空间字典 `__dict__`，为 `onInstance` 自身设置 `wrapped` 属性（直接赋值会陷入循环，必须写 `self.__dict__[attr]`）。对被包装对象则用 `setattr` 设置、用 `getattr` 抓取（因为属性可能存于对象本体或由它继承）。因此它对大多数类都适用——包括基于 `__slots__`、`property`、描述符甚至 `__getattr__` 的虚拟类级别属性。代理类本身始终有 `__dict__`（不用 slots），故 "自己只管字典、被包装者用存储无关工具" 的策略让代理类免于各种底层存储工具的限制。

### 深度理解

- **核心概念**："为什么用委托不用继承"的核心答案——**区分内外部访问**在委托下天然成立、在继承下几乎做不到。
- **底层实现**：`__setattr__` 里"自设属性绕过 `__setattr__`"使用 `self.__dict__[attr]=...` 直写，规避死循环；代理自身的 `wrapped` 与"外来属性"走向两套逻辑。
- **设计原因**：Python 哲学是"**不加护栏**"，作者刻意把私有放在"可选工具"的位置，而非语言层面的强约束。
- **实际问题**：对 `__slots__` 类的委托依然有效——因为代理自己对 `__dict__` 的依赖在"代理层"而非被包装层。
- **初学者误区**：在 `__setattr__` 里直接 `self.attr = value` 会引发无限递归——必须明白"赋值操作步步都经过 `__setattr__`"这个 Python 事实；这是本次实现最反直觉的一行。

### 代码分析

（关键岔路演示——为什么 `__setattr__` 要走 `__dict__`）

```python
def __setattr__(self, attr, value):
    if attr == 'wrapped':
        self.__dict__[attr] = value   # 直接写字典，避免再一次调用 __setattr__
    elif attr in privates:
        raise TypeError('private attribute change, ' + attr)
    else:
        setattr(self.wrapped, attr, value)   # 被包装对象的属性用它自己的协议设置
```

**解释器执行链**：`X.label = 'Hack'` → `onInstance.__setattr__('label','Hack')` → 不在 privates → `setattr(self.wrapped, 'label', 'Hack')` → 委托到内嵌对象。而 `self.__dict__['wrapped'] = ...` 直接写实例字典，**不再触发 `__setattr__`**，杜绝死循环。**设计思想**：区分"管理代理自身"与"操作被包装对象"两条赋值通道，是代理型工具的通用骨架。

## 39.31 Generalizing for Public Declarations（泛化出 Public 声明）

### 英文原文

> Now that we have a Private attribute implementation, it's straightforward to generalize the code to allow for Public declarations too—they are essentially the inverse of Private declarations, so we need only negate the inner test.
>
> The example listed in Example 39-18 allows a class to use decorators to define a set of either Private or Public instance attributes—attributes of any kind stored on an instance or inherited from its classes—with the following semantics:
>
> **Private** declares attributes that cannot be fetched or assigned except from within the class's methods. Any name declared Private is inaccessible outside the class; any name not declared Private can be freely fetched or assigned from outside.
>
> **Public** declares attributes that can be fetched or assigned both from outside the class and within its methods. Any name declared Public is freely accessible; any name not declared Public cannot be accessed from outside.
>
> Private and Public declarations are mutually exclusive. When using Private, all undeclared names are Public; when using Public, all undeclared names are Private. They are opposites; new names can be assigned (and thus created) outside the class under Private, but not under Public.
>
> Again, study the code on your own. Note that this scheme adds a fourth level of state retention at the top: the validation function (failIf) is saved in an extra enclosing scope.

### 中文翻译

> 既然我们有了 Private 属性实现，泛化出 Public 声明就顺理成章——Public 本质上是 Private 的反面，只需取反内层测试即可。示例 39-18 允许一个类用装饰器定义一组"Private 或 Public 的实例属性"——即存储在实例上或从类继承的任何属性——其语义如下：
>
> **Private（私有）**声明"除了在类的方法代码之内，不能被抓取或赋值"的属性。任何声明为 Private 的名字都不能从类外访问；任何未声明为 Private 的名字都可以从类外自由抓取或赋值。
>
> **Public（公共）**声明"既可从类外也可从类内方法中抓取或赋值"的属性。任何声明为 Public 的名字都可自由访问；任何未声明为 Public 的名字都不能从类外访问。
>
> Private 与 Public 声明互斥。用 Private 时，所有未声明名字被视为 Public；用 Public 时，所有未声明名字被视为 Private。它们本质上相反——在 Private 下，类外可以新赋值并**创造**新名字；在 Public 下则不行。
>
> 再次提醒：请自行研读代码。注意本方案在最顶层又添加了**第四级状态保存**：验证函数（`failIf`）保存在额外的外层作用域里（供 lambda 使用）。

### 深度理解

- **核心概念**：把"名单判定"抽象成**策略函数 `failIf`**——`Private` 传"∈名单"，`Public` 传"∉名单"，一正一反两个入口共用一套骨架。
- **底层实现**：`accessControl(failIf)` 工厂把判定函数保存在最外层作用域；`Private(*attrs)` 与 `Public(*attrs)` 只是两个薄壳。
- **设计原因**：第四级作用域让"校验策略"与"代理逻辑"解耦——将来换规则（如正则匹配）只需换 `failIf`。
- **实际问题**：把"默认拒绝 vs 默认放行"两种安全模型用同一实现切换，白名单/黑名单通用。
- **初学者误区**：忘了"新名字"规则——Private 模式下 `X.newattr = 1` 是合法的（未声明即公开），Public 模式下同样操作被拒。这种不对称最易踩坑。

### 代码分析

```python
# 示例 39-18：access2.py（节选）
def accessControl(failIf):
    def onDecorator(aClass):
        class onInstance:
            def __init__(self, *args, **kargs):
                self.__wrapped = aClass(*args, **kargs)   # __X 伪私有名
            def __getattr__(self, attr):
                trace('get:', attr)
                if failIf(attr):                          # 用策略函数判定
                    raise TypeError('private attribute fetch, ' + attr)
                else:
                    return getattr(self.__wrapped, attr)
            def __setattr__(self, attr, value):
                trace('set:', attr, value)
                if attr == '_onInstance__wrapped':        # 用变形后的全名
                    self.__dict__[attr] = value
                elif failIf(attr):
                    raise TypeError('private attribute change, ' + attr)
                else:
                    setattr(self.__wrapped, attr, value)
        return onInstance
    return onDecorator

def Private(*attributes):
    return accessControl(failIf=(lambda attr: attr in attributes))      # 白名单
def Public(*attributes):
    return accessControl(failIf=(lambda attr: attr not in attributes))  # 黑名单
```

REPL 演示：`@Private('age')` 的 `Person`，`X.name` 可读写、`X.age` 读写均被拒；`@Public('name')` 时则 `X.name` 可读写、`X.age` 被拒。**设计思想**：判定逻辑提升为"一等公民"（函数），语义仅由一个 lambda 的取反决定——这是泛化（generalization）的教科书式范例。

## 39.32 Implementation Details II（实现细节（二））

### 英文原文

> To help you analyze Example 39-18's code, here are a few final notes on this version.
>
> **Using "__X" pseudoprivate names**: This version also makes use of Python's __X pseudoprivate name mangling feature to localize the wrapped attribute to the proxy class by automatically prefixing it with the class's name. This avoids collisions with a wrapped attribute that may be used by the real, wrapped class.
>
> It's not quite "privacy," though, because the mangled version can be used freely outside the class. Notice we must use the expanded name string, '_onInstance__wrapped', as an admin-name test value in __setattr__.
>
> **Breaking privacy**: Though it implements access controls, it is possible to subvert them trivially—e.g., by fetching through the fully mangled name bob._onInstance__wrapped.pay. If you have to try that hard to break them, these tools probably suffice for intended roles.
>
> Of course, privacy can generally be subverted in other languages too (e.g., #define private public in C++). Python is about enabling, not controlling; privacy is a tool best used sparingly (if at all).
>
> **Decorator trade-offs**: The chief downsides of this wrapper-based approach are that attribute access incurs an extra call, and instances of decorated classes are not really instances of the original class—X.__class__ or isinstance(X, C) reveal they are instances of the wrapper class.
>
> Unless you plan to do introspection, the type issue is irrelevant; and the extra call may apply mostly to development time, as it's possible to remove decorations automatically via -O.

### 中文翻译

> 为了帮你分析示例 39-18 的代码，这里给出该版本的几条最后备注。
>
> **使用 `__X` 伪私有名称**：这个版本还利用了 Python 的 `__X` 伪私有名（name mangling，名字改编）特性——给 `wrapped` 属性自动加上类名前缀，把它局部化到代理控制类里。这避免了与真实被包装类可能使用的 `wrapped` 属性冲突。不过这并非真正的"隐私"——变形后的全名在类外仍可自由使用。注意：在 `__setattr__` 里，我们必须用展开后的全名串 `'_onInstance__wrapped'` 作为管理名测试值，因为那才是 Python 改写后的名字。
>
> **破坏隐私**：尽管本示例确实实现了属性访问控制，但**可以**轻易地绕过——例如通过展开后的全名显式抓取（`bob.pay` 可能不行，但 `bob._onInstance__wrapped.pay` 可以）。如果必须费这么大力气才能绕过，那这些工具大概已足以胜任预期角色。当然，其他语言里隐私通常也可以被绕过（例如某些 C++ 实现里 `#define private public` 可能有效）。只要源代码可被修改，滴水不漏的访问控制永远是白日梦。更根本的是，Python 讲的是"赋能（enabling）"，不是"控制（controlling）"；隐私是一种最好少用（甚至不用）的工具。
>
> **装饰器的权衡（trade-offs）**：这个以及任何基于包装器的方法，其主要缺点是属性访问多一次额外调用，而且被装饰类的实例并不是原装饰类的真正实例——用 `X.__class__` 或 `isinstance(X, C)` 测试，你会发现它们是包装器类的实例。除非你打算对对象类型做内省（introspection），类型问题无关紧要；额外调用也主要发生在开发期——如后所述，用 `-O` 可以自动移除装饰。

### 深度理解

- **核心概念**：伪私有名（`__wrapped` → `_onInstance__wrapped`）解决"名字冲突"；**但这不是安全机制**——Python 的隐私向来是"君子协定"。
- **底层实现**：类体内的 `__attr` 会被编译器改写为 `_类名__attr`，类外无此改写；因此管理名测试必须用变形后的全串。
- **设计原因**：作者的态度——"隐私工具"用于开发期防手滑，不是安全边界；C++/Java 的 private 同样可被暴力绕过。
- **实际问题**：权衡清单——每次属性访问多一次调用（性能）、`isinstance` 失效（类型内省）、`-O` 可整体移除（优化通道）。
- **初学者误区**：把"装饰后的代理实例"当作原类实例用 `isinstance` 判断而得到 False，误以为程序有 bug；这是代理模式的固有性质而非缺陷。

## 39.33 Delegating Built-In Operations（委托内置运算）

### 英文原文

> As is, this section's examples work as planned for methods and other attributes fetched explicitly by name. As with most software, though, there is always room for improvement. Most notably, this tool turns in mixed performance on operator-overloading methods if they are used by client classes.
>
> Specifically, the proxy class fails to validate or delegate operator-overloading methods fetched implicitly by built-in operations unless such methods are redefined in the proxy. Clients that do not use operator overloading are fully supported, but others may require additional code.
>
> It's unclear that operator-overloading methods should be validated as private or public, but they are a part of an object's interface and should at least be routed to wrapped objects that define them.
>
> The basic issue is easy to demo. A class that overloads print calls and + expressions works normally. But objects that implement built-in operations fail in our proxy classes because built-in operations skip instance-level lookup protocols like __getattr__, and instead search namespaces of classes.
>
> In this session, the first two explicit fetches of sum and __add__ are kicked out as privates as they should be. Because the last two implicit fetches of print and + aren't caught by the proxy, they are never delegated to the wrapped Tally object. The print works at all only because it runs an object default to print the proxy itself.

### 中文翻译

> 就现状而言，本节示例对"显式按名字抓取的方法和其他属性"能按计划工作。但和大多数软件一样，总有改进空间。最值得注意的是：如果客户端类使用了运算符重载方法，这个工具的表现就参差不齐。
>
> 具体来说，除非运算符重载方法在代理中被重新定义，否则代理类无法校验或委托**内置运算隐式抓取**的那些运算符重载方法。不使用运算符重载的客户端完全受支持，但其他客户端可能需要额外代码。运算符重载方法是否应被当作私有或公共来校验并不清楚，但它们是对象接口的一部分，至少应被路由到定义了它们的被包装对象。
>
> 基本问题很容易演示。重载了 `print` 调用与 `+` 表达式的类本来工作正常。但实现内置运算的对象在我们的代理类里会失败——因为内置运算会**跳过** `__getattr__` 这类实例级查找协议，转而去类的命名空间里搜索。
>
> 在本会话中，前两次对 `sum` 和 `__add__` 的**显式**抓取如预期那样被当作私有点名拒绝。而后两次 `print` 与 `+` 的**隐式**抓取没被代理接住，因此永远不会被委托给被包装的 `Tally` 对象。`print` 之所以还能工作，只是因为它运行的是 object 的默认行为——打印代理对象自身。

### 深度理解

- **核心概念**：**内置运算的查找协议绕过实例层**——`X + 5` 直接在 `type(X)` 的类命名空间找 `__add__`，根本不会落入 `__getattr__`。这是 Python 属性协议的一个著名怪癖。
- **底层实现**：`__getattr__` 只在"实例正常属性查找链全失败"时触发；而内置运算走"类型（类）层面"的特殊槽位查找，两套通道并行不悖。
- **设计原因**：性能考量与历史包袱使然——Python 为内置运算保留快速路径。理解它，才能解释"代理为何接不住 `+`"。
- **实际问题**：任何"委托代理"（ORM、RPC、mock）都要为 `__str__`、`__add__` 等显式补一层，否则内置语法失效。
- **初学者误区**：`print(X)` 能输出"对象地址"，让人误以为委托成功；其实那是 object 的默认 `__str__`，被包装对象的 `__str__` 从未被调用。

### 代码分析

```python
>>> class Tally:                # 一个重载内置运算的类
...     def __init__(self): self.sum = 0
...     def __str__(self): return f'Tally: {self.sum}'
...     def __add__(self, add): self.sum += add
>>> X = Tally()
>>> print(X)          # 正常：Tally: 0
>>> X + 5             # 正常：X.__add__(5)
>>> print(X)          # Tally: 5

>>> from access2 import Private
>>> @Private('sum', '__add__')
... class Tally: ...
>>> X = Tally()
>>> X.sum             # 显式抓取 → 被拦截：private attribute fetch, sum
>>> print(X)          # 隐式抓取 → 未被拦截：打印的是代理对象本身！
>>> X + 5             # 隐式抓取 → 未被拦截：unsupported operand type(s)
```

**执行链对比**：`X.sum` 走实例查找链 → 落入 `__getattr__` → 校验；`print(X)` 走类层面 `__str__` 槽位 → 代理类没定义 → 退回 `object.__str__`；`X + 5` 同理在代理类上找不到 `__add__` 而抛类型错误。**设计思想**：两条查找通道（实例协议 vs 类槽位）是理解 Python 全部"魔法方法"行为的地基。

### Workaround 1: Coding operator-overloading methods inline（方案一：内联重定义）

### 英文原文

> The most straightforward way to support built-ins in delegation proxies is to redefine operator-overloading names that may appear in embedded objects. This creates some code redundancy, but it isn't impossibly onerous; it can be automated with tools or superclasses; and it can choose to run or skip validations for operator-overloading names declared Private or Public, depending on redefinitions' routing.
>
> For instance, the partial listing of Example 39-19 sketches an inline redefinition approach—it catches and delegates built-ins by adding method definitions to the proxy itself for every operator-overloading method a wrapped object may define. It adds just four operation interceptors to illustrate, but others are similar.

### 中文翻译

> 在委托代理中支持内置运算最直接的方法，是把嵌入对象可能出现的运算符重载名字**在代理里重定义一遍**。这会造成一些代码冗余，但并非无法承受；可以用工具或超类自动化；也可以根据重定义的路由选择"对声明为 Private/Public 的运算符重载名做校验或跳过校验"。
>
> 例如，示例 39-19 的局部清单勾勒了"内联重定义"方案——给代理本身添加方法定义，逐个捕获并委托被包装对象可能定义的运算符重载方法。这里只加了四个运算拦截器示意，其他同理。

### 深度理解

- **核心概念**：既然内置运算在代理类上找不到名字，就"手动在代理类里摆好这些名字"，让它们显式转发到 `self.__wrapped`。
- **底层实现**：`__add__` 等在代理类命名空间里存在后，内置运算的类级查找命中，直接调用代理方法，代理方法内再调被包装对象。
- **设计原因**：直接、可预期、零元编程；代价是"每运算符一行样板"。
- **实际问题**：绕过校验直接转发（跳过 `__getattr__` 验证），适合"信任被包装对象"的场合。
- **初学者误区**：以为加一个 `__add__` 就能接住所有运算——`__radd__`、`__iadd__`、比较符、`__len__`……清单很长，通用代理需要穷举。

### 代码分析
```python
# 示例 39-19：access_builtins_inline_direct.py（节选）
def accessControl(failIf):
    def onDecorator(aClass):
        class onInstance:
            def __init__(self, *args, **kargs):
                self.__wrapped = aClass(*args, **kargs)
            # 专门拦截并委托内置运算的隐式访问（新代码）
            def __add__(self, other):
                return self.__wrapped + other      # 或 getattr()/__getattr__()
            def __str__(self):
                return str(self.__wrapped)          # 或 self.__wrapped.__str__()
            def __getitem__(self, index):
                return self.__wrapped[index]
            def __call__(self, *args, **kargs):
                return self.__wrapped(*args, **kargs)
            # ……其余需要的运算符依此类推
            # 通用：显式属性访问的拦截照旧
            def __getattr__(self, attr): ...
            def __setattr__(self, attr, value): ...
        return onInstance
    return onDecorator
```

**执行链**：`print(X)` → 类级找 `__str__` → 命中代理的 `__str__` → 返回 `str(self.__wrapped)` → 触发被包装对象的 `__str__`。**设计思想**：把"内置运算"显式桥接进代理——本质是"按需列举接口"。

### Workaround 2: In superclasses（方案二：写在超类/混入类中）

### 英文原文

> More usefully, the prior section's added methods can be added by a common superclass. Given that there are dozens of such methods, an external class may be better suited to the task, especially if it is general enough to be used in any such interface-proxy class.
>
> To demo, the superclass of Example 39-20 catches built-ins and reroutes to the wrapped object directly again. It's largely just a repackaging of the prior section's inline scheme, but as a separate class it requires a proxy attribute named _wrapped, giving access to the embedded object. The decorator itself must use this name instead of __wrapped in self references, and sans mangling in __setattr__.
>
> Alternatively, the superclass in Example 39-21 catches built-ins and reroutes them down through the subclass __getattr__ to apply its access controls to the operation's method name. It requires that operator-overloading names be non-Private (or Public) per the decorator's arguments if they are to be run, but it treats the implicit fetches of built-in operations the same as explicit-name fetches, and no _wrapped is required in subclasses.

### 中文翻译

> 更有用的是，把上一节的"新增方法"放进一个公共超类里。既然这类方法有几十个，外部类可能更适合这个任务——尤其是当它通用到"任何此类接口代理类都能用"时。
>
> 演示一下：示例 39-20 的超类再次直接捕获内置运算并转发给被包装对象。它大体只是把上一节的内联方案重新打包，但作为独立类，它要求代理有一个名为 `_wrapped` 的属性以访问嵌入对象；装饰器自身在 `self` 引用里也必须用它（不用 `__wrapped`），`__setattr__` 里也不涉及名字变形。
>
> 另外，示例 39-21 的超类捕获内置运算后，会**经由子类的 `__getattr__`** 再路由下去，从而把访问控制施加到该运算的方法名上。它要求运算符重载名字按装饰器参数是"非 Private（即 Public）"才能运行；它把内置运算的隐式抓取与显式名字抓取同等对待，而且子类无需 `_wrapped`。

### 深度理解

- **核心概念**：把几十个 `__X__` 样板**提升为混入超类（mixin）**——`class onInstance(BuiltinsMixin)`，一处编写、处处继承。
- **底层实现**：示例 39-20 直连 `self._wrapped`（跳过校验）；示例 39-21 改为 `self.__getattr__('__add__')(other)`（走校验），只是转发路径不同。
- **设计原因**：MRO 查找让子类自动获得全套内置桥接，既省样板又保证一致性。
- **实际问题**：需要一个共享的 `_wrapped` 名字约定，且不能与包装类自己的属性冲突——通用工具设计时命名即契约。
- **初学者误区**：只记得"加方法"，却忘了"走哪条通道"决定是否经过校验——两条 mixin 路线代表两种语义，用途不同。

### 代码分析
```python
# 示例 39-20：access_builtins_mixin_direct.py（跳过校验）
class BuiltinsMixin:
    def __add__(self, other):
        return self._wrapped + other     # 假定存在 _wrapped；绕过 __getattr__
    def __str__(self):
        return str(self._wrapped)
    def __getitem__(self, index):
        return self._wrapped[index]
    def __call__(self, *args, **kargs):
        return self._wrapped(*args, **kargs)
# 装饰器内 class onInstance(BuiltinsMixin): 使用不带变形的 _wrapped

# 示例 39-21：access_builtins_mixin_getattr.py（走校验）
class BuiltinsMixin:
    def __add__(self, other):
        return self.__getattr__('__add__')(other)   # 路由到校验器
    def __str__(self):
        return self.__getattr__('__str__')()         # 完成运算
    def __getitem__(self, index):
        return self.__getattr__('__getitem__')(index)
    def __call__(self, *args, **kargs):
        return self.__getattr__('__call__')(*args, **kargs)
```

**执行链（39-21 版）**：`X + 10` → 类级找到 mixin 的 `__add__` → `self.__getattr__('__add__')` → 若 `__add__` 被声明 Private 则抛异常；否则委托 `wrapped.__add__(10)`。**设计思想**：让内置运算"绕回" `__getattr__`，一举统一"显式/隐式"两条抓取通道的校验语义。

### Workaround 3: Generating operator-overloading descriptors（方案三：生成运算符重载描述符）

### 英文原文

> Finally, all of the inline and mix-in workarounds for built-ins we've seen so far code each operator-overloading method explicitly, and intercept the actual call issued for the operation, including its arguments. That makes them responsible for completing the operation, whether by operation syntax or equivalent calls.
>
> With an alternative coding, we could instead intercept only the attribute fetch preceding the call by using the class-level descriptors of the prior chapter. Moreover, because all such descriptors will run the same, they can be generated automatically from a list of method names. Example 39-22 shows one way to code this scheme. Like Example 39-21, it routes built-in operations through the decorator's validations logic.
>
> Recall that the exec built-in by default runs a string of code as if it was pasted where exec appears. Hence, the loop at the end of this mix-in class is equivalent to the following statements, run in the mix-in class's local scope: __add__ = ProxyDesc("__add__"); __str__ = ProxyDesc("__str__"); and so on.
>
> The net effect creates inherited descriptor instances that respond to initial name lookups by fetching from the wrapped object in __get__ rather than catching the later operation call itself.

### 中文翻译

> 最后，目前看到的所有内联与混入内置运算修补方案，都是显式编写每个运算符重载方法，并拦截"为运算发出的实际调用（含参数）"。这让它们负有"完成运算"之责——无论用运算语法还是等价调用。
>
> 另一种编码可以只用前一章的**类级描述符**，只拦截"调用之前的那次属性抓取"。而且，因为所有这些描述符行为一致，它们可以从一个方法名列表**自动生成**。示例 39-22 演示了该方案的一种写法。与示例 39-21 一样，它让内置运算经过装饰器的校验逻辑。
>
> 回忆一下：`exec` 内建函数默认把一串字符串代码当作"粘贴在 exec 出现处"来执行。因此，该混入类末尾的循环等价于下列在混入类局部作用域中执行的语句：`__add__ = ProxyDesc("__add__")`、`__str__ = ProxyDesc("__str__")`……依此类推。
>
> 净效果是创建了一组被继承的描述符实例：它们响应"首次名字查找"，在 `__get__` 里从被包装对象取货，而不是去拦截之后的运算调用本身。

### 深度理解

- **核心概念**：把"拦截调用"换成"拦截**属性抓取**"——用描述符在类级把 `__add__` 等名字占位，抓取时经 `__get__` 注入校验与委托。
- **底层实现**：`exec(f'__{attr}__ = ProxyDesc("__{attr}__")')` 在类体里批量生成类属性；每个 `ProxyDesc.__get__` 调用 `instance.__getattr__(self.attrname)`。
- **设计原因**：从方法名**列表**生成描述符，几十个运算符零样板——把"元编程"用到极致，但作者直白警告这是"最隐晦、最复杂"的方案。
- **实际问题**：运维通用代理时，"列表驱动"比"手工抄写"更不易漏；代价是可读性。
- **初学者误区**：被 `exec` 吓到或滥用——`exec` 是运行时执行字符串代码，等同"在类体里粘贴语句"，本文用它正是生成重复样板的正规场合。

### 代码分析

```python
# 示例 39-22：access_builtins_mixin_desc.py（节选）
class BuiltinsMixin:
    class ProxyDesc:                       # 定义描述符
        def __init__(self, attrname):
            self.attrname = attrname
        def __get__(self, instance, owner):
            return instance.__getattr__(self.attrname)   # 运行校验

    builtins = ['add', 'str', 'getitem', 'call']   # 还可加上其他
    for attr in builtins:
        exec(f'__{attr}__ = ProxyDesc("__{attr}__")')   # 批量生成描述符
# 装饰器中 class onInstance(BuiltinsMixin): ... 继承这些描述符

# 等价的展开形式（手动粘贴版）：
# __add__ = ProxyDesc("__add__")
# __str__ = ProxyDesc("__str__")
# ...

# 若想跳过校验，直接转发：
#     def __get__(self, instance, owner):
#         return getattr(instance._wrapped, self.attrname)   # 假定 _wrapped
```

**执行链**：`X + 10` → 类级找到继承来的 `__add__` 描述符 → 调用它触发 `ProxyDesc.__get__(X, onInstance)` → `X.__getattr__('__add__')` → 校验（Private 则抛错；否则委托被包装对象）→ 得到的可调用再被 `+` 运算调用。**设计思想**：描述符把"抓取时刻"与"调用时刻"分离，前者挂接校验、后者自然完成——比"拦截调用"更早一步介入，也更容易批量化。

## 39.36 A Basic Range-Testing Decorator for Positional Arguments（基础版：仅支持位置参数）

### 英文原文

> To keep things simple, we'll begin by coding a decorator that works only for positional arguments and assumes they always appear at the same positions in every call; they cannot be passed by keyword name because this invalidates the positions declared in the decorator. Example 39-23 is our first-cut checker.
>
> This code is mostly a rehash of the coding patterns we explored earlier: decorator arguments, nested scopes for state retention, and nested def to support both functions and methods. When used on a method, onCall receives the subject class's instance in the first item in *args and passes this along to self; explicitly passed argument numbers in the decorator line start at 1 in that case to accommodate the implicit self.
>
> New here is the __debug__ built-in variable: Python sets it to True unless the program runs with the -O optimize flag. When __debug__ is False, the decorator returns the original function instead of a wrapper to avoid extra calls and their performance penalty—automatically removing augmentation logic without requiring you to physically remove the decoration lines.

### 中文翻译

> 为了保持简单，我们先写一个只适用于位置参数的装饰器，并假设它们在**每次调用中总出现在相同位置**；不能用关键字名字传它们，因为那会让声明的位置号失效。示例 39-23 是第一版检查器。
>
> 这段代码基本是前面讲的编码模式的旧瓶新酒：装饰器参数、嵌套作用域做状态保存、嵌套 `def` 以同时支持函数与方法。用于类的某个方法时，`onCall` 会在 `*args` 的第一项收到主题类实例并转发给 `self`；此时装饰器行里显式写的参数编号要从 1 开始（0 位留给了隐式 `self`）。
>
> 本节新引入了 `__debug__` 内建变量：除非程序以 `-O` 优化标志运行，Python 把它设为 True。当 `__debug__` 为 False 时，装饰器返回原函数而非包装器，以避开额外调用及其性能代价——自动移除增强逻辑，无需你从源码里手工删行。

### 深度理解

- **核心概念**：**位置参数校验**的第一版——`@rangetest((1, 0, 120))` 意为"第 1 个（从 0 数）位置参数必须在 0..120"。
- **底层实现**：三层结构 `rangetest(*argchecks) → onDecorator(func) → onCall(*args)`；`onCall` 逐个处理 `(ix, low, high)` 检查 `args[ix]`。
- **关键设计**：`__debug__`/`-O` 开关——`python -O main.py` 时校验自动失效、性能零损耗，这是"开发校验、生产直通"的力作。
- **实际问题**：方法场景：`@rangetest([1, 0.0, 1.0])` 因为 `args[0]` 是 `self`，参数号从 1 起。
- **初学者误区**：调试期忘了"位置参数版**不能接受关键字传参**"——一旦 `persinfo(name='Bob', age=45)` 传入，位置语义立刻错乱。

### 代码分析

```python
# 示例 39-23：rangetest0.py
def rangetest(*argchecks):           # 校验位置参数范围
    def onDecorator(func):
        if not __debug__:            # 若用 "python -O main.py args" 运行则为真
            return func             # 无操作：直接调用原函数
        else:                       # 否则调试期间用包装
            def onCall(*args):
                for (ix, low, high) in argchecks:
                    if args[ix] < low or args[ix] > high:
                        errmsg = f'Argument {ix} not in {low}..{high}'
                        raise TypeError(errmsg)
                return func(*args)
            return onCall
    return onDecorator

# 示例 39-24：rangetest0_test.py（节选）
@rangetest((1, 0, 120))           # persinfo = rangetest(...)(persinfo)
def persinfo(name, age):          # age 必须在 0..120
    print(f'{name} is {age} years old')

class Person:
    @rangetest([1, 0.0, 1.0])     # giveRaise = rangetest(...)(giveRaise)
    def giveRaise(self, percent): # 这里第 0 个参数是 self 实例
        self.pay = int(self.pay * (1 + percent))

#persinfo('Bob Smith', 200)       # 打开注释 → TypeError: Argument 1 not in 0..120
sue.giveRaise(.10)                # 运行成功时 runs onCall(self, .10)
#sue.giveRaise(1.10)              # TypeError: Argument 1 not in 0.0..1.0
```

### 英文原文

> The prior version illustrates the basics we need to employ, but it's fairly limited—it supports validating arguments passed by position only and it doesn't validate keyword arguments; it also does nothing about arguments with defaults that may be omitted. ### 中文翻译

> 前面的版本拿出了我们所需的基础，但相当受限——只支持按位置传入的参数校验，不校验关键字参数（事实上它**假设**没有以关键字方式传入的参数）。它对"有默认值、可能被省略"的参数也毫无作为。如果所有参数都按位置传递、从不省略，这没什么问题；可作为通用工具就不太理想了。

>
> 最终版同时支持位置参数、关键字参数与省略默认值。下面是测试代码（展示装饰器用法）及其输出。

### 深度理解

- **核心概念**：**从面向位置到面向名字**——用函数内省获知"期望参数名列表"，从而把"装饰器声明的参数名"映射到"实际调用传入的值/位置"。
- **底层实现**：`func.__code__.co_varnames[:co_argcount]` 截取"前 N 个局部变量"作为期望参数名；`*pargs` 的前 N 个即位置实参。
- **设计原因**：固定位置方案太脆；按名字匹配方案柔性覆盖"位置/关键字/默认省略"三种传法。
- **解决问题**：一版通用工具通吃三种传参风格，甚至 `birthday(8, D=31, Y=2024)` 这种混合调用。
- **初学者误区**：以为"默认值参数也必须校验"。设计正确行为是**省略即跳过**——`omitargs(1, 2, 3)` 时 `d` 没传，就不检查 `d`。

### 代码分析

```python
# 示例 39-25：rangetest.py（节选）
trace = True
def rangetest(**argchecks):                # 校验范围：按名指定
    def onDecorator(func):                # onCall 记住 func 与 argchecks
        if not __debug__:
            return func                   # 调试时包装；否则用原函数
        else:
            funcname = func.__name__
            funccode = func.__code__
            funcargs = funccode.co_varnames[:funccode.co_argcount]   # 期望参数名
            def onCall(*pargs, **kargs):
                # 所有 pargs 按位置匹配前 N 个期望参数
                # 其余必须在 kargs 里，或是被省略的默认值
                positionals = funcargs[:len(pargs)]
                errormsg = lambda *args: '%s argument "%s" not in %s..%s' % args
                for (argname, (low, high)) in argchecks.items():
                    if argname in kargs:                 # 按名传入
                        if kargs[argname] < low or kargs[argname] > high:
                            raise TypeError(errormsg(funcname, argname, low, high))
                    elif argname in positionals:         # 按位置传入
                        position = positionals.index(argname)
                        if pargs[position] < low or pargs[position] > high:
                            raise TypeError(errormsg(funcname, argname, low, high))
                    else:
                        if trace:                        # 未传：假设默认值
                            print(f'-Argument "{argname}" defaulted')
                return func(*pargs, **kargs)             # 全通过：执行原调用
            return onCall
    return onDecorator
```

## 39.38 Implementation Details（实现细节）

### 英文原文

> This range-tester decorator's code relies on both introspection APIs and subtle constraints of argument passing. To be fully general, we could try to mimic Python's argument-matching logic in its entirety, but that's too much complexity for our tool and is prone to change over time. It would be better if we could match the names of testable arguments given to the decorator against the names of actual arguments expected by the function.
>
> **Function introspection**: The introspection API available on function objects and their associated code objects has exactly the tool we need. The set of expected argument names is simply the first N variable names attached to a function's code object: func.__code__.co_varnames[:func.__code__.co_argcount].
>
> **Argument assumptions**: Given the expected argument names, the solution relies upon two constraints on ordering: - At the call, all positional arguments appear before all keyword arguments. - In the def, all nondefault arguments appear before all default arguments.
>
> That is, a nonkeyword argument cannot follow a keyword argument at a call, and a nondefault argument cannot follow a default argument in a definition. All name=value syntax must appear after any simple name in both places.
>
> We can also assume the call is valid in general—that all arguments either receive values or are omitted to pick up defaults. This won't necessarily hold, but since the call would fail here anyway, we might as well let Python's own argument matching detect invalid calls.
>
> **Matching algorithm**: Given these constraints, for a call being intercepted we can deduce: 1. Let N be the number of passed positional arguments (the length of the *pargs tuple).
>
> 2. All N positional arguments must match the first N expected arguments, by Python's call ordering rules.
>
> 3. To obtain the names of arguments passed by position, slice the list of all expected arguments up to N.
>
> 4. Any arguments after the first N expected arguments either were passed by keyword or were defaulted by omission.
>
> 5. For each argument name to validate: (a) if in **kargs, it was passed by name; (b) if in the first N expected, it was passed by position; (c) otherwise, assume it was omitted and defaulted and need not be checked.
>

### 中文翻译

> 这个区间测试装饰器的代码依赖两样东西：自省（introspection）API，以及参数传递顺序的微妙约束。要做到完全通用，可以尝试完整模拟 Python 的参数匹配逻辑，但对我们的工具来说这过于复杂，而且随时间易变。更好的办法是：把"给装饰器的可测试参数名"与"函数期望达到的实际参数名"对照起来。 **函数内省（function introspection）**：函数对象及其关联代码对象上的内省 API，正好提供我们需要的工具。期望参数名集合，就是函数代码对象上附着的**前 N 个变量名**连接：`func.__code__.co_varnames[:func.__code__.co_argcount]`。 演示：`def func(a, b, c, e=True, f=None)` 加上局部变量 x、y 后，`co_nlocals=7`、`co_varnames=('a','b','c','e','f','x','y')`，而前 `co_argcount=5` 个是 `('a','b','c','e','f')`。 **参数假设**：有了期望参数名集合，我们的解法依赖两条 Python 强加的排序约束（第 18 章已述）： - 在调用处，所有位置参数都在所有关键字参数之前。 - 在定义处，所有非默认参数都在所有默认参数之前。 也就是说：调用处，非关键字参数不能跟在关键字参数之后；定义处，非默认参数不能跟在默认参数之后。任何 `name=value` 语法都必须出现在两处所有简单名字之后。 我们还可以假设本次调用**总体上是合法的**——所有参数要么收到值，要么故意省略取默认值。这条假设不必然成立，但反正调用在这里也会失败，不如让 Python 自己的参数匹配逻辑替我们发现非法调用。 **匹配算法（matching algorithm）**：在这些约束下，对一次被拦截的调用可以按如下推演： 1. 令 N 为传入的位置参数个数，即 `*pargs` 元组的长度。 2. 全部 N 个位置参数，按 Python 调用排序规则，必须与前 N 个期望参数匹配。 3. 为得到"按位置传入的参数名"，把全部期望参数列表切片到第 N 个。 4. 前 N 个期望参数之后的任何参数，要么按关键字传入，要么因省略而取了默认值。 5. 对每个待校验参数名：(a) 若在 `**kargs` 里 → 按名传入，作弊索引即得值；(b) 若在前 N 个里 → 按位置传入，期望列表里的相对位置即它在 `*pargs` 里的相对位置；(c) 否则假设在调用中被省略、取了默认值，无需检查。

### 深度理解

- **核心概念**：**参数匹配算法的根在两条排序不变量**（位置先于关键字── call 侧；非默认先于默认── def 侧），本书用它们省掉了"模拟整个匹配引擎"的苦役。
- **底层实现**：`co_varnames` 给出全部局部变量（含形参与函数体局部），`co_argcount` 标出"前 N 个是形参"；配合调用处 `*pargs/**kargs` 的收集，恰好能完成"名字 ↔ 位置 ↔ 值"三方对账。
- **设计原因**：不模拟 CPython 的匹配（易碎、难维护），而是利用两条排序规则**推理**出必然而然——算法的优雅老师。
- **解决实际**：三种传参风格混合的任意调用（`birthday(8, D=31, Y=2024)`、`omitargs(1, b=2, d=4)`），都能正确找到待校验参数的值。
- **初学者误区**：`co_varnames` 不只是参数——它还包含函数体内声明的局部变量（本例 x、y），必须靠 `co_argcount` 截断，否则会误把局部变量当作形参。

### 代码分析

```python
>>> def func(a, b, c, e=True, f=None):   # 形参：三个必选、两个默认
...     x = 1                             # 外加两个局部变量
...     y = 2
>>> code = func.__code__                  # 函数对象的代码对象

7
>>> code.co_varnames                      # 所有局部变量名
('a', 'b', 'c', 'e', 'f', 'x', 'y')
>>> code.co_varnames[:code.co_argcount]   # <== 前 N 个局部变量就是期望参数
('a', 'b', 'c', 'e', 'f')

def catcher(*pargs, **kargs): print(f'{pargs}, {kargs}')
catcher(1, 2, c=3, d=4, e=5)             # (1, 2), {'c': 3, 'd': 4, 'e': 5}
```

**执行解读**：调用侧 `*pargs` 收集"位置实参元组"，`**kargs` 收集"关键字命名参数字典"；被包装侧的 `co_varnames[:co_argcount]` 提供"期望形参名元组"。装饰器在两者之间做映射：先看 kargs（按名），再看 positionals（按位置），都不中则视为默认省略。**设计思想**：把"实参与形参的对应关系"不做黑盒猜测，而是由语言规范与内省 API 共同推出——这类"基于契约的推理"是自己写框架时的核心素养。

## 39.39 Open Issues（遗留问题）

### 英文原文

> Although our range-testing tool works as planned, three caveats remain—it doesn't detect invalid calls, doesn't handle some arbitrary-argument signatures, and doesn't fully support nesting.
>
> **Invalid calls**: Calls that are not valid still fail in our final decorator—e.g., omitargs() and omitargs(d=8, c=7, b=6) both raise TypeError for a missing positional argument a. These fail though only when we actually call the original function at the end of the wrapper; since the call would fail anyway, we might as well let Python's own argument-matching logic detect the problem.
>
> **Arbitrary arguments**: Although handled for the ordinary modes, the final version doesn't handle *pargs and **kargs names used as the decorated function's own arguments. If an extra keyword is passed, its name will show up in kargs and can be tested normally; if not passed, it's treated as though defaulted; if an extra positional is passed, there's no way to reference it—its name won't be in either collection.
>
> In other words, it tests arbitrary keywords by name but not unnamed positionals beyond the signature.
>
> **Decorator nesting**: The approach doesn't fully support decorator nesting in which multiple stages are combined. Because it analyzes arguments using names in function definitions, proxies change argument-name signatures at their levels; as coded, only the most-deeply-nested validations run in full. (Position-based solution supports proxies better but not keywords.)

### 中文翻译

> 虽然我们的区间测试工具按计划工作，但仍留三个警告——它不检测无效调用、不处理某些任意参数签名、也不完全支持嵌套。
>
> **无效调用（invalid calls）**：对原函数合法的"调用"仍然会在包装器里失败——例如 `omitargs()` 和 `omitargs(d=8, c=7, b=6)` 都会因缺少位置参数 `a` 而抛 TypeError。但这只在包装器末尾真正调用原函数时才失败。反正这个调用本就要失败，不如就让 Python 自己的参数匹配逻辑替我们抓问题。
>
> **任意参数（arbitrary arguments）**：虽然普通模式都已处理，最终版还是没有显式处理"被装饰函数自身使用 `*pargs`/`**kargs`（星号收集器）"的情况。若多传了关键字 → 名字会出现在 `**kargs`, 可按名正常测试；若没传 → 视同默认而被跳过（虽然它是可选额外参数）；若多传了位置参数 → 根本没法引用它（不在期望参数对照里，也无法映射相对位置）。即：按名的任意关键字天然支持，但超出签名的"无名位置参数"无法挂载校验。
>
> 关于调用里的星号展开（如 `f(*[1], 2, *[3]...)`）——它们在到达装饰器之前就已被展开（flattened），对装饰器代码毫无影响，所以可以安然无忧。
>
> **装饰器嵌套（decorator nesting）**：此方案并不完全支持"用嵌套把多级步骤组合起来"。因为它用函数定义里的名字分析参数，而嵌套装饰返回的代理 `onCall` 的调用签名与"原函数或装饰器参数中的参数名"并不对应——当嵌套时，只有最内层出现的校验会完整运行；其余层只对"按名传入"的参数抛校验（按位置传的会被当作省略默认值而跳过）。这正是"位置派"（rangetest0）与"名字派"（rangetest）各残余半边的体现：位置派更支持代理但不懂关键字，名字派反过来。

### 深度理解

- **核心概念**：再好的工具也有"假设边界"——本章诚实地罗列三条：非法调用、任意参数签名、嵌套场景。
- **底层实现**：嵌套失效的根因——`onCall` 代理的函数签名是 `(*pargs, **kargs)`，它"期望参数名元组"在装饰时刻被换成别的名（如 `onCall` 自己的 argnames），外层的名字映射就错位了。
- **设计原因**：作者故意不把工具做到"全能"——宁可"明确边界"也不"复杂到不可维护"，并把扩展列为练习。
- **解决问题**：提醒我们"通用工具"的谦虚心态——知道自己的失效模式，好过假装全能。
- **初学者误区**：想当然认为"装饰器嵌套"就该像括号一样天然工作——嵌套推理与参数名映射是最容易想当然的位置。

### 代码分析

```python
# 演示星号展开在调用点就被扁平化（对装饰器透明）：
>>> def f(a, b, c, d, e, f, g, h, i): pass
>>> f(*[1], 2, *[3], 4, f=6, *[5], **dict(g=7), h=8, **{'i': 9})
# 星号在函数启动前已解析：(1, 2, 3, 4, 5) 与 {'f': 6, 'g': 7, 'h': 8, 'i': 9}
```

**执行链**：Python 对调用的展开发生在"进入函数体之前"，故装饰器里的 `*pargs/**kargs` 只看到"已扁平化"的值。**设计思想**：理解"调用压缩先于被调用者"，就能避免在装饰器里重复实现展开逻辑。

## 39.40 Decorator Arguments Versus Function Annotations（装饰器参数对比函数注解）

### 英文原文

> In closing, Python's annotation feature (introduced in Chapter 19) could also provide an alternative to decorator arguments for specifying the valid ranges in our example. We could use annotations to code range limits in the header line instead of in decorator arguments. We would still need a decorator, but we would essentially trade decorator-argument syntax:
>
> @rangetest(a=(1, 5), c=(0.0, 1.0)) / def func(a, b, c): ...
>
> for annotation syntax like this:
>
> @rangetest / def func(a:(1, 5), b, c:(0.0, 1.0)): ...
>
> That is, the range constraints would be moved into the function itself instead of being coded externally in a decorator line. Example 39-27 illustrates the structure of the resulting decorators under both schemes. The annotation version requires one fewer level of nesting because it doesn't need to retain decorator arguments as state.
>
> In fact, using annotations instead of decorator arguments in this example actually limits its utility. By moving the validation specs into the def header, we essentially commit the function to single role—annotation directly allows only one expression per argument, so it can have only one purpose.
>
> By contrast, because decorator arguments are coded outside the function itself, they are easier to remove and more general. Crucially, by nesting decorators with arguments, we can often apply multiple augmentation steps to the same function.
>
> Still, if you have a single purpose in mind, the choice is largely stylistic and subjective. As is so often true in life, one person's decoration may well be another's syntactic clutter.

### 中文翻译

> 最后提一句：Python 的**注解（annotation）**特性（第 19 章引入）也能为"指定测试区间"提供装饰器参数的替代方案。我们可以用注解把区间限制写进 `def` 头行，而不是写进装饰器参数。我们仍然需要一个装饰器去包装函数、拦截调用，但本质上是用"装饰器参数"语法换"注解"语法：
>
> @rangetest(a=(1, 5), c=(0.0, 1.0)) / def func(a, b, c): ...   → 换为
> @rangetest / def func(a:(1, 5), b, c:(0.0, 1.0)): ...
>
> 也就是说，区间约束从"装饰器行的外部配置"，移到了函数内部。示例 39-27 给出了两种方案下结果装饰器的结构。注解版因为不必保留装饰器参数作为状态，少了一层嵌套。两种方案运行输出一致：都打印 `{'a': (1,5), 'c': (0.0,1.0)}`。
>
> 不过实际上，这个工具上用注解替代装饰器参数会**限制用途**。把校验规范挪进 `def` 头，相当于给函数"赋予单一角色"：注解规定每个参数只能有一个表达式，于是参数只能有一种用途（比如区间校验）——无法再兼作类型提示（第 6 章）。而装饰器参数在函数之外，既更容易去掉，又更通用；关键还有，通过**嵌套带参装饰器**，我们能对同一函数施加多个增强步骤。从审美与主观角度，两者之争基本是风格之争。"如生活常事：一个人的装饰，可能是另一个人的语法堆砌。"

### 深度理解

- **核心概念**：同一桩"规范校验配置"，两个载体——外部（装饰器参数）vs 内部（注解）。二选一其实是"职责是否移出函数"的选择。
- **底层实现**：注解版直接 `func.__annotations__` 取字典；少一层闭包，因为无需先接参数。新代码骨架：`def rangetest(func): def onCall(*pargs,**kargs): argchecks = func.__annotations__ ...`
- **设计原因**：注解"每参数一个表达式"的固有局限——无法多用途复用；装饰参数则天然支持"多装饰器叠加多个角色"。
- **实际选择**：类型提示最好用它自己的机制（typing）；运行期校验用装饰器参数更清晰。
- **初学者误区**：以为注解就是"类型声明"。注解纯粹是写入 `__annotations__` 字典的表达式，解释器不主动校验——可当元数据、可运行时读取。

### 代码分析

```python
# 骨架：装饰器参数版（三层）
def rangetest(**argchecks):
    def onDecorator(func):
        def onCall(*pargs, **kargs):
            print(argchecks)          # {'a': (1,5), 'c': (0.0,1.0)}
            for check in argchecks: ...     # 这里加入校验代码
            return func(*pargs, **kargs)
        return onCall
    return onDecorator

# 骨架：注解版（两层，无需保存配置）
def rangetest(func):
    def onCall(*pargs, **kargs):
        argchecks = func.__annotations__   # 从函数对象取注解
        print(argchecks)                   # {'a': (1,5), 'c': (0.0,1.0)}
        for check in argchecks: ...        # 校验代码几乎相同
        return func(*pargs, **kargs)
    return onCall
```

**执行链**：注解版在 `@rangetest` 时 `func` 已编译、`func.__annotations__` 已就位，包装器每次调用动态读取。**设计思想**：同一个"区间表"，存"闭包外层"还是存"函数属性"二者等价、界面不同——这正是"状态容器选择决定 API 姿态"的又一印证。

## 技术拓展（Technical Expansion）

- **实际项目中的应用场景**
  - Flask/FastAPI 的路由注册（`@app.route('/path')` 本质就是"装饰器参数 + 引用注册"）、Django 的 `@login_required`（函数/方法鉴权包装）、PyTorch 的 `@torch.no_grad()`、pytest 的 `@pytest.fixture`。
  - `functools.lru_cache` 是"带参数的装饰器工厂"，与本章 `@timer(label=...)` 结构完全同构——先接受配置、再接受函数。
  - 你自己写 Web 框架时，`@app.route`、`@middleware`、参数校验 `@validate_schema(...)` 都是本章三体术（路由/开关/回调）的直接落场。
- **与其他语言（Java/C++）的区别**

  | 语言 | 类似机制 | 本质 | Python 差异 |
  |---|---|---|---|
  | Python | 装饰器 | 运行时名字重绑定 | 调用封装、无文本展开 |
  | Java | 注解（annotation） | 编译期元数据 | 注解默认不改行为，Python 装饰器真改行为 |
  | C++ | 宏 `#define` | 预处理文本替换 | 与 `import` vs `#include` 同级的分别 |
  | Rust | 过程宏 | 编译期代码生成 | 属"文本/语法层"，非运行期对象操作 |

  Python 装饰器与这些"代码生成"路线最根本的区别：它是**运行时的对象操作**，一切皆可推迟到 import/调用时刻，灵活但少了编译期保证。

- **Python 发展历史背景**：装饰器的语法灵感可追溯到 Python 2.4 引入的"函数装饰器"，其语法形式整体借鉴自 Java 注解；类装饰器与参数式装饰器在 Python 3.0 面世；此后 `` `functools.wraps`（保留 `__name__`/`__doc__` 元数据）、`__wrapped__` 等配套标准被补齐。Python 3.9 才允许 `@` 后跟任意表达式；3.12 又允许对 `@` 表达式里的复合 f-string 等更自由的写法。作者在书里标注了大量 "Python 3.12" 实例（如嵌套 f-string 的 trace 打印）。
- **高级开发者需要掌握的相关知识**

  | 主题 | 作用 |
  |---|---|
  | `functools.wraps` | 把被包装函数的元数据（`__name__` 等）复制到 wrapper，保证测试/文档工具正常 |
  | `functools.cached_property` / `lru_cache` | 官方缓存装饰器，理解其"多级状态"设计 |
  | 参数内省 `inspect.signature` | 现代替代 `__code__.co_varnames` 的规范做法 |
  | 元类（第 40 章） | 装饰器+元类的职责边界与配合 |
  | 类型注解 + 装饰 | `typing` 与 `@` 组合出契约式校验框架 |

## 学习建议（Learning Advice）

- **重要程度：5/5 星（必读）**。装饰器与闭包、描述符并称 Python"高级三件套"，是通往框架源码、元编程的必经关。
- **应该掌握到什么程度**：
  1. 能把"任意 `@dec`"翻译成"`名字 = dec(名字)`"并反义。
  2. 能写出 4 种状态载体（实例属性/global/nonlocal/函数属性）版本的 tracer，并说清差异。
  3. 能指出"类包装器 + `__call__`"为何在方法上翻车，改用嵌套 `def`。
  4. 理解两级类装饰器（拦截实例创建 vs 拦截属性访问）与两级代理陷阱。
  5. 能读懂 `__getattr__` / `__setattr__` / `__get__` 三者合成的大案例（access2、rangetest）。
- **后续学习方向**：
  1. 第 40 章「元类（metaclasses）」——理解"类装饰器 = 元类的轻量版"这一对偶关系。
  2. 重新阅读第 31 章委托模式、第 38 章描述符与 property，把"钩子机制"串成一张网。
  3. 动手改这三道章末测验题（计时器方法化、`__debug__` 免包装、校验回调泛化），并对照 `_QuizAnswers` 子文件夹的官方解答。
  4. 用 `functools.wraps`、`inspect.signature`、`singledispatch` 重写本章工具，体会标准库对它们的使用。
