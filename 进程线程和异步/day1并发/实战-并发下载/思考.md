1.GIL 与多线程：如果 GIL 阻止了多线程并行执行 Python 代码，为什么 Python 还要提供 threading 模块？它主要解决什么问题？
    hreading 主要解决的是 I/O 密集型任务 的并发问题，而非 CPU 密集型任务的并行问题。

详细解释：
GIL（全局解释器锁）确实保证同一时刻只有一个线程执行 Python 字节码。但线程在以下情况会释放 GIL：
1.执行 I/O 操作（如网络请求、读写磁盘、数据库查询）时，线程会主动释放 GIL，让其他线程运行。
2.使用 time.sleep() 时。
因此，在 Web 爬虫、文件读写、网络服务等场景中，等待 I/O 的时间远大于 CPU 计算时间，多线程可以让这些等待时间重叠，大幅提升程序吞吐量。而对于 CPU 密集型任务（如循环计算、图像处理），多线程反而因 GIL 竞争降低性能，此时应使用 multiprocessing。



2.死锁场景：以下代码有什么问题？如何修复？
lock_a = threading.Lock()
lock_b = threading.Lock()

def task1():
    with lock_a:
        with lock_b:
            print("task1")

def task2():
    with lock_b:
        with lock_a:
            print("task2")
答案：
问题：这段代码存在 死锁（Deadlock） 风险。
task1 先获取 lock_a，再获取 lock_b。
task2 先获取 lock_b，再获取 lock_a。

如果两个线程几乎同时执行，task1 拿到 lock_a 等待 lock_b，而 task2 拿到 lock_b 等待 lock_a，双方永远互相等待，程序卡死。

修复方案（三种常用方法）：
统一锁的获取顺序（最推荐）：
让所有任务都以相同的顺序获取锁，例如都先 lock_a 再 lock_b。
python
def task2():
    with lock_a:  # 改为先 a 后 b
        with lock_b:
            print("task2")
使用超时机制：
用 lock.acquire(timeout=1)，超时后释放已持有的锁并重试，避免无限等待。
使用 threading.RLock()（可重入锁）：
虽然这里 RLock 不能直接解决不同线程间的死锁，但如果两个任务实际上属于同一个线程逻辑，RLock 允许同一线程多次获取锁。

3.线程 vs 进程：一个 Web 爬虫程序需要同时下载 100 个网页，应该用 threading 还是 multiprocessing？为什么？
答案：应该用 threading（多线程）。

原因：

下载网页是 I/O 密集型 任务：大部分时间花在网络传输上，CPU 几乎空闲。
多线程在 I/O 等待时释放 GIL，可以同时发起 100 个请求，并发处理响应，资源开销小（线程轻量）。
multiprocessing 适用于 CPU 密集型任务。如果此处使用多进程，每个进程都有独立内存空间，创建开销大，且进程间通信复杂，收益不高。
补充：更现代的做法是使用 asyncio（异步 I/O），用更少的线程实现更高的并发。


4.锁的选择：什么场景下应该用 threading.Lock()？什么场景下应该用 threading.RLock()？
答案：
锁类型	适用场景
threading.Lock()	普通互斥锁。用于保护一段代码或资源不被多个线程同时访问。一旦被某线程获取，其他线程必须等待。不记录持有者，同一线程不能重复获取（否则死锁）。适用于大多数简单的同步场景。
threading.RLock()	可重入锁（Reentrant Lock）。当同一个线程需要多次获取同一把锁时使用，比如：
- 一个函数调用自身（递归）且需要加锁。
- 一个方法调用了另一个需要同一把锁的方法。
RLock 会记录持有线程和计数器，允许同一线程多次 acquire，但必须同样次数 release。

简单原则：默认用 Lock()，只有明确需要在同一线程中多次获取锁时，才用 RLock()。



5.守护线程陷阱：如果一个守护线程正在写文件，主线程退出时守护线程被强制终止，可能导致什么问题？如何避免？

答案：
可能的问题：

文件写入不完整：数据可能只写了一半，缓冲区未刷新（flush），导致文件损坏或丢失数据。
资源未释放：文件句柄未正确关闭，可能造成资源泄漏。
数据不一致：例如在写数据库日志时，可能写入半条记录，破坏日志格式。
如何避免：
不使用守护线程（最稳妥）：将线程设为非守护（daemon=False，默认），主线程用 join() 等待所有写入线程完成后再退出。
python
t = threading.Thread(target=write_file)
t.daemon = False  # 默认就是 False
t.start()
t.join()  # 主线程等待
使用 atexit 注册清理函数：在程序退出前，主动等待所有写任务完成或强制刷新缓冲区。
使用 with 上下文管理器：确保文件在写入完成后自动关闭和刷新，即使线程被强制终止，也能保证已写入的内容落盘（但无法保证未写入的内容）。
主线程捕获退出信号，主动通知守护线程停止接受新任务，并等待已接收任务完成，再优雅退出。
